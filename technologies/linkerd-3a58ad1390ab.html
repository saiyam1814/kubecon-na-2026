    Free Tokens for Everyone

    William Morgan

    William Morgan says running open-weight models on Kubernetes shifts inference costs from buying tokens to operating GPU capacity. He presents Kinference as a layer for defining tenant policy, tracking usage, and routing requests to local or external backends.

    30 min slot · Beginner · Session

    AI inference and serving

    Watch this if: You run a Kubernetes platform and need to share inference capacity across teams without giving up visibility or control.

    1. 12:01 Morgan explains that choosing an open-weight model variant depends on available memory, context length, and expected concurrency, not just the model family.
    2. 14:39 Morgan frames shared GPU inference as a platform problem: teams want self-service and different levels of service while operators must keep finite capacity reliable.
    3. 18:12 Morgan describes putting a traffic enforcement gateway in front of model servers to handle multiple models and tenants with explicit policy.
    4. 21:01 Morgan says the gateway can export Prometheus-compatible metrics for existing dashboards and break out performance by model and tenant.
    5. 23:47 Morgan walks through policies that can choose a model, reject a request, or send it to an external provider using prompt, GPU, and tenant signals.

    Is Service Mesh for Everyone?

    Phil Henderson

    Phil Henderson of Buoyant argues that a service mesh is still relevant in 2026 and makes the case for Linkerd in particular. He says a mesh and OpenTelemetry observe different things and cannot replace each other, describes who he thinks a mesh is for, and mentions a new Buoyant project for inference.

    5 min slot · Level not listed · Lightning Talk

    Networking and connectivityObservability and reliability

    Watch this if: you are deciding whether a service mesh still earns its place next to OpenTelemetry and want to hear the argument from a Linkerd vendor.

    1. 0:36 Phil Henderson gives a short history: he says Buoyant shipped Linkerd as the first service mesh in 2016, and that it was the first service mesh to graduate, in 2021.
    2. 1:05 He says a service mesh should bring security, reliability and observability without affecting the applications.
    3. 1:22 He makes his case for Linkerd, calling it ultra light, low maintenance and secure by default, with a Go control plane and a Rust data plane, and claims benchmarking shows it reduces latency.
    4. 2:01 He argues OpenTelemetry does not replace a mesh: in his view one observes inside the code and the other on the wire, and neither can replace the other.
    5. 4:14 He says Buoyant is releasing a new project this week, which he describes as a control plane for running inference in-house on Kubernetes.

    Linkerd, The Service Mesh for Everyone: gRPC Load Balancing & More

    Joe Fuller

    Joe Fuller of Buoyant explains why gRPC over a single HTTP/2 connection defeats connection-level load balancing on Kubernetes and presents a benchmark he says Buoyant ran comparing Linkerd with Istio and Cilium. He then covers what Linkerd 2.20 adds, mainly rate-limit-aware load balancing and a new circuit breaking mode, both alpha and opt-in, and what has shipped in edge releases for 2.21.

    30 min slot · Level not listed · Session

    Networking and connectivity

    Watch this if: you run gRPC services on Kubernetes and want to understand per-request load balancing, or you are deciding whether to turn on the new Linkerd 2.20 overload features.

    1. 4:21 Joe Fuller explains the gRPC problem: a client opens one HTTP/2 connection, every request lands on one pod, and scaling up does not help because new pods get none of the existing connections.
    2. 6:58 He describes a benchmark he says Buoyant's engineers ran on EKS against Istio in ambient and sidecar mode and Cilium in L7 mode, and reports Linkerd at about 92% of no-mesh throughput.
    3. 10:51 He describes the failure mode 2.20 targets: an overloaded pod that rejects requests quickly with 429 or RESOURCE_EXHAUSTED looks like the fastest endpoint to a latency-based balancer and gets more traffic.
    4. 12:11 He explains rate-limit-aware load balancing: the client proxy records a penalty of five seconds by default, or the server's back-off hint, instead of the fast rejection, so traffic shifts away and then returns as the penalty decays.
    5. 20:06 He says the destination controller no longer keeps a per-subscriber endpoint snapshot, which he says cut control plane memory by about 84% in load tests, and that native sidecars are GA and on by default.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    Open Source Has a Human Deficit. Here's How We Fix It.

    Catherine Paganini

    Catherine Paganini argues that open source is short on maintainers and that welcoming underrepresented groups is a way to make projects more sustainable. She introduces Merge Forward, a CNCF community group with groups such as Women in Cloud Native and Deaf and Hard of Hearing, and invites people to join as members, mentors or allies.

    5 min slot · Any Level · Lightning Talk

    Community and open source adoption

    Watch this if: you want to help more people from underrepresented groups become open source contributors and maintainers.

    1. 0:07 Catherine Paganini recalls a March 2022 warning to the Kubernetes steering committee that etcd had only one active and two occasional reviewing maintainers.
    2. 0:26 She points to ingress-nginx, which she says was wound down and stopped getting security patches, as another case of the same maintainer pattern.
    3. 1:25 She says more maintainers means more people, and that open source has overlooked many who do not see themselves represented and so see no path in.
    4. 2:41 She argues that people with similar backgrounds share unchallenged assumptions, which she links to missed edge cases and shipped defects.
    5. 3:23 She lists the Merge Forward groups, from Deep Roots and Women in Cloud Native to Neurodiversity and Deaf and Hard of Hearing, and points to the upcoming 2027 buddy program.

    Verticalizing Platform Intelligence for Regulated Domains

    William Rizzo, Kasper Borg Nissen

    William Rizzo of Mirantis and Kasper Borg Nissen of Dash0 argue that limits on AI agents in regulated industries should be enforced by the platform and not by the agent framework or its system prompt. They demo an insurance claims setup in which, as they describe it, agents get SPIFFE identities, reach tools only through a gateway with a hard payout ceiling, and leave an audit trail in OpenTelemetry traces.

    30 min slot · Advanced · Session

    Security, identity and policyAI agents and automationPlatform engineering and developer experience

    Watch this if: you have to put AI agents on a platform in a regulated business and need to show auditors what an agent did and who allowed it.

    1. 9:01 Rizzo describes the agent's identity as a passport: a SPIFFE-validated identity with no stored passwords, with Linkerd restricting which paths the agent can reach.
    2. 11:27 Nissen shows the two controls they set in agentgateway: a CEL rule with a hard 50,000 euro payout ceiling and an MCP guardrail that calls their own policy decision service.
    3. 13:00 Nissen explains using an OpenFeature flag to set how much autonomy the agent has, from every claim needing human approval to automatic payouts up to a set amount.
    4. 19:32 In the demo a customer message tries prompt injection to get 80,000 euros paid out, and Nissen shows the gateway refusing a payment above the ceiling.
    5. 23:41 Nissen shows the policy decision recorded as a custom span with attributes defined through OpenTelemetry Weaver, and the human approval linked to it as a second trace.

    When Infrastructure Breaks in Production: How EarnIn Brought Testing to the Full CNCF Stack

    Priya Namasivayam

    Priya Namasivayam of EarnIn describes a cert-manager upgrade that looked healthy but broke Linkerd certificates and customer logins, and says the team responded by running infrastructure tests as Kubernetes resources with Testkube, triggered by Flux reconciliation. A co-presenter from Testkube runs a live demo on a kind cluster in which an operator upgrade passes health checks but fails a test workflow.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyObservability and reliability

    Watch this if: you upgrade cluster add-ons through GitOps and want to catch breakage that pod health checks do not show.

    1. 3:48 The speaker explains the incident: she says cert-manager 1.18 began rotating private keys on renewal instead of extending them, which broke certificates for Linkerd while everything looked green.
    2. 5:26 The speaker describes the fix as a Kubernetes-native testing setup built on Testkube, where tests and triggers are CRDs and a Git commit that starts Flux reconciliation also starts the tests.
    3. 10:35 The co-presenter starts the live demo by bringing up a kind cluster with Flux, CloudNativePG, cert-manager and a sample to-do application.
    4. 12:42 The co-presenter shows a Testkube test workflow for cert-manager that checks certificates are still valid after an upgrade.
    5. 20:49 After the simulated upgrade the test workflow fails, and the co-presenter explains that the operator is running but a breaking change stops the ServiceMonitor from working.
