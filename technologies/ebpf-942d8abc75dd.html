    Debugging the Invisible: Standardizing Kubernetes Networking Expertise

    Faseela Kundattil, Marino Wijay, James Spurin, Chad M. Crowell, Christophe Sauthier

    Five panelists who created or teach around the Certified Kubernetes Network Engineer (CKNE) exam discuss why CNCF added a hands-on networking certification and what foundational networking knowledge they think Kubernetes engineers need. They argue that AI tools can speed up troubleshooting but that an engineer still has to judge the suggested fix, and they describe what the exam covers and how to prepare.

    30 min slot · Beginner · Panel

    Networking and connectivityCommunity and open source adoption

    Watch this if: you are deciding whether to study for the CKNE exam, or you come from traditional networking and want to know how that knowledge carries over to Kubernetes.

    1. 4:10 Sauthier says CKNE is a separate hands-on exam, not an extension of CKA, because practice builds instincts for a 3 a.m. incident and he wants common ground between the older NetOps world and the cloud native one.
    2. 10:20 Spurin says network policy lets you ignore iptables, nftables and eBPF until something breaks, and argues that without that low-level knowledge a person can only approve whatever an AI tool concludes.
    3. 15:34 Kundattil gives the example of an AI tool suggesting to disable mTLS to restore pod-to-pod connectivity in a service mesh, which she calls not the right fix.
    4. 20:11 Sauthier says some exam questions name the project to use while others leave the choice open, for example Cilium or Istio, and Wijay adds that candidates need subnetting, routing and BGP fundamentals and must read a tcpdump.
    5. 28:36 Asked whether CKNE will count toward Kubestronaut, Sauthier says it becomes a requirement for both Kubestronaut and Golden Kubestronaut from February 15.

    Falco Never Flies Alone: Runtime Security as an Ecosystem

    Leonardo Grasso, Alessandro Cannarella

    Leonardo Grasso and Alessandro Cannarella describe how Falco, now ten years old, spent the year consolidating its core and growing an ecosystem around it. They cover core and plugin updates, new experiments for AI coding agents, Falco Operator 0.5, and a from-scratch rewrite of Falcosidekick as version 3.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you run Falco for runtime security and want to see what changed in its core, the Falco Operator and Falcosidekick.

    1. 0:51 Grasso explains how Falco taps the Linux kernel with an eBPF probe or kernel module, enriches events with plugins, and matches them against YAML rules.
    2. 3:22 Grasso lists core cleanups such as removing the legacy BPF probe and gVisor support, new list operators in the rule language, and an experimental GPU hijacking rule.
    3. 6:38 Grasso introduces a new subproject that gives coding agents a version-pinned knowledge base and skills for contributing to the Falco code base.
    4. 16:35 Cannarella says Falco Operator 0.5 pulls artifacts from the registry once, serves them to every node, and checks rules against the Falco version before installing.
    5. 19:55 Cannarella announces Falcosidekick version 3, rewritten with per-output pipelines, live config reloads, API and UI configuration, and a single binary.

    From Bytes to Traces: A Deep Dive into OpenTelemetry eBPF Instrumentation Internals

    Rafael Roquetto, Mike Dame

    Mike Dame walks through the user-space side of OpenTelemetry eBPF Instrumentation (OBI): how it discovers processes, enriches them with Kubernetes and container metadata, matches them against configured selectors and attaches eBPF programs. Rafael Roquetto then follows one HTTP request from bytes on the TCP receive path through eBPF maps and a ring buffer into a request span that is enriched and exported as OpenTelemetry traces and metrics.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you want to debug, extend or contribute to OpenTelemetry eBPF Instrumentation and need to know how it works internally.

    1. 1:50 Dame says a stated intent such as observing the checkout service has to be resolved to PIDs, and that everything in OBI works by PIDs.
    2. 7:39 Dame explains that OBI attaches a syscall probe to the bind function as a lazy signal that ports changed, instead of constantly scanning every process's ports.
    3. 14:52 Roquetto describes OBI hooking the TCP receive path and reading bytes into a small buffer along with the PID and connection information.
    4. 18:54 Roquetto says the completed HTTP info struct is shipped to user space through an eBPF ring buffer, where another enrichment pipeline starts.
    5. 22:41 Roquetto says the same request span structure feeds OpenTelemetry spans, span metrics, service graph metrics and RED metrics.

    From ListenerSets to eBPF Plugins: Cilium's Evolution Across the Stack

    Christine Kim, Katie Meinders, Hadrien Patte

    Katie Meinders walks through what the speakers say shipped in Cilium 1.20 and Tetragon 1.8, including datapath plugins, netkit auto mode and ztunnel-based mTLS in beta. Hadrien Patte of Datadog then explains why IPv6 for AWS ENI IPAM took four years to land, and Christine Kim covers the Gateway API additions of external auth, TCPRoute and UDPRoute, and ListenerSets.

    30 min slot · Level not listed · Session

    Networking and connectivity

    Watch this if: you run Cilium and want a tour of 1.20, or want to see how one long-requested feature, IPv6 on AWS ENI, finally got built.

    1. 2:23 Katie Meinders describes datapath plugins, which she says came from Google and let third-party code instrument Cilium's datapath as a plugin without patching or forking Cilium.
    2. 3:35 She says ztunnel mTLS is now in beta, built on Istio's ztunnel, and replaces the older Cilium mutual authentication feature, which she says is deprecated.
    3. 8:38 Hadrien Patte shows the feature request for IPv6 in AWS ENI mode, opened in January 2022 the day after AWS announced IPv6 for EKS, and says it shipped in 1.20 in July 2026.
    4. 13:26 He explains the blocker: the operator listed every available IP in the CiliumNode resource, which cannot hold a /80 IPv6 prefix, so ENI mode was changed to advertise CIDRs as the multi-pool IPAM mode does.
    5. 18:20 Christine Kim explains ListenerSets, which she says lift the limit of 64 listeners per Gateway and let application teams manage their own TLS certificates, with the older listener winning conflicts.

    Gone in 60 Minutes: Effectively Close the Exploitable Window with Detection as Code

    Ben Hirschberg, Constanze Roedig

    Ben Hirschberg and Constanze Roedig show two ways to detect exploitation with Kubescape in the hours between a vulnerability becoming public and a patch being deployed, both shipped to the cluster as YAML through GitOps. Hirschberg writes rules from published indicators of compromise, and Roedig uses behavior profiles to flag deviations when the attacker's methods are not yet known.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyObservability and reliability

    Watch this if: you need a way to detect exploitation of a newly disclosed vulnerability in running workloads before a patch can be rolled out.

    1. 2:19 Hirschberg describes the setup: the Kubescape node agent with eBPF sensors and a rule engine whose detection rules are written in CEL, with alerts sent to Slack.
    2. 6:16 In a recorded demo he pastes the indicators of compromise from a published write-up of the poisoned Trivy GitHub Action into an AI agent, which opens a pull request with Kubescape detection rules that Argo CD syncs to the cluster.
    3. 9:32 Roedig introduces what she calls a software bill of behavior, a custom resource listing allowed capabilities, network traffic, executables and file opens as composable fragments that can be signed separately.
    4. 11:56 She says build runners are a poor fit for anomaly detection because their behavior is not bounded, then shows a profile-based setup still flagging the same indicators as the rules did.
    5. 16:54 For a PHP server that normally spawns shells, she says the profile caught the exploit because the id command ran outside the expected process tree, and argues a good profile has as few entries as possible.

    GPU Observability with eBPF: From Kernel Hooks to Kubernetes Metrics

    Qasim Sarfraz, Michael Friese

    Inspektor Gadget maintainers Qasim Sarfraz and Michael Friese of Microsoft show how eBPF probes on CUDA libraries can report GPU memory allocations per pod and trace them back to application code without changing the application. They demo allocation profiles and a Grafana dashboard for a vLLM workload, then explain how gadgets are packaged as OCI images and installed with one Helm chart.

    30 min slot · Advanced · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: you run GPU inference on Kubernetes and want per-pod GPU memory metrics and allocation profiles without changing application code.

    1. 2:13 Sarfraz explains attaching uprobes and uretprobes to CUDA allocation and free functions and recording each call in BPF maps, which the framework enriches with pod and namespace and exposes to Prometheus.
    2. 5:45 In a demo he reads an allocation profile for a vLLM workload and uses it to raise the GPU memory utilization setting, which he says yields about 3 GB more allocation.
    3. 9:51 He says device state such as memory held and utilization comes from NVIDIA's NVML library, not from eBPF probes, and is joined with the eBPF data per workload.
    4. 12:36 Friese describes a gadget as an OCI image holding eBPF programs, optional WebAssembly modules, metadata YAML and BTF information, with signatures verified by default.
    5. 16:36 He lists four official GPU gadgets covering allocation activity, allocation call stacks, per-GPU state and per-pod state, and says profiles can go to Pyroscope or any OpenTelemetry endpoint.

    Keeping Envoy Boring in an eBPF Datapath (Cilium L7)

    Kateryna Nezdolii

    Kateryna Nezdolii of Isovalent, an Envoy maintainer, follows one HTTP request and one policy update through Cilium to show where the eBPF datapath enforces L3/L4 checks and where a node-local Envoy enforces HTTP rules. She then describes how Cilium ships and tests its own Envoy build, keeps the last accepted configuration on rejected updates and agent restarts, and is migrating its xDS control plane.

    10 min slot · Level not listed · Session

    Networking and connectivityKubernetes internals and runtimes

    Watch this if: You run Cilium with L7 policies and want to know what Envoy does in that path and how updates are kept safe.

    1. 2:22 She says Cilium turns one CiliumNetworkPolicy into a datapath redirect plus an Envoy HTTP rule: the datapath checks identity, protocol and port, and Envoy checks method and path.
    2. 5:03 She explains that a request denied at L3/L4 is dropped in the datapath with no HTTP response, while one that fails the HTTP rule gets a 403 from Envoy, and that Hubble records the L7 verdict.
    3. 6:42 She says Cilium ships its own Envoy build called cilium-proxy with a minimal set of extensions, its own policy filters, a version compatibility matrix and a set of patches.
    4. 7:28 She says that when Envoy rejects a configuration update the last accepted config keeps running, and that an agent restart compares desired and accepted config so a working proxy is left alone.
    5. 8:37 She describes ongoing work: migrating from a custom split-xDS control plane to an ADS implementation, adding delta ADS, and a Network Policy Resource Discovery Service that splits the policy into smaller resources.

    Monitoring Power at Planet Scale with Kepler

    Niki Manoledaki

    Niki Manoledaki, who introduces herself as Kepler's project leader, says power is a limiting factor for scaling compute and explains that Kepler reads hardware power meters, attributes energy from process up to cluster, and exports metrics. She then describes how CERN, Project Sylva and Fermilab use Kepler, mostly for benchmarking and capacity planning.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: You want to measure the power use of Kubernetes workloads and hear who is using Kepler for it.

    1. 0:40 Niki Manoledaki cites an International Energy Agency projection that data center power consumption will double between 2024 and 2030, and says power is already a capacity constraint.
    2. 0:55 She says Kepler reads hardware sensors such as Intel RAPL, NVIDIA NVML and Redfish, attributes energy from kernel process to container, pod, namespace and cluster, and exports Prometheus metrics.
    3. 1:50 She says Kepler got rid of eBPF to need fewer privileges and get better accuracy, and lists GPU power telemetry as a very popular feature.
    4. 2:26 She says CERN has used Kepler for over a year to monitor the energy consumption of servers for machine learning, and used it to find more power-efficient workload placements on its GPUs.
    5. 3:05 She says Project Sylva's telcos use Kepler to benchmark cloud-native network functions before production, and sees a user pattern of benchmarking, profiling and capacity planning.

    Spark on Kubernetes: The Gap Between “It Works” and “It Works Well”

    Damon Cortesi

    Damon Cortesi says Airbnb finished moving its Spark fleet from Hadoop to Kubernetes two weeks before the talk and goes layer by layer through what failed on the way: the control plane, scheduling, nodes, disks, networking, Spark itself and observability. He says most of the 34 changes were small config edits or backported patches that were hard to find, and sums up the lesson as check your config, stress test, repeat.

    30 min slot · Advanced · Session

    Data, storage and stateKubernetes internals and runtimesObservability and reliability

    Watch this if: you run or plan to run Apache Spark on Kubernetes at scale and want a list of concrete failure points and the fixes one team applied.

    1. 1:23 Cortesi says Airbnb hit 100% two weeks earlier, shutting down its last legacy Hadoop cluster, with a fleet of about 588,000 daily Spark jobs.
    2. 4:55 On the control plane, he says dropping the events TTL from one hour to 10 minutes cut etcd P99 latency from half a second to under 25 milliseconds and the object count from 2 million to 400,000.
    3. 9:06 He describes two Apache YuniKorn problems, one asking for far more capacity than needed because of a Go bug and one asking for too little under FIFO sorting, and says KWOK let him test YuniKorn at scale without provisioning real capacity.
    4. 12:35 He says a Node Problem Detector log rotation bug marked healthy nodes as dead, so that about 74 nodes were removed in 24 hours, one of four node-health bugs they found.
    5. 16:28 He says unique pod labels pushed Cilium past its 65,000 identity limit at their pod creation rates, and the fix was basing identities on a short allow list of labels.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.

He also describes Cluster API providers for Kairos, which he says let Kamaji hosted control planes use Kairos-managed worker nodes.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run Kairos or immutable Linux at the edge and want a quick list of what changed over the past year.
