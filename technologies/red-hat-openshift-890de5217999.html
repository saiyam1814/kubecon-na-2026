    AI Found a 0-Day in Metal3. What Happens Next?

    Tuomo Tanskanen

    Tuomo Tanskanen, who leads the Metal3 security committee, follows a vulnerability report from arrival through triage, fix, release and downstream upgrade, drawing on reports from his own AI discovery pipeline and showing how its findings broke down after triage. He also describes how fixes in OpenStack Ironic reach Metal3 and vendor distributions, and advises users to run supported releases, know their configuration and ask vendors how quickly they take in fixes.

    30 min slot · Level not listed · Session

    Security, identity and policyDelivery, GitOps and release safetyAI agents and automation

    Watch this if: you maintain a project that receives AI-generated vulnerability reports, or you run Metal3 and want to know how its security fixes reach you.

    1. 4:12 Tuomo Tanskanen says every vulnerability disclosure Metal3 received this year came from an AI discovery pipeline he built himself, which also scans OpenStack Ironic, and that its findings go through each project's normal security process.
    2. 8:27 He gives the pipeline's numbers: of about 220 findings, 80 were false or duplicates, 31 became hardening issues, 22 were plain bugs and 22 were confirmed, and he concludes that discovery is fast while triage, fixing and coordinated release are slow.
    3. 10:34 He says Metal3 fixes low and medium issues in the open, because GitHub private forks give almost no CI support and force manual testing, and reserves embargoed handling for high and critical ones.
    4. 14:41 He describes a lesson from combining four related cross-namespace issues into one advisory: no CVE could be issued for it, because a CVE covers a single issue.
    5. 20:20 Using two fixes as examples, he says each step down the dependency chain into vendor distributions took roughly a month, so fixes take a long time to reach production.

    CoHDI: Bridging Kubernetes and Disaggregated Memory for Memory-Aware LLM Inference

    Naoki Oguchi, Hidetsugu Sugiyama

    Naoki Oguchi and Hidetsugu Sugiyama present CoHDI, a CNCF Sandbox project they describe as letting Kubernetes attach pooled CXL memory and GPUs to worker nodes on demand, with a focus on giving LLM inference more room for KV cache. They walk through the allocation sequence for an LMCache pod, share early measurements, and outline plans to split prefill and decode across sites connected by an optical network.

    30 min slot · Advanced · Session

    Data, storage and stateAI inference and servingAccelerators and workload scheduling

    Watch this if: you run LLM inference on Kubernetes and want to see how pooled CXL memory could be attached to nodes as an extra KV cache tier.

    1. 2:50 Oguchi says KV cache capacity needs to scale independently from GPU compute, after listing the drawbacks he sees in adding GPUs, adding local DRAM, or evicting the cache to storage.
    2. 6:47 Oguchi explains the CoHDI flow: a scheduled pod triggers composition, the Dynamic Device Scaler evaluates the GPU and CXL memory needed, and the Composable Resource Operator requests them from the pool and attaches them to the worker node.
    3. 11:52 Oguchi shows cache metrics where resubmitting the first prompt raises the blocks read from the second tier from 105 to 135, which he reads as KV cache kept in CXL memory being reused.
    4. 12:44 Oguchi reports first-stage results in which attached CXL memory was 10 times faster than SSD for random reads and 18 times faster for writes, and says LMCache still needs optimization for CXL access.
    5. 18:27 Sugiyama says GPU overprovisioning at the decode site remains a problem and describes decode nodes with few GPUs and large CXL memory pools composed by CoHDI as his answer.

    GitOps Without You Writing YAML: How Flux Grounds AI Agents in Real APIs

    Stefan Prodan

    Stefan Prodan argues that AI agents struggle more with Kubernetes YAML than with code because they lack a fast way to verify it, and presents the Flux Schema CLI plugin, a public catalog of custom resource schemas and an MCP server that he says give agents that feedback loop without a live cluster. He also describes the GitOps agent skills the Flux maintainers wrote and evaluated, and closes with the Flux roadmap and how to contribute to the catalog.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyAI agents and automation

    Watch this if: you use AI coding agents to write Kubernetes or Flux manifests and want to see how the Flux maintainers validate and ground that output.

    1. 1:01 Stefan Prodan says his conclusion from the Flux team's experiments is that generating YAML is harder for AI than generating code, because agents can test code in a fast loop but have no equivalent check for configuration data.
    2. 8:47 He introduces Flux Schema, a Flux CLI plugin that he says reproduces the Kubernetes API's validation rules offline, including label value rules and SOPS-encrypted secrets, and works on any Kubernetes YAML, not only Flux repositories.
    3. 13:27 He describes a public MCP server built on the project's ecosystem catalog of controller schemas, which he says reached one million requests a day and sees similar traffic from Codex, Claude and Copilot.
    4. 17:03 He says returning full OpenAPI schemas made agents hallucinate in long sessions, so the MCP server now exposes a grep schema tool that returns a compact format, after which he could generate hundreds of manifests.
    5. 26:48 He says the first agent skills were built with frontier models and failed on quantized open models he ran at home, so the team rewrote them, and he advises evaluating skills on weaker models.

    Ground Control to Major Tom: We Need your Public Cloud in our Private Cloud

    Andrew Block, Mike Wilson

    The speakers, from Red Hat and Adobe, describe how an Adobe private cloud team that ran virtual machines on VMware is moving to OpenShift Virtualization and adopting the GitOps practices Adobe's public cloud Kubernetes platform, Ethos, already used. They cover the team's shift from click-driven operations to Git, architectural decision records kept in a repository, and lessons about working across storage, network and platform teams.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You are moving virtual machines from VMware to a Kubernetes-based platform and want to hear how one team changed its ways of working along the way.

    1. 6:23 Mike Wilson says the move was a business decision, not a technology one: after Broadcom acquired their main platform provider, Adobe chose OpenShift Virtualization and set a mandate to exit by 2028.
    2. 7:34 Wilson says the team's first instinct was to make the new platform feel as much like VMware as possible, and that they later moved to declarative, cloud native practices built on Kubernetes, Open Cluster Management, Argo CD and KubeVirt.
    3. 14:22 Wilson describes adopting architectural decision records in Git after decisions kept being reopened, and shows a cluster naming record with its proposed, accepted, rejected and superseded states.
    4. 16:39 He says the decision record repository was structured so AI agents can review it, for example checking whether a new implementation matches the recorded architectural intent.
    5. 24:03 Wilson says they have five production clusters and need to deploy around 60 more next year, using Open Cluster Management as the factory and a Cluster API provider so Ethos can target the private cloud.

    Carlos Santana

    Carlos Santana explains how Kubernetes handles requests to resize an existing pod's CPU and memory. He walks through the API request, the kubelet's decisions, and how Vertical Pod Autoscaler can use the mechanism.

    30 min slot · Beginner · Session

    Platform Engineering's Missing Chapter: Services Organizations

    Atulpriya Sharma

    Atulpriya argues that platform engineering models built for product companies do not directly fit consultancies and services organizations. He presents delivery capital and a capability layer as ways to reuse organizational learning across client engagements while measuring ramp time, consistency, proposal strength, and delivery time.

    25 min slot · Intermediate · Session

    Platform engineering and developer experience

    Watch this if: you build or operate platforms in a consultancy, systems integrator, or client-facing delivery organization.

    1. 2:59 Atulpriya argues that platform engineering's familiar vocabulary was not built around the operating model of consulting firms and services organizations.
    2. 9:03 Atulpriya defines delivery capital as the learning a services organization accumulates across engagements, and says it is the asset the organization truly owns.
    3. 11:04 Atulpriya says the capability layer joins reusable organizational knowledge with an internal consultant IDP of sandboxes and demo clusters so teams can apply prior learning.
    4. 12:57 Atulpriya maps the approach across cloud, IaC, CI/CD, observability, and monitoring, with artifacts such as decision records, checklists, templates, baselines, and named alert owners.
    5. 23:29 Atulpriya argues that ownership, rotation, and billable-work identity block adoption in services firms, and says time-to-ramp, delivery consistency, proposal strength, and delivery time are the measures to watch.

    Sandbox Your Agents

    Jessica Forrester

    Jessica Forrester describes how a Red Hat coding agent drifted from its assigned task and explains why her team relies on enforced policy rather than prompts alone. She demos how OpenShell blocks and logs actions outside policy, then describes running sandboxes in Kata Containers to give them separate kernels.

    5 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you are giving coding agents access to internal systems and want an example of enforcing boundaries outside the prompt.

    1. 0:41 Forrester describes a requirements-scoring agent that started inventing ideas without being attacked, and says Red Hat designs its platform as if agents were already compromised.
    2. 1:34 Forrester compares prompts to signs in an escape room and enforced policies to bolts that prevent players from moving things they should not touch.
    3. 2:16 Forrester demos an agent that can read a GitHub README but cannot follow instructions outside its policy, and explains how denied attempts can become access proposals for review.
    4. 3:16 Forrester says standard OpenShell containers share a host kernel and describes using Kata Containers to put the sandbox behind a separate kernel.
    5. 3:53 Forrester says OpenShell gives agents placeholder credentials and swaps in the real credentials when an allowed request leaves the sandbox.

    Splitting the Monolith at Cloudera - Building Fault-Tolerant Workflows with Cadence

    Soma Koltai, Ender Demirkaya

    Soma Koltai of Cloudera describes moving the Cloudera Data Warehouse control service from a single Go binary to Cadence workflows, using a small bridging layer shaped like the Cadence client API and a lease service on PostgreSQL so the refactoring could start before Cadence was integrated. Ender Demirkaya of the Cadence project explains how workflows and activities recover state, and says the Cadence team built distributed semaphores after hearing about Cloudera's use.

    30 min slot · Advanced · Session

    Observability and reliabilityData, storage and state

    Watch this if: you are breaking up a stateful monolith with long-running operations and want a staged way to adopt a workflow engine.

    1. 1:47 Koltai says provisioning a cluster and restoring workloads can take a whole hour, and under the previous architecture a failure meant the whole process was retried.
    2. 5:36 Demirkaya explains that developers annotate one function as a workflow and its external calls as activities, and if everything crashes another worker continues where it left off.
    3. 9:48 Koltai describes the Async Executor, a bridging layer modeled on the Cadence client API that he says took about 600 lines and two weeks, and let them reuse every activity handler when they switched to Cadence.
    4. 12:32 For locking, Koltai says they chose leases, locks with a time to live, behind a three-method interface, implemented with essentially one insert call on the PostgreSQL database they already had.
    5. 18:54 Koltai tells of a memory leak that went unnoticed because Karpenter rescheduled the pod before it hit its memory limit, and says restarts after the migration no longer caused workflow failures or pages.

    Validating Kubernetes Workloads: Checklists and Best Practices

    Nabarun Pal, Maciej Szulik, Liz Rice, Ricardo Aravena

    Organizers of the Kubernetes working group on workload conformance explain its charter: define how a well-behaved workload acts in a cluster, write objective tests for that, and eventually propose a CNCF conformance program. Most of the session is discussion with the audience about what should be in scope, including configuration variants, SBOMs, neutrality of the requirements and upgrade paths.

    30 min slot · Level not listed · Birds of a Feather

    Kubernetes internals and runtimesCommunity and open source adoption

    Watch this if: you ship or operate applications on Kubernetes and want a say in what a conformance check for well-behaved workloads should test.

    1. 1:53 Pal sets out the working group's charter: define generic behavior of workloads on Kubernetes, write verifiable tests for it, and build a conformance suite to hand to steering and architecture for vetting, while saying the group is far from that point.
    2. 6:25 Szulik says one goal is for an application vendor to be able to say its workload is a good citizen, for example respecting disruptions and graceful node shutdown, in the way a provider shows a cluster is conformant, with tooling anyone can run on their own apps.
    3. 14:16 An audience member asks for SBOMs with every delivered application; Szulik says the group had planned only must conditions and that he now leans toward adding optional ones, and Pal notes this would mean choosing between formats such as CycloneDX and SPDX.
    4. 18:35 An audience member warns that an earlier operator conformance effort turned into subjective rules such as requiring startup probes, and Szulik answers that he has no solution yet and that finding common ground is why the working group was started.
    5. 27:38 On upgrades, Pal says the group does want to check upgrade readiness, such as flagging use of deprecated Kubernetes APIs, and points to the API server's deprecated API usage metrics as one way to test it.
