    AI agents and automation

    Watch this if: you want a live example of agents working across Kubernetes, pull requests, authentication, and distributed tracing.

    Integrating Envoy AI Gateway and Kyverno Authz for Realtime Governance of LLM and MCP Traffic

    Jim Bugwadia, Deepak Goel

    Deepak Goel explains why enterprises put Agent Router, which he says was formerly called Envoy AI Gateway, between agents and their models and MCP tools, and Jim Bugwadia shows Kyverno Authz plugging into it through Envoy's external authorization protocol. In a live demo, Kyverno allows or blocks MCP tool calls by asking the Kubernetes API whether the calling user has the matching RBAC permission.

    25 min slot · Level not listed · Session

    Security, identity and policyNetworking and connectivityAI agents and automation

    Watch this if: You route LLM and MCP traffic through an Envoy-based gateway and want tool calls authorized against the Kubernetes RBAC you already have.

    1. 2:57 Deepak Goel says that once many agents, models, users and sessions are involved, enterprises need a layer between agent and model for routing, security, observability and token cost, which is what Agent Router provides.
    2. 8:51 Jim Bugwadia explains Envoy's two plugin protocols: external authz returns allow or deny on a request, while external processing also sees the response, which he says matters because an MCP server's reply can carry a prompt injection.
    3. 10:04 He says Agent Router already has JWT authentication, MCP session management, CEL checks and quotas, but not policy as code with reporting and exception management, which Kyverno adds.
    4. 15:56 In the demo, a tool call by user Alice against another team's namespace is blocked because Kyverno ran a Kubernetes SubjectAccessReview and RBAC denied it.
    5. 18:02 After he adds a role binding for Alice, the scale call that failed earlier goes through, and he then shows the policy report Kyverno generated for the blocked calls.

    Least-Privilege by Default: Standardizing Identity-Aware AI Agent Access into a Golden Path

    Masato Kozuka

    Masato Kozuka of Hitachi lays out a security model for AI agents that act for a user, in which every call to an MCP server carries both the user's and the agent's identity and is allowed only if both may do it. He then shows how he would have a platform team make that the default for every team, using Keycloak, SPIRE and Backstage templates, and plays a recorded demo of an attack being stopped.

    30 min slot · Advanced · Session

    Security, identity and policyAI agents and automationPlatform engineering and developer experience

    Watch this if: your teams connect AI agents to internal tools over MCP and you want one standard way to enforce least privilege for all of them.

    1. 4:56 Kozuka explains exchanging the token at every hop with OAuth token exchange, so each token is valid for one MCP server only while the sub claim stays the user.
    2. 5:40 He calls letting the agent log in as itself with the client credentials grant a confused deputy, and says they disable agent service accounts and reject any token without a user.
    3. 7:12 He describes proving the agent's identity with SPIFFE: the pod's namespace and image digest are checked before it gets a short-lived ID, in place of a static key anyone could copy.
    4. 13:59 He splits the seven rules: three are enforced in Keycloak and SPIRE where no agent can skip them, and four ship in the sidecar and server middleware that Backstage templates generate.
    5. 25:06 In the recorded demo a receipt with a hidden instruction sends the agent after payroll data, and Kozuka shows Keycloak refusing a token for the payroll server because it was never approved.

    One Platform for AuthN and AuthZ: Keycloak Meets AuthZEN

    Yoshiyuki Tabata

    Yoshiyuki Tabata splits authorization into delegation and access control, explains that the OpenID AuthZEN standard defines the interface between a policy enforcement point and a policy decision point, and describes Keycloak's experimental AuthZEN support. He then demonstrates an MCP setup in which Envoy enforces decisions it requests from Keycloak, which acts as both the OAuth authorization server and the decision point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Keycloak and want to see how it can also make fine-grained authorization decisions for MCP tools through the AuthZEN API.

    1. 2:20 Tabata separates authorization into two phases: delegation, where one party grants limited authority as in OAuth, and access control, where a gatekeeper decides on each request, and says good authorization needs both.
    2. 6:36 He explains that AuthZEN standardizes the interface between the policy enforcement point and the policy decision point, so the enforcement point does not depend on a product-specific API.
    3. 10:35 He says Keycloak has experimental support for the AuthZEN Authorization API 1.0 starting with version 26.7, exposing the evaluation and evaluations APIs so it can act as a decision point.
    4. 13:55 He introduces the demo architecture: MCP Inspector as the client, Envoy in front of the MCP server as the enforcement point, and Keycloak as both OAuth authorization server and AuthZEN decision point.
    5. 25:41 In the demo he assigns a role to the user in Keycloak and the previously denied delete tool call succeeds with the same access token, which he uses to show that no separate synchronization with a decision point is needed.

    Supply Chain, Runtime and SDLC: A Cloud Native Security Tour

    Dr. Constanze Roedig

    Constanze Roedig walks through cloud native security in three parts, the software supply chain you consume, the software development lifecycle where you build and deploy, and the runtime, naming CNCF and OpenSSF projects for each. She closes with her view that AI agents put more weight on runtime detection and on protecting and rotating secrets.

    12 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: You find cloud native security overwhelming and want a 16-minute overview of which problem each group of projects addresses.

    1. 0:40 The speaker frames the talk around three areas: the supply chain of software you consume, the software development lifecycle where you produce and deploy it, and the runtime.
    2. 3:44 She says an SBOM declares what is in your software but cannot be assumed complete, and suggests following OpenSSF recommendations on tooling.
    3. 5:51 She distinguishes a signature from an attestation, which she describes as a piece of evidence put in an envelope together with a signature, and names in-toto.
    4. 10:36 For runtime detection she contrasts signatures, which encode known adversary behavior, with anomalies, which are deviations from your own baseline, and says to combine them.
    5. 14:18 She says that with AI agents there are vulnerabilities with no patches available, which in her view puts the spotlight on runtime detection and on short-lived, rotatable secrets.

    The Agent Has Entered the Cluster: AI Auth 101 for Kubernetes

    Jackie Maertens, Nilekh Chaudhari

    Jackie Maertens and Nilekh Chaudhari of Microsoft use a diagnostic agent that calls an MCP tool service against the Kubernetes API to show where a user's identity and permissions get lost between the agent and the cluster. They offer three assessment questions about identity, delegation and scoped authority, and demo three fixes in turn: least-privilege RBAC, tool policies at agentgateway, and passing the user's token to the gateway.

    30 min slot · Beginner · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are putting an AI agent in front of your cluster and want a starting checklist for identity and permissions.

    1. 2:48 Jackie describes two incidents, PocketOS and Replit, in which she says an agent deleted production data because it could do more than its task needed.
    2. 11:04 Jackie follows the identities in the example: Keycloak authenticates Alice, but the Kubernetes API sees only the tool service's service account, so the user sign-in does not travel with later calls.
    3. 13:17 Jackie gives three assessment questions: who the participants are, what authority they carry for someone else, and what each component can actually do.
    4. 16:22 In Nilekh's demo of the unsafe system, the agent deletes Alice's failing checkout service and Kubernetes permits it, because the user's identity stopped at the agent.
    5. 20:14 Nilekh adds agentgateway as a proxy between the agent and downstream systems, first to block the delete tool call and then to check Alice's token claims so she cannot read another team's logs.
