    Kubernetes Data Protection WG Intro & Deep Dive

    Xing Yang, Dave Smith-Uchida

    Xing Yang and Dave Smith-Uchida explain why the Kubernetes Data Protection Working Group formed and walk through the backup and restore building blocks it drives, including COSI, snapshot topology, changed block tracking and volume group snapshots. Smith-Uchida then presents two white papers in progress, on data protection best practices and on recovering from ransomware attacks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you back up stateful workloads on Kubernetes or are planning how to recover from a ransomware attack.

    1. 0:53 Yang says GitOps can recreate manifests, but secrets and data in persistent volumes are not in Git, which is why the group builds Kubernetes-native data protection blocks.
    2. 5:47 Yang highlights COSI v1alpha2 support for one bucket access covering multiple buckets with read-write, write-only and read-only modes.
    3. 8:40 Yang explains changed block tracking, which lets backup vendors copy only the blocks that changed between two snapshots through a new CSI snapshot metadata service.
    4. 14:08 Smith-Uchida describes ransomware as an adversarial problem where the control plane and backups may be compromised and must be verified before restoring.
    5. 15:52 Smith-Uchida recommends immutable backups, such as S3 compliance mode, and moving backup tools from static API keys to short-lived tokens obtained via OIDC.

    Longhorn: Intro, Deep Dive and Q&A

    Shuo Wu, David Ko

    David Ko introduces Longhorn, a cloud native distributed block storage system for Kubernetes, and shares its release cadence, adoption numbers and contributor growth. He then compares the V1 and SPDK-based V2 data engines, explains snapshots, backups, disaster recovery and live upgrades, and outlines the 1.13 and 1.14 roadmap with early RDMA benchmarks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run Longhorn or need block storage on Kubernetes and want to compare the V1 and V2 data engines.

    1. 2:32 Ko says Longhorn runs on any compatible Kubernetes cluster and Linux distribution, including Talos, and ships minor releases every four months in line with Kubernetes.
    2. 4:58 Ko reports adoption up about 21% in six months to roughly 276,000 nodes and 60,000 clusters, from Longhorn's public usage metrics.
    3. 12:22 Ko explains that the V2 data engine uses SPDK in user space with NVMe over Fabrics, plus an interrupt mode so it can share CPU with applications.
    4. 19:21 Ko walks through V2 live upgrades, which move the volume target to another node so I/O continues while the upgrading node's instance manager restarts.
    5. 23:44 Ko lists the 1.14 plans, including RDMA support, I/O QoS, a new data engine for strict-local volumes and application-consistent snapshots and backups.

    Many Clusters, One GPU Pool: Locality-Aware Scheduling and Data Delivery With Kueue and Dragonfly

    Yiqing Wang, Adam Buran

    Yiqing Wang and Adam Buran describe how Roblox shares GPU capacity across clusters using Kueue while leaving each cluster to check its own capacity. They explain how a locality-aware dispatcher chooses clusters and how Dragonfly caches training data and checkpoints near the jobs that use them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingData, storage and state

    Watch this if: You operate GPU clusters in more than one location and want to share capacity without repeatedly pulling the same datasets across regions.

    1. 6:55 The speakers describe two levels of MultiKueue admission: the hub checks team quota, then the candidate clusters check node capacity and the first to admit the job runs it with KubeRay.
    2. 8:15 The speakers explain how the dispatcher first filters for requirements such as GPU type and full-job fit, then prefers the data region for a limited time before considering other regions.
    3. 9:19 The speakers explain how Roblox separates pool-wide guaranteed quota from cluster-level borrowing and uses preemption to reclaim borrowed GPUs when a guaranteed job arrives.
    4. 14:51 The speakers describe Dragonfly looking for file pieces in the local cache, other peers, and seed peers before falling back to Amazon S3.
    5. 15:55 The speakers report that half of the data served came from node-local cache and another 43 percent from peers in the same cluster, leaving 7 percent served from Amazon S3.

  • Platform Engineering Day

    Platform as a Product in a 300-Year-Old Bank

    Abby Bangser, Joel King

    Abby frames platform engineering as a shift toward self-service with guardrails and connects it to the CNCF white papers, maturity model, and an emerging marketplace model. Joel describes how NatWest used product thinking, Kubernetes CRDs, GitOps reconciliation, and clear ownership boundaries to cut EKS cluster provisioning from eight to twelve weeks to 35 minutes.

    25 min slot · Intermediate · Session

    Platform engineering and developer experience

    Watch this if: you want a regulated-enterprise case study connecting platform-as-product theory to Kubernetes and GitOps implementation plus measured outcomes.

    1. 3:43 Joel says reuse failed when each application team copied and modified patterns, producing more than 135 variants, high cognitive load, configuration drift, and an eight-to-twelve-week path to a usable EKS cluster.
    2. 8:34 Joel says NatWest adopted platform as a product by exposing curated products through an abstracted API, using Git as the source of truth, reconciliation loops, and fleet management rather than team-by-team manual change.
    3. 11:13 Joel explains that Kratix provides the product API through Kubernetes CRDs, after which pipelines write validated desired state to Git for downstream reconciliation.
    4. 19:55 Joel says the automated EKS product reduced provisioning from eight to twelve weeks to 35 minutes while including the AWS account, networking connectivity, guardrails, and self-service request path.
    5. 23:30 Abby closes by arguing that platform teams must optimize for outcomes over outputs, composing contributions into products that give users self-service access rather than merely automating infrastructure.

    Platform Engineering's Missing Chapter: Services Organizations

    Atulpriya Sharma

    Atulpriya argues that platform engineering models built for product companies do not directly fit consultancies and services organizations. He presents delivery capital and a capability layer as ways to reuse organizational learning across client engagements while measuring ramp time, consistency, proposal strength, and delivery time.

    25 min slot · Intermediate · Session

    Platform engineering and developer experience

    Watch this if: you build or operate platforms in a consultancy, systems integrator, or client-facing delivery organization.

    1. 2:59 Atulpriya argues that platform engineering's familiar vocabulary was not built around the operating model of consulting firms and services organizations.
    2. 9:03 Atulpriya defines delivery capital as the learning a services organization accumulates across engagements, and says it is the asset the organization truly owns.
    3. 11:04 Atulpriya says the capability layer joins reusable organizational knowledge with an internal consultant IDP of sandboxes and demo clusters so teams can apply prior learning.
    4. 12:57 Atulpriya maps the approach across cloud, IaC, CI/CD, observability, and monitoring, with artifacts such as decision records, checklists, templates, baselines, and named alert owners.
    5. 23:29 Atulpriya argues that ownership, rotation, and billable-work identity block adoption in services firms, and says time-to-ramp, delivery consistency, proposal strength, and delivery time are the measures to watch.

    Running Stateful Analytics on Kubernetes: Lessons from Building a Distributed DuckDB Platform

    Seth McCombs, Karim Alibhai

    Seth McCombs and Karim Alibhai explain the storage and operational decisions their teams had to make when running embedded DuckDB on Kubernetes. They describe treating data as versioned releases so teams could track its provenance, stage rollouts, and roll back.

    30 min slot · Any Level · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you already run DuckDB queries and need to manage data delivery, worker failures, and rollbacks on Kubernetes.

    1. 5:39 The speakers explain that an embedded database does not provide the data delivery path, so their design needs to account for storage, retrieval, and how quickly a query needs its data.
    2. 8:14 They sketch a query router that chooses between Snowflake and Greybeam and accounts for whether data lives in object storage or on a local drive.
    3. 10:44 They describe out-of-memory failures and ask how the service should report a lost query when a worker pod dies.
    4. 19:16 They argue that versioning data packages lets a team trace a discrepancy to the pipeline that produced the data.
    5. 21:20 They describe making data part of the application release cycle, with Argo CD rollbacks and an operator reconciling which source the pods read.
