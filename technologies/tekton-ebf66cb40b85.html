    CNCF Bingo: Play, Learn, Win!!!!!!

    Michael Rishi Forrester

    Michael Forrester runs a live bingo game he calls unofficial, in which the audience marks CNCF projects on a phone card as he reads three clues per project, from broad to narrow. He works through about fifteen projects, from Kubeflow to Knative, until three attendees win, and points to flashcards he wrote covering every CNCF project.

    12 min slot · Level not listed · Session

    Community and open source adoption

    Watch this if: You are new to the CNCF landscape and want a quick, game-style pass over what about fifteen well-known projects do.

    1. 0:13 The speaker explains the game: scan a QR code for a bingo card of CNCF projects with Kubernetes as the free middle square, and long-press a square to read what the project does.
    2. 2:17 He runs a practice round with three clues that lead to Kubeflow: a machine learning platform with notebooks and pipelines, started at Google, used for MLOps on Kubernetes.
    3. 4:15 He gives clues for Open Policy Agent: a general-purpose engine that answers allow or deny, run by Gatekeeper for Kubernetes admission, with rules written in Rego.
    4. 9:20 The first attendee gets bingo after the Harbor clues, which describe a private registry that scans images for vulnerabilities.
    5. 10:50 He says the same site has flashcards for every CNCF project, and that he had to look up about a third of the projects when writing them.

    Container Builds at Scale with Buildpacks

    Joe Kutner

    Joe Kutner of Salesforce presents Cloud Native Buildpacks as a way to turn source code into well-structured container images without a Dockerfile, and says the project graduated in the CNCF this past August. He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    1. 0:55 Joe Kutner says Cloud Native Buildpacks were created at Heroku about 12 years ago, joined the CNCF eight years ago and reached graduation this past August.
    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.
    3. 2:54 He says that with Dockerfiles a vulnerability in a shared base image means rebuilding every image, because of how linear layer caching works.
    4. 3:20 He explains rebase: because buildpacks know the boundary between OS and application layers, existing layers can be moved onto a new OS image without a build, which he says runs in milliseconds.
    5. 4:19 He says buildpacks can be run locally by installing the pack CLI and running pack build, choosing off-the-shelf buildpacks from Heroku, Google or Paketo, or writing your own.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: You can build and push a container image and want to see the next supply chain security steps done live, one command at a time.

    KubeVirt's Architectural Leap: Pluggability, AI Hardware, and Maturing Governance

    Vladik Romanovsky, Itamar Holder

    KubeVirt maintainers Vladik Romanovsky and Itamar Holder mark the project's tenth year and its CNCF graduation by reviewing its pod-based architecture, its adoption of an enhancement proposal process, and this year's work on confidential VMs, NVIDIA hardware support and Dynamic Resource Allocation. Holder then explains the plugin framework from enhancement proposal 190, which is meant to let features be built out of tree, along with early work on supporting hypervisors beyond QEMU/KVM and the idea of using KubeVirt as an isolation backend for agent sandboxes.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run or extend KubeVirt and want to know how the plugin framework will replace sidecar hooks.

    1. 1:02 Vladik Romanovsky recalls early doubts about the project and explains the choice to tie a virtual machine's life cycle to a pod and run the virtualization stack inside it, which he says let KubeVirt reuse the Kubernetes security model, CNI, CSI and device plugins.
    2. 6:48 He says the last cycle had more than 100 open enhancement proposals, and that the project built a per-release tracker plus an AI agent that gathers related pull requests and estimates how likely each piece of work is to land by the freeze.
    3. 9:23 He describes building support for NVIDIA's newest hardware in a fork with Red Hat and NVIDIA engineers before bringing it back upstream, keeping the virt-launcher unprivileged by moving privileged operations into a device plugin.
    4. 14:39 Itamar Holder lists drawbacks of the existing sidecar hook: it edits the libvirt domain XML as a raw string, has no node access, and can only be enabled for everyone through one feature gate.
    5. 16:44 He walks through the new plugin model's three levels: a CEL expression that mutates the domain XML, a sidecar that works on a structured libvirt object with new pre-boot and pre-migration hooks, and node hooks answered by a plugin author's own DaemonSet.

    Next Generation DevOps: Reshaping the Cloud Native DevOps Infinity Loop with AI

    Rey Lejano

    The speaker reviews how DevOps and cloud native grew up together and then proposes a framework that places an example AI agent in each phase of the DevOps infinity loop. He says the agents take the drafting and repetitive work while people keep the judgment and approval steps.

    30 min slot · Beginner · Session

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You are new to cloud native delivery and want a phase-by-phase picture of where AI agents could fit in the DevOps loop.

    1. 3:28 The speaker introduces a framework for embedding AI in each phase of the DevOps infinity loop, with people remaining in the loop for accountability.
    2. 15:37 The speaker argues that AI is the next substrate, and says it does not change the stages of the loop but who or what executes each one.
    3. 17:31 For the plan phase, the speaker describes a spec agent that turns vague requests into user stories and draft architectural decision records, with the human deciding.
    4. 22:50 For the build phase, the speaker describes a pipeline agent that reviews container files, runs CVE scans, generates SBOMs and signs images, with policies enforced by the pipeline, in his case Tekton.
    5. 28:44 For deploy and operate, the speaker describes a rollout agent that runs canary steps with Argo Rollouts and watches metrics for rollback, and a runbook agent that does root cause analysis.

    Supply Chain Security at Home: From Source to Service Without the Hassle

    Andrew Thorp

    Andrew Thorp, a Tekton maintainer, walks through a self-hosted pipeline that takes a commit pushed to Forgejo and builds, pushes and signs a container image with Tekton on Kubernetes. He describes the roles of Tekton Pipelines, Pipelines as Code and Tekton Chains, shows a hermetic build step, and verifies the resulting attestation with Cosign.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you build your own container images, at home or at work, and want to see what a signed, attested Tekton build pipeline involves.

    1. 0:54 Andrew Thorp lists what the setup needs: a Git host such as Forgejo, Tekton running on a Kubernetes cluster (he says a local kind cluster is enough for a small setup), and an image registry such as Harbor.
    2. 1:28 He describes three Tekton components: Tekton Pipelines as the engine that executes pipeline runs, Pipelines as Code as the bridge between the Git forge's webhook events and Tekton, and Tekton Chains for producing SLSA provenance attestations.
    3. 3:00 He shows a build step annotated with what he calls an alpha feature, hermetic execution mode, which he says runs the build in an isolated network space with no network access.
    4. 3:15 He explains that a hermetic build needs an earlier step that prefetches dependencies onto a persistent volume unless they are vendored, and a separate step afterwards to push the image.
    5. 4:21 He shows the attestation and signature from Tekton Chains and says cosign verify-attestation can be used to check them.

    Your CI's Mistaken Identity

    Andrew McNamara, Maia Iyer

    Andrew McNamara and Maia Iyer say a namespace and service account can tell you where a CI task runs without telling you what it should be allowed to do. They describe pairing per-task workload identities with admission-time policy and using those identities to authorize access and sign attestations.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetySecurity, identity and policy

    Watch this if: You want to avoid giving every task in a Kubernetes CI pipeline the same privileges.

    1. 4:30 The speakers explain that SPIRE can use more than namespace and service account when assigning workload identities, so CI pods in the same namespace can have different roles.
    2. 9:19 The speakers explain that a Tekton bundle's digest changes when its task definition changes, and show where Sigstore signatures and attestations can be stored.
    3. 14:14 The speakers describe using Kyverno admission policy to require extra verification before a task can get a production identity.
    4. 16:57 In the live demo, the speakers show that an unsigned task from an untrusted catalog was blocked before a pod was scheduled.
    5. 22:21 The speakers explain how task-scoped identities let a verification policy check not just for an attestation, but for the specific CI task expected to produce it.
