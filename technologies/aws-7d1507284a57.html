    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

Michael then shares a tool they wrote to probe GPU availability across AWS and Azure regions, what four weeks of samples showed them, and their idea for a booking agent that reserves capacity ahead of demand.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you need GPUs without long reservations and want measured data on whether multi-region and multi-cloud help.

    1. 1:45 Michael gives the takeaways first: current single-GPU SKUs need multi-region support, flagship eight-GPU nodes have to be booked ahead, and he says the autoscaler will not do the booking.
    2. 3:43 Yuva explains the platform from the bottom up: one flat L3 network across every provider, identically built Kubernetes clusters, then SPIFFE/SPIRE identity, Istio mutual TLS and Cilium deny-by-default policy.

    4. 16:54 Michael introduces their Follow the GPUs tool, which asks for GPUs, doubles the request after each yes until it gets a no, then waits about an hour and starts again.

    Brian Ugie, Aanchal Khandelwal

    Brian Ugie and Aanchal Khandelwal describe how Adobe's platform team attributes AWS network costs to tenants on multi-tenant Kubernetes clusters by collecting per-pod byte counts with Retina, rolling them up in sharded Prometheus, and classifying each flow into billing categories. They say the pipeline runs in production but still needs hand tuning of Prometheus shards per cluster, and they call it not a victory lap.

    30 min slot · Any Level · Session

    Networking and connectivityObservability and reliabilityPlatform engineering and developer experience

    Watch this if: you run multi-tenant clusters and need to split cloud network charges by team.

    1. 3:42 Brian says Hubble flow counts were not enough for chargeback, using an example where one namespace has 90% of the flows but moves far less data than another.
    2. 5:53 Aanchal walks through the pipeline: Retina on every node, Prometheus collection, a classification step, results in S3, and a billing team that turns bytes into cost.
    3. 10:24 Aanchal says raw flow queries timed out and shards ran out of memory until a recording rule on each shard pre-aggregated bytes with node region and zone every three minutes.

    Tracing at Scale: Running a 16 Billion Spans/Hour Pipeline at Nubank

    Felipe Araujo, Kaynan Coelho

    The speakers describe how Nubank built its distributed tracing pipeline, from instrumenting a handful of shared libraries to an ingestion platform built around the OpenTelemetry Collector, micro-batches on S3 and queues, KEDA scaling and tail sampling with Refinery before data goes to Honeycomb. They share the sampling rules they settled on, cases where traces helped them cut latency and storage, and advice for teams building something similar.

    30 min slot · Any Level · Session

    Observability and reliability

    Watch this if: You are scaling distributed tracing past what head sampling and a single vendor pipeline handle and want one bank's architecture and sampling choices.

    1. 1:34 Kaynan Coelho says the pipeline now receives more than 23 billion spans per hour, over 700 terabytes of data a day, and that five engineers work on it full time.
    2. 4:01 Coelho explains that because most Nubank services share the same Clojure template and libraries, they instrumented six core libraries instead of more than 4,000 services.
    3. 8:21 Felipe Araujo says streaming was too expensive and large batches too slow, so the collector writes roughly 10-second micro-batches to S3 and a queue notification tells the next application to pick them up, a pattern he identifies as claim check.
    4. 12:06 Araujo says percentage-based tail sampling hid rare critical paths, so they moved to dynamic rules that keep slow requests and all 500 errors and reduce fast, common successes.
    5. 14:23 Coelho describes using traces to find that some app requests waited on more than 30 content providers, and says the fixes brought latency in those transactions down to about 200 milliseconds.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
