    Dashboards-as-Code: Easy to Ship, Easy to Get Wrong

    Cecil Wöbker

    Cecil Wöbker describes how remberg moved from hand-written Grafana dashboards to scripts in CI that generate per-team dashboards, loaded into the cluster by the Grafana sidecar. He lists the mistakes his engineers ran into, including kube-state-metrics label allow lists, series that change across pod restarts and JSON that Grafana ignores.

    5 min slot · Beginner · Lightning Talk

    Delivery, GitOps and release safetyObservability and reliability

    Watch this if: you want engineers to ship their own dashboards as code and avoid common mistakes.

    1. 0:58 Cecil Wöbker says remberg's two hand-written Grafana dashboards were painful to keep current, so they were broken about half the time.
    2. 1:56 He describes scripts in CI/CD, often written with AI, that generate individual dashboards for each team based on the services it owns.
    3. 2:38 He explains the deployment: CI commits the script output, a labeled ConfigMap marks it as a dashboard, and the Grafana sidecar loads it automatically.
    4. 3:30 His first caveat: kube-state-metrics does not export all labels by default, so labels used for joins or filters must be on its allow list.
    5. 4:37 He warns that valid JSON is not always valid for Grafana and that AI tends to add fields from outdated docs, so dashboards still need checking.

    Istio at Scale: Lessons, Pitfalls, and Observability

    Adarsh Kumar

    The speaker recounts debugging recurring CPU spikes in Istio sidecars that kept pushing autoscalers to their maximum without any rise in traffic. He says the cause was configuration pushes triggered by churn in an unrelated namespace, and that limiting what each sidecar can see removed the spikes and lowered sidecar memory use.

    Length not listed · Level not listed · Type not listed

    Networking and connectivityObservability and reliability

    Watch this if: You run Istio sidecars at scale and see unexplained proxy CPU spikes or heavy configuration pushes.

    1. 2:45 The speaker says the problem began with alerts that Horizontal Pod Autoscalers had hit their maximum even though traffic had not grown.
    2. 3:14 He says the sidecar containers showed a repeating spiky CPU pattern, and telemetry showed a large number of xDS pushes with no obvious cause.
    3. 4:32 He inspects what a proxy knows with istioctl proxy-config on a recreated Bookinfo setup and finds a noisy worker from another namespace in the cluster list.
    4. 5:23 He explains that background workers on spot VMs were preempted often, so new pod IPs kept triggering endpoint pushes to every sidecar.
    5. 6:36 He applies a Sidecar resource that limits visibility to the same namespace and shows the unrelated clusters gone, which he says ended the CPU spikes and cut sidecar memory.

    SIG Instrumentation Introduction and Deep Dive

    David Ashpole, Catherine Fang, Stephen Lang

    The three maintainers describe what Kubernetes SIG Instrumentation owns, from the metrics, logging and tracing frameworks to subprojects such as kube-state-metrics and the newly adopted kubernetes-mixin. They walk through the past year's changes, including structured z-pages, Resource State Metrics and native histograms, then list next year's plans and the subprojects where they say they need contributors.

    30 min slot · Level not listed · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you run Kubernetes monitoring and want the maintainers' view of what changed in metrics, logs and traces and where the SIG wants help.

    1. 4:10 Catherine Fang presents the statusz and flagz z-pages, which she says expose a component's binary version and effective flags on its serving port and are gaining structured output formats this year.
    2. 8:02 Catherine introduces Resource State Metrics, a new component that she says uses CEL-style expressions to read any field of a custom resource without writing Go code in kube-state-metrics.
    3. 9:00 Stephen Lang says kubernetes-mixin is new to SIG Instrumentation and describes work to cut alert fatigue and to tie mixin releases to Kubernetes versions with a scrape allow list and a version support matrix.
    4. 10:27 David Ashpole says Prometheus native histograms are now beta and on by default in Kubernetes, claims they cost about ten times less than classic histograms, and notes users must enable them in Prometheus and update queries.
    5. 18:52 David says Prometheus Adapter has no maintainers, so the SIG is formally deprecating it and encouraging users to migrate to KEDA.

    SIG Storage Intro and Deep Dive

    Xing Yang, Hemant Kumar, Michelle Au

    Xing Yang, Hemant Kumar and Michelle Au explain what Kubernetes SIG Storage owns, from persistent volume APIs to CSI and COSI, and walk through recent storage features by category. They cover volume health, security changes, ephemeral volume updates, data protection, storage-aware scheduling and features still in design, then explain how to get involved.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run stateful workloads on Kubernetes and want a tour of the storage features landing in recent releases.

    1. 2:49 Kumar shows volume health reported on PVC and pod objects, plus a new alpha condition for the health of a whole storage subsystem on the CSINode object.
    2. 6:41 Au explains that the gitRepo volume plugin was removed because kubelet ran git clone on the host, and recommends an init container or sidecar instead.
    3. 10:02 Au introduces dynamic node-local ephemeral volumes, alpha in 1.38, which add and remove volumes from a running pod without recreating it.
    4. 14:55 Yang describes volume group snapshots, GA in 1.36, and changed block tracking, beta in 1.36, which lets backup vendors fetch only the blocks that changed.
    5. 19:58 Kumar explains an opt-in CSIDriver setting that stops pods from being scheduled to nodes without the driver, and how it interacts with Cluster Autoscaler.
