    Architecture Without Gatekeepers: Decoupling for Neutrality

    Kate Obiidykhata

    Kate Obiidykhata of Percona tells how Percona Everest, which had its database operators and monitoring baked into the core, drew almost no outside contributions until it was renamed OpenEverest and donated to the CNCF. She says a second change, shrinking the core and moving everything else into providers and plugins, was followed by more supported technologies and new contributors.

    5 min slot · Level not listed · Lightning Talk

    Community and open source adoptionData, storage and state

    Watch this if: you maintain an open source project started inside one company and want to hear what one team changed to attract outside contributors.

    1. 1:04 Obiidykhata says the project started under the Percona brand with MySQL, PostgreSQL and MongoDB support based on Percona's own operators, plus monitoring based on Percona Monitoring and Management.
    2. 1:49 She says all of those elements were baked into the core and the project had almost zero traction from the open source community because it was hard to contribute to and change.
    3. 2:31 She describes renaming Percona Everest to OpenEverest and donating it as a CNCF sandbox project, saying the governance protects the license and core, and that GitHub stars grew right after the move in early 2026.
    4. 3:32 She explains the architecture change: a very small core with providers for adding new technologies through an SDK and plugins for extending things like the UI, and says adding a database now takes days instead of weeks or months.
    5. 4:35 She reports that the community added technologies such as ClickHouse and KServe, that the project went from three technologies to 12, and that 89 new contributors had merged pull requests.

    Going Cloud Native in Baseball

    Matt Dering, Long Nguyen

    Matt Dering and Long Nguyen explain how the Phillies platform team supports baseball analysts without asking them to become infrastructure specialists. They describe workflows for containerized model jobs, typed inference APIs, and an event-driven approach to data processing with Knative.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You support a small data science team that needs to run large jobs and ship inference services without managing Kubernetes directly.

    1. 4:26 The speakers trace model input and output through BigQuery and explain how selected outputs move into relational databases for the web app used by coaches and front-office staff.
    2. 6:55 The speakers show how projects can share code while keeping separate dependencies and container definitions, with a template that works for local Docker Compose and Kubernetes.
    3. 8:31 The speakers describe replacing hand-managed compute with templated Kubernetes Jobs that analysts can launch with their own image and command.
    4. 13:35 The speakers describe turning familiar typed Python code into validated clients and FastAPI services, with automated checks for schema compatibility.
    5. 17:52 The speakers outline how Knative Functions, Eventing, and request-driven scaling fit their move from scheduled batch scripts toward event-driven processing.

    Horizontally Scale MySQL on Kubernetes

    Matt Lord, Florent Poinsard

    Matt Lord introduces Vitess as a way to spread a MySQL workload across many servers while applications still see a single MySQL server, and walks through its components. Florent Poinsard then explains the MoveTables and Reshard workflows and runs a live demo that splits one shard into two under load on Kubernetes.

    30 min slot · Level not listed · Session

    Data, storage and state

    Watch this if: your MySQL database is outgrowing a single instance and you want to see what sharding it with Vitess on Kubernetes looks like.

    1. 2:46 Matt Lord says Vitess lets you distribute the workload of one MySQL instance across hundreds or thousands of MySQL servers while users still see a single server.
    2. 6:52 Matt Lord walks through the architecture: stateless VTGates that speak the MySQL protocol, VTTablets in front of each mysqld, the topology server, vtctld and VTOrc.
    3. 16:09 Florent Poinsard explains the MoveTables workflow: copy the data, keep streaming changes, switch reads and writes, and revert through reverse replication if needed.
    4. 21:02 Florent Poinsard starts the demo: a Vitess cluster on Kubernetes with the open source Vitess Operator on his laptop, with load pushing the single shard's CPU to 100%.
    5. 25:12 After completing the Reshard workflow, Florent Poinsard reports the demo going from about 7 to 8K QPS to 10 to 11K, with latency moving from about three milliseconds to two.

    Kubernetes Data Protection WG Intro & Deep Dive

    Xing Yang, Dave Smith-Uchida

    Xing Yang and Dave Smith-Uchida explain why the Kubernetes Data Protection Working Group formed and walk through the backup and restore building blocks it drives, including COSI, snapshot topology, changed block tracking and volume group snapshots. Smith-Uchida then presents two white papers in progress, on data protection best practices and on recovering from ransomware attacks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you back up stateful workloads on Kubernetes or are planning how to recover from a ransomware attack.

    1. 0:53 Yang says GitOps can recreate manifests, but secrets and data in persistent volumes are not in Git, which is why the group builds Kubernetes-native data protection blocks.
    2. 5:47 Yang highlights COSI v1alpha2 support for one bucket access covering multiple buckets with read-write, write-only and read-only modes.
    3. 8:40 Yang explains changed block tracking, which lets backup vendors copy only the blocks that changed between two snapshots through a new CSI snapshot metadata service.
    4. 14:08 Smith-Uchida describes ransomware as an adversarial problem where the control plane and backups may be compromised and must be verified before restoring.
    5. 15:52 Smith-Uchida recommends immutable backups, such as S3 compliance mode, and moving backup tools from static API keys to short-lived tokens obtained via OIDC.
