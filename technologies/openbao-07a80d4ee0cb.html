    Celebrate Flux's 10 Years!

    Tamao Nakahara

    Tamao Nakahara, a Flux maintainer, gives an overview of Flux and says it is trusted by cloud providers, telcos and enterprises because it was designed security first. She then describes identity features built on SPIFFE and mTLS and the Artifact Generator, which she says composes and decomposes deployment artifacts and now supports multi-tenancy.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetySecurity, identity and policyCommunity and open source adoption

    Watch this if: You want a quick update on Flux's security and artifact features at its ten-year mark.

    1. 0:22 Tamao Nakahara says Flux is the project that created the term and practice of GitOps.
    2. 1:25 She says several cloud providers that offer GitOps run Flux under the hood, naming Microsoft Azure as a long-time maintainer, and that almost every telco the team has spoken to uses Flux.
    3. 3:05 She says Flux has always had object and workload identity and that users can now customize them directly with SPIFFE or mTLS, moving toward no passwords and no secrets.
    4. 3:34 She argues that Flux controllers in the same cluster should not trust each other by default, and says they can now verify each other with certificates and two-way handshakes.
    5. 4:18 She describes Artifact Generator as composing one artifact from multiple sources and decomposing monorepos into smaller ones, and says multi-tenancy is new to it.

    Every Kubernetes Object Deserves an Identity: The SPIFFE Broker API

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    Kubernetes Secrets Were a Bad Idea. Now What?

    Maxime Coquerel

    Maxime Coquerel argues, as his own opinion, that Kubernetes Secrets are risky because they are only base64 encoded in etcd, readable with broad RBAC permissions and have no lifecycle. He recommends encrypting etcd with a customer managed key, keeping secrets out of Git and mounting secrets from a real vault at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    5 min slot · Beginner · Lightning Talk

    Security, identity and policy

    Watch this if: you are deciding whether Kubernetes Secrets are good enough for your platform or which alternative to use.

    1. 0:43 Maxime Coquerel says a Kubernetes Secret is stored in etcd only base64 encoded, not encrypted, and that etcd is a key value store, not a vault.
    2. 1:46 He lists the weaknesses he sees, including that anyone with get, list or watch permissions can read secret contents.
    3. 2:05 He adds that Kubernetes Secrets have no lifecycle: no expiration date and no automatic renewal.
    4. 2:47 His first recommendation is to encrypt etcd with a customer managed key, which he says managed services such as Azure Kubernetes Service support.
    5. 3:49 He compares Sealed Secrets, SOPS and External Secrets Operator, and recommends mounting secrets as files at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    Stop Writing Secrets Into YAML: A Rotation-First Identity Pattern for Kubernetes

    Fabrizio Sgura

    Fabrizio Sgura proposes using workload identity first and issuing short-lived credentials only for dependencies that still require them. He walks through how Kubernetes, SPIRE, and OpenBao could support issuance, renewal, delivery, and revocation.

    30 min slot · Beginner · Session

    Security, identity and policy

    Watch this if: you want to replace static Kubernetes credentials a step at a time.

    1. 5:35 Sgura separates the roles of SPIFFE as a workload identity standard, SPIRE as its implementation, and OpenBao as a credential lifecycle manager.
    2. 10:26 He describes a layered design in which a workload first gets a short-lived identity document, and only uses a traditional credential if an external dependency needs one.
    3. 20:45 He explains that SPIRE issues a verifiable identity document after checking the workload, and gives X.509 and JWT as examples.
    4. 25:37 He describes using OpenBao for dynamic credentials, with External Secrets Operator or the Secrets Store CSI Driver handling delivery.
    5. 28:44 He recommends avoiding credentials when workload identity is enough, limiting the lifetime of any credentials issued, and designing for renewal and revocation.
