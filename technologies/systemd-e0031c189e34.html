    Every Kubernetes Object Deserves an Identity: The SPIFFE Broker API

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    Extending the Immutable OS: Adding Tools to Flatcar with Systemd-Sysext

    Jan Bronicki

    Jan Bronicki, a Flatcar Container Linux maintainer, explains that an immutable OS has no package manager for adding software to the read-only /usr. He describes systemd-sysext as a signed, verifiable overlay on /usr for things like GPU drivers or Kubernetes binaries, and shows how it is declared in Butane.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: You run or are considering an immutable node OS and wonder how to add drivers or debugging tools to it.

    1. 0:46 Jan Bronicki says the core of an immutable OS, such as /usr, cannot be changed and is verifiable, meaning the kernel can check whether someone tampered with it.
    2. 1:19 He says package managers such as apt or dnf do not exist on such a system, which raises the question of how to get your software onto it.
    3. 1:48 He says systemd-sysext creates an overlay on top of /usr to add a particular runtime version, a GPU driver or anything else needed.
    4. 2:48 He says the key part is that a sysext is not a random blob of binaries: it plugs into the immutability and verification system, so tampering would not go unnoticed.
    5. 3:13 He shows a Butane config that declares which sysext version to fetch from where, says offline sources work, and says the binary is linked into /usr at boot.

    Shachar Tal

He demos kubectl exec and logs running over bucket objects and says adaptive polling keeps the cost at about $5 per VM instance per month.

    30 min slot · Any Level · Session

    Networking and connectivitySecurity, identity and policy

    1. 3:58 Tal says the outpost VPC is designed so that an attacker who gets code running inside cannot exfiltrate data, with one tightly controlled bucket as the only path.
    2. 11:17 Tal says Konnectivity solves only one direction of reachability, so his team carries messages in both directions through the bucket as a rendezvous point.

    When the Clock Lies: How an 8-Minute Time Skew Locked Kubernetes cluster for a day

    Akhil Mohan

    Akhil Mohan of VMware by Broadcom, a containerd maintainer, retraces how a CSI pod on an internal cluster sat in CreateContainerError for 19 hours after a hypervisor power failure while its containers were in fact running. He traces it to a VM that booted about eight minutes in the future, so tokens were issued in the future and kubelet's sorting of containers by creation time got stuck once chrony stepped the clock back, and he describes the fix of starting kubelet only after time sync.

    30 min slot · Any Level · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you operate Kubernetes nodes on virtual machines and want a worked example of debugging from a stuck pod down to the hardware clock.

    1. 0:26 Mohan lays out the symptom: a CSI pod in CreateContainerError with over 5,000 retries failing on a container name reservation, while crictl on the node shows the same containers already running.
    2. 8:51 He finds kube-proxy rejected by the API server because its service account token is not valid yet, issued by a control plane VM whose clock was ahead of the other two.
    3. 10:08 Journal logs show the time jumping backwards 45 seconds after boot: he says the VM inherited a clock about eight minutes ahead from the ESXi host and chrony stepped it back in one go, after kubelet had already started.
    4. 18:55 He explains the loop: kubelet sorts container statuses by created-at wall clock time, so the attempt created on the future clock always looks newest and kubelet keeps trying to recreate an attempt that is already running.
    5. 21:36 The fix he describes is ordering the kubelet systemd unit after a chrony wait service with a 180 second timeout, chosen so a node boots slower instead of never booting when NTP is unavailable.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
