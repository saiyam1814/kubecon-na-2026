    Beyond Dashboards: A Semantic Layer for AI-Driven Observability in Kubernetes

    Pronnoy Goswami

    Pronnoy Goswami argues that pasting raw logs and traces into an LLM gives unreliable answers, and presents a four-layer design that uses OpenTelemetry for consistent context and an MCP server that exposes typed, bounded, summarized tools instead of raw query access. He shows a recorded local demo with synthetic data and shares lessons on cardinality, latency and when he thinks the approach reduces MTTR.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automation

    Watch this if: you are wiring an AI agent to your metrics and traces and want a bounded design for it.

    1. 1:52 Pronnoy lists four ways he says raw telemetry in a prompt fails: volume, no schema, unbounded queries and no provenance.
    2. 4:20 He outlines the four layers: instrument with OpenTelemetry semantic conventions, collect and store, an MCP semantic query layer, and agents with human approval.
    3. 9:21 He says MCP tools should be designed for how an on-call engineer thinks rather than wrapping the Prometheus API, and should be typed, discoverable, summarized and cited.
    4. 13:00 In a recorded demo with a fault injected into a payments API, the tool reports spikes in the checkout API's error ratio and p99 latency and in the payments API's p99 latency as the top three signals.
    5. 17:32 He shares production lessons: never offer a free-form group by, back the catalog with recording rules, set per-tool timeouts and budgets, cache, and summarize inside the server.

    Following the Evidence with HolmesGPT: Troubleshooting Kubernetes Apps and Infrastructure

    Yash Sharma

    Yash Sharma, presenting alone after saying his co-speaker could not attend, describes his own experiment with HolmesGPT on a demo shop application running on a DigitalOcean Kubernetes cluster with three planted faults. He shows it investigating a full Postgres volume, a CPU-hungry CronJob and a cloud-side volume attachment limit, and then outlines how he would run it in production with read-only access and human approval for changes.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automation

    Watch this if: you are considering an AI troubleshooting assistant for Kubernetes and want to see it work through storage, CPU and cloud-provider faults before deciding how much access to give it.

    1. 4:41 Sharma describes HolmesGPT's loop: starting from an alert thread, it calls toolsets such as kubectl, PromQL, APIs and SQL, reruns the investigation if the results are not enough, and returns a root cause with evidence and a suggested fix.
    2. 12:21 In the live demo, after he fills the Postgres volume and checkout errors rise, the holmes ask command returns evidence of no space left on the device along with possible fixes.
    3. 17:26 He says HolmesGPT runs read-only in his cluster, so a kubectl exec it attempted was denied as needing approval, and it still traced the slow checkout API to the batch job he had added.
    4. 18:38 For the third case he explains a setup where a 16th pod cannot get a volume because of a per-node attachment limit on DigitalOcean Kubernetes, and shows holmes investigate alertmanager attributing the pending pod to the cloud provider side.
    5. 24:44 His security advice is to keep the tool read-only, require human approval for any write, issue least-privilege tokens per task, and check the logs rather than fully trusting the output, since logs can carry injected content.

    Green Dashboards, Broken Clusters: Taming Stale Watches in Kubernetes Operators

    Michael Aspinwall, Alvaro Aleman

    Michael Aspinwall and Alvaro Aleman explain how a controller that reads from a lagging informer cache can miss its own writes, using a DaemonSet controller case in which duplicate pods were created on every node. They describe the upstream Kubernetes work on comparable resource versions, informer staleness metrics and a consistency store in client-go, and the different approach controller-runtime takes with a client that waits for the cache to catch up.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you write or operate Kubernetes controllers and want to know how stale informer caches cause duplicate or wrong actions, and what client-go and controller-runtime now offer to avoid them.

    1. 3:47 Aspinwall walks through the case study: the DaemonSet controller's write expectations expire after about five minutes, so when the pod informer lags longer than that, the controller sees no pod in its stale cache and creates another one on the same node.
    2. 5:53 He says KEP-5504 extends to clients the guarantee that resource versions can be compared, so a controller can tell from the version returned by its write whether its cache has caught up.
    3. 6:21 He describes a new metric on every informer store in client-go that can be subtracted from the API server's watch cache resource version, and shows a scale-test graph in which one API server falls up to 350,000 resource versions behind.
    4. 7:17 He explains the consistency store, which records the resource version of each write and returns an error at the start of the next reconcile until the store has synced past it, and says it is already in the DaemonSet, Job, StatefulSet and ReplicaSet controllers.
    5. 18:27 Aleman describes controller-runtime's consistent client as two layers: reads that start after a write block until the write finishes, and then wait until the cache has reached the resource version that write returned.

    Two-Stage OTel Aggregation: Taming Istio Cardinality at 10k-Pod Scale

    Evelyn (Chungyu) Chen

    The speaker, from Yahoo, describes cutting the Istio metric series of a large production cluster by 86% by aggregating away pod-level identity in OpenTelemetry Collectors, first on each node and then at a gateway. She walks through the processor order this needs and the problems her team says it hit along the way, including counters that went down after pod restarts and data lost at one backend.

    30 min slot · Advanced · Session

    Observability and reliabilityNetworking and connectivity

    Watch this if: You run Istio at scale, pay per metric series, and want to see how one team aggregated pod-level labels away inside the OpenTelemetry Collector.

    1. 0:26 The speaker says one production cluster with over 800 nodes and 24,000 pods went from more than 2 million active series to an 86% smaller set, which she puts at about $140,000 a year saved on that cluster.
    2. 8:05 She explains the per-node steps: the transform processor deletes pod and container identifiers at the resource level, a batch step lets data points meet, groupbyattrs promotes the app label to the resource, and metricstransform sums the series.
    3. 12:47 She explains why the pipeline runs twice: each node agent collapses its own pods' metrics, then the gateway removes node identity and aggregates across nodes to one series per app.
    4. 15:05 She says summing cumulative counters across pods made totals drop when a pod restarted, producing rate spikes, and that the fix was converting to delta with cumulativetodelta first and rewriting queries from rate to sum_over_time.
    5. 21:16 She says a second vendor's backend stored only one point per second per series, so values pushed by three gateway pods in the same second collided and only the last was kept, a problem she says is still open.
