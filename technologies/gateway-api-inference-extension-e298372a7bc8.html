    AI on Kubernetes Is Just a Pod With a GPU (and That's the Problem)

    Graziano Casto

    Graziano Casto compares deploying a web application with deploying a model on Kubernetes, starting from a plain Deployment that runs a vLLM container. He names three differences, which are whole-number GPU allocation, slow startup while model weights load, and requests that cost very different amounts of GPU work, and for each he points to projects he says address it.

    12 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You run web applications on Kubernetes and want a short orientation on what changes with model serving before choosing AI talks to watch.

    1. 0:36 The speaker shows what he calls the easiest way to deploy a model on Kubernetes: an ordinary Deployment running a vLLM container that serves a Llama 3.1 model.
    2. 3:01 He says a GPU is requested as a whole number, so a model that does not use a full GPU still leaves it overprovisioned.
    3. 3:43 He lists dynamic resource allocation in Kubernetes, HAMi for software-level enforcement and NVIDIA MIG for hardware partitioning as ways to share a GPU.
    4. 5:03 For slow startup he suggests relaxing liveness and readiness probes, caching downloaded weights on a persistent volume, and packaging weights as OCI artifacts mounted as image volumes.
    5. 6:57 He says round-robin load balancing does not fit chat workloads, and describes llm-d's KV-cache-aware routing, built on the Gateway API Inference Extension, as sending a conversation back to where its context lives.

    Watch this if: you serve LLMs on Kubernetes and want the KServe maintainers' checklist of routing, scaling and cold-start issues to plan for.

    1. 4:07 Jooho Lee describes the LLMInferenceService API, in which he says a workload controller manages single-node, multi-node and separate prefill deployments while a route controller manages the scheduler and Gateway API resources.

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    What the Docs Don't Tell You: A Telecom's Year Operating Cache-Aware LLM Inference on Kubernetes

    YoungJoon Jeong, Seol Heo

    The speakers describe how LG Uplus raised its KV cache hit rate from 71.6% to 95.4% on 16 vLLM replicas by reordering prompts, routing each request to the pod that holds its prefix with llm-d, and adding a CPU memory tier for evicted blocks. They say time to first token is queue time plus prefill time, so once prefill was cached they tuned concurrency, and they report that splitting prefill and decode cut inter-token latency while lowering throughput.

    30 min slot · Advanced · Session

    AI inference and servingObservability and reliability

    Watch this if: You serve LLMs for multi-turn or agent traffic on Kubernetes and want measured numbers on what prefix-aware routing, cache tiers and prefill/decode separation each bought.

    1. 4:51 YoungJoon Jeong says vLLM hashes prompt blocks in a chain, so one small change near the start, such as a timestamp in the system prompt, turns every later block into a miss; his advice is to put the stable part first.
    2. 9:07 He frames KV cache hit rate as ceiling times placement times survival, which he calls their own framing and not an upstream metric, with a different owner for each factor.
    3. 13:05 Seol Heo says their initial hit rate was 71.6% because routing on pod load sent turns of one conversation to different pods, duplicating prefixes in GPU memory and causing evictions.
    4. 17:38 He says that after prefill was optimized the queue became the bottleneck, and setting vLLM's max number of sequences to 24 brought time to first token from 2.09 to 0.39 seconds in their benchmark.
    5. 20:11 He reports that separating prefill and decode pools, with KV transfer over InfiniBand RDMA through NIXL, cut inter-token latency from 69.8 to 19.5 milliseconds while generation throughput fell about 30%.

    Your Peers Are Struggling With LLM Inference on Kubernetes Too. Here's What the Data Says.

    Danielle Cook, Andy Suderman

They group the problems into scheduling, scaling, routing, placement and ownership, and close with five steps they recommend, from starting on an AI-conformant cluster to setting a time-to-first-token SLO.

    30 min slot · Any Level · Session

    AI inference and servingObservability and reliability

    Watch this if: you run LLM inference on Kubernetes and want survey numbers to compare your latency targets, GPU utilization and routing setup against.

    1. 4:33 Cook presents the survey's performance expectations: 82% of respondents need an end-to-end response within 500 milliseconds, 64% within 250, and nearly half expect to roll back within 15 minutes when inference degrades.
