    Architecture Without Gatekeepers: Decoupling for Neutrality

    Kate Obiidykhata

    Kate Obiidykhata of Percona tells how Percona Everest, which had its database operators and monitoring baked into the core, drew almost no outside contributions until it was renamed OpenEverest and donated to the CNCF. She says a second change, shrinking the core and moving everything else into providers and plugins, was followed by more supported technologies and new contributors.

    5 min slot · Level not listed · Lightning Talk

    Community and open source adoptionData, storage and state

    Watch this if: you maintain an open source project started inside one company and want to hear what one team changed to attract outside contributors.

    1. 1:04 Obiidykhata says the project started under the Percona brand with MySQL, PostgreSQL and MongoDB support based on Percona's own operators, plus monitoring based on Percona Monitoring and Management.
    2. 1:49 She says all of those elements were baked into the core and the project had almost zero traction from the open source community because it was hard to contribute to and change.
    3. 2:31 She describes renaming Percona Everest to OpenEverest and donating it as a CNCF sandbox project, saying the governance protects the license and core, and that GitHub stars grew right after the move in early 2026.
    4. 3:32 She explains the architecture change: a very small core with providers for adding new technologies through an SDK and plugins for extending things like the UI, and says adding a database now takes days instead of weeks or months.
    5. 4:35 She reports that the community added technologies such as ClickHouse and KServe, that the project went from three technologies to 12, and that 89 new contributors had merged pull requests.

    Ask Your Platform: Putting AI to Work Where the Questions Live

    Anton Alexander, Scott Adams

    Two platform engineers at a Fortune 100 company describe adding AI agents to the places people already ask questions: the developer portal, kubectl, node debugging with netshoot, and a ClickHouse history of cluster objects. They say they keep the agents safe with a read-only kubectl wrapper, permission rules shared in a Git repository and RBAC that excludes secrets, and that deterministic tools worked better for them than prompts.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceAI agents and automation

    Watch this if: You run a platform team and want concrete, read-only ways to let AI agents answer developers' and on-call engineers' questions about clusters.

    1. 4:15 Anton Alexander says their approach was to start with a question, not an AI product, and to put AI where that question is already asked.
    2. 5:24 He says the agent in the developer portal passes the developer's identity to the cluster so it cannot see more than that person can, and it traces a 503 to a wrong service selector.
    3. 9:19 He says instructions are guidance, not enforcement, so their coding agent may only call a wrapper CLI that exposes read-only kubectl operations, with other commands denied by permission rules.
    4. 12:26 The wrapper also lets the agent schedule a netshoot pod on a target node and run an allowed set of commands, for node-level questions the Kubernetes API cannot answer.
    5. 15:43 Scott Adams describes watching every object in their clusters and storing spec and status history in ClickHouse, so an agent can answer with SQL what changed or whether an image ever ran.

    Feeding the GPU: Streaming Data into Training, Lakehouse, and Serving without the Serialization Tax

    Dheeraj Kapur, Deepak Choudhary

    The speakers describe a streaming design in which producers send Arrow IPC batches once to a gateway that writes them to GPU memory and to a lakehouse without converting rows to columns again. They share their own measurements for throughput, query engines and crash recovery, and say the work is not open source yet.

    30 min slot · Any Level · Session

    Data, storage and stateAccelerators and workload schedulingAI inference and serving

    Watch this if: You build streaming pipelines that feed both GPUs and lakehouse tables and want to see where serialization cost goes.

    1. 2:59 The speaker says separate pipelines for the GPU, the lakehouse and other destinations each convert row data into a columnar format again.
    2. 6:37 The speaker says the producer should send Arrow IPC so that preparation happens once, and that the format converts one to one into cuDF and Parquet.
    3. 10:51 The speaker explains that the gateway transfers batches into GPU memory, stores them in a durable log for the lakehouse, and sends the acknowledgment once the data is on disk.
    4. 17:00 The speaker reports a throughput of 3 million points per second with 20 pods, and says they want to scale the system to 17 million points per second.
    5. 21:33 The speaker says a fix took them from 25,000 duplicates to zero duplicates and no data loss over two weeks of chaos testing.

    Set the Terms for Your Agents and Let Your Humans Be Creative: How to Govern Code Nobody Reviewed

    Thomas Schuetz, Dr. Constanze Roedig

    Thomas Schuetz and Constanze Roedig demonstrate a platform feedback loop that checks AI-generated applications against engineering and compliance requirements. In a recorded example, they show how evidence from runtime probes guides the coding agent's next revision.

    25 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You want a way to check what AI-generated apps do at runtime and turn that evidence into feedback.

    1. 5:40 The speakers ask how to translate a human-readable architectural decision record or regulation into something that runtime probes can check and produce evidence for.
    2. 9:23 They explain how they made decision records machine-readable for the demo and used profiles to define a starting boundary for observed runtime behavior.
    3. 11:04 In a recorded demo, they show the first app revision, evidence from ClickHouse in the Pixie UI, and findings sent back to the coding agent to guide the next revision.
    4. 14:33 They point out that the same feedback loop produced a PostgreSQL backend in one run and Redis in another, illustrating why teams must state any backend requirements explicitly.
    5. 21:03 They recap handing off a generated app without a pre-existing CI pipeline or guardrails, and describe using runtime evidence to assess it and send feedback with little human involvement.
