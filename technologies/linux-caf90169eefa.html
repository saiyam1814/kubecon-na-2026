    Here be DRAgons: Bringing native zero-copy networking to Pods with Cilium and netkit

    Daniel Borkmann, Aaron Campbell

    The speakers compare two Cilium network drivers for Kubernetes Dynamic Resource Allocation, one using SR-IOV and the other using netkit with queue leasing. They demonstrate how a pod can use a leased hardware receive queue and explain how zero-copy receive works with the kernel networking stack.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you are evaluating hardware-accelerated pod networking and want to understand what Cilium queue leasing requires.

    1. 8:37 Borkmann explains how running BPF in the netkit device driver reduces the queue traversals seen with virtual Ethernet devices.
    2. 14:33 He introduces Cilium's two DRA driver options, SR-IOV and netkit queue leasing, and describes how the agent integrates with the node.
    3. 19:54 He explains how Linux queue leasing removes selected receive queues from the default set and binds them to a netkit device in a pod.
    4. 22:13 Campbell begins the demo by showing the operator's view of queue leasing and identifying the required hardware receive-queue capabilities.
    5. 30:22 He explains how packet headers stay in kernel memory while io_uring enables payload delivery directly to user space.

    Hidden Pod Startup Latency: Container Image Pull

    Omer Oz

    Omer Oz describes how LinkedIn investigated slow pod startups on its bare-metal fleet and traced most of the time to unpacking container image layers, not downloading them. He walks through the kubelet and containerd settings his team changed, the results he reports, and further options such as zstd compression, the EROFS snapshotter and peer-to-peer caching.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimesObservability and reliability

    Watch this if: large container images slow your pod startups and you want a mental model of the pull path plus settings to try.

    1. 9:12 Oz describes the trigger: Flink apps shipping about 28 GB of images against a 20-minute pod startup SLO, which he says caused a series of incidents at LinkedIn.
    2. 14:46 Oz walks through an image pull timeline and says the download finishes early while most time goes to unpacking, which containerd does one layer at a time by default.
    3. 15:26 Oz explains LinkedIn's fix of raising the kubelet's parallel image pulls to three and lowering containerd's download concurrency, then shows the latency results he measured.
    4. 21:46 Oz presents the EROFS snapshotter for containerd, which he says skips eager unpacking and cut unpack time to under 0.4 seconds in his tests.
    5. 23:57 Oz describes a serialization point he found in containerd that capped total download throughput, and points to his pull request removing it.

    Look Before You Leap: Preventing In-Motion K8s Updates in Fleet Robotics

    Tom Ingleby, Rian Bogle

    Rian Bogle and Tom Ingleby of Agility Robotics describe how they run K3s on humanoid robots and manage them from the cloud with GitOps. Ingleby then shows an admission webhook he calls the locomotion guard, which he says rejects cluster changes in restricted namespaces while a robot is walking.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetySecurity, identity and policy

    Watch this if: you run Kubernetes on edge or embedded devices and need to block changes while the device is in a state where a restart is unsafe.

    1. 4:56 Bogle lays out the on-robot stack: K3s on a read-only OS, GitOps with continuous deployment, OCI images, OpenTelemetry and Fluent Bit for telemetry, and Teleport with SPIFFE identities.
    2. 7:44 Ingleby explains the risk they want to avoid: a cluster change that restarts critical software while the robot is balancing could make it fall and damage itself or the customer site.
    3. 11:38 Ingleby describes the locomotion guard, a small admission webhook that queries the robot's control software for its state and rejects changes while it is walking.
    4. 14:43 Ingleby shows the override: an operator creates a ConfigMap that opens a short exemption window, and he says Teleport's audit trail records who did it.
    5. 28:06 Asked whether the webhook fails open or closed, Ingleby says it currently fails open and that they plan to fail closed as confidence grows.

    Not All Memory Is Equal: How To Properly Observe Memory Usage

    Braydon Kains, Roger Coll

    The speakers explain why host, node, pod and process memory metrics differ, tracing each to the Linux file it is read from and to how the kernel treats anonymous and file-backed pages. Using the OpenTelemetry Collector contrib binary in live demos, they show that much of its resident memory is file-backed data that can be reclaimed, and they recommend collecting system usage, container usage and working set together.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: You size memory limits or alert on memory in Kubernetes and want to know what RSS, usage and working set each count.

    1. 4:40 Roger Coll says the metrics differ because they are read from different files: system memory usage comes from /proc/meminfo, while the kubelet's node usage, RSS and working set come from the cgroup memory stats.
    2. 11:17 Braydon Kains says an OOM kill happens when there are no clean file-backed pages left to reclaim, not simply when a process is over its limit.
    3. 15:34 Roger Coll says the Collector contrib binary has 12,000 Go init functions, about 17 megabytes loaded into RAM, which run once at startup.
    4. 17:41 In a live demo, forcing a reclaim removes a large share of the contrib Collector's memory and much of it never pages back in; Braydon Kains adds that working set drops only after a reclaim classifies file pages as inactive.
    5. 23:14 Roger Coll says working set is the value Kubernetes treats as memory usage and the one the kubelet uses to pick pods to evict under node memory pressure.

    Project Lightning Talk - Project Overview

    Jorge Castro, Katherine Druckman

    Katherine Druckman and Jorge Castro open the project lightning talks with a guide for first-time attendees to the CNCF, the Linux Foundation and the project maturity levels. They recommend starting from a problem instead of a project, and show the landscape site and CLOMonitor live with Helm and Parsec.

    15 min slot · Level not listed · Lightning Talk

    Community and open source adoption

    Watch this if: this is your first KubeCon and you want to know what the CNCF maturity levels mean and where to start with the landscape.

    1. 2:16 Jorge Castro says there is a landscape MCP server that people can run in their own container and connect to an agent, to evaluate software and look up contribution stats and project health.
    2. 4:48 He says that organizations and individuals who donate a project to the CNCF give up control of it, the CNCF holds the trademark, and the project runs under vendor-neutral community processes.
    3. 7:20 Katherine Druckman says that to graduate a project has to show thriving adoption, committers from at least two organizations and documented governance, and that she believes it still has to earn the OpenSSF Best Practices badge.
    4. 9:45 She gives their basic guide: find the problem space, filter projects by maturity and category, check project health and security audits, test in a development environment, then contribute.
    5. 13:34 She shows Parsec, a sandbox project with a lower CLOMonitor score than Helm, and says that is not an indictment but an opportunity to get involved.
