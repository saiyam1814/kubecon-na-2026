    5,000 Nodes in Minutes, Twice in a Week: A Pattern for Fleet-Wide Node Changes

    Alex Yuskauskas

    Alex Yuskauskas describes patching the Copy-Fail and Dirty Frag kernel CVEs across NVIDIA's fleet with NodeWright, a controller he maintains for changing node operating systems. His main point is to ship every node change together with a check that fails when the change did not work, declared as a Kubernetes resource so kubectl shows the rollout status.

    5 min slot · Advanced · Lightning Talk

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to roll out a kernel or OS change to every node and prove it actually took effect.

    1. 0:18 Alex Yuskauskas recounts the Copy-Fail CVE workaround: a one-line modprobe drop-in file plus unloading the module with rmmod.
    2. 0:45 He explains the catch: if the module is in use, rmmod silently leaves it loaded, so nodes look fixed but are not until they reboot.
    3. 1:20 He says the NodeWright package ships the change and its check in the same image, and the check only passes once the module is gone from /proc/modules.
    4. 2:26 He describes rollout status as a fixed set of values (complete, in progress, erroring, blocked), which let the SRE team write an agent skill that stops and asks a human when a cluster does not complete.
    5. 3:05 He says they ran it across 16 clusters with thousands of nodes in half an hour, then folded Dirty Frag into the same package so the next CVE is a YAML change.

They announce container cluster for local multi-node Kubernetes clusters and demo building a controller and deploying it to a three-node cluster with Cilium.

    10 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    1. 1:12 Vince Prignano says Apple bootstraps every cluster declaratively with Kubernetes Cluster API and ships a signed, continuously enforced bill of materials, and asks what it would take to bring that same bill of materials to the MacBook.

    5. 6:53 Demo: Vince builds a controller image, creates a three-worker cluster with Cilium and the shared local image store, deploys with kubectl, then fixes a blocked app with a Cilium network policy.

    Stop Writing Secrets Into YAML: A Rotation-First Identity Pattern for Kubernetes

    Fabrizio Sgura

    Fabrizio Sgura proposes using workload identity first and issuing short-lived credentials only for dependencies that still require them. He walks through how Kubernetes, SPIRE, and OpenBao could support issuance, renewal, delivery, and revocation.

    30 min slot · Beginner · Session

    Security, identity and policy

    Watch this if: you want to replace static Kubernetes credentials a step at a time.

    1. 5:35 Sgura separates the roles of SPIFFE as a workload identity standard, SPIRE as its implementation, and OpenBao as a credential lifecycle manager.
    2. 10:26 He describes a layered design in which a workload first gets a short-lived identity document, and only uses a traditional credential if an external dependency needs one.
    3. 20:45 He explains that SPIRE issues a verifiable identity document after checking the workload, and gives X.509 and JWT as examples.
    4. 25:37 He describes using OpenBao for dynamic credentials, with External Secrets Operator or the Secrets Store CSI Driver handling delivery.
    5. 28:44 He recommends avoiding credentials when workload identity is enough, limiting the lifetime of any credentials issued, and designing for renewal and revocation.

    Why Your Monitoring Stack is a Security Risk

    Vinayak Goyal, Graham Helton

    Vinayak Goyal and Graham Helton say Kubernetes monitoring components may be granted more kubelet access than they need. They explain fine-grained authorization and recommend checking existing roles and vendor charts rather than assuming a cluster upgrade removes broad grants.

    30 min slot · Advanced · Session

    Observability and reliabilitySecurity, identity and policy

    Watch this if: You maintain Kubernetes monitoring agents and want to check whether their permissions match what they actually scrape.

    1. 1:09 The speakers explain that the kubelet first establishes the caller's identity and then asks the Kubernetes API server whether the caller may access the requested resource.
    2. 4:15 The speakers warn that a role granted for a simple health check can also authorize far more sensitive kubelet operations.
    3. 9:30 The speakers say API server audit logs may show the authorization check for direct kubelet traffic without showing the underlying action.
    4. 13:44 The speakers explain why finer-grained kubelet permissions were added alongside the older proxy permission, rather than replacing it outright.
    5. 16:33 The speakers recommend reviewing roles for unnecessary proxy access, adopting narrower permissions or updated vendor charts, and considering network policies as another layer.
