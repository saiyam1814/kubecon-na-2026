    A Decade of AI on Kubernetes: Kubeflow’s Journey to CNCF Graduation

    Valentina Rodriguez Sosa, Alexander Perlman, Christian Heusel, Shivay Lamba, David Aronchick

    Kubeflow co-founder David Aronchick recounts how the project started, and contributors describe its components, governance and what they say CNCF graduation required. The speakers then outline planned work, including Kubeflow Pipelines 3.0 changes such as removing the ML Metadata service, a unified Python SDK, trainer and notebook features, an MCP server and experimental Helm charts for the community distribution.

    30 min slot · Level not listed · Session

    Community and open source adoption

    Watch this if: you run or contribute to Kubeflow and want the origin story, what graduation involved, and the maintainers' stated plans for Pipelines 3.0, the SDK and agent support.

    1. 2:30 David Aronchick says the first Kubeflow release was deliberately small, with only a Jupyter notebook, a TensorFlow CRD and what later became KServe, and that pipelines came about six months later.
    2. 12:22 Christian Heusel says Kubeflow reached CNCF graduated status in July 2026, and that graduation required maintainers from at least two organizations per sub-project, independent adopters and a security and governance review.
    3. 20:56 Alexander Perlman says Kubeflow Pipelines 3.0 will consolidate the per-step driver pods into one pod per run, roughly halving the pod count, using Argo Workflows executor plugins.
    4. 22:13 He says 3.0 removes the ML Metadata microservice and database and moves execution tracking, artifacts, lineage and caching into the Pipelines API server.
    5. 29:24 Shivay Lamba describes an experimental Kubeflow MCP server that exposes trainer jobs to agents while applying the user's own Kubernetes permissions so the agent stays within bounds.

    One Workload to Rule Them All: Workload Aware Scheduling for Distributed AI Training on Kubernetes

    Andrey Velichkevich

    Andrey Velichkevich explains why scheduling distributed training one pod at a time can deadlock jobs and how the Kubernetes Workload and PodGroup APIs model them as a unit. He shows how Kubeflow Trainer exposes those capabilities through training runtimes and compares three scheduling policies on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: You run distributed training on Kubernetes and want to understand when pod groups and topology constraints matter.

    1. 0:48 Velichkevich illustrates how two training jobs can deadlock when the scheduler gives each job some GPUs but neither gets enough to start all its ranks.
    2. 4:44 Velichkevich distinguishes the Workload template from runtime PodGroups and shows how a PodGroup can express a minimum pod count and topology constraints.
    3. 7:10 Velichkevich introduces composite PodGroups for workloads with a hierarchy, where a parent can require a minimum number of child groups before scheduling proceeds.
    4. 10:12 Velichkevich explains the Kubeflow Trainer split: platform admins define runtime blueprints, and scientists use a Python SDK to submit jobs without managing Kubernetes deployment details.
    5. 15:17 In a local kind demo, Velichkevich sets up a comparison of default pod-by-pod placement, gang scheduling, and rack-constrained placement for a PyTorch job.

    OptimizationJob: Hyperparameter Optimization at Scale with Kubeflow Trainer

    Aniket Shaha, Ricardo Aravena

    The speakers present OptimizationJob, a new Kubeflow Trainer API that they say runs hyperparameter tuning with each trial as a TrainJob and no second system to install. They explain how it grew out of Katib, play a recorded demo, and list the limits of the first alpha phase and the roadmap.

    20 min slot · Level not listed · Session

    Accelerators and workload scheduling

    Watch this if: You tune hyperparameters on Kubernetes and want to know what the new OptimizationJob API in Kubeflow Trainer does today and what it leaves out.

    1. 3:13 The speaker says Katib works but means two installs, two APIs and metrics that live outside the job.
    2. 3:51 The speaker says the change that made this possible was putting training metrics in the TrainJob status, so tuning can live inside Trainer.
    3. 12:13 The speaker says trials are just TrainJobs, so they reuse runtimes, JobSet and gang scheduling, and each trial is queued by Kueue like any other.
    4. 13:04 The speaker says phase one is small on purpose, with random search, one objective, alpha feature gates that are off by default, and YAML only.
    5. 14:17 The speaker lays out the roadmap in three buckets, which are smarter search, more resiliency and a Python SDK.

    The Missing Front-Door to Your AI Supercomputer – Kubeflow Workspaces

    Mathew Wicks, Siyuan Zhang

    The speakers introduce Kubeflow Workspaces, which they describe as the second major version of Kubeflow Notebooks and say reached GA about five days before the talk. They show how admins define workspace options and access rules while users launch Spark, training and inference jobs from a workspace, and they lay out the roadmap and the end of life of v1.

    20 min slot · Level not listed · Session

    Accelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: You run notebooks for data scientists on Kubernetes and want to see what the new Workspaces version changes for admins and users.

    1. 2:24 The speaker introduces the two new custom resources, WorkspaceKind for the admin and Workspace for the user, with admin-defined options in between.
    2. 3:12 The speaker walks through redirects, filter rules and activity rules, which he says help admins manage image upgrades, valid combinations and idle workspaces.
    3. 9:32 The speaker says admins can define fine-grained access rules in a WorkspaceKind and the controller creates a dedicated service account per workspace.
    4. 10:45 The speaker walks through a demo that launches a PySpark job, a four-GPU PyTorch training job, a TPU run and inference from one CPU workspace.
    5. 15:31 The speaker says v1 is end of life with security patches until April next year, and that v1 and v2 can be installed side by side to migrate.
