    GitOps Without You Writing YAML: How Flux Grounds AI Agents in Real APIs

    Stefan Prodan

    Stefan Prodan argues that AI agents struggle more with Kubernetes YAML than with code because they lack a fast way to verify it, and presents the Flux Schema CLI plugin, a public catalog of custom resource schemas and an MCP server that he says give agents that feedback loop without a live cluster. He also describes the GitOps agent skills the Flux maintainers wrote and evaluated, and closes with the Flux roadmap and how to contribute to the catalog.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyAI agents and automation

    Watch this if: you use AI coding agents to write Kubernetes or Flux manifests and want to see how the Flux maintainers validate and ground that output.

    1. 1:01 Stefan Prodan says his conclusion from the Flux team's experiments is that generating YAML is harder for AI than generating code, because agents can test code in a fast loop but have no equivalent check for configuration data.
    2. 8:47 He introduces Flux Schema, a Flux CLI plugin that he says reproduces the Kubernetes API's validation rules offline, including label value rules and SOPS-encrypted secrets, and works on any Kubernetes YAML, not only Flux repositories.
    3. 13:27 He describes a public MCP server built on the project's ecosystem catalog of controller schemas, which he says reached one million requests a day and sees similar traffic from Codex, Claude and Copilot.
    4. 17:03 He says returning full OpenAPI schemas made agents hallucinate in long sessions, so the MCP server now exposes a grep schema tool that returns a compact format, after which he could generate hundreds of manifests.
    5. 26:48 He says the first agent skills were built with frontier models and failed on quantized open models he ran at home, so the team rewrote them, and he advises evaluating skills on weaker models.

    Lima as the Universal AI Sandbox

    Akihiro Suda

    Akihiro Suda of NTT presents Lima as a virtual machine sandbox for AI coding agents, arguing that agents' built-in sandboxes are weaker than VMs and citing reports of agents deleting home directories, installing hallucinated packages and being prompt-injected. He covers the project's history and adopters, the two ways to pair agents with Lima (agent inside the VM, or outside it through Lima's MCP server), a demo of the sync mode that asks before writing changes back to the host, and the features added in versions 2.0 through 2.3.

    30 min slot · Level not listed · Session

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run AI coding agents on your laptop and want to confine them to a virtual machine.

    1. 2:08 Suda says the sandboxes built into AI agents, such as Landlock on Linux and sandbox-exec on macOS, are not as strong as virtual machines, and that with Lima any damage stays inside the VM or the files mounted into it.
    2. 12:36 He lays out two options: run the agent, and optionally GPU-accelerated inference, inside the VM, or keep the agent outside and connect it to Lima through its MCP server.
    3. 13:37 He describes sync mode as an alternative to mounting, in which synced directories are written back to the host only after the user confirms.
    4. 14:40 Demo: he runs OpenCode inside a Lima VM against a model running in the VM, has it edit a file, and on exit is asked whether to accept the changes, declining to sync them back.
    5. 20:21 He lists what version 2.3 adds, including a native Windows driver based on the Host Compute System, real IP networking on Linux hosts, hiding secrets from agents with an ignore file, and blocking guest access to the host's loopback.

    No RAG, No Regrets: Letting an LLM Drive 30 EKS Clusters in Production

    Trevor Linton

    Trevor Linton describes how Mastercard built an agent harness to handle repeatable infrastructure work without retrieval-augmented generation. He walks through a cert-manager upgrade and explains how scoped tools, result filtering, token limits, and human approvals fit into the workflow.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You want to automate routine Kubernetes maintenance while keeping approvals and audit trails visible.

    1. 7:30 Linton says his team deploys its Node.js agent harness as a Kubernetes application and uses PostgreSQL to resume interrupted sessions.
    2. 10:16 Linton shows a cert-manager upgrade run that reads release notes, checks compatibility, proposes changes, and leaves merge and production change approvals to people.
    3. 11:39 Linton opens an audit trace that exposes individual tool calls and lets reviewers inspect the data given to the model.
    4. 16:46 Linton describes projections that filter or aggregate tool results before they enter the model context, using a SQL-like interface.
    5. 18:50 Linton explains how each task gets a hard token budget and iteration cap, with the remaining allowance available to the agent on each loop.

    Steering the Ship: Ask the Kubernetes Steering Committee

    Kat Cosgrove, Maciej Szulik, Paco Xu, Michael McCune

    Members of the Kubernetes Steering Committee introduce three newly elected members and answer audience and anonymous questions in an open Q&A. Most questions concern AI: the load that AI-generated pull requests, issues and vulnerability reports put on maintainers, which AI tools the project is piloting, and whether agents could take over maintenance work. The panel also covers what Kubernetes does well, the new members' goals and their technical wish lists.

    30 min slot · Level not listed · Session

    Community and open source adoptionAI agents and automation

    Watch this if: you contribute to or maintain an open source project and want to hear how Kubernetes leadership is handling AI-generated contributions.

    1. 3:35 Asked for the biggest near-term challenge, the moderator says many on the committee think it is AI-generated contributions and their cost in maintainer time, and other members add AI-generated issues and vulnerability reports.
    2. 6:44 Michael McCune names workload-aware scheduling as the technical challenge and, on the social side, a growing knowledge gap between senior developers and juniors who arrive with AI tools.
    3. 7:47 The moderator says the committee asked GitHub for a way to stop Copilot being summoned in repositories that have it disabled, and that the setting is now generally available.
    4. 10:25 A committee member says CodeRabbit is approved by the CNCF and available to repositories on request, and the moderator clarifies that it is used in kubernetes-sigs but is not enabled in the main kubernetes repository or the website.
    5. 24:37 On agents taking over toil, the moderator says there is no scenario in which pull request review is fully handed to an agent, and Maciej Szulik says the project will limit how many pull requests one person can open in a given time frame.

    The Race to Standardize AI Observability

    Liudmila Molkova, Trask Stalnaker

    The speakers show a demo application whose two services emit AI telemetry in three different schemas, and argue that a shared protocol without a shared structure breaks cost tracking and evals. They present the OpenTelemetry GenAI semantic conventions, the common instrumentation layer, and a Weaver-based conformance suite, and say stabilizing the conventions is their top priority.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automationAI inference and serving

    Watch this if: you instrument LLM or agent applications and want to know where the OpenTelemetry GenAI conventions stand and how to check your telemetry against them.

    1. 6:10 The speaker shows a token-count query over traces that reports two model calls when the demo made at least three, and says a dashboard built on it would not match the provider bill.
    2. 10:38 The speaker says each message in the conventions has a role and a list of parts, so attribute values share one shape as well as one name.
    3. 14:28 The speaker describes a common layer that traces, measures, and logs every inference call the same way, leaving each library as a thin wrapper.
    4. 22:30 The speaker shows a conformance report for one Python SDK, with a column per instrumentation and a row per convention attribute, where the basics line up and gaps appear beyond them.
    5. 26:45 The speaker says they want a first release candidate covering inference, agents, and tools this year and hope to stabilize it by KubeCon Europe next year.
