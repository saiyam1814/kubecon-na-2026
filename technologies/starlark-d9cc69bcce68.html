    Stop Templating YAML: Build Configuration Supply Chains with kpt and Porch

    Liam Fallon

    Liam Fallon introduces kpt as a tool built on the configuration-as-data principle, where a package is a directory of Kubernetes resource YAML that functions change in place instead of through templates. He says Ericsson uses kpt packages as blueprints for edge deployments that are pushed out through GitOps tools, and he skips the planned demo because of the hour.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you manage Kubernetes configuration with templates and want a five-minute introduction to how kpt treats configuration as data.

    1. 0:42 Fallon describes a kpt package as a directory of Kubernetes resources in YAML files, possibly nested, plus a Kptfile that defines what configuration to inject.
    2. 1:04 He says kpt changes the resources in place with no embedded templating, which in his view makes modifications and updates easier because no directives in the YAML go out of date.
    3. 1:45 He explains that the Kptfile lists a series of mutations, compared to pipes in Linux, and that kpt reads the package's YAML, passes it from one KRM function to the next and writes the result back to the file system.
    4. 2:50 He says there is a standard library of KRM functions such as search and replace, set namespace and annotations, and that custom functions can be written with an SDK or scripted in Starlark.
    5. 3:11 Fallon says what makes kpt powerful for Ericsson is that packages can spawn other packages and be orchestrated, so blueprints for edge deployments are pushed to GitOps frameworks such as Argo or Flux and deployed to thousands of edge nodes.
