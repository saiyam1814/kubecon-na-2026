    AI on Kubernetes Is Just a Pod With a GPU (and That's the Problem)

    Graziano Casto

    Graziano Casto compares deploying a web application with deploying a model on Kubernetes, starting from a plain Deployment that runs a vLLM container. He names three differences, which are whole-number GPU allocation, slow startup while model weights load, and requests that cost very different amounts of GPU work, and for each he points to projects he says address it.

    12 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You run web applications on Kubernetes and want a short orientation on what changes with model serving before choosing AI talks to watch.

    1. 0:36 The speaker shows what he calls the easiest way to deploy a model on Kubernetes: an ordinary Deployment running a vLLM container that serves a Llama 3.1 model.
    2. 3:01 He says a GPU is requested as a whole number, so a model that does not use a full GPU still leaves it overprovisioned.
    3. 3:43 He lists dynamic resource allocation in Kubernetes, HAMi for software-level enforcement and NVIDIA MIG for hardware partitioning as ways to share a GPU.
    4. 5:03 For slow startup he suggests relaxing liveness and readiness probes, caching downloaded weights on a persistent volume, and packaging weights as OCI artifacts mounted as image volumes.
    5. 6:57 He says round-robin load balancing does not fit chat workloads, and describes llm-d's KV-cache-aware routing, built on the Gateway API Inference Extension, as sending a conversation back to where its context lives.

    One Platform for AuthN and AuthZ: Keycloak Meets AuthZEN

    Yoshiyuki Tabata

    Yoshiyuki Tabata splits authorization into delegation and access control, explains that the OpenID AuthZEN standard defines the interface between a policy enforcement point and a policy decision point, and describes Keycloak's experimental AuthZEN support. He then demonstrates an MCP setup in which Envoy enforces decisions it requests from Keycloak, which acts as both the OAuth authorization server and the decision point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Keycloak and want to see how it can also make fine-grained authorization decisions for MCP tools through the AuthZEN API.

    1. 2:20 Tabata separates authorization into two phases: delegation, where one party grants limited authority as in OAuth, and access control, where a gatekeeper decides on each request, and says good authorization needs both.
    2. 6:36 He explains that AuthZEN standardizes the interface between the policy enforcement point and the policy decision point, so the enforcement point does not depend on a product-specific API.
    3. 10:35 He says Keycloak has experimental support for the AuthZEN Authorization API 1.0 starting with version 26.7, exposing the evaluation and evaluations APIs so it can act as a decision point.
    4. 13:55 He introduces the demo architecture: MCP Inspector as the client, Envoy in front of the MCP server as the enforcement point, and Keycloak as both OAuth authorization server and AuthZEN decision point.
    5. 25:41 In the demo he assigns a role to the user in Keycloak and the previously denied delete tool call succeeds with the same access token, which he uses to show that no separate synchronization with a decision point is needed.
