    CoHDI: Bridging Kubernetes and Disaggregated Memory for Memory-Aware LLM Inference

    Naoki Oguchi, Hidetsugu Sugiyama

    Naoki Oguchi and Hidetsugu Sugiyama present CoHDI, a CNCF Sandbox project they describe as letting Kubernetes attach pooled CXL memory and GPUs to worker nodes on demand, with a focus on giving LLM inference more room for KV cache. They walk through the allocation sequence for an LMCache pod, share early measurements, and outline plans to split prefill and decode across sites connected by an optical network.

    30 min slot · Advanced · Session

    Data, storage and stateAI inference and servingAccelerators and workload scheduling

    Watch this if: you run LLM inference on Kubernetes and want to see how pooled CXL memory could be attached to nodes as an extra KV cache tier.

    1. 2:50 Oguchi says KV cache capacity needs to scale independently from GPU compute, after listing the drawbacks he sees in adding GPUs, adding local DRAM, or evicting the cache to storage.
    2. 6:47 Oguchi explains the CoHDI flow: a scheduled pod triggers composition, the Dynamic Device Scaler evaluates the GPU and CXL memory needed, and the Composable Resource Operator requests them from the pool and attaches them to the worker node.
    3. 11:52 Oguchi shows cache metrics where resubmitting the first prompt raises the blocks read from the second tier from 105 to 135, which he reads as KV cache kept in CXL memory being reused.
    4. 12:44 Oguchi reports first-stage results in which attached CXL memory was 10 times faster than SSD for random reads and 18 times faster for writes, and says LMCache still needs optimization for CXL access.
    5. 18:27 Sugiyama says GPU overprovisioning at the decode site remains a problem and describes decode nodes with few GPUs and large CXL memory pools composed by CoHDI as his answer.

    Longhorn: Intro, Deep Dive and Q&A

    Shuo Wu, David Ko

    David Ko introduces Longhorn, a cloud native distributed block storage system for Kubernetes, and shares its release cadence, adoption numbers and contributor growth. He then compares the V1 and SPDK-based V2 data engines, explains snapshots, backups, disaster recovery and live upgrades, and outlines the 1.13 and 1.14 roadmap with early RDMA benchmarks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run Longhorn or need block storage on Kubernetes and want to compare the V1 and V2 data engines.

    1. 2:32 Ko says Longhorn runs on any compatible Kubernetes cluster and Linux distribution, including Talos, and ships minor releases every four months in line with Kubernetes.
    2. 4:58 Ko reports adoption up about 21% in six months to roughly 276,000 nodes and 60,000 clusters, from Longhorn's public usage metrics.
    3. 12:22 Ko explains that the V2 data engine uses SPDK in user space with NVMe over Fabrics, plus an interrupt mode so it can share CPU with applications.
    4. 19:21 Ko walks through V2 live upgrades, which move the volume target to another node so I/O continues while the upgrading node's instance manager restarts.
    5. 23:44 Ko lists the 1.14 plans, including RDMA support, I/O QoS, a new data engine for strict-local volumes and application-consistent snapshots and backups.

    Many Clusters, One GPU Pool: Locality-Aware Scheduling and Data Delivery With Kueue and Dragonfly

    Yiqing Wang, Adam Buran

    Yiqing Wang and Adam Buran describe how Roblox shares GPU capacity across clusters using Kueue while leaving each cluster to check its own capacity. They explain how a locality-aware dispatcher chooses clusters and how Dragonfly caches training data and checkpoints near the jobs that use them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingData, storage and state

    Watch this if: You operate GPU clusters in more than one location and want to share capacity without repeatedly pulling the same datasets across regions.

    1. 6:55 The speakers describe two levels of MultiKueue admission: the hub checks team quota, then the candidate clusters check node capacity and the first to admit the job runs it with KubeRay.
    2. 8:15 The speakers explain how the dispatcher first filters for requirements such as GPU type and full-job fit, then prefers the data region for a limited time before considering other regions.
    3. 9:19 The speakers explain how Roblox separates pool-wide guaranteed quota from cluster-level borrowing and uses preemption to reclaim borrowed GPUs when a guaranteed job arrives.
    4. 14:51 The speakers describe Dragonfly looking for file pieces in the local cache, other peers, and seed peers before falling back to Amazon S3.
    5. 15:55 The speakers report that half of the data served came from node-local cache and another 43 percent from peers in the same cluster, leaving 7 percent served from Amazon S3.

    Time to Learn New Tricks to Improve Performance on DRA-Managed Devices

    Alexander Kanevskiy, Sara Qasmi

    Sara Qasmi of T-Systems shows measurements from LLM serving on two GPU server types, where she says the default Kubernetes device placement often lost bandwidth or added latency compared with hand-aligned devices. Alexander Kanevskiy of Intel explains why a NUMA number no longer describes modern CPU and PCI topology, and walks through newer Dynamic Resource Allocation features he says help express the alignment a workload needs.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you place GPUs, NICs and CPUs for inference on Kubernetes and want measured examples of what device alignment changes.

    1. 5:23 Qasmi reports that GPU and NIC pairs aligned on the same PCI root reached full RDMA bandwidth on one platform while other pairings got 38%, yet on the second platform NUMA alignment was enough.
    2. 6:50 She says the default claim picked the wrong GPU pair in five of five runs on a busy node, and that NCCL's own peer-to-peer default also limited bandwidth until it was changed.
    3. 10:08 She measures CPU to GPU round-trip latency and says default pods were 33% slower, with eight of ten landing on the wrong socket, which an NRI topology plugin corrected.
    4. 14:56 Kanevskiy argues that a NUMA number only maps to the memory controller's mode of operation and is now a virtual value that does not describe physical topology.
    5. 20:38 He presents list attributes and derived attributes in DRA as ways to describe topology and compare values across drivers, and warns that a claim with no overlapping solution leaves the pod unscheduled.

    Two Drivers, One Topology: GPU:NIC Rail Alignment for RDMA VMs with KubeVirt DRA

    Jian Li, Alay Patel, Kazuki Sato

    Kazuki Sato of NTT DOCOMO BUSINESS, Jian Li of SK Telecom and Alay Patel describe how a multi-site GPU platform on KubeVirt moved from a manual workaround to Dynamic Resource Allocation claims that pair each GPU with an RDMA NIC under the same PCIe root. They show a recorded benchmark comparing aligned and misaligned VMs, explain the Multus change they are proposing upstream, and outline what KubeVirt's DRA support covers today and what is planned.

    15 min slot · Level not listed · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you run GPU virtual machines with RDMA networking on KubeVirt and need each GPU paired with the right NIC without pinning devices by hand.

    1. 2:07 Sato describes the earlier workaround: filling a node with placeholder pods that each hold one GPU or NIC and deleting only the ones holding the wanted pair, which had to be redone VM by VM after every node or VM restart.
    2. 5:10 Li explains that the GPU driver and the SR-IOV NIC driver both publish the standard PCI root attribute, so one resource claim with a GPU request, a VF request and a match constraint lets the scheduler allocate them as a pair.
    3. 7:15 He says upstream KubeVirt network DRA could not consume a VF wired through a Multus network, so they added a feature gate that takes the VF from the resource claim and leaves the existing CNI chain unchanged.
    4. 10:21 In the recorded demo Sato compares two four-GPU VMs: he reports about 200 Gbps of RDMA bandwidth on the misaligned VM and 391 Gbps on the aligned one, with placement as the only difference.
    5. 12:33 Li says the next gap is that CPUs and huge pages are still placed by the kubelet without topology hints from DRA devices, so a VM can get its GPU and NIC on one socket and its memory on another.

    What the Docs Don't Tell You: A Telecom's Year Operating Cache-Aware LLM Inference on Kubernetes

    YoungJoon Jeong, Seol Heo

    The speakers describe how LG Uplus raised its KV cache hit rate from 71.6% to 95.4% on 16 vLLM replicas by reordering prompts, routing each request to the pod that holds its prefix with llm-d, and adding a CPU memory tier for evicted blocks. They say time to first token is queue time plus prefill time, so once prefill was cached they tuned concurrency, and they report that splitting prefill and decode cut inter-token latency while lowering throughput.

    30 min slot · Advanced · Session

    AI inference and servingObservability and reliability

    Watch this if: You serve LLMs for multi-turn or agent traffic on Kubernetes and want measured numbers on what prefix-aware routing, cache tiers and prefill/decode separation each bought.

    1. 4:51 YoungJoon Jeong says vLLM hashes prompt blocks in a chain, so one small change near the start, such as a timestamp in the system prompt, turns every later block into a miss; his advice is to put the stable part first.
    2. 9:07 He frames KV cache hit rate as ceiling times placement times survival, which he calls their own framing and not an upstream metric, with a different owner for each factor.
    3. 13:05 Seol Heo says their initial hit rate was 71.6% because routing on pod load sent turns of one conversation to different pods, duplicating prefixes in GPU memory and causing evictions.
    4. 17:38 He says that after prefill was optimized the queue became the bottleneck, and setting vLLM's max number of sequences to 24 brought time to first token from 2.09 to 0.39 seconds in their benchmark.
    5. 20:11 He reports that separating prefill and decode pools, with KV transfer over InfiniBand RDMA through NIXL, cut inter-token latency from 69.8 to 19.5 milliseconds while generation throughput fell about 30%.
