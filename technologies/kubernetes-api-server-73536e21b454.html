    Engineering Kubernetes for the Next Era of Workloads

    Mike Stefaniak

    Mike Stefaniak describes bottlenecks AWS found when running large Kubernetes clusters and says the team contributed fixes upstream. He walks through watch-cache and scheduler changes, accelerator-aware provisioning with Karpenter, and parallel image unpacking in containerd.

    5 min slot · Level not listed · Keynote

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run large GPU clusters and want concrete examples of upstream fixes from image unpacking to accelerator placement.

    1. 0:47 Stefaniak says AWS replaced a long-held Kubernetes API server watch-cache lock with a lazy snapshot, cutting writer wait from over half a second to 2 ms in its million-pod benchmark.
    2. 1:03 Stefaniak says a new Horizontal Pod Autoscaler selector store removed a read/write bottleneck, letting AWS run four times as many HPA workers in its largest clusters.
    3. 1:21 Stefaniak says an incremental scheduler cache avoided rebuilding volume reference counts and that AWS saw scheduling stay above 300 pods per second in its largest clusters.
    4. 2:28 Stefaniak explains that Dynamic Resource Allocation can describe GPU and network topology, and says Karpenter can now model devices for instances it has not launched yet.
    5. 3:48 Stefaniak says parallel layer unpacking in containerd brought a 10 GB image pull from about two minutes to under 45 seconds in AWS's testing.

    Every Kubernetes Object Deserves an Identity: The SPIFFE Broker API

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    30 min slot · Advanced · Session

    Observability and reliabilitySecurity, identity and policy

    Watch this if: You maintain Kubernetes monitoring agents and want to check whether their permissions match what they actually scrape.

    1. 1:09 The speakers explain that the kubelet first establishes the caller's identity and then asks the Kubernetes API server whether the caller may access the requested resource.
    2. 4:15 The speakers warn that a role granted for a simple health check can also authorize far more sensitive kubelet operations.
