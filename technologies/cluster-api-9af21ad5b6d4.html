    Cloud Native: Built by Humans, Engineered to Evolve

    Jeffrey Sica

    Jeffrey Sica argues that cloud native can adapt to AI because the people who maintain its projects keep changing how they work without abandoning human review. He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    10 min slot · Level not listed · Keynote

    Community and open source adoptionKubernetes internals and runtimes

    Watch this if: you want to connect AI agent workloads to the reliability practices and contribution norms cloud native teams already use.

    1. 2:55 Sica asks the audience to see the people who keep showing up behind each logo in the cloud native landscape.
    2. 4:25 Sica says maintainers responded to AI-generated contributions by writing policies for what a good contribution looks like and what they expect the submitting human to review.
    3. 5:37 Sica uses the term agent speed for the number of machine actions between human decisions and argues that the change matters for software architecture.
    4. 6:30 Sica points to small blast radii, fast iteration and rollback, sandboxing, and APIs as reasons cloud native systems can adapt to agent workloads.
    5. 7:59 Sica argues that Kubernetes fits training and inference because they are distributed systems problems, not because Kubernetes was originally built for AI.

    Code, Containers, and Clusters: The Next Chapter of Apple's Container Framework

    Kathryn Baldauf, Vince Prignano

    Kathryn Baldauf and Vince Prignano of Apple walk through Apple container, which runs each Linux container in its own lightweight VM on a Mac, plus container machines for persistent Linux dev environments. They announce container cluster for local multi-node Kubernetes clusters and demo building a controller and deploying it to a three-node cluster with Cilium.

    10 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    Watch this if: you develop for Kubernetes on a Mac and want a local multi-node cluster that uses your locally built images without pushing them.

    1. 1:12 Vince Prignano says Apple bootstraps every cluster declaratively with Kubernetes Cluster API and ships a signed, continuously enforced bill of materials, and asks what it would take to bring that same bill of materials to the MacBook.
    2. 1:59 Kathryn Baldauf says Apple container, written in Swift for Apple silicon, runs each Linux container in its own lightweight VM, shares only the files you choose, and boots in under a second.
    3. 2:48 She introduces container machines: persistent Linux environments built from OCI images that share your Mac user and home folder, which she pitches as a good place for agent sessions.
    4. 4:06 She announces container cluster, which creates a real Kubernetes cluster bootstrapped by kubeadm, with each node as its own VM and a default CNI or one you bring.
    5. 6:53 Demo: Vince builds a controller image, creates a three-worker cluster with Cilium and the shared local image store, deploys with kubectl, then fixes a blocked app with a Cilium network policy.

    Data-Driven Platform Guardrails: What 16,500 Incidents Tell You to Automate First

    Henrique Santana, Henrique Dalssaso

    Henrique Santana and Henrique Dalssaso walk through the top root causes they found in more than 16,000 Kubernetes incidents, including IP exhaustion, auth failures and node provisioning problems. For each one they suggest platform guardrails to automate, and they explain how to run the same analysis on your own incident data.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you want a list of common Kubernetes incident root causes and the guardrails these speakers suggest automating for each.

    1. 1:35 The speakers describe their dataset as more than 16,000 incidents across many Kubernetes clusters from January to mid-May, grouped with AI and then reviewed by hand. They say DNS did not make their top 10 root causes.
    2. 3:57 They say about a third of one top pattern was pods with no IP address available, from small or shared subnets, and suggest Cilium multi-pool IPAM and broader Karpenter node pools.
    3. 6:59 For auth failures they separate missing permissions, RBAC that was never bound to the pod, and policies on the target endpoint, and suggest Kyverno policies, projected service account tokens and cert-manager.
    4. 16:20 For node provisioning failures, which they put at almost 15% of incidents, they suggest setting kube-reserved and system-reserved, Cluster API machine health checks and Karpenter node auto repair.
    5. 20:59 To repeat the analysis on your own data, they suggest classifying by what actually failed rather than the symptom, ranking by frequency, and asking whether the platform, the app team or both can fix it.

    From Proxy to Platform: Building a Multi-Tenant AI Gateway

    Dibyo Mukherjee, Tushar More

    The speakers describe how Adobe turned an internal model proxy into a shared gateway with team-scoped access and self-service configuration. They explain how customer-facing agents changed the way they attributed spending and which safeguards they put around platform upgrades.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivity

    Watch this if: several teams need to share an AI gateway without sharing model access, logs, or spend limits.

    1. 6:46 The speakers explain how teams share a gateway while using separate model deployments, cloud accounts, and scoped keys.
    2. 8:23 They walk through a console that lets tenant admins add models and set fallback rules and budgets without a platform ticket.
    3. 11:08 They explain how internal applications provide a customer identity so budgets and rate limits can follow the customer rather than a shared agent key.

    5. 15:54 They describe using KEDA to scale the proxy by in-flight requests and setting a grace period to let requests drain during rollouts.

    One Kubernetes, Different Environments: Closing the Portability Gaps

    Dilpreet Bindra

    Dilpreet Bindra argues that conformant Kubernetes clusters do not guarantee that applications will behave the same across environments. He introduces the Workload Conformance Working Group and describes VM API as a way to manage virtual machines through a common Kubernetes interface.

    5 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    Watch this if: you want the distinction between Kubernetes cluster conformance, workload portability, and a common API for virtual machines.

    1. 1:03 Bindra says cluster conformance does not guarantee that an application behaves consistently across infrastructure and configurations.
    2. 1:27 Bindra announces the Kubernetes Workload Conformance Working Group with SIG Apps and SIG Architecture, and says it will define and verify expected workload behavior.
    3. 2:30 Bindra argues virtual machines should be first-class Kubernetes resources and says declarative APIs should account for their distinct lifecycle and I/O needs.
    4. 3:08 Bindra uses Cluster API as a precedent and describes VM API as a provider-neutral interface for managing VMs without giving up hardware capabilities.
    5. 3:26 Bindra connects VM API to agent workloads that need isolation, state management, and I/O control, and says the project has joined the CNCF Sandbox.

    Standardized Yet Adaptable: How Nutanix is Evolving Cluster API with CAREN

    Deepak Goel

    Deepak Goel explains how declarative cluster resources and reusable ClusterClass templates made Kubernetes fleet management easier, but says complex YAML patches became hard to maintain. He presents CAREN as a way to write reusable Go hooks for cluster customization without forking the base templates.

    5 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    Watch this if: you manage Kubernetes fleets and need more flexibility than shared templates alone can give you.

    1. 0:41 Goel recalls the scale Mesosphere handled and describes its pivot from Mesos to Kubernetes.
    2. 2:34 Goel explains how Cluster API can represent clusters as Kubernetes resources and make lifecycle management declarative.
    3. 3:15 Goel describes how ClusterClass lets teams reuse configuration and attach custom logic through lifecycle hooks.
    4. 3:41 Goel uses add-on installation and upgrades to illustrate how custom logic written as YAML patches can become fragile.
    5. 4:09 Goel introduces CAREN's Go implementation of Cluster API runtime extensions and says it avoids having to fork or patch base templates.
