    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

    Four Resources, One Object: Surviving Gateway API After Ingress NGINX

    Sitesh Pattanaik

    Pattanaik demonstrates how replacing Ingress NGINX annotations with separate Gateway API and Envoy Gateway objects can leave route policies out of sync. He shows how his example uses a resource graph to manage those objects together and compares that approach with other ways to manage their lifecycle.

    30 min slot · Advanced · Session

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: you are migrating from Ingress NGINX and need a way to keep routes and their policies from drifting apart.

    1. 6:19 Pattanaik identifies the four resources in his example: an HTTPRoute plus security, backend traffic, and client traffic policies.
    2. 10:43 He explains that a policy's target reference does not tell the route about the policy or require it to share the route's lifetime.
    3. 20:47 He describes the platform team owning a ResourceGraphDefinition while an application team supplies inputs such as the hostname.
    4. 27:41 He shows that the graph manages the route and its authorization policy together when he switches to a replacement resource.
    5. 29:13 He compares Helm, kro, Crossplane, and a custom operator, asking which component will manage the full resource graph as a unit.

    Guardrails, Not Gatekeepers: Envoy Gateway in the Enterprise

    Matthew Slater

    The speaker, from the Kubernetes platform engineering team at JPMorgan Chase, describes bringing Envoy Gateway and Gateway API to application teams in a regulated enterprise after the ingress-nginx retirement. He covers which parts of the API his team blocks, how policy denials explain the fix, and workarounds for load balancers and enterprise identity providers.

    10 min slot · Level not listed · Session

    Networking and connectivitySecurity, identity and policyPlatform engineering and developer experience

    Watch this if: You are a platform engineer moving teams from ingress-nginx to Gateway API in a company with strict security and cloud rules.

    1. 4:08 He recommends blocking users from creating roles that grant themselves access to EnvoyPatchPolicy and EnvoyExtensionPolicy, since patching xDS directly would bypass every other rule.
    2. 4:56 He says every rule in their shared Gatekeeper policy library must carry a message and a remedy, so a denied user sees why and how to fix it.
    3. 7:09 He describes separating load balancing from the Envoy deployment: the Envoy service is set to NodePort and Terraform-managed load balancers map target groups to those ports.
    4. 8:57 He shares identity provider workarounds: append extra request parameters to the authorization endpoint, use the resources field for ADFS, and use a private client with a secret because public clients did not work.
    5. 11:50 He sums up five things to copy: write constraints down first, map roles onto the four-tier RBAC model, bring security in as a design input, ship safe defaults teams can change, and budget for teaching.

    30 min slot · Level not listed · Session

    Data, storage and stateDelivery, GitOps and release safety

    Watch this if: you run Kafka on Kubernetes with Strimzi and want to know what changed after 1.0 and what the maintainers plan next.

    1. 2:16 Scholz says cert-manager integration is in Strimzi 1.3 as early access, and notes it needs a private CA because certificates must carry internal Kubernetes DNS names.
    2. 6:49 He says internal cluster encryption can now be turned off, with service account tokens added as an alternative to mTLS so that authorization still works.

    5. 19:51 He introduces gatekeeper plugins, hooks called before and after reconciliation that he says can enforce or enrich custom resources, inspired by admission controllers, Kyverno and Open Policy Agent.

    ListenerSets: Ingress → Gateway API

    Karol Szwaj, Isaac Wilson

    Two Envoy Gateway maintainers compare Envoy Gateway's Merged Gateways feature with ListenerSets in Gateway API as ways for many teams to share one proxy fleet when moving off Ingress. They recommend that Envoy Gateway users switch to ListenerSets and say they plan to deprecate Merged Gateways.

    10 min slot · Level not listed · Session

    Networking and connectivity

    Watch this if: You share one ingress proxy between many teams and want to know whether to use Merged Gateways or ListenerSets in Envoy Gateway.

    1. 1:00 Karol Szwaj contrasts Ingress, where any team could claim any hostname and annotations shared one proxy configuration, with Gateway API's role split through Kubernetes RBAC and explicit cross-namespace attachment.
    2. 1:46 He describes Merged Gateways, added to Envoy Gateway three years ago and enabled by setting mergeGateways to true on the EnvoyProxy resource linked to a GatewayClass, so all Gateways share one Envoy fleet, IP and load balancer.
    3. 3:12 He lists the trade-offs: one fleet to scale and simpler DNS, but port, hostname and protocol must not collide across Gateways, fleet settings are not per team, and failures have a larger blast radius.
    4. 4:23 Isaac Wilson says ListenerSets have been standard in Gateway API since v1.5 and let teams attach their own listeners to a single shared Gateway.
    5. 6:33 He says Envoy Gateway now recommends that users move to ListenerSets because the maintainers plan to deprecate Merged Gateways.

    LTS, EOL, CVEs: Solutions for Stress-Inducing Scenarios

    Bridget Kromhout, Lachlan Evenson

    Bridget Kromhout and Lachlan Evenson of Microsoft discuss three pressures of running open source in production: long-term support for Kubernetes, projects reaching end of life, and the rising rate of vulnerabilities. They argue for upgrading regularly, looking for migration paths when a project ends, proposing changes upstream instead of carrying private forks, and judging patches by whether a flaw is exploitable in context.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyCommunity and open source adoption

    Watch this if: you run Kubernetes platforms and need arguments for regular upgrades, handling end-of-life projects and a sane approach to CVE patching.

    1. 7:51 The speakers say the long-term support discussion showed that users objected less to change than to breaking changes in every Kubernetes release, which led to work on better upgrades.
    2. 10:28 Evenson says their provider platform will start upgrades on behalf of customers, and Kromhout adds that this begins next summer.
    3. 13:12 Evenson says ingress-nginx had asked for maintainers for several years before its end of life, and points to Gateway API and other ingress controllers as paths forward.
    4. 17:08 Kromhout calls forking a trap, accepts a soft fork meant for upstreaming, and the speakers describe an etcd change whose authors became upstream maintainers.
    5. 20:54 Evenson calls chasing zero CVEs a trap as vulnerability rates rise, and points to VEX and OpenVEX for stating whether a flaw is exploitable in a given context.

    Open Source Has a Human Deficit. Here's How We Fix It.

    Catherine Paganini

    Catherine Paganini argues that open source is short on maintainers and that welcoming underrepresented groups is a way to make projects more sustainable. She introduces Merge Forward, a CNCF community group with groups such as Women in Cloud Native and Deaf and Hard of Hearing, and invites people to join as members, mentors or allies.

    5 min slot · Any Level · Lightning Talk

    Community and open source adoption

    Watch this if: you want to help more people from underrepresented groups become open source contributors and maintainers.

    1. 0:07 Catherine Paganini recalls a March 2022 warning to the Kubernetes steering committee that etcd had only one active and two occasional reviewing maintainers.
    2. 0:26 She points to ingress-nginx, which she says was wound down and stopped getting security patches, as another case of the same maintainer pattern.
    3. 1:25 She says more maintainers means more people, and that open source has overlooked many who do not see themselves represented and so see no path in.
    4. 2:41 She argues that people with similar backgrounds share unchallenged assumptions, which she links to missed edge cases and shipped defects.
    5. 3:23 She lists the Merge Forward groups, from Deep Roots and Women in Cloud Native to Neurodiversity and Deaf and Hard of Hearing, and points to the upcoming 2027 buddy program.

    Platform as Context: Evolving Our IDP for AI Agents

    Gang Luo

    Gang Luo of Electrolux Group explains how his team extended their internal developer platform so AI agents can use it as context through MCP tools. He shares the context categories they defined, a switch to GraphQL, and benchmarks where he reports lower token use and fewer tool calls.

    25 min slot · Intermediate · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    1. 1:56 Luo describes the starting point: about 400 developers, an average of six SREs, and an IDP where developers pick templates, get approval and have infrastructure provisioned for them on golden paths.
    2. 3:50 Because developers work in the IDE and terminal, his team added MCP read and write tools on top of the IDP so agents can read and provision the infrastructure it manages.
    3. 6:41 He lists the context agents need, starting with ownership, then infrastructure, deployment through GitHub Actions and telemetry, and says the IDP should hold only what is needed and point to the other sources.
    4. 9:29 He says moving the MCP tools from static APIs to GraphQL cut the tokens an agent used for discovery by about 80% from roughly 17K.
    5. 12:19 In benchmarks comparing an agent with GitHub alone against GitHub plus the IDP, he reports one task using 50% fewer tool calls and 65% fewer tokens, while noting some experiments got worse.

    Securing Rural Colorado with Open Source: Running a Student-Led SOC on Kubernetes

    Maciej Wal

    Maciej Wal describes how the Cybersecurity Center at Metropolitan State University of Denver replaced a vendor's security monitoring service, first with four virtual machines and then with a Kubernetes platform that he says he runs as the one full-time staff member. He covers the outages and adoption problems along the way, and how students learn log analysis and GitOps on the platform that monitors public sector partners.

    30 min slot · Any Level · Session

    Security, identity and policyObservability and reliability

    Watch this if: you are a very small team weighing Kubernetes for a security monitoring service, or want ideas for teaching students with real infrastructure.

    1. 3:19 The speaker says that after the vendor ended the service he built a replacement in about 66 days on four virtual machines, with WireGuard, single-node OpenSearch and a new ticketing tool.
    2. 6:45 The speaker explains picking the Kubernetes stack from the CNCF landscape, including Keycloak, Argo CD, OpenTofu and Fluent Bit, and says it cost around $1,000 a month.

    5. 13:48 The speaker describes a student workshop on Argo CD, Envoy Gateway, cert-manager and GitHub Actions that ended with deploying a Minecraft server through GitOps.

    SIG Network Intro and Updates

    Surya Seetharaman, Guilherme Cassolato, Austin Abro, Bowei Du

    Four SIG Network contributors review what the SIG owns and what changed in 2026 across Kubernetes core and its subprojects, including kube-proxy's planned move to nftables as the default mode, Gateway API releases, Cluster Network Policy reaching v1beta1 and the status of smaller subprojects. They also report findings from the SIG's first structured survey of its 22 subprojects, and Austin Abro describes how he used AI to make his first contribution.

    30 min slot · Level not listed · Session

    Networking and connectivityKubernetes internals and runtimes

    Watch this if: you want a year's worth of Kubernetes networking changes in one session, or you run kube-proxy and need to plan for nftables.

    1. 3:40 Bowei Du mentions a new proposal for network-isolated pods with no networking by default, which he links to agent sandbox use cases, and lists deprecations of external IPs, kube-proxy IPVS mode and the Endpoints API.
    2. 4:45 Austin Abro explains the opt-in TCP userspace proxy that lets nftables mode serve NodePorts on localhost, and advises setting the kube-proxy backend explicitly before the default changes to nftables in 1.40.
    3. 9:57 Surya Seetharaman announces the v1beta1 release of Cluster Network Policy, which unifies the former admin and baseline CRDs, and notes the work began in March 2020.
    4. 16:11 Guilherme Cassolato says the SIG ran its first structured survey of its 22 subprojects and learned that AI is driving many agendas to the point of overlap, some projects have only one or two maintainers, and maintainers want faster API review.
    5. 20:47 Abro recounts using AI to learn kube-proxy internals for his localhost NodePort contribution, and says the maintainers' insistence on not breaking existing users kept the feature opt-in.
