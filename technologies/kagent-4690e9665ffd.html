    I Built an AI Running Coach: A Personal kagent Agent in Production

    Adam Gordon Bell

    Adam Gordon Bell of Pulumi tells how he built a personal AI running coach that messages him in Slack, first as a Lambda function and then as a single long-running kagent session on a small Kubernetes cluster, to train for a trail race against a friend. He describes the design choices he says worked for him, shows his own training graphs from the year, and encourages the audience to build small agents for their own needs.

    30 min slot · Any Level · Session

    AI agents and automation

    Watch this if: you want a small, concrete example of a long-running personal agent on Kubernetes, told as a story with the design choices that kept it simple.

    1. 9:15 Bell describes his first version: an AWS Lambda called by a Strava webhook, a scraper for his Peloton treadmill data, a morning cron job, DynamoDB for storage and one LLM call that posted to Slack.
    2. 12:22 He shows the kagent version, an agent defined as one Kubernetes resource deployed with Pulumi, where the Strava hook, the Peloton sync and a morning cron all post messages into the running session over the agent-to-agent protocol.
    3. 13:54 His main lesson is to use deterministic code wherever possible: the MCP tool parses raw run data and hands the agent only the date, duration, incline and heart rate zones.
    4. 15:25 He keeps one session going indefinitely and handles memory with a custom compaction rule under fixed headings, plus tools that let the agent write to a plan file and an athlete file.
    5. 27:47 He reports finishing the 30K race in 4:30 against his friend's 4:41 from the previous year, after a year in which he says his weeks with three or more runs almost doubled.

    Just Keep Swimming: Benchmarking OSS Agent Memory on Kubernetes with OpenTelemetry

    Henrik Rexed

    Henrik Rexed describes benchmarking five open source agent memory servers (Mem0, MemOS, MemPalace, Zep and his own MemKeys) behind kagent agents on Kubernetes, with OpenTelemetry metrics he says he contributed to most of them. He reports results for an SRE troubleshooting scenario and a multi-agent coding scenario, and says which approach suited each in his tests.

    30 min slot · Advanced · Session

    AI agents and automationObservability and reliability

    Watch this if: you are choosing a memory backend for agents on Kubernetes and want to see how one benchmark compared token use, resource use and recall.

    1. 4:06 The speaker walks through the memory architectures he compares: plain embeddings, vector plus graph, knowledge graph, temporal knowledge graph, and a key-based store.
    2. 12:37 The speaker says he built one generic MCP server in front of all the memory backends so the kagent agent setup stays the same across runs.
    3. 13:36 The speaker explains the SRE scenario: a cold run with empty memory, then a warm run with memory populated, measuring the difference across injected Kubernetes and Gateway API failures.
    4. 19:56 The speaker reports that in the SRE scenario MemOS, Zep and MemPalace gained from memory on the warm run, while Mem0 and MemKeys did worse, which he puts down to retrieving wrong or too many facts.
    5. 22:36 The speaker concludes that embedding or text search suited the SRE case in his tests, while a key store helped the coding crew that already works with project metadata.

    Lessons Learned Sandboxing Agents with kagent

    Peter Jausovec, Nina Polshakova, Eitan Yarmush

    Peter Jausovec and Eitan Yarmush of Solo.io, the two speakers heard in the recording, walk through the sandboxing approaches they tried for kagent and say each one still kept an idle agent's pod running or tied identity to the pod. They explain why kagent 1.0 was rebuilt on Agent Substrate, list five lessons from that work, and demo Claude Managed Agents sessions running in sandboxes on their own cluster.

    30 min slot · Any Level · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing how to sandbox AI agents on Kubernetes and want to hear what one team found lacking in pod-per-agent setups.

    1. 3:40 Jausovec says they tried four things before Agent Substrate: their own pod-per-agent runtime, Anthropic's Sandbox Runtime, Agent Sandbox and NVIDIA's OpenShell, and that each solved only part of the problem.
    2. 9:08 Jausovec gives the reasons for Agent Substrate: idle agents are snapshotted to object storage and hold no compute, the Kubernetes API is off the hot path, restores take milliseconds, and actors are sandboxed with default-deny networking.
    3. 10:04 Yarmush tells how Solo started building an internal sandbox layer called Moat, then joined Google's Agent Substrate work instead, and says kagent 1.0 is now based entirely on Agent Substrate.
    4. 17:42 Yarmush starts the takeaways: isolation is table stakes and pause and resume is the hard part, every control must sit outside the agent, identity follows the actor, a suspended agent is stored data, and the sandbox runtime becomes a data format.
    5. 22:56 Demo: Jausovec creates two Claude Managed Agents sessions whose sandboxes run on his cluster, shows that one session cannot read the other's file, and shows a blocked request succeed after he applies an egress policy.

    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    Christian Posta

    Christian Posta says long-lived agent sessions need an identity and state that can outlast any one Kubernetes pod. He demonstrates how Agent Substrate suspends and resumes actors on shared workers and controls their access to outside services.

    30 min slot · Any Level · Session

    AI agents and automationKubernetes internals and runtimes

    Watch this if: You need to run agents that pause and resume without keeping one Kubernetes pod per session.

    1. 8:16 Posta says an actor's identity and policy should be independent of the pod so the actor can keep its state when it isn't running.
    2. 11:06 Posta explains that an actor's identity persists for the actor's lifetime and that network calls from the sandbox require policy approval.
    3. 18:22 Posta suspends one actor in the demo, freeing enough capacity in the same worker for another actor to run.

    5. 28:47 Posta distinguishes Agent Substrate's actor runtime from kagent, which can use conversation and user context to decide when to suspend or resume an actor.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.

    Transforming Retail with AI: From Automation to Autonomous Decisioning

    Arunkumar Amaran

    The speaker gives an overview of how he sees retail moving from automated processes to agents that make pricing, supply chain and customer decisions with few human touch points. He says the main challenge is governance, and calls for traceability, bias monitoring, human-in-the-loop checkpoints and a kill switch, plus open standards so multi-vendor agents can work together.

    30 min slot · Beginner · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You want a high-level view of where a retail technology manager sees agentic AI going and which governance questions he thinks platform teams need to answer.

    1. 9:15 The speaker describes four maturity levels, from rule-based automation through predictive and adaptive decisioning to autonomous decisioning, and says most retailers are at level three.
    2. 10:45 He gives examples of agentic AI in retail: autonomous pricing engines that watch competitor prices and margin targets, self-healing supply chain pipelines and conversational commerce agents.
    3. 16:51 He describes an architecture where point-of-sale, clickstream and external feeds go into a unified intelligence layer of LLMs and agents on Kubernetes clusters, backed by a unified data layer of governed data.

    5. 23:22 He says a trusted governance framework should always include a kill switch, with override controls, regular governance reviews and an AI council before production deployment.

    Translating Mesh Identity into MCP Impersonation: Governing AI Agent Identities with Istio

    Juan David Arguello Plata

    The speaker describes an agent platform on Istio ambient in which agents and tools get workload identities and each user's token travels with a request, so third-party tools are called on behalf of that user. He argues that without mesh authorization policies the prompt is the only guardrail, and that the mesh, not the model, should be the security boundary.

    5 min slot · Level not listed · Session

    Security, identity and policyAI agents and automationNetworking and connectivity

    Watch this if: You are building an agent platform and need tool calls to carry the real user's identity, not a shared service account.

    1. 0:18 The speaker names prompt injection, user impersonation and secret leakage as the three red flags of the agent identity problem.
    2. 0:57 He says that without workload identities in the mesh, a triage agent can reach every other agent and every tool.
    3. 2:09 He says third-party tools reached through service accounts log only the service account, so the audit trail does not show which user an agent acted for.
    4. 2:48 He describes the platform: Istio ambient with peer authentication and authorization policies, kagent and kmcp managing agents and tools with SPIFFE identities, and agentgateway checking user tokens.
    5. 4:52 He walks through the flow in which a token is minted at login, an Argo workflow sends the event and token to agentgateway, and the chosen agent calls the tool through an MCP server, REST API or CLI.
