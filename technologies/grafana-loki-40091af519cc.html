    Following the Evidence with HolmesGPT: Troubleshooting Kubernetes Apps and Infrastructure

    Yash Sharma

    Yash Sharma, presenting alone after saying his co-speaker could not attend, describes his own experiment with HolmesGPT on a demo shop application running on a DigitalOcean Kubernetes cluster with three planted faults. He shows it investigating a full Postgres volume, a CPU-hungry CronJob and a cloud-side volume attachment limit, and then outlines how he would run it in production with read-only access and human approval for changes.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automation

    Watch this if: you are considering an AI troubleshooting assistant for Kubernetes and want to see it work through storage, CPU and cloud-provider faults before deciding how much access to give it.

    1. 4:41 Sharma describes HolmesGPT's loop: starting from an alert thread, it calls toolsets such as kubectl, PromQL, APIs and SQL, reruns the investigation if the results are not enough, and returns a root cause with evidence and a suggested fix.
    2. 12:21 In the live demo, after he fills the Postgres volume and checkout errors rise, the holmes ask command returns evidence of no space left on the device along with possible fixes.
    3. 17:26 He says HolmesGPT runs read-only in his cluster, so a kubectl exec it attempted was denied as needing approval, and it still traced the slow checkout API to the batch job he had added.
    4. 18:38 For the third case he explains a setup where a 16th pod cannot get a volume because of a per-node attachment limit on DigitalOcean Kubernetes, and shows holmes investigate alertmanager attributing the pending pod to the cloud provider side.
    5. 24:44 His security advice is to keep the tool read-only, require human approval for any write, issue least-privilege tokens per task, and check the logs rather than fully trusting the output, since logs can carry injected content.

    Observability for LLM Inference on Kubernetes

    Oscar Castillo, Jeffry Hernández

    The speakers explain which signals they use to observe inference from the client through the model server to the GPU. They demonstrate how they correlate traces, logs, and metrics for a passport-data extraction app using synthetic inputs.

    30 min slot · Any Level · Session

    AI inference and servingObservability and reliability

    Watch this if: You need to see where inference latency or errors originate instead of stopping at a single GPU dashboard.

    1. 1:43 The speakers distinguish prefill from iterative decode and introduce time to first token and time per output token as ways to observe those stages.
    2. 4:52 The speakers compare their client-side timing with the provider dashboard and explain why network hops and client processing can make the end-to-end delay longer.
    3. 9:20 The speakers show a synthetic passport image going through an instrumented OCR application that returns extracted data and token counts.
    4. 13:59 The speakers use a Grafana dashboard to show why a busy GPU reading can be misleading when the inference server's KV cache is far from full.
    5. 17:04 The speakers inspect a failed trace from an empty model response and show how a trace ID can connect the request to logs from Envoy and the inference scheduler.

    Progressive Delivery for Trust: How Agents Earn the Right to Merge

    Darian DeFalco

    Darian DeFalco describes how Transfix applies progressive delivery to deciding when an automated pull request can merge. He explains how shadow evaluations, per-PR test environments, and narrow, reversible grants keep the decision separate from the permission to act.

    30 min slot · Any Level · Session

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You want to move from human review of every agent-written change to limited auto-merge based on observed outcomes.

    1. 8:27 DeFalco describes how Transfix turns each task into a Kubernetes Job with a limited GitHub token and runs it only in staging.
    2. 10:57 DeFalco explains that in shadow mode the agent opens a pull request and an evaluator logs what it would do without acting on the decision.
    3. 12:12 DeFalco shows how Argo CD creates a staging namespace for a labeled pull request and removes it when the label is removed.
    4. 13:35 DeFalco says a grant covers a narrow class of changes and each new pull request still needs a passing test for that exact commit.
    5. 16:22 DeFalco describes how a reverted merge suspends automation for that repository and triggers a pull request to remove the grant.

    The Healthy Cluster, The Unhealthy VM:Why Infrastructure Metrics Are Only Half the Story in KubeVirt

    Smit Jain

    Smit Jain of the Portworx team at Everpure argues that infrastructure telemetry shows whether a KubeVirt cluster is healthy but not what the guest operating system inside a VM is experiencing. He walks through three incidents from his team's lab, a triage workflow that combines both views, and an open source operator his team wrote to collect guest metrics and logs.

    20 min slot · Level not listed · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you run production VMs on KubeVirt and have had users report slow or failing VMs while every cluster dashboard was green.

    1. 2:43 Jain lists what he says guest telemetry adds to infrastructure telemetry: detecting OS failures KubeVirt does not see, measuring which VMs are actually affected, narrowing the search, and validating that a fix worked.
    2. 7:33 First incident: a Linux VM's application filled a 50 GB filesystem and I/O failed while the VMI was running and the node looked healthy; his lesson is that filesystem usage in the guest is not volume usage.
    3. 9:41 Second incident: a Windows VM logged Event 129 I/O timeouts, and with guest telemetry enabled he says they could tie them to storage failures on the infrastructure side without logging into the VM.
    4. 10:43 Third incident: one VM saturated the disk on a shared node and two neighbours hit guest timeouts; they applied volume-level throttling and used guest metrics to confirm the recovery.
    5. 14:18 He introduces the KubeVirt observability operator, which reads an OS label in the VM spec, deploys node exporter or Windows exporter in the guest, and ships event logs and syslogs through Alloy to Loki.

    Zero-Trust Telemetry: Stopping AI-Powered Poisoning Attacks on Observability Pipelines

    Chad M. Crowell, Diana Todea

    Chad M. Crowell and Diana Todea describe why telemetry should be treated as untrusted input when it feeds automated decisions. They propose independent controls for transport, query access, and network policy, then discuss how to verify those controls in Kubernetes.

    30 min slot · Advanced · Session

    Observability and reliabilitySecurity, identity and policy

    Watch this if: telemetry drives automated responses and you want to limit what each source and consumer can do.

    1. 13:37 The speakers describe using mutual TLS between OpenTelemetry Collectors and backends, and explain that verifying the sender does not verify that the data is true.
    2. 16:43 They propose checking the identity and scope of human and agent queries with fine-grained role-based access, then logging those decisions for audit.
    3. 20:02 They recommend default-deny network policies for the telemetry namespace, with explicit allowances for the application-to-collector and collector-to-backend flows.
    4. 22:42 They describe using Falco with Kubernetes audit events to detect suspicious activity, complementing the communication limits from network policy.
    5. 23:54 They recommend validating which sources feed Prometheus federation and restricting who can reach federation endpoints and exporters.
