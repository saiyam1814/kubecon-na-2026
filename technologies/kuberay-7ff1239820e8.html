    Cloud Native Operators and You

    Corey McGalliard

    Corey McGalliard explains the Kubernetes control loop and the operator pattern of a custom resource definition plus a controller, then acts it out with three audience volunteers who keep a set number of balloons in a bucket. In the Q&A he says his team prefers operators over raw config maps because a custom resource can be validated, while noting this is an opinion and that implementations differ between projects.

    12 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: You want an intuitive picture of how Kubernetes controllers and operators reconcile state before reading any operator code.

    1. 1:09 The speaker describes the control loop from control theory: observe the current state, compare it with the desired state, and act to reconcile the two.
    2. 1:54 He explains the operator pattern as a custom resource definition that holds the desired state plus a controller that reconciles it, for things inside or outside the cluster.
    3. 4:35 He starts a live demonstration in which volunteers act as controllers: one inflates balloons to reach three in a bucket, one enforces a limit of two, and one reports when the bucket is empty.
    4. 7:59 He names cert-manager and KubeRay as CNCF projects that use the operator pattern, and says his team writes its own operators for an internal platform.
    5. 9:21 Asked whether to always use an operator when one exists, he says his team prefers it because a custom resource is a defined API contract that can be validated, unlike raw text in a config map.

He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    Volcano for the Agentic AI Era: Unified Scheduling Across Training, Inference, and Agents

    Ricardo Aravena, Rainie Li

    Rainie Li explains how Volcano aims to schedule training, inference and agent workloads on one Kubernetes cluster, using a batch scheduler and an agent scheduler that share nodes through a sharding controller, plus multi-level gang scheduling, network topology hypernodes and gang-aware preemption. Ricardo Aravena then covers how workload controllers such as Kthena, KubeRay and Grove map onto Volcano primitives, the project's benchmarking work and the roadmap.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingAI agents and automationAI inference and serving

    Watch this if: you schedule AI training, inference or agent workloads on shared GPU clusters and want to know what Volcano offers for gang and topology-aware placement.

    1. 3:02 Rainie Li says Volcano uses two schedulers, a batch scheduler for coordinated workloads and an agent scheduler for latency-sensitive pods, with a sharding controller assigning candidate nodes to each and moving them as demand changes.
    2. 6:49 She introduces multi-level gang scheduling, in which a pod group contains subgroups with their own completeness requirements, such as a tensor-parallel group or a prefill or decode replica.
    3. 9:56 She explains gang-aware preemption, which treats victims as groups and simulates placement first, so no pod is evicted if the whole incoming gang cannot fit.
    4. 15:12 Ricardo Aravena says KubeRay support is merged upstream and listed for Volcano 1.16, and walks through how its head and worker groups translate into Volcano subgroups.
    5. 18:35 He describes the scheduling benchmark framework shipped with Volcano 1.15, which reports scheduling latency and binding throughput on kind, KWOK or an existing cluster, and notes it says nothing about GPU job speed.

    When Training Dies at 3 AM: Correlating Kubernetes Events with AI-Framework Failures

    Wenjia Zhang, Yuchen Zhou

    Wenjia Zhang and Yuchen Zhou of Google, standing in for the work's main contributor Richa Banker, explain why a hardware fault under a distributed training job is hard to trace back from Kubernetes events hours later. They describe the pipeline they say is merged upstream in Ray and KubeRay, which joins events to pods and parent jobs while the pod still exists, shows them in a Platform Events tab in the Ray dashboard and exports them with Ray's own events.

    30 min slot · Any Level · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: ML engineers on your platform ask whether their code or the infrastructure killed a training job and you cannot answer from Kubernetes events the next morning.

    1. 3:39 Zhang walks through a 512-GPU training run where a GPU fault at 3:14 a.m. becomes, seven seconds later, a Python exception reported by Ray as an application failure, and by 9 a.m. kubectl get events shows nothing.
    2. 8:52 She names three obstacles: events expire after a one-hour TTL, or five minutes in a large cluster with heavy churn, they carry no labels or owner references, and the pod needed for the join may already be garbage collected.
    3. 15:43 Zhou describes two watches in the Ray head: one keeps an in-memory list of the cluster's live pods by label, the other checks namespace pod events against that list, with events kept in a fixed buffer of 1,000 keyed by event UID.
    4. 17:19 He says platform events are wrapped in the standard Ray event format and exported asynchronously to a log file or HTTP endpoint, so they stay searchable in a logging backend after the cluster and the Kubernetes events are gone.
    5. 20:59 He explains that node events land in the default or kube-system namespace where a Ray head cannot see them, so the KubeRay operator watches node warnings and re-emits one event per affected RayCluster into the team's namespace.
