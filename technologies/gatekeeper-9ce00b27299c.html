    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    Goodbye Webhooks, Hello CEL: Using Native Validating and Mutating Admission Policies in Kubernetes

    Greg Bray

    Greg Bray of Google Cloud explains how ValidatingAdmissionPolicy and MutatingAdmissionPolicy let Kubernetes evaluate CEL expressions inside the API server, which he says avoids the latency and failure risk of admission webhooks. He also covers where he thinks the native policies fall short and a full policy engine such as Kyverno or Gatekeeper is still needed.

    30 min slot · Any Level · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you run admission webhooks for simple checks and want to know which of them can move to policies built into the API server.

    1. 4:49 Bray lists the pain points of webhooks: the API server has to call out of process, and he says a failing webhook set to fail closed can bring the whole control plane to a halt.
    2. 8:20 He shows CEL optional values, which he says arrived in Kubernetes 1.29 and replace long guarded expressions for fields such as annotations that may not exist.
    3. 12:16 He walks through MutatingAdmissionPolicy, which he says went GA in April, and compares declarative apply configurations with imperative JSON patches.
    4. 18:13 He describes manifest-based policies loaded from disk before the API server starts serving, which he says close the bootstrap gap and cannot be changed or deleted through the API.
    5. 20:46 He lists the limits of native policies: they see only the request and the old object, cannot read other resources or external data, and stop when a CEL cost budget is exceeded.

  • EnvoyCon

    Guardrails, Not Gatekeepers: Envoy Gateway in the Enterprise

    Matthew Slater

    The speaker, from the Kubernetes platform engineering team at JPMorgan Chase, describes bringing Envoy Gateway and Gateway API to application teams in a regulated enterprise after the ingress-nginx retirement. He covers which parts of the API his team blocks, how policy denials explain the fix, and workarounds for load balancers and enterprise identity providers.

    10 min slot · Level not listed · Session

    Networking and connectivitySecurity, identity and policyPlatform engineering and developer experience

    Watch this if: You are a platform engineer moving teams from ingress-nginx to Gateway API in a company with strict security and cloud rules.

    1. 4:08 He recommends blocking users from creating roles that grant themselves access to EnvoyPatchPolicy and EnvoyExtensionPolicy, since patching xDS directly would bypass every other rule.
    2. 4:56 He says every rule in their shared Gatekeeper policy library must carry a message and a remedy, so a denied user sees why and how to fix it.
    3. 7:09 He describes separating load balancing from the Envoy deployment: the Envoy service is set to NodePort and Terraform-managed load balancers map target groups to those ports.
    4. 8:57 He shares identity provider workarounds: append extra request parameters to the authorization endpoint, use the resources field for ADFS, and use a private client with a secret because public clients did not work.
    5. 11:50 He sums up five things to copy: write constraints down first, map roles onto the four-tier RBAC model, bring security in as a design input, ship safe defaults teams can change, and budget for teaching.

    Open Policy Agent. (OPA) Intro & Deep Dive

    Sebastian Spaink, Johan Fylling

    Sebastian Spaink and Johan Fylling introduce Open Policy Agent as a general-purpose policy engine and Rego as its declarative policy language. They then cover this year's Rego changes, new Java and Swift evaluators built on OPA's intermediate representation, runtime improvements, and updates from Gatekeeper, opa-java-wasm and Conftest.

    30 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: you write Rego policies and want to know about the new and, or and not semantics and the coming Rego v2.

    1. 0:53 Spaink describes the problem OPA targets: policy scattered across enforcement points owned by different teams, so nobody can easily answer what the policy is.
    2. 8:42 Fylling shows the new or keyword for inline disjunction, while still recommending helper rules to keep large logical expressions maintainable.
    3. 12:33 Fylling explains the pitfall where a not expression over an undefined input value stopped the whole rule, and how the compiler now wraps negations in closures.
    4. 17:14 Fylling says a Rego v2 import enables the new syntax per module, ahead of an OPA 2.0 release the team plans for next year.
    5. 20:06 Fylling presents Java and Swift evaluators that run OPA's intermediate representation inside applications as libraries, with bundle management and decision logging.
