    Agentic AI, Assembled in the Open

    Jorge Palma

    Jorge Palma asks how teams can reproduce an agent's work after its compute goes away and define what runs inside it. He introduces a durable session journal and a portable agent definition, then walks through a scenario where an agent pauses for human approval and resumes later.

    5 min slot · Level not listed · Keynote

    AI agents and automationCommunity and open source adoption

    Watch this if: you want to understand what an agent platform needs for reproducible work, human approvals, and auditing.

    1. 0:37 Palma frames two problems: preserving an agent's work after compute is released and defining what runs inside the agent.
    2. 1:47 Palma explains how recording completions in a hash-linked, append-only journal lets a session be replayed or forked without making the same model calls again.
    3. 3:03 Palma introduces a portable, versioned JSON definition for an agent's instructions, tool providers, build information, and evaluation cases.
    4. 4:14 Palma describes a remediation workflow that waits for human approval and releases idle compute while the session waits.
    5. 4:49 Palma walks through how a suspended session resumes for a change-ticket request and how an auditor could replay or verify the record later.

    Don’t Lose Your Agent’s Mind: Platform Patterns for Stateful Agents

    Evaline Ju, Maia Iyer

    The speakers explain why stateful agents lose sessions, files, and context when treated like ordinary pods, and they examine community work on sandboxing, snapshotting, and resuming agent state. They present their moca prototype and argue for server-held sessions, harness-neutral state, and an open harness-sandbox boundary.

    25 min slot · Any Level · Session

    AI agents and automationData, storage and state

    Watch this if: you are designing Kubernetes platform support for stateful or delegated AI agents.

    1. 4:00 The speakers say a plain pod is a poor fit for stateful agents because deleting the pod discards sessions, files, and learned context.
    2. 5:48 The speakers point to Agent Sandbox templates and Agent Substrate snapshot and resume work as community efforts aimed at configurable isolation and multiplexing idle agents.
    3. 9:19 The speakers present moca as their open-source managed-agents experiment, using Pi for the harness, Valkey for externalized sessions, and a relay boundary into pluggable sandboxes.
    4. 16:10 In the recorded demo, Evaline shows the user closing a session, starting another one, and still picking up the subagent's work without resending context.
    5. 18:41 The speakers argue that platforms should make sessions first-class and server-held, treat agent state as harness-neutral data, and make the harness-sandbox boundary an open protocol, while provenance, cost attribution, legibility, and delegated trust remain open.

    From Clever to Correct: Lessons from Rebuilding SeatGeek's Platform AI Agent

    Colin O'Dell

    Colin O'Dell describes why SeatGeek replaced its specialist-heavy platform agent, Rufus, with a generalist agent called Sandy that can carry a task from investigation through a code change. He explains how a per-session sandbox keeps full logs out of the agent's context and how the team uses reports from Slack or Jira to improve the agent itself.

    10 min slot · Intermediate · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You are deciding what to build yourself when an internal platform agent needs to diagnose problems and make changes.

    1. 1:23 O'Dell explains how Rufus routed requests to four specialists that could not easily hand work off. An Argo CD specialist could diagnose a deployment failure but could not pass the fix to the coding agent.
    2. 4:10 He describes rebuilding around one OpenCode harness and a per-session sandbox, where Sandy can store full logs on disk and pull only the relevant lines into its context.
    3. 6:43 He explains why the team reused OpenCode and Daytona for the harness and sandboxes, leaving more time for platform-specific routines and skills.
    4. 7:05 He describes how the team uses Sandy to fix Sandy: a report from Slack or Jira can start a sandboxed fix and merge request. He also describes a tool that posts a short report when the agent gets stuck.
    5. 8:56 He argues for treating the internal agent as a product that keeps evolving, after putting Rufus into maintenance mode made later improvements harder to adopt.

    KubeVirt's Architectural Leap: Pluggability, AI Hardware, and Maturing Governance

    Vladik Romanovsky, Itamar Holder

    KubeVirt maintainers Vladik Romanovsky and Itamar Holder mark the project's tenth year and its CNCF graduation by reviewing its pod-based architecture, its adoption of an enhancement proposal process, and this year's work on confidential VMs, NVIDIA hardware support and Dynamic Resource Allocation. Holder then explains the plugin framework from enhancement proposal 190, which is meant to let features be built out of tree, along with early work on supporting hypervisors beyond QEMU/KVM and the idea of using KubeVirt as an isolation backend for agent sandboxes.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run or extend KubeVirt and want to know how the plugin framework will replace sidecar hooks.

    1. 1:02 Vladik Romanovsky recalls early doubts about the project and explains the choice to tie a virtual machine's life cycle to a pod and run the virtualization stack inside it, which he says let KubeVirt reuse the Kubernetes security model, CNI, CSI and device plugins.
    2. 6:48 He says the last cycle had more than 100 open enhancement proposals, and that the project built a per-release tracker plus an AI agent that gathers related pull requests and estimates how likely each piece of work is to land by the freeze.
    3. 9:23 He describes building support for NVIDIA's newest hardware in a fork with Red Hat and NVIDIA engineers before bringing it back upstream, keeping the virt-launcher unprivileged by moving privileged operations into a device plugin.
    4. 14:39 Itamar Holder lists drawbacks of the existing sidecar hook: it edits the libvirt domain XML as a raw string, has no node access, and can only be enabled for everyone through one feature gate.
    5. 16:44 He walks through the new plugin model's three levels: a CEL expression that mutates the domain XML, a sidecar that works on a structured libvirt object with new pre-boot and pre-migration hooks, and node hooks answered by a plugin author's own DaemonSet.

    Lessons Learned Sandboxing Agents with kagent

    Peter Jausovec, Nina Polshakova, Eitan Yarmush

    Peter Jausovec and Eitan Yarmush of Solo.io, the two speakers heard in the recording, walk through the sandboxing approaches they tried for kagent and say each one still kept an idle agent's pod running or tied identity to the pod. They explain why kagent 1.0 was rebuilt on Agent Substrate, list five lessons from that work, and demo Claude Managed Agents sessions running in sandboxes on their own cluster.

    30 min slot · Any Level · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing how to sandbox AI agents on Kubernetes and want to hear what one team found lacking in pod-per-agent setups.

    1. 3:40 Jausovec says they tried four things before Agent Substrate: their own pod-per-agent runtime, Anthropic's Sandbox Runtime, Agent Sandbox and NVIDIA's OpenShell, and that each solved only part of the problem.
    2. 9:08 Jausovec gives the reasons for Agent Substrate: idle agents are snapshotted to object storage and hold no compute, the Kubernetes API is off the hot path, restores take milliseconds, and actors are sandboxed with default-deny networking.
    3. 10:04 Yarmush tells how Solo started building an internal sandbox layer called Moat, then joined Google's Agent Substrate work instead, and says kagent 1.0 is now based entirely on Agent Substrate.
    4. 17:42 Yarmush starts the takeaways: isolation is table stakes and pause and resume is the hard part, every control must sit outside the agent, identity follows the actor, a suspended agent is stored data, and the sandbox runtime becomes a data format.
    5. 22:56 Demo: Jausovec creates two Claude Managed Agents sessions whose sandboxes run on his cluster, shows that one session cannot read the other's file, and shows a blocked request succeed after he applies an egress policy.

    Managing Data at Scale: Best Practices and Evolution of SIG-Apps

    Maciej Szulik, Janet Kuo

    SIG Apps leads Maciej Szulik and Janet Kuo review recent and in-progress changes to the core Kubernetes workload APIs, including Job failure policy, workload-aware (gang) scheduling in the Job and Deployment controllers, and StatefulSet rollout options, noting which may miss the 1.38 code freeze. Kuo then covers the SIG's subprojects for batch, AI inference and agents, among them JobSet, LeaderWorkerSet, Agent Sandbox and an MCP lifecycle operator, plus a new workload conformance working group.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesData, storage and stateAccelerators and workload scheduling

    Watch this if: you run Jobs, StatefulSets or AI workloads on Kubernetes and want to know what SIG Apps is changing and which subprojects it has added.

    1. 4:09 Maciej Szulik explains gang scheduling, where a group of pods is scheduled together rather than one at a time, and says the Deployment controller is the second controller getting workload-aware scheduling after the Job controller.
    2. 6:46 He describes a long-standing StatefulSet complaint, that a broken rollout is not repaired automatically and pods must be fixed by hand, and the recreate update strategy introduced to partly address it.
    3. 13:31 Janet Kuo presents Agent Sandbox, the subproject she leads for isolated, stateful singleton workloads such as AI agents and code execution, and says it reached a 1.0 release with about 180 contributors.
    4. 17:46 She introduces a new subproject for maintenance windows, because a PodDisruptionBudget only counts pods and has no notion of when disruption is acceptable, and mentions a workload conformance working group.
    5. 25:33 Asked how upstream gang scheduling relates to Kueue and KAI Scheduler, Szulik says the aim is for those projects to reuse the new primitives, and that the API must be enabled explicitly until it reaches v1.

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.

    Untrusted Code on Secure Runtimes: Agent Sandboxes on Kubernetes

    Mofi Rahman

    Mofi Rahman leads a hands-on lab on GKE, with four Google colleagues helping attendees in the room, and explains that it uses the newly open-sourced Agent Substrate where the abstract promised Agent Sandbox. Attendees create workers, actor templates and actors, suspend and resume them with their state, allow a model call through an egress policy and run 20 actors on two workers, and he says internal benchmarks reached more than 100 million actors.

    80 min slot · Beginner · Tutorial

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you want to follow a full lab on suspending and resuming agent workloads on Kubernetes and see how actors differ from one pod per sandbox.

    1. 21:39 Rahman explains why the lab switched projects: Agent Sandbox maps a sandbox to a pod with warm pools, while Agent Substrate adds actors, many per pod, and he suggests Sandbox for agents that run for days and Substrate for short, bursty sessions.
    2. 25:22 He lists Substrate's parts: an API server, Postgres in place of etcd, which he says could not scale to the 100 million actor goal, egress control, and a router that proxies requests so actors do not each need an IP address.
    3. 36:15 He suspends an actor, sends it a request and gets an answer anyway, explaining that the router holds the request while the actor resumes from its snapshot mid-state, unlike Cloud Run, Lambda or Knative starting from zero.
    4. 49:14 A model call from the actor fails because egress is denied by default, and it succeeds after he creates an egress gateway and a policy that allows the one model URL.
    5. 57:09 A third actor times out on two full workers, and he stresses that Substrate does not decide when to suspend: the platform team defines idle, here three seconds without a request, after which 20 actors share two workers.
