    Agentic AI, Assembled in the Open

    Jorge Palma

    Jorge Palma asks how teams can reproduce an agent's work after its compute goes away and define what runs inside it. He introduces a durable session journal and a portable agent definition, then walks through a scenario where an agent pauses for human approval and resumes later.

    5 min slot · Level not listed · Keynote

    AI agents and automationCommunity and open source adoption

    Watch this if: you want to understand what an agent platform needs for reproducible work, human approvals, and auditing.

    1. 0:37 Palma frames two problems: preserving an agent's work after compute is released and defining what runs inside the agent.
    2. 1:47 Palma explains how recording completions in a hash-linked, append-only journal lets a session be replayed or forked without making the same model calls again.
    3. 3:03 Palma introduces a portable, versioned JSON definition for an agent's instructions, tool providers, build information, and evaluation cases.
    4. 4:14 Palma describes a remediation workflow that waits for human approval and releases idle compute while the session waits.
    5. 4:49 Palma walks through how a suspended session resumes for a change-ticket request and how an auditor could replay or verify the record later.

    Don’t Lose Your Agent’s Mind: Platform Patterns for Stateful Agents

    Evaline Ju, Maia Iyer

    The speakers explain why stateful agents lose sessions, files, and context when treated like ordinary pods, and they examine community work on sandboxing, snapshotting, and resuming agent state. They present their moca prototype and argue for server-held sessions, harness-neutral state, and an open harness-sandbox boundary.

    25 min slot · Any Level · Session

    AI agents and automationData, storage and state

    Watch this if: you are designing Kubernetes platform support for stateful or delegated AI agents.

    1. 4:00 The speakers say a plain pod is a poor fit for stateful agents because deleting the pod discards sessions, files, and learned context.
    2. 5:48 The speakers point to Agent Sandbox templates and Agent Substrate snapshot and resume work as community efforts aimed at configurable isolation and multiplexing idle agents.
    3. 9:19 The speakers present moca as their open-source managed-agents experiment, using Pi for the harness, Valkey for externalized sessions, and a relay boundary into pluggable sandboxes.
    4. 16:10 In the recorded demo, Evaline shows the user closing a session, starting another one, and still picking up the subagent's work without resending context.
    5. 18:41 The speakers argue that platforms should make sessions first-class and server-held, treat agent state as harness-neutral data, and make the harness-sandbox boundary an open protocol, while provenance, cost attribution, legibility, and delegated trust remain open.

    From Clever to Correct: Lessons from Rebuilding SeatGeek's Platform AI Agent

    Colin O'Dell

    Colin O'Dell describes why SeatGeek replaced its specialist-heavy platform agent, Rufus, with a generalist agent called Sandy that can carry a task from investigation through a code change. He explains how a per-session sandbox keeps full logs out of the agent's context and how the team uses reports from Slack or Jira to improve the agent itself.

    10 min slot · Intermediate · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You are deciding what to build yourself when an internal platform agent needs to diagnose problems and make changes.

    1. 1:23 O'Dell explains how Rufus routed requests to four specialists that could not easily hand work off. An Argo CD specialist could diagnose a deployment failure but could not pass the fix to the coding agent.
    2. 4:10 He describes rebuilding around one OpenCode harness and a per-session sandbox, where Sandy can store full logs on disk and pull only the relevant lines into its context.
    3. 6:43 He explains why the team reused OpenCode and Daytona for the harness and sandboxes, leaving more time for platform-specific routines and skills.
    4. 7:05 He describes how the team uses Sandy to fix Sandy: a report from Slack or Jira can start a sandboxed fix and merge request. He also describes a tool that posts a short report when the agent gets stuck.
    5. 8:56 He argues for treating the internal agent as a product that keeps evolving, after putting Rufus into maintenance mode made later improvements harder to adopt.

    OpenChoreo: Developer Platform for Humans & Agents

    Sameera Jayasoma

    Sameera presents OpenChoreo as a Kubernetes-native control plane that hides tooling complexity behind guarded abstractions for humans and agents. He argues that agents should become first-class platform workloads and shows how catalogs, deployment state, logs, metrics, cost insights, and audit data can share those abstractions.

    5 min slot · Any Level · Keynote

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are evaluating control-plane abstractions that serve both developers and AI agents.

    1. 1:20 Sameera says platform maintainability becomes difficult when added capabilities require repeated changes to glue code across portals and pipelines.
    2. 2:18 Sameera argues that exposing every underlying tool directly to agents can work but wastes iterations and tokens, while a smaller set of guarded abstractions gives agents a controlled interface.
    3. 3:36 Sameera presents OpenChoreo as a control-plane middle layer that abstracts the tooling layer and compiles higher-level concepts toward Kubernetes while preserving their meaning for status, logs, and metrics.
    4. 5:29 Sameera says OpenChoreo expands its control plane to treat agents as first-class workloads because they can run untrusted or unpredictable code and need runtimes such as Agent Sandbox and Agent Substrate.
    5. 5:56 Sameera introduces a quick portal demo built around a CLI and Backstage-based plugins, showing catalogs, component deployment state, logs, metrics, cost insights, and audit data.

    Platform-First AI Agent Security: Zero-Trust Patterns for Kubernetes

    Carlos Santana

    Carlos Santana argues that a Kubernetes platform should treat agent-generated code as untrusted and provision isolation, credentials, and network policy separately. He describes using kro to compose those controls behind a platform API and shows captures of an Agent Sandbox warm pool assigning a ready pod.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to give teams a Kubernetes API for agents without giving those agents unrestricted access.

    1. 5:25 Santana describes SPIFFE and SPIRE as a way to identify an agent by URI and associate that identity with a credential across different environments.
    2. 12:14 Santana shows a kro ResourceGraphDefinition and explains how a declarative resource graph can give platform users a custom API without requiring the platform team to write a Go controller.
    3. 19:05 Santana compares gVisor, Kata Containers, and AWS Nitro Sandboxes as different isolation choices for running untrusted agent code.
    4. 21:27 Santana shows captures of a two-pod Agent Sandbox warm pool and says applying a claim assigned a ready pod instead of waiting for a fresh sandbox to start.
    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    Carlos Sanchez

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.
