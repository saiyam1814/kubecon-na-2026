    Container Builds at Scale with Buildpacks

    Joe Kutner

    Joe Kutner of Salesforce presents Cloud Native Buildpacks as a way to turn source code into well-structured container images without a Dockerfile, and says the project graduated in the CNCF this past August. He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    1. 0:55 Joe Kutner says Cloud Native Buildpacks were created at Heroku about 12 years ago, joined the CNCF eight years ago and reached graduation this past August.
    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.
    3. 2:54 He says that with Dockerfiles a vulnerability in a shared base image means rebuilding every image, because of how linear layer caching works.
    4. 3:20 He explains rebase: because buildpacks know the boundary between OS and application layers, existing layers can be moved onto a new OS image without a build, which he says runs in milliseconds.
    5. 4:19 He says buildpacks can be run locally by installing the pack CLI and running pack build, choosing off-the-shelf buildpacks from Heroku, Google or Paketo, or writing your own.

    Turning Apple Silicon into Production GPU Nodes for LLM Inference on Kubernetes

    Christopher Maher

    The speaker, who maintains LLMKube, shows live how a Mac joins a Kubernetes cluster as a MetalNode: an agent on the Mac starts the inference engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service. He says unified memory makes memory the thing to schedule on, recounts a kernel panic that led him to make the agent refuse models it cannot size, and shows traffic failing over to NVIDIA nodes when the Mac's lid closes.

    30 min slot · Advanced · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You want to serve LLMs on Macs or other unified-memory machines you already own, behind the same Kubernetes operator and service as your NVIDIA nodes.

    1. 5:16 The speaker lists why a Mac cannot simply join a cluster: Metal is not available inside a Linux container, no device plugin advertises the Mac's GPU, and the kubelet cannot see how much unified memory the GPU holds.
    2. 6:32 He describes the Mac path: an agent running under launchd watches for inference services, starts the engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service.
    3. 9:16 In a live demo a second MacBook joins his home cluster with a token-based join command and appears as a MetalNode.
    4. 12:23 He says the agent now fails closed after an incident in which a memory check failed open, llama-server ran with mlock and the laptop hit a kernel panic; admission also counts memory already committed.
    5. 15:56 In a live demo he closes the lid of the Mac serving traffic, and the same endpoint is then answered by NVIDIA nodes in his home lab.
