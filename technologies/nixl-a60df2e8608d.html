    CoHDI: Bridging Kubernetes and Disaggregated Memory for Memory-Aware LLM Inference

    Naoki Oguchi, Hidetsugu Sugiyama

    Naoki Oguchi and Hidetsugu Sugiyama present CoHDI, a CNCF Sandbox project they describe as letting Kubernetes attach pooled CXL memory and GPUs to worker nodes on demand, with a focus on giving LLM inference more room for KV cache. They walk through the allocation sequence for an LMCache pod, share early measurements, and outline plans to split prefill and decode across sites connected by an optical network.

    30 min slot · Advanced · Session

    Data, storage and stateAI inference and servingAccelerators and workload scheduling

    Watch this if: you run LLM inference on Kubernetes and want to see how pooled CXL memory could be attached to nodes as an extra KV cache tier.

    1. 2:50 Oguchi says KV cache capacity needs to scale independently from GPU compute, after listing the drawbacks he sees in adding GPUs, adding local DRAM, or evicting the cache to storage.
    2. 6:47 Oguchi explains the CoHDI flow: a scheduled pod triggers composition, the Dynamic Device Scaler evaluates the GPU and CXL memory needed, and the Composable Resource Operator requests them from the pool and attaches them to the worker node.
    3. 11:52 Oguchi shows cache metrics where resubmitting the first prompt raises the blocks read from the second tier from 105 to 135, which he reads as KV cache kept in CXL memory being reused.
    4. 12:44 Oguchi reports first-stage results in which attached CXL memory was 10 times faster than SSD for random reads and 18 times faster for writes, and says LMCache still needs optimization for CXL access.
    5. 18:27 Sugiyama says GPU overprovisioning at the decode site remains a problem and describes decode nodes with few GPUs and large CXL memory pools composed by CoHDI as his answer.

    From GPU to Fleet. The llm-d KV Cache Hierarchy

    Vita Bortnikov, Nishtha Jain

    Vita Bortnikov and Nishtha Jain describe how llm-d and vLLM keep KV cache across GPU memory, CPU memory, local disks, network storage and peer-to-peer transfers between pods. They present benchmarks they say show storage offloading only holds up at scale when it is paired with storage-aware routing in the llm-d router.

    20 min slot · Level not listed · Session

    AI inference and servingData, storage and state

    Watch this if: You run LLM inference on Kubernetes and want to understand KV cache offloading tiers and cache-aware routing.

    1. 1:51 Vita Bortnikov says agentic workloads read far more than they write, with long inputs and short outputs, and cites up to 95% KV cache reuse.
    2. 4:44 She describes the offloading connector contributed upstream to vLLM, which tiers KV cache from GPU to CPU to storage, while llm-d handles orchestration and eviction.
    3. 7:15 She explains peer-to-peer KV cache transfer between nodes, used when the node holding a prefix is busy and for prefill/decode disaggregation.
    4. 12:15 Nishtha Jain introduces the third tier, shared network storage such as parallel file systems, which she says takes KV cache from gigabytes and terabytes to petabytes.
    5. 19:18 She calls storage offloading without storage-aware routing a failure at scale, citing throughput falling from about 2,500 to 700 tokens per second at 800 users when the router's storage index was off.

    What the Docs Don't Tell You: A Telecom's Year Operating Cache-Aware LLM Inference on Kubernetes

    YoungJoon Jeong, Seol Heo

    The speakers describe how LG Uplus raised its KV cache hit rate from 71.6% to 95.4% on 16 vLLM replicas by reordering prompts, routing each request to the pod that holds its prefix with llm-d, and adding a CPU memory tier for evicted blocks. They say time to first token is queue time plus prefill time, so once prefill was cached they tuned concurrency, and they report that splitting prefill and decode cut inter-token latency while lowering throughput.

    30 min slot · Advanced · Session

    AI inference and servingObservability and reliability

    Watch this if: You serve LLMs for multi-turn or agent traffic on Kubernetes and want measured numbers on what prefix-aware routing, cache tiers and prefill/decode separation each bought.

    1. 4:51 YoungJoon Jeong says vLLM hashes prompt blocks in a chain, so one small change near the start, such as a timestamp in the system prompt, turns every later block into a miss; his advice is to put the stable part first.
    2. 9:07 He frames KV cache hit rate as ceiling times placement times survival, which he calls their own framing and not an upstream metric, with a different owner for each factor.
    3. 13:05 Seol Heo says their initial hit rate was 71.6% because routing on pod load sent turns of one conversation to different pods, duplicating prefixes in GPU memory and causing evictions.
    4. 17:38 He says that after prefill was optimized the queue became the bottleneck, and setting vLLM's max number of sequences to 24 brought time to first token from 2.09 to 0.39 seconds in their benchmark.
    5. 20:11 He reports that separating prefill and decode pools, with KV transfer over InfiniBand RDMA through NIXL, cut inter-token latency from 69.8 to 19.5 milliseconds while generation throughput fell about 30%.
