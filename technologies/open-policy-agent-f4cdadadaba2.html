    Agentic Ops: Building Guardrails for Autonomous AI with Policy-as-Code

    Pavan Madduri

    The speaker describes the guardrails he wants before agents act on production clusters: GitOps-only writes, a shadow mode, least privilege and Kyverno policies as a deterministic ring around the agent. He frames unsafe agent actions as a permissions problem, not a model problem, and sorts actions into ones the agent may take alone, ones that need human approval and ones that are always denied.

    25 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: You are considering letting AI agents remediate incidents on Kubernetes and want a staged, policy-backed way to limit what they can do.

    1. 0:56 The speaker describes an agent that, when a restart did not clear an alert, scaled the workload down and deleted its PVC, causing a data recovery incident.
    2. 3:21 He lays out autonomy levels from L0, where humans do everything, through suggestions and shadow mode to L3 with guardrails, and says he would not suggest L4 full autonomy without concrete guardrails.
    3. 4:56 He sets the rule that the agent only writes to Git, so every fix becomes a pull request that a human approves and a policy check validates before it reaches the cluster.
    4. 12:20 He shows a hard-deny Kyverno policy that matches every service account in the agent namespace and blocks actions on PVCs, namespaces, StatefulSets, roles and role bindings.
    5. 14:00 He sorts actions into three colors: green ones such as restarts and bounded scaling the agent does alone, amber ones that need human approval, and red ones such as data deletion that are always denied.

    Cedar Authorization with Incomplete Information

    John Kastner

    John Kastner, a Cedar maintainer at Amazon Web Services, explains how partial evaluation lets Cedar authorize a request when some information is not yet known. He walks through an AI assistant that sends email, where he says the user is asked for approval only when the other policies cannot decide.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policyAI agents and automation

    Watch this if: you want an AI agent or service to ask for approval or fetch data only when the authorization decision needs it.

    1. 0:48 John Kastner says Cedar is an authorization policy language designed around four principles: expressive, fast, safe and analyzable.
    2. 1:12 He sets up the use case: an AI assistant that sends email on your behalf, with something in the middle deciding when that is allowed and when a human needs to intervene.
    3. 1:41 He shows three policies: allow email to members of his team, never allow email with confidential information, and for any other case ask him for explicit approval.
    4. 2:50 He says partial evaluation lets the request leave the approval unknown, so an email to a teammate is allowed without asking the user, which he presents as a way to avoid decision fatigue.
    5. 4:44 He generalizes the pattern: give the partial authorizer what you know, and if it cannot decide, it returns residual policies that show which expensive information to fetch.

    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    Kubernetes Solutions for Agent-Shaped Problems

    Tim Hockin, Dmitry Berkovich

    Tim Hockin and Dmitry Berkovich of Google say agent workloads are bursty, run untrusted code and have a human waiting, which makes one sandboxed pod per agent session wasteful and slow on Kubernetes. They present Agent Substrate, an open source system built on Kubernetes that suspends idle agents to snapshots and resumes them on request, and spend the second half answering audience questions about policy, autoscaling, memory and where it fits.

    30 min slot · Any Level · Session

    AI agents and automationKubernetes internals and runtimes

    Watch this if: you run or plan to run many agent sessions on your own Kubernetes clusters and want the reasoning behind Agent Substrate from its authors, plus a long Q&A on its current limits.

    1. 0:47 Hockin and Berkovich name three traits of agent workloads: they are bursty and mostly idle, they run untrusted code that must be sandboxed, and a human is usually waiting for the response.
    2. 6:57 Hockin states the three design principles of Agent Substrate (security by default, near-zero cost for idle agents, fast wake-up) and what he calls aspirational goals: billions of agents per cluster, 10,000 activations per second and wake-up in about 100 milliseconds.
    3. 9:16 Berkovich defines the five terms: an actor runs one agent session, an actor template configures it, a worker is the pod that hosts actors, a node-level manager handles images and snapshots, and a network layer routes requests in and applies policy to traffic out.
    4. 13:06 He explains resume speed through layers: volumes always survive, while root filesystem changes and the memory snapshot are reused only if the OCI image is unchanged, otherwise the actor cold starts from its volumes.
    5. 15:26 Hockin describes a use case they see often: a managed agent service runs the agentic loop while the work it triggers runs in Agent Substrate inside the customer's own cluster, where it can be audited and shut off.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    Rego Without Borders: Breaking Down Language Barriers for Security Policy

    Philip Conrad

    Philip Conrad, an Open Policy Agent maintainer, describes how the project wants policy decisions to run inside applications instead of in a sidecar, which he says has so far been easy only in Go. He explains how the Rego intermediate representation lets other languages run policies natively, and names Swift OPA and the Java OPA SDK as two new projects that do it.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policy

    Watch this if: you want to run Rego policies inside a Swift or Java application without calling a separate Open Policy Agent over the network.

    1. 0:41 Philip Conrad describes Open Policy Agent as a general purpose policy engine, a CNCF graduated project since 2021, that takes structured input such as JSON or YAML and returns decisions.
    2. 1:36 He says the community increasingly wants the policy engine embedded in the application itself instead of running as a sidecar.
    3. 2:22 He says Go makes it hard to package a library for other languages, so those languages have been limited to REST API calls to an Open Policy Agent running elsewhere.
    4. 2:58 He explains the Rego intermediate representation from the project's Wasm pipeline: query plans that break rules into smaller imperative instructions, built with opa build and a plan target.
    5. 3:46 He names Swift OPA and the Java OPA SDK as two new projects this year that run these plans natively, and says the main gain is debugging, with data-heavy policies sometimes running faster than in OPA.
