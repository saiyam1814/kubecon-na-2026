    Engineering Kubernetes for the Next Era of Workloads

    Mike Stefaniak

    Mike Stefaniak describes bottlenecks AWS found when running large Kubernetes clusters and says the team contributed fixes upstream. He walks through watch-cache and scheduler changes, accelerator-aware provisioning with Karpenter, and parallel image unpacking in containerd.

    5 min slot · Level not listed · Keynote

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run large GPU clusters and want concrete examples of upstream fixes from image unpacking to accelerator placement.

    1. 0:47 Stefaniak says AWS replaced a long-held Kubernetes API server watch-cache lock with a lazy snapshot, cutting writer wait from over half a second to 2 ms in its million-pod benchmark.
    2. 1:03 Stefaniak says a new Horizontal Pod Autoscaler selector store removed a read/write bottleneck, letting AWS run four times as many HPA workers in its largest clusters.
    3. 1:21 Stefaniak says an incremental scheduler cache avoided rebuilding volume reference counts and that AWS saw scheduling stay above 300 pods per second in its largest clusters.
    4. 2:28 Stefaniak explains that Dynamic Resource Allocation can describe GPU and network topology, and says Karpenter can now model devices for instances it has not launched yet.
    5. 3:48 Stefaniak says parallel layer unpacking in containerd brought a 10 GB image pull from about two minutes to under 45 seconds in AWS's testing.

    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    Governing and Scaling Agents in Heterogeneous Environments

    Antonio Ojea, Tomás Tormo

    Antonio Ojea and Tomás Tormo say agents on phones, laptops, and in clusters need common identity and policy without forcing every workload into Kubernetes. They present Agent Mesh and demonstrate how node-level policy limits who can reach services in a simulated hospital workflow.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You need agents to discover services across devices and clouds without giving every node the same access.

    1. 4:06 The speakers describe why the same connectivity layer needs to run as an edge gateway, inside an agent framework, or beside a workload in a Kubernetes pod.
    2. 8:57 The speakers describe using libp2p for a distributed data plane with service discovery and cryptographic node identities.
    3. 15:04 The speakers explain that Biscuit credentials can be checked offline and narrowed when a node delegates access to a sub-agent.
    4. 18:11 The speakers distinguish the control plane that enrolls nodes, the routers that keep the distributed network connected, and the nodes or SDKs used by agents.
    5. 29:38 In a simulated hospital workflow, the speakers recap how the mesh blocked traffic to an out-of-region agent and rejected requests from nodes without the required identity.

    Here be DRAgons: Bringing native zero-copy networking to Pods with Cilium and netkit

    Daniel Borkmann, Aaron Campbell

    The speakers compare two Cilium network drivers for Kubernetes Dynamic Resource Allocation, one using SR-IOV and the other using netkit with queue leasing. They demonstrate how a pod can use a leased hardware receive queue and explain how zero-copy receive works with the kernel networking stack.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you are evaluating hardware-accelerated pod networking and want to understand what Cilium queue leasing requires.

    1. 8:37 Borkmann explains how running BPF in the netkit device driver reduces the queue traversals seen with virtual Ethernet devices.
    2. 14:33 He introduces Cilium's two DRA driver options, SR-IOV and netkit queue leasing, and describes how the agent integrates with the node.
    3. 19:54 He explains how Linux queue leasing removes selected receive queues from the default set and binds them to a netkit device in a pod.
    4. 22:13 Campbell begins the demo by showing the operator's view of queue leasing and identifying the required hardware receive-queue capabilities.
    5. 30:22 He explains how packet headers stay in kernel memory while io_uring enables payload delivery directly to user space.
