    Cloud Native: Built by Humans, Engineered to Evolve

    Jeffrey Sica

    Jeffrey Sica argues that cloud native can adapt to AI because the people who maintain its projects keep changing how they work without abandoning human review. He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    10 min slot · Level not listed · Keynote

    Community and open source adoptionKubernetes internals and runtimes

    1. 2:55 Sica asks the audience to see the people who keep showing up behind each logo in the cloud native landscape.
    2. 4:25 Sica says maintainers responded to AI-generated contributions by writing policies for what a good contribution looks like and what they expect the submitting human to review.
    3. 5:37 Sica uses the term agent speed for the number of machine actions between human decisions and argues that the change matters for software architecture.
    4. 6:30 Sica points to small blast radii, fast iteration and rollback, sandboxing, and APIs as reasons cloud native systems can adapt to agent workloads.
    5. 7:59 Sica argues that Kubernetes fits training and inference because they are distributed systems problems, not because Kubernetes was originally built for AI.

    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    Dockerfiles Made Software Reproducible. What Makes an Agent Reproducible?

    Per Krogslund

    Per Krogslund argues that a Dockerfile describes an agent's workload but says nothing about what the agent is allowed to reach, and presents Docker's open sandbox kit spec, which records those capabilities as annotations on an OCI image. He shows kits being run and built with Docker's microVM-based sandbox runtime and takes audience questions on Kubernetes support, other runtimes and updating a kit's metadata.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run coding agents and want to see one proposal for declaring an agent's network, credential and device access alongside its image so teams can share and check it.

    1. 4:54 Krogslund says a container is process isolation and not a security boundary, and that running a coding agent in a privileged container with access to the Docker socket gives it a route to the host machine.
    2. 6:57 He says Docker is building an agent runtime and supply chain on top of OCI and not a new format, that the sandbox kit spec is already open source, and that Docker has discussed handing it over to the CNCF.
    3. 11:03 He describes Docker's own runtime as a microVM with a private Docker engine whose only way out is a network proxy, which applies allow and deny rules and swaps a placeholder credential for the real one on outbound requests.
    4. 13:36 He walks through a kit's YAML file, which names the hosts the agent needs, the service credential it needs without storing it, and any agent context file, and later shows network rules that differ between install and run time.
    5. 21:31 Asked about Kubernetes, he says there is no Kubernetes runtime yet beyond an experimental version inside Docker, that the focus so far is the local experience, and that he wants input on the use cases.

    Lessons Learned Sandboxing Agents with kagent

    Peter Jausovec, Nina Polshakova, Eitan Yarmush

    Peter Jausovec and Eitan Yarmush of Solo.io, the two speakers heard in the recording, walk through the sandboxing approaches they tried for kagent and say each one still kept an idle agent's pod running or tied identity to the pod. They explain why kagent 1.0 was rebuilt on Agent Substrate, list five lessons from that work, and demo Claude Managed Agents sessions running in sandboxes on their own cluster.

    30 min slot · Any Level · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing how to sandbox AI agents on Kubernetes and want to hear what one team found lacking in pod-per-agent setups.

    1. 3:40 Jausovec says they tried four things before Agent Substrate: their own pod-per-agent runtime, Anthropic's Sandbox Runtime, Agent Sandbox and NVIDIA's OpenShell, and that each solved only part of the problem.
    2. 9:08 Jausovec gives the reasons for Agent Substrate: idle agents are snapshotted to object storage and hold no compute, the Kubernetes API is off the hot path, restores take milliseconds, and actors are sandboxed with default-deny networking.
    3. 10:04 Yarmush tells how Solo started building an internal sandbox layer called Moat, then joined Google's Agent Substrate work instead, and says kagent 1.0 is now based entirely on Agent Substrate.
    4. 17:42 Yarmush starts the takeaways: isolation is table stakes and pause and resume is the hard part, every control must sit outside the agent, identity follows the actor, a suspended agent is stored data, and the sandbox runtime becomes a data format.
    5. 22:56 Demo: Jausovec creates two Claude Managed Agents sessions whose sandboxes run on his cluster, shows that one session cannot read the other's file, and shows a blocked request succeed after he applies an egress policy.

    SIG-Node: Intro and Deep Dive

    Peter Hunt, Tim Allclair, Dawn Chen, Mrunal Patel, Sergey Kanzhelev

    Host Peter Hunt introduces what SIG Node owns and then runs a panel of SIG Node leads on how the kubelet should serve agentic workloads alongside traditional ones. The panelists discuss dynamic containers, agent frameworks that bypass Kubernetes features, and how the SIG is trying to move enhancements from alpha to GA faster.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAI agents and automation

    Watch this if: you run agent or other short-lived workloads on Kubernetes and want to hear where SIG Node is taking the pod and the kubelet.

    1. 3:54 Peter Hunt lists what he says went GA in Kubernetes 1.36 and 1.37, including user namespaces, PSI and OCI volumes, and what moved to beta.
    2. 9:36 Dawn Chen says agent frameworks find the API server too slow for actors that want to resume in milliseconds, and that she told the Agent Substrate team to move fast and learn from users.

    5. 31:27 Asked when dynamic containers will be ready, Tim Allclair says the plan is alpha in 1.38, beta in 1.39 and GA in 1.40, and that he would not be surprised by a delay.

    The Next Generation of Kyverno — Unified Policy as Code at Scale

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.
    3. 11:57 He describes a policy that intercepts Argo CD sync events and allows them only when a custom resource shows an approved change management window is open, with a precise denial reason otherwise.
    4. 13:34 He shares lessons learned: start in audit mode, treat the denial message as the user interface, make the paved path compliant by default and ship policy through the normal software lifecycle.
    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.
