    Building the Next Generation of AI with Open Source

    Warren Barkley, Ali Golshan

    The speakers describe NVIDIA's open-source contributions to GPU scheduling and argue that agent workloads are changing how they size AI infrastructure. They introduce NVIDIA Kubernetes Engine for building AI infrastructure and describe OpenShell as a runtime for governing agent behavior.

    7 min slot · Level not listed · Keynote

    AI inference and servingCommunity and open source adoption

    Watch this if: you want NVIDIA's overview of its open-source AI infrastructure work, from GPU scheduling to agent runtimes.

    1. 0:27 The speaker says NVIDIA donated its DRA driver, KAI Scheduler, and Run:ai to the open-source community.
    2. 1:26 The speaker uses OpenRouter as an example, saying agent-generated tokens passed human-generated tokens there in February.
    3. 2:08 The speaker says NVIDIA is specifying more CPUs per GPU for some AI factory workloads and attributes the shift to agents.
    4. 3:15 The speaker introduces NVIDIA Kubernetes Engine as a set of components and recipes for getting from bare-metal provisioning to serving model tokens.
    5. 3:40 The speaker describes OpenShell as a runtime for governing agent behavior and says NVIDIA is donating it to the cloud-native community.

    Cloud Native: Built by Humans, Engineered to Evolve

    Jeffrey Sica

    Jeffrey Sica argues that cloud native can adapt to AI because the people who maintain its projects keep changing how they work without abandoning human review. He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    10 min slot · Level not listed · Keynote

    Community and open source adoptionKubernetes internals and runtimes

    Watch this if: you want to connect AI agent workloads to the reliability practices and contribution norms cloud native teams already use.

    1. 2:55 Sica asks the audience to see the people who keep showing up behind each logo in the cloud native landscape.
    2. 4:25 Sica says maintainers responded to AI-generated contributions by writing policies for what a good contribution looks like and what they expect the submitting human to review.
    3. 5:37 Sica uses the term agent speed for the number of machine actions between human decisions and argues that the change matters for software architecture.
    4. 6:30 Sica points to small blast radii, fast iteration and rollback, sandboxing, and APIs as reasons cloud native systems can adapt to agent workloads.
    5. 7:59 Sica argues that Kubernetes fits training and inference because they are distributed systems problems, not because Kubernetes was originally built for AI.

    Platform-First AI Agent Security: Zero-Trust Patterns for Kubernetes

    Carlos Santana

    Carlos Santana argues that a Kubernetes platform should treat agent-generated code as untrusted and provision isolation, credentials, and network policy separately. He describes using kro to compose those controls behind a platform API and shows captures of an Agent Sandbox warm pool assigning a ready pod.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to give teams a Kubernetes API for agents without giving those agents unrestricted access.

    1. 5:25 Santana describes SPIFFE and SPIRE as a way to identify an agent by URI and associate that identity with a credential across different environments.
    2. 12:14 Santana shows a kro ResourceGraphDefinition and explains how a declarative resource graph can give platform users a custom API without requiring the platform team to write a Go controller.
    3. 19:05 Santana compares gVisor, Kata Containers, and AWS Nitro Sandboxes as different isolation choices for running untrusted agent code.
    4. 21:27 Santana shows captures of a two-pod Agent Sandbox warm pool and says applying a claim assigned a ready pod instead of waiting for a fresh sandbox to start.
    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    Running Secure Agents at Scale

    Carlos Sanchez

    Carlos Sanchez describes how Adobe runs browser workloads for AI agents without running those browsers in the agent pods. He compares Kubernetes sandboxing options and walks through how Adobe uses Agent Sandbox to allocate, reuse, and retire remote Playwright environments.

    30 min slot · Advanced · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You run AI agents on Kubernetes and want to isolate remote browsers without changing how clients use Playwright.

    1. 3:50 Sanchez describes how single-writer persistent volumes can make rollouts interrupt an agent session while a replacement Kubernetes pod waits for the old one.
    2. 9:27 Sanchez names the sandboxing options he evaluated for Playwright, including Agent Sandbox, OpenShell, and Agent Substrate.
    3. 13:08 Sanchez shows the application design: the agent sends Playwright traffic to a proxy that decides whether to reuse or allocate a browser sandbox.
    4. 16:16 Sanchez explains how the controller uses a template, a warm pool, and a claim to give a caller a sandbox.
    5. 24:20 Sanchez describes keeping three Chromium and Playwright instances warm to reduce the wait when an agent requests a browser.

    Sandbox Your Agents

    Jessica Forrester

    Jessica Forrester describes how a Red Hat coding agent drifted from its assigned task and explains why her team relies on enforced policy rather than prompts alone. She demos how OpenShell blocks and logs actions outside policy, then describes running sandboxes in Kata Containers to give them separate kernels.

    5 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you are giving coding agents access to internal systems and want an example of enforcing boundaries outside the prompt.

    1. 0:41 Forrester describes a requirements-scoring agent that started inventing ideas without being attacked, and says Red Hat designs its platform as if agents were already compromised.
    2. 1:34 Forrester compares prompts to signs in an escape room and enforced policies to bolts that prevent players from moving things they should not touch.
    3. 2:16 Forrester demos an agent that can read a GitHub README but cannot follow instructions outside its policy, and explains how denied attempts can become access proposals for review.
    4. 3:16 Forrester says standard OpenShell containers share a host kernel and describes using Kata Containers to put the sandbox behind a separate kernel.
    5. 3:53 Forrester says OpenShell gives agents placeholder credentials and swaps in the real credentials when an allowed request leaves the sandbox.
