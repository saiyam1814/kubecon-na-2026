    Autoscaling Reality Check: The Hands-On HTTP Optimization Challenge

    David Pech

    David Pech runs a hands-on tutorial in which attendees benchmark HTTP services in NGINX, Go, PHP and Java with k6 and watch how autoscaling reacts, first with the CPU-based Horizontal Pod Autoscaler and then with Knative scaling on concurrent requests. He walks through each round on a Grafana dashboard and describes the tuning he tried, including cases where he says his own improvement failed.

    80 min slot · Any Level · Tutorial

    Accelerators and workload schedulingObservability and reliability

    Watch this if: you run HTTP services behind HPA or Knative and want to see, round by round, where autoscaling lags behind real traffic.

    1. 10:11 The speaker lays out the lab: Argo CD, Istio, Knative and a Prometheus stack on a local k3d cluster or GitHub Codespaces, with k6 load tests run against services in several flavors.
    2. 29:15 In the NGINX round scaled on CPU, the speaker shows on the dashboard that pods stay at the maximum after the load falls and that latencies remain, and asks the room why.
    3. 36:23 The speaker explains Knative's panic window: when demand jumps well above the estimate the autoscaler enters panic mode and does not scale down during it.
    4. 1:03:46 For the Java round the speaker says slow startup limits how fast scaling can react, names GraalVM as one option, and shows a tuning attempt that he says failed completely.
    5. 1:06:13 In the scale-to-zero round the speaker points out that a workload at zero has no metrics, which he says makes alerting on it hard.

    Fluent Bit: The Evolution of High-Performance Telemetry Pipelines

    Eduardo Silva

    Eduardo Silva introduces Fluent Bit as an agent or aggregator for moving logs, metrics and traces, and announces the Fluent Bit 5.2 release. He highlights a new typed Lua scripting interface, performance comparisons he presents against Fluent Bit 5.1 and the OpenTelemetry Collector, and a build of Fluent Bit that runs in the browser.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliability

    Watch this if: You run Fluent Bit and want the 5.2 release highlights in five minutes.

    1. 0:49 Eduardo Silva says Fluent Bit collects from sources such as journald, HTTP and OTLP with more than a hundred connectors, then filters data and routes it to multiple destinations.
    2. 1:46 He announces Fluent Bit 5.2 and lists a new journald collector that converts to OpenTelemetry logs, throttling for slow destinations, and improved filesystem buffering.
    3. 2:53 He says a new fully typed interface for Lua scripts, which he calls FTS, gives an API for logs, with the same available for metrics and traces.
    4. 4:11 He shows a comparison of the new version with Fluent Bit 5.1 and the OpenTelemetry Collector on throughput and CPU use when ingesting JSON logs and OTLP.
    5. 4:51 He says Fluent Bit can now be compiled to run in the browser, and that a first implementation called Fluent Bit Studio lets users test Lua scripts and processors before production.

    Kubernetes The Hard Way - Live

    Lucy Sweet, Sandeep Kanabar

    Lucy Sweet and Sandeep Kanabar build a Kubernetes cluster live, starting each component on local virtual machines. They trace an application from a kubectl request through the API server, the scheduler, and the kubelet to a running container.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimes

    Watch this if: You want to see what changes when each Kubernetes component starts and how those changes turn a pod request into a running container.

    1. 6:54 Kanabar starts etcd and inspects its membership, explaining how the API server uses it to persist cluster state.
    2. 7:58 Kanabar verifies etcd by writing and reading a key, then explains why the API server is the entry point for other control-plane components.
    3. 12:41 Sweet explains reconciliation as observing actual state and taking steps toward the desired state, using a deployment with missing replicas as the example.
    4. 13:55 Sweet distinguishes the controller manager, which runs core controllers, from the scheduler, which chooses a node for a pod.
    5. 17:35 Sweet shows why a pod stays pending until a node joins, then uses crictl to inspect the NGINX container running under containerd.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
