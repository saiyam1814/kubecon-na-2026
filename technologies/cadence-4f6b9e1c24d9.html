    Agents Fail. Workflows Recover. Durable Agent Orchestration with Cadence

    Diana Zawadzki, Shijie Sheng

    Diana Zawadzki and Shijie Sheng of Uber's Cadence team argue that agent workflows fail like any other workflow and describe wrapping model and tool calls as Cadence activities so a replacement worker can resume from recorded history. They show a demo of an error-analysis agent that survives a rate limit and a killed worker, share numbers from Uber's Agent Executor Service, and answer questions on Temporal, guardrails and operating Cadence.

    30 min slot · Any Level · Session

    AI agents and automationObservability and reliability

    Watch this if: you run long-lived AI agents in production and want to see how a workflow engine can let them resume after crashes instead of starting over.

    1. 1:02 Zawadzki explains the model: each model call is a Cadence activity, the workflow is the code that orders them, and progress is recorded in a separate service so a replacement worker can reuse completed results.
    2. 5:31 She says Uber's Agent Executor Service, built in July, hosted around 830,000 agentic workflows on Cadence in September for background and scheduled jobs.
    3. 8:19 Sheng demos an error-analysis agent with a human in the loop: a rate-limited log fetch is retried automatically, a human signal asks for more evidence, and after the worker is killed a new worker replays history to the current state.
    4. 12:33 Zawadzki says the protected run in their demo used about half the model responses and tokens of the raw run with zero new calls during recovery, while cautioning that failures were injected on purpose.
    5. 18:36 Asked how Cadence compares with Temporal, the speakers say Temporal forked from Cadence in 2019 and describe Cadence as the more community-driven CNCF project.

    Secure Your Agents in 5 Minutes: Durable Execution with Cadence

    Diana Zawadzki

    Diana Zawadzki of the Cadence team at Uber presents Cadence as a way to make long-running AI agent tasks durable, so that a crashed worker resumes from saved progress instead of starting over. She plays a recorded run of an on-call agent workflow that she says is deployed at Uber, with injected failures, and outlines the steps for wrapping an agent in Cadence activities and workflows.

    5 min slot · Level not listed · Lightning Talk

    AI agents and automationObservability and reliability

    Watch this if: you run long, multi-step AI agent tasks and want to see how a workflow engine keeps their progress across failures.

    1. 0:48 Diana Zawadzki describes Cadence as open source software built at Uber that tracks a job through its steps, so in her words a crash is a pause and not a reset from scratch.
    2. 1:15 She explains the model: the workflow tracks what happens next, activities are the model or tool calls, and if a worker stops another worker can pick up where it left off.
    3. 1:38 She lists what she says Cadence gives agents: recovery from crashes and API rate limits, waiting for human review, rewinding to the last viable step, and child workflows for child agents.
    4. 2:46 She introduces a case study, an on-call agent workflow she says is deployed live at Uber, that traces logs, drafts a report, waits for human review and saves the report.
    5. 3:44 She plays a recorded run in which a rate limit error is retried, a human signal asks for a deeper draft, and the workers are killed before the run resumes from saved progress and completes.

    Splitting the Monolith at Cloudera - Building Fault-Tolerant Workflows with Cadence

    Soma Koltai, Ender Demirkaya

    Soma Koltai of Cloudera describes moving the Cloudera Data Warehouse control service from a single Go binary to Cadence workflows, using a small bridging layer shaped like the Cadence client API and a lease service on PostgreSQL so the refactoring could start before Cadence was integrated. Ender Demirkaya of the Cadence project explains how workflows and activities recover state, and says the Cadence team built distributed semaphores after hearing about Cloudera's use.

    30 min slot · Advanced · Session

    Observability and reliabilityData, storage and state

    Watch this if: you are breaking up a stateful monolith with long-running operations and want a staged way to adopt a workflow engine.

    1. 1:47 Koltai says provisioning a cluster and restoring workloads can take a whole hour, and under the previous architecture a failure meant the whole process was retried.
    2. 5:36 Demirkaya explains that developers annotate one function as a workflow and its external calls as activities, and if everything crashes another worker continues where it left off.
    3. 9:48 Koltai describes the Async Executor, a bridging layer modeled on the Cadence client API that he says took about 600 lines and two weeks, and let them reuse every activity handler when they switched to Cadence.
    4. 12:32 For locking, Koltai says they chose leases, locks with a time to live, behind a three-method interface, implemented with essentially one insert call on the PostgreSQL database they already had.
    5. 18:54 Koltai tells of a memory leak that went unnoticed because Karpenter rescheduled the pod before it hit its memory limit, and says restarts after the migration no longer caused workflow failures or pages.
