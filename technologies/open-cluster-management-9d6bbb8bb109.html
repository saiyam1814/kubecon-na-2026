    Beyond Stateless vs Stateful: A Unified Workload API for Multi-Cluster Kubernetes

    Ronak Nathani

    Ronak Nathani describes how LinkedIn built a composable, multi-cluster workload API that treats the pod template, update strategy, persistence and placement as separate concerns instead of splitting workloads into stateless and stateful. He walks through the hub-and-spoke design, a demo of moving and coordinating workloads, and says the team plans to open source it.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesData, storage and state

    Watch this if: you design workload APIs for a platform that spans many clusters.

    1. 0:25 Ronak says LinkedIn's fleet has half a million machines, more than 3,000 applications and about 5 million containers, with over 100,000 deployments a week.
    2. 3:41 He introduces three objects: an immutable revision, a workload with replica count, revision distribution and update strategy, and a workload placement that admins control.
    3. 5:30 He says LinkedIn runs one generic controller for all stateful workloads and asks each team to write a coordinator that must approve every change before the workload acts.
    4. 11:15 He says pod disruption budgets stop working across clusters, so they use workload disruption budgets with an eviction webhook in each spoke that checks the hub.
    5. 17:43 Asked about existing projects, he says they looked at Open Cluster Management and Karmada but wanted rollouts, disruptions and availability respected globally rather than per cluster.

    Ground Control to Major Tom: We Need your Public Cloud in our Private Cloud

    Andrew Block, Mike Wilson

    The speakers, from Red Hat and Adobe, describe how an Adobe private cloud team that ran virtual machines on VMware is moving to OpenShift Virtualization and adopting the GitOps practices Adobe's public cloud Kubernetes platform, Ethos, already used. They cover the team's shift from click-driven operations to Git, architectural decision records kept in a repository, and lessons about working across storage, network and platform teams.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You are moving virtual machines from VMware to a Kubernetes-based platform and want to hear how one team changed its ways of working along the way.

    1. 6:23 Mike Wilson says the move was a business decision, not a technology one: after Broadcom acquired their main platform provider, Adobe chose OpenShift Virtualization and set a mandate to exit by 2028.
    2. 7:34 Wilson says the team's first instinct was to make the new platform feel as much like VMware as possible, and that they later moved to declarative, cloud native practices built on Kubernetes, Open Cluster Management, Argo CD and KubeVirt.
    3. 14:22 Wilson describes adopting architectural decision records in Git after decisions kept being reopened, and shows a cluster naming record with its proposed, accepted, rejected and superseded states.
    4. 16:39 He says the decision record repository was structured so AI agents can review it, for example checking whether a new implementation matches the recorded architectural intent.
    5. 24:03 Wilson says they have five production clusters and need to deploy around 60 more next year, using Open Cluster Management as the factory and a Cluster API provider so Ethos can target the private cloud.

    Hub → Managed Cluster: How Long Did the Workload Take? Did It Arrive?

    Suvaansh Kumar

    Suvaansh Kumar of Guidewire Software describes how to measure the time a ManifestWork takes to travel from an Open Cluster Management hub to a managed cluster, and how to tell that it never arrived. He says the approach matches a timestamp logged on the hub with one logged by the work agent, the latter added in OCM v1.4 by Guidewire.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliabilityDelivery, GitOps and release safety

    Watch this if: you deploy through an OCM hub and want a simple way to measure delivery latency to managed clusters.

    1. 0:26 Kumar says OCM is in its sixth year, is a CNCF incubating project and offers a hub-and-spoke model for deploying workloads to many clusters.
    2. 0:52 He says Guidewire used to deploy from CI/CD pipelines straight to managed clusters in different AWS regions and wants the same confidence once a hub sits in between.
    3. 2:09 He proposes an admission webhook on the hub that logs a timestamp with the ManifestWork name, managed cluster name and generation when a workload is applied.
    4. 2:34 He says the work agent on the managed cluster logs a second timestamp with the same keys when it observes the workload, a feature he says is in OCM v1.4 and was contributed by Guidewire.
    5. 3:24 He explains that if the second timestamp does not show up within a chosen timeout, the workload is treated as never having arrived.

    Multicluster AMA: The Community Answers

    August Simonelli, Laura Lorenz, Liqian Luo, Trevor Swanson

    Moderator August Simonelli puts audience questions about running many Kubernetes clusters to Laura Lorenz of SIG Multicluster, Liqian Luo of Azure Kubernetes Service and Trevor Swanson of Evernorth. The panelists share their views on going from one cluster to many, GitOps and scheduling, staged upgrades, self-service for developers, and where AI fits.

    30 min slot · Any Level · Panel

    Platform engineering and developer experienceNetworking and connectivityCommunity and open source adoption

    Watch this if: your cluster count grew without a plan and you want to hear how an operator, a cloud provider and the upstream SIG think about managing a fleet.

    1. 6:05 Laura Lorenz says SIG Multicluster focuses on APIs for cross-cluster problems and names the Multi-Cluster Services API, the Work API and the newer Cluster Inventory API.
    2. 8:05 Trevor Swanson advises building for a fleet of one cluster: nothing bespoke to a cluster name, label everything and make it policy-based from day one.
    3. 8:48 Liqian Luo says GitOps may suit static placement, but in her view is not enough when workloads must be placed by GPU type, topology and available capacity.
    4. 18:17 Lorenz says the SIG has focused on small composable building blocks rather than one monolithic solution, and that it could do more to explain how the pieces fit together.
    5. 23:45 Swanson argues that declarative beats clever when agents act on a fleet, and Luo says AI helps with observing and diagnosing but that letting it change clusters arbitrarily is not safe.

    N Clusters, One kubectl: Multi-Cluster That Just Works

    Anne Lau, Scott Brimhall

    The speakers describe how Salesforce spread workloads across clusters with Open Cluster Management and built a routing proxy so that developers keep using one kubeconfig and standard kubectl. They explain how the proxy fans out reads, sends writes to the hub's ManifestWorkReplicaSet, and routes logs and exec to the right cluster, followed by a recorded demo.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: You run workloads across several clusters and want developers to keep their single-cluster kubectl workflow.

    1. 2:25 The speaker says they chose Open Cluster Management and its ManifestWorkReplicaSet to run the same workloads in several clusters and load balance between them.
    2. 6:38 The speaker introduces what Salesforce calls Workload API, a routing proxy that passes Kubernetes API calls to the right cluster and stores no credentials on the server side.
    3. 8:02 The speaker explains reads: a list fans out to all managed clusters and aggregates the results with their origin, and a get treats the ManifestWorkReplicaSet spec as the source of truth.
    4. 10:56 The speaker explains how they guard against stale overwrites by using the parent ManifestWorkReplicaSet's resource version for concurrency control.
    5. 14:16 The recorded demo starts, showing get, scale, rollout restart, logs and exec through one gateway with standard kubectl.
