    Building Better Integration Test Images with Buildpacks

    Kathan Kashiparekh, Damini Satya

    Damini Satya and Kathan Kashiparekh of Salesforce describe how their integration testing platform team took over test image builds from service teams by adopting Cloud Native Buildpacks, replacing what they say were more than 6,000 Dockerfiles. They explain four buildpack concepts with examples from that work (buildpacks and builder images, layer caching, image extensions and rebase), show short demos, and close with when buildpacks fit and when Dockerfiles still do.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: your platform team maintains many similar Dockerfiles and you want to see how buildpacks centralize image builds and base image patching.

    1. 1:04 Damini Satya says service teams used to maintain a Dockerfile for every test repository, and that the platform team took over image builds with buildpacks and removed more than 6,000 Dockerfiles.
    2. 5:12 She walks through a minimal Python buildpack: a buildpack.toml manifest, a detect script that decides whether the buildpack applies, and a build script that creates a layer.
    3. 12:28 Kathan Kashiparekh contrasts Dockerfile caching, where changing one instruction invalidates everything after it, with buildpack layers that are isolated and marked for launch, build or cache.
    4. 16:06 He explains that buildpacks run as non-root and cannot install OS packages or pick a different run image, and that image extensions address this by generating a Dockerfile the lifecycle applies on top of the builder's images.
    5. 20:47 He describes rebase, which swaps a patched base image under unchanged layers with one pack rebase command instead of thousands of rebuilds, and says his team hopes to take it to production soon.

    No RAG, No Regrets: Letting an LLM Drive 30 EKS Clusters in Production

    Trevor Linton

    Trevor Linton describes how Mastercard built an agent harness to handle repeatable infrastructure work without retrieval-augmented generation. He walks through a cert-manager upgrade and explains how scoped tools, result filtering, token limits, and human approvals fit into the workflow.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You want to automate routine Kubernetes maintenance while keeping approvals and audit trails visible.

    1. 7:30 Linton says his team deploys its Node.js agent harness as a Kubernetes application and uses PostgreSQL to resume interrupted sessions.
    2. 10:16 Linton shows a cert-manager upgrade run that reads release notes, checks compatibility, proposes changes, and leaves merge and production change approvals to people.
    3. 11:39 Linton opens an audit trace that exposes individual tool calls and lets reviewers inspect the data given to the model.
    4. 16:46 Linton describes projections that filter or aggregate tool results before they enter the model context, using a SQL-like interface.
    5. 18:50 Linton explains how each task gets a hard token budget and iteration cap, with the remaining allowance available to the agent on each loop.

    What's New with Kubectl and Kustomize … and How You Can Help!

    Eddie Zaneski, Yugo Kobayashi, Maciej Szulik, Marly Salazar

    The SIG CLI maintainers walk through the past year of Kustomize and kubectl changes, including kuberc, KYAML and the move from SPDY to WebSockets. They then describe ideas they are still working on, ask for contributors, and take audience questions on drain flags and multi-cluster commands.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: you use kubectl or Kustomize daily and want to know what changed, what is planned, and where a first contribution is easiest.

    1. 5:18 Yugo Kobayashi says AI contributions have raised the number of open Kustomize PRs and that he is preparing an AI contribution guide: state when AI was used, generated code is acceptable, but AI is not to be used for communication with maintainers.
    2. 7:25 Marly Salazar covers kuberc, which she says now includes command aliasing and a credential plugin allowlist, and the maintainers say it has fully graduated.
    3. 10:35 Maciej Szulik explains new node lifecycle conditions for maintenance, which he says were published in 1.37 and are being added to kubectl drain as an alpha behind a feature flag.
    4. 14:42 Eddie Zaneski describes the idea of a CRI-native copy API to replace the tar-based kubectl cp, which the maintainers say has a long history of path traversal CVEs.
    5. 20:37 The maintainers say Kustomize is kept alive by one maintainer and ask users to get their employers to let them contribute.
