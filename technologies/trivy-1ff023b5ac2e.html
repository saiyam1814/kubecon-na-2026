    Gone in 60 Minutes: Effectively Close the Exploitable Window with Detection as Code

    Ben Hirschberg, Constanze Roedig

    Ben Hirschberg and Constanze Roedig show two ways to detect exploitation with Kubescape in the hours between a vulnerability becoming public and a patch being deployed, both shipped to the cluster as YAML through GitOps. Hirschberg writes rules from published indicators of compromise, and Roedig uses behavior profiles to flag deviations when the attacker's methods are not yet known.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyObservability and reliability

    Watch this if: you need a way to detect exploitation of a newly disclosed vulnerability in running workloads before a patch can be rolled out.

    1. 2:19 Hirschberg describes the setup: the Kubescape node agent with eBPF sensors and a rule engine whose detection rules are written in CEL, with alerts sent to Slack.
    2. 6:16 In a recorded demo he pastes the indicators of compromise from a published write-up of the poisoned Trivy GitHub Action into an AI agent, which opens a pull request with Kubescape detection rules that Argo CD syncs to the cluster.
    3. 9:32 Roedig introduces what she calls a software bill of behavior, a custom resource listing allowed capabilities, network traffic, executables and file opens as composable fragments that can be signed separately.
    4. 11:56 She says build runners are a poor fit for anomaly detection because their behavior is not bounded, then shows a profile-based setup still flagging the same indicators as the rules did.
    5. 16:54 For a PHP server that normally spawns shells, she says the profile caught the exploit because the id command ran outside the expected process tree, and argues a good profile has as few entries as possible.

    Harbor Project – The Maintainers Session

    Orlin Vasilev, Vadim Bauer, Rani Chowdary Mandepudi

    Three Harbor maintainers and contributors cover what is in Harbor 2.16, including custom project roles, proxy cache filters and upstream Arm64 builds, and share community statistics. They then outline what they are working on for 2.17, such as syncing AI models from Hugging Face into Harbor as OCI artifacts, and ask for feedback on the open proposals.

    30 min slot · Level not listed · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you run Harbor and want to know what 2.16 changed and what the maintainers plan for 2.17, or if you need Harbor on Arm.

    1. 0:40 Vadim Bauer lists the highlights he picks from Harbor 2.16: custom project roles, a configurable proxy cache with bandwidth limits and regex filters, Valkey replacing Redis, multi-architecture images and PostgreSQL 18.
    2. 7:36 Rani Chowdary Mandepudi explains how Arm64 support landed upstream in four parts: native CI, build tooling, online and offline installers, and multi-platform OCI manifests.
    3. 14:23 Orlin Vasilev shows that pull requests nearly doubled year over year, which he attributes to AI, and asks contributors to link an issue, keep PRs small and be patient.
    4. 18:05 Vadim Bauer describes the model sync proposal for 2.17: replicate models from Hugging Face and convert them on the fly into OCI artifacts in the model spec format.
    5. 21:13 Vadim Bauer describes a proposed scanner spec upgrade that he says would let Harbor run several scanners at once, including linters, license and secret scanners, and aggregate the results.

    I Packaged My Application in a Container Image, and Now What?

    Aurélie Vache

    The speaker takes a small Go API packaged as a container image and walks through supply chain security steps for it, with a live demo for each one. She covers generating an SBOM, scanning for vulnerabilities, publishing a VEX file, signing the image, generating SLSA provenance and automating all of it in a GitHub Action.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: You can build and push a container image and want to see the next supply chain security steps done live, one command at a time.

    1. 2:18 The speaker starts with the SBOM, an inventory of the components in an image, and says it is no longer nice to have but becoming mandatory.
    2. 10:32 In the demo, a Trivy scan of the image reports 26 vulnerabilities, and the speaker points out that the first one applies to a Go version her application does not use.
    3. 13:22 The speaker introduces VEX as a way to tell users whether a vulnerability is exploitable in the application, and says OpenVEX is her favorite format.
    4. 17:11 After generating a VEX file with govulncheck and fixing its product ID, the speaker scans again with Trivy and she says the filtered result shows zero exploitable ones among the high and critical findings.
    5. 20:32 The speaker generates a key pair in a KMS, signs the image with Cosign and verifies the signature.

    Kyverno: The Supercharged Future of Cloud Native Policy as Code

    Jim Bugwadia

    Jim Bugwadia presents Kyverno as a framework for governance in Kubernetes, with policies written as declarative YAML and enforced in pipelines, at admission control and at runtime. He describes its policy types, exception management and reporting, and says it now also applies to other JSON and YAML such as Terraform, OpenTofu and Dockerfiles.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you want a five-minute overview of what Kyverno covers beyond Kubernetes admission control.

    1. 0:48 Jim Bugwadia describes Kyverno as a framework that enables governance in Kubernetes by making policies as simple to write as any Kubernetes manifest.
    2. 1:40 He says Kubernetes native policies only apply at admission control, while Kyverno also covers existing resources and adds image verification, complex checks, exception management and reporting.
    3. 2:08 He lists the policy types: validate, mutate, generate, and delete or clean up resources, plus image verification for signing and attestations.
    4. 2:29 He says later releases apply Kyverno policies to any JSON or YAML, such as Terraform, OpenTofu, Dockerfiles and cloud configurations, and mentions AI use cases like intercepting MCP and LLM calls with Envoy.
    5. 3:41 He says every enforcement point needs to produce reports for compliance, and that Kyverno supports OpenReports, a format he says other tools such as Trivy also produce.

    Public Sector User Group BoF: Roadmap, White Papers, Our Group

    William Crum, Daniel Moch

    William Crum and Daniel Moch describe how the CNCF Public Sector User Group brings shared problems to the wider cloud-native community. They review the group's secure software delivery paper and ask for input on a planned paper about delivering software into disconnected environments.

    30 min slot · Level not listed · Birds of a Feather

    Community and open source adoption

    Watch this if: you deliver cloud-native software into air-gapped environments and want to compare approaches with public-sector peers.

    1. 2:33 The speakers describe the user group as a way for people running cloud-native systems in production to identify common problems and bring them to CNCF advisory bodies.
    2. 6:31 The speakers say their first white paper covers trusted software delivery and how producers can package, sign, and attest software for public-sector consumers.
    3. 8:01 The speakers describe comparing how Hoppr and Droppr, Zarf, the Open Component Model, and Hauler approach software delivery into disconnected environments.
    4. 9:24 The speakers say the next white paper aims to give teams a shared vocabulary for air-gapped deployments, including the work of mirroring registries and sideloading images.
    5. 16:59 In the discussion, the speakers suggest starting in the user group and bringing the question to the Technical Advisory Board if it draws wider interest.
