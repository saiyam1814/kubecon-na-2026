    Splitting the Monolith at Cloudera - Building Fault-Tolerant Workflows with Cadence

    Soma Koltai, Ender Demirkaya

    Soma Koltai of Cloudera describes moving the Cloudera Data Warehouse control service from a single Go binary to Cadence workflows, using a small bridging layer shaped like the Cadence client API and a lease service on PostgreSQL so the refactoring could start before Cadence was integrated. Ender Demirkaya of the Cadence project explains how workflows and activities recover state, and says the Cadence team built distributed semaphores after hearing about Cloudera's use.

    30 min slot · Advanced · Session

    Observability and reliabilityData, storage and state

    Watch this if: you are breaking up a stateful monolith with long-running operations and want a staged way to adopt a workflow engine.

    1. 1:47 Koltai says provisioning a cluster and restoring workloads can take a whole hour, and under the previous architecture a failure meant the whole process was retried.
    2. 5:36 Demirkaya explains that developers annotate one function as a workflow and its external calls as activities, and if everything crashes another worker continues where it left off.
    3. 9:48 Koltai describes the Async Executor, a bridging layer modeled on the Cadence client API that he says took about 600 lines and two weeks, and let them reuse every activity handler when they switched to Cadence.
    4. 12:32 For locking, Koltai says they chose leases, locks with a time to live, behind a three-method interface, implemented with essentially one insert call on the PostgreSQL database they already had.
    5. 18:54 Koltai tells of a memory leak that went unnoticed because Karpenter rescheduled the pod before it hit its memory limit, and says restarts after the migration no longer caused workflow failures or pages.
