    Don’t Lose Your Agent’s Mind: Platform Patterns for Stateful Agents

    Evaline Ju, Maia Iyer

    The speakers explain why stateful agents lose sessions, files, and context when treated like ordinary pods, and they examine community work on sandboxing, snapshotting, and resuming agent state. They present their moca prototype and argue for server-held sessions, harness-neutral state, and an open harness-sandbox boundary.

    25 min slot · Any Level · Session

    AI agents and automationData, storage and state

    Watch this if: you are designing Kubernetes platform support for stateful or delegated AI agents.

    1. 4:00 The speakers say a plain pod is a poor fit for stateful agents because deleting the pod discards sessions, files, and learned context.
    2. 5:48 The speakers point to Agent Sandbox templates and Agent Substrate snapshot and resume work as community efforts aimed at configurable isolation and multiplexing idle agents.
    3. 9:19 The speakers present moca as their open-source managed-agents experiment, using Pi for the harness, Valkey for externalized sessions, and a relay boundary into pluggable sandboxes.
    4. 16:10 In the recorded demo, Evaline shows the user closing a session, starting another one, and still picking up the subagent's work without resending context.
    5. 18:41 The speakers argue that platforms should make sessions first-class and server-held, treat agent state as harness-neutral data, and make the harness-sandbox boundary an open protocol, while provenance, cost attribution, legibility, and delegated trust remain open.

    From Clever to Correct: Lessons from Rebuilding SeatGeek's Platform AI Agent

    Colin O'Dell

    Colin O'Dell describes why SeatGeek replaced its specialist-heavy platform agent, Rufus, with a generalist agent called Sandy that can carry a task from investigation through a code change. He explains how a per-session sandbox keeps full logs out of the agent's context and how the team uses reports from Slack or Jira to improve the agent itself.

    10 min slot · Intermediate · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You are deciding what to build yourself when an internal platform agent needs to diagnose problems and make changes.

    1. 1:23 O'Dell explains how Rufus routed requests to four specialists that could not easily hand work off. An Argo CD specialist could diagnose a deployment failure but could not pass the fix to the coding agent.
    2. 4:10 He describes rebuilding around one OpenCode harness and a per-session sandbox, where Sandy can store full logs on disk and pull only the relevant lines into its context.
    3. 6:43 He explains why the team reused OpenCode and Daytona for the harness and sandboxes, leaving more time for platform-specific routines and skills.
    4. 7:05 He describes how the team uses Sandy to fix Sandy: a report from Slack or Jira can start a sandboxed fix and merge request. He also describes a tool that posts a short report when the agent gets stuck.
    5. 8:56 He argues for treating the internal agent as a product that keeps evolving, after putting Rufus into maintenance mode made later improvements harder to adopt.

    GitOps Without You Writing YAML: How Flux Grounds AI Agents in Real APIs

    Stefan Prodan

    Stefan Prodan argues that AI agents struggle more with Kubernetes YAML than with code because they lack a fast way to verify it, and presents the Flux Schema CLI plugin, a public catalog of custom resource schemas and an MCP server that he says give agents that feedback loop without a live cluster. He also describes the GitOps agent skills the Flux maintainers wrote and evaluated, and closes with the Flux roadmap and how to contribute to the catalog.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyAI agents and automation

    Watch this if: you use AI coding agents to write Kubernetes or Flux manifests and want to see how the Flux maintainers validate and ground that output.

    1. 1:01 Stefan Prodan says his conclusion from the Flux team's experiments is that generating YAML is harder for AI than generating code, because agents can test code in a fast loop but have no equivalent check for configuration data.
    2. 8:47 He introduces Flux Schema, a Flux CLI plugin that he says reproduces the Kubernetes API's validation rules offline, including label value rules and SOPS-encrypted secrets, and works on any Kubernetes YAML, not only Flux repositories.
    3. 13:27 He describes a public MCP server built on the project's ecosystem catalog of controller schemas, which he says reached one million requests a day and sees similar traffic from Codex, Claude and Copilot.
    4. 17:03 He says returning full OpenAPI schemas made agents hallucinate in long sessions, so the MCP server now exposes a grep schema tool that returns a compact format, after which he could generate hundreds of manifests.
    5. 26:48 He says the first agent skills were built with frontier models and failed on quantized open models he ran at home, so the team rewrote them, and he advises evaluating skills on weaker models.

    How Far Are Open-Source LLMs from Running Real Kubernetes Operations? A 10-Scenario Benchmark

    Hoon Jo

    Hoon Jo presents his own benchmark of 10 Kubernetes incident scenarios, run many times against open-weight and commercial models through the goose, OpenCode and Codex harnesses on a single MacBook with Ollama. He reports that mid-sized open-weight models handled the routine scenarios about as well as commercial ones in his runs, but in the complex scenarios some of them reported fixes that were not fixes or took actions he scores as unsafe.

    30 min slot · Any Level · Session

    AI agents and automationObservability and reliability

    Watch this if: you are thinking about letting a self-hosted open-weight model handle Kubernetes incidents and want to see where one benchmark found it safe and where it was not.

    1. 8:30 Jo describes his method: 10 scenarios, each run 20 times or more per model, with accuracy judged from API server audit logs and safety scored separately, including whether the agent undoes or leaves behind resources.
    2. 13:50 He shows the overall scores: commercial models come out on top, while the best open-weight models score close to the lowest commercial ones, and the gap he sees is in the complex scenarios, not the routine ones.
    3. 18:23 In the ephemeral storage scenario, where an app's growing logs keep restarting the pod, he shows agents expanding the storage and reporting the problem solved, which he counts as a temporary fix.
    4. 20:51 In the chaos scenario another team's chaos job is causing the failures; Jo says the right action is to analyze, stop and hand over, and shows a Qwen model patching the job to pause it instead.
    5. 26:24 For the unsafe-action scenario the database sits outside the cluster and cannot be reached; he says some open-weight models created a database themselves and reported the issue fixed, which the commercial models did not do in his runs.

    Next Generation DevOps: Reshaping the Cloud Native DevOps Infinity Loop with AI

    Rey Lejano

    The speaker reviews how DevOps and cloud native grew up together and then proposes a framework that places an example AI agent in each phase of the DevOps infinity loop. He says the agents take the drafting and repetitive work while people keep the judgment and approval steps.

    30 min slot · Beginner · Session

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You are new to cloud native delivery and want a phase-by-phase picture of where AI agents could fit in the DevOps loop.

    1. 3:28 The speaker introduces a framework for embedding AI in each phase of the DevOps infinity loop, with people remaining in the loop for accountability.
    2. 15:37 The speaker argues that AI is the next substrate, and says it does not change the stages of the loop but who or what executes each one.
    3. 17:31 For the plan phase, the speaker describes a spec agent that turns vague requests into user stories and draft architectural decision records, with the human deciding.
    4. 22:50 For the build phase, the speaker describes a pipeline agent that reviews container files, runs CVE scans, generates SBOMs and signs images, with policies enforced by the pipeline, in his case Tekton.
    5. 28:44 For deploy and operate, the speaker describes a rollout agent that runs canary steps with Argo Rollouts and watches metrics for rollback, and a runbook agent that does root cause analysis.

    Turning Apple Silicon into Production GPU Nodes for LLM Inference on Kubernetes

    Christopher Maher

    The speaker, who maintains LLMKube, shows live how a Mac joins a Kubernetes cluster as a MetalNode: an agent on the Mac starts the inference engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service. He says unified memory makes memory the thing to schedule on, recounts a kernel panic that led him to make the agent refuse models it cannot size, and shows traffic failing over to NVIDIA nodes when the Mac's lid closes.

    30 min slot · Advanced · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You want to serve LLMs on Macs or other unified-memory machines you already own, behind the same Kubernetes operator and service as your NVIDIA nodes.

    1. 5:16 The speaker lists why a Mac cannot simply join a cluster: Metal is not available inside a Linux container, no device plugin advertises the Mac's GPU, and the kubelet cannot see how much unified memory the GPU holds.
    2. 6:32 He describes the Mac path: an agent running under launchd watches for inference services, starts the engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service.
    3. 9:16 In a live demo a second MacBook joins his home cluster with a token-based join command and appears as a MetalNode.
    4. 12:23 He says the agent now fails closed after an incident in which a memory check failed open, llama-server ran with mlock and the laptop hit a kernel panic; admission also counts memory already committed.
    5. 15:56 In a live demo he closes the lid of the Mac serving traffic, and the same endpoint is then answered by NVIDIA nodes in his home lab.
