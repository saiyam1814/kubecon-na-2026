    A Decade of AI on Kubernetes: Kubeflow’s Journey to CNCF Graduation

    Valentina Rodriguez Sosa, Alexander Perlman, Christian Heusel, Shivay Lamba, David Aronchick

    Kubeflow co-founder David Aronchick recounts how the project started, and contributors describe its components, governance and what they say CNCF graduation required. The speakers then outline planned work, including Kubeflow Pipelines 3.0 changes such as removing the ML Metadata service, a unified Python SDK, trainer and notebook features, an MCP server and experimental Helm charts for the community distribution.

    30 min slot · Level not listed · Session

    Community and open source adoption

    Watch this if: you run or contribute to Kubeflow and want the origin story, what graduation involved, and the maintainers' stated plans for Pipelines 3.0, the SDK and agent support.

    1. 2:30 David Aronchick says the first Kubeflow release was deliberately small, with only a Jupyter notebook, a TensorFlow CRD and what later became KServe, and that pipelines came about six months later.
    2. 12:22 Christian Heusel says Kubeflow reached CNCF graduated status in July 2026, and that graduation required maintainers from at least two organizations per sub-project, independent adopters and a security and governance review.
    3. 20:56 Alexander Perlman says Kubeflow Pipelines 3.0 will consolidate the per-step driver pods into one pod per run, roughly halving the pod count, using Argo Workflows executor plugins.
    4. 22:13 He says 3.0 removes the ML Metadata microservice and database and moves execution tracking, artifacts, lineage and caching into the Pipelines API server.
    5. 29:24 Shivay Lamba describes an experimental Kubeflow MCP server that exposes trainer jobs to agents while applying the user's own Kubernetes permissions so the agent stays within bounds.

    Container Builds at Scale with Buildpacks

    Joe Kutner

    Joe Kutner of Salesforce presents Cloud Native Buildpacks as a way to turn source code into well-structured container images without a Dockerfile, and says the project graduated in the CNCF this past August. He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    1. 0:55 Joe Kutner says Cloud Native Buildpacks were created at Heroku about 12 years ago, joined the CNCF eight years ago and reached graduation this past August.
    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.
    3. 2:54 He says that with Dockerfiles a vulnerability in a shared base image means rebuilding every image, because of how linear layer caching works.
    4. 3:20 He explains rebase: because buildpacks know the boundary between OS and application layers, existing layers can be moved onto a new OS image without a build, which he says runs in milliseconds.
    5. 4:19 He says buildpacks can be run locally by installing the pack CLI and running pack build, choosing off-the-shelf buildpacks from Heroku, Google or Paketo, or writing your own.

    Fast and Furious: OTel Drift

    Laura Luttmer

    Laura Luttmer of Bindplane straps a Raspberry Pi, sensors and an OpenTelemetry Collector to a toy truck that a colleague drives around the stage, and uses it to show problems she says edge deployments such as connected cars run into. She covers choosing on the device what to send, queueing through a network outage, and managing collectors that can only call out, pointing to OpAMP, the OpAMP supervisor and partial reload.

    30 min slot · Any Level · Session

    Observability and reliability

    Watch this if: you run or plan to run collectors on devices that go offline and cannot be reached from outside, and want the trade-offs shown on a toy truck.

    1. 4:07 Luttmer says the hardware gave her trouble but the collector did not, and that it uses about 150 to 200 MB of the Pi's 512 MB and 1 to 2% of its cores with host metrics and system logs on.
    2. 8:17 She shows that a speed gauge sent every 10 seconds missed the truck stopping against her couch, so her script keeps the peak impact reading per window and also emits a log record for each crash.
    3. 14:27 She simulates a five-minute network outage and shows the collector's on-disk queue filling and then draining, with more than 4,000 items sent in the first minute back against a normal 1,200 or so.
    4. 20:08 She pushes a config change from Bindplane over an OpAMP connection that the truck's collector opened outward, and notes a real car cannot be logged into, so it has to call in itself.
    5. 21:42 She says a config push today restarts the whole collector, which she calls unacceptable across a fleet, and points to partial reload, which she believes is an alpha covering receivers so far.

    OpenFeature as a Control Plane for OpenTelemetry

    Simon Schrottner and Juliano Costa present a proof of concept that uses OpenFeature flags to change at runtime which spans a service creates and how much it samples, without restarting the service or the collector. They say it is an experiment for Python and Java with no reliable performance numbers yet, and ask the community whether it should continue and where it should live.

    30 min slot · Advanced · Session

    Observability and reliabilityDelivery, GitOps and release safety

    Watch this if: you pay for more telemetry than you read and want to see feature flags switching span detail and sampling per service at runtime.

    1. 6:16 Costa reports that a flag limiting export to incoming requests and outgoing calls gave about 55% fewer spans stored and 31% fewer trace bytes received in their demo, traces only.
    2. 7:53 Schrottner uses the OpenFeature evaluation context with OpenTelemetry semantic convention attributes (service name, span kind, URL path) to write a rule that drops health-check spans at runtime.
    3. 10:33 They set sampling rates through flag rules, 50% for one production service, 10% for the rest of production and 100% for staging, and show the ingestion chart splitting per service and environment.
    4. 13:39 Costa argues that dropping telemetry in the collector still spends application CPU, memory and network egress on producing it, and both say they would keep the collector's sampling as a safety net.
    5. 18:20 Schrottner says they saw no big performance impact when switching flags but calls these not reliable benchmarks, and Costa adds they have not compared their instrumentation against stock OpenTelemetry instrumentation.
