    A Decade of AI on Kubernetes: Kubeflow’s Journey to CNCF Graduation

    Valentina Rodriguez Sosa, Alexander Perlman, Christian Heusel, Shivay Lamba, David Aronchick

    Kubeflow co-founder David Aronchick recounts how the project started, and contributors describe its components, governance and what they say CNCF graduation required. The speakers then outline planned work, including Kubeflow Pipelines 3.0 changes such as removing the ML Metadata service, a unified Python SDK, trainer and notebook features, an MCP server and experimental Helm charts for the community distribution.

    30 min slot · Level not listed · Session

    Community and open source adoption

    Watch this if: you run or contribute to Kubeflow and want the origin story, what graduation involved, and the maintainers' stated plans for Pipelines 3.0, the SDK and agent support.

    1. 2:30 David Aronchick says the first Kubeflow release was deliberately small, with only a Jupyter notebook, a TensorFlow CRD and what later became KServe, and that pipelines came about six months later.
    2. 12:22 Christian Heusel says Kubeflow reached CNCF graduated status in July 2026, and that graduation required maintainers from at least two organizations per sub-project, independent adopters and a security and governance review.
    3. 20:56 Alexander Perlman says Kubeflow Pipelines 3.0 will consolidate the per-step driver pods into one pod per run, roughly halving the pod count, using Argo Workflows executor plugins.
    4. 22:13 He says 3.0 removes the ML Metadata microservice and database and moves execution tracking, artifacts, lineage and caching into the Pipelines API server.
    5. 29:24 Shivay Lamba describes an experimental Kubeflow MCP server that exposes trainer jobs to agents while applying the user's own Kubernetes permissions so the agent stays within bounds.

    Falco Never Flies Alone: Runtime Security as an Ecosystem

    Leonardo Grasso, Alessandro Cannarella

    Leonardo Grasso and Alessandro Cannarella describe how Falco, now ten years old, spent the year consolidating its core and growing an ecosystem around it. They cover core and plugin updates, new experiments for AI coding agents, Falco Operator 0.5, and a from-scratch rewrite of Falcosidekick as version 3.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you run Falco for runtime security and want to see what changed in its core, the Falco Operator and Falcosidekick.

    1. 0:51 Grasso explains how Falco taps the Linux kernel with an eBPF probe or kernel module, enriches events with plugins, and matches them against YAML rules.
    2. 3:22 Grasso lists core cleanups such as removing the legacy BPF probe and gVisor support, new list operators in the rule language, and an experimental GPU hijacking rule.
    3. 6:38 Grasso introduces a new subproject that gives coding agents a version-pinned knowledge base and skills for contributing to the Falco code base.
    4. 16:35 Cannarella says Falco Operator 0.5 pulls artifacts from the registry once, serves them to every node, and checks rules against the Falco version before installing.
    5. 19:55 Cannarella announces Falcosidekick version 3, rewritten with per-output pipelines, live config reloads, API and UI configuration, and a single binary.

    Running Stateful Analytics on Kubernetes: Lessons from Building a Distributed DuckDB Platform

    Seth McCombs, Karim Alibhai

    Seth McCombs and Karim Alibhai explain the storage and operational decisions their teams had to make when running embedded DuckDB on Kubernetes. They describe treating data as versioned releases so teams could track its provenance, stage rollouts, and roll back.

    30 min slot · Any Level · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you already run DuckDB queries and need to manage data delivery, worker failures, and rollbacks on Kubernetes.

    1. 5:39 The speakers explain that an embedded database does not provide the data delivery path, so their design needs to account for storage, retrieval, and how quickly a query needs its data.
    2. 8:14 They sketch a query router that chooses between Snowflake and Greybeam and accounts for whether data lives in object storage or on a local drive.
    3. 10:44 They describe out-of-memory failures and ask how the service should report a lost query when a worker pod dies.
    4. 19:16 They argue that versioning data packages lets a team trace a discrepancy to the pipeline that produced the data.
    5. 21:20 They describe making data part of the application release cycle, with Argo CD rollbacks and an operator reconciling which source the pods read.

    Sandboxing on Kubernetes with WebAssembly: A Hands-on Tutorial

    Eric Gregory, Bailey Hayes

    Eric Gregory and Bailey Hayes use wasmCloud and Kubernetes to show how WebAssembly components get explicit permissions for the resources they need. In the workshop, they start with an agent that has no tools and add capabilities one at a time, then show a separate scaling benchmark.

    80 min slot · Beginner · Tutorial

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: You want to see a WebAssembly sandbox on Kubernetes and how to grant an agent tool only the access it needs.

    1. 6:18 The speakers explain the deny-by-default model and show where the wasmCloud operator schedules a workload onto a host pod.
    2. 23:14 The speakers introduce the workshop's scripted model and explain why it makes the effect of sandbox permissions easier to distinguish from model behavior.
    3. 37:40 The speakers build an optional Rust component and inspect the WebAssembly interfaces it imports for HTTP and filesystem access.
    4. 56:36 The speakers demonstrate a narrow GitHub integration for triaging pull requests and explain how the host plugin keeps the sign-in token out of the workload.
    5. 1:03:56 The speakers switch from the single-instance workshop to a recorded density test and explain the resource constraints they encountered while scaling on Kubernetes.
