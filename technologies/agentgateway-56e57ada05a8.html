    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    Kubernetes Solutions for Agent-Shaped Problems

    Tim Hockin, Dmitry Berkovich

    Tim Hockin and Dmitry Berkovich of Google say agent workloads are bursty, run untrusted code and have a human waiting, which makes one sandboxed pod per agent session wasteful and slow on Kubernetes. They present Agent Substrate, an open source system built on Kubernetes that suspends idle agents to snapshots and resumes them on request, and spend the second half answering audience questions about policy, autoscaling, memory and where it fits.

    30 min slot · Any Level · Session

    AI agents and automationKubernetes internals and runtimes

    Watch this if: you run or plan to run many agent sessions on your own Kubernetes clusters and want the reasoning behind Agent Substrate from its authors, plus a long Q&A on its current limits.

    1. 0:47 Hockin and Berkovich name three traits of agent workloads: they are bursty and mostly idle, they run untrusted code that must be sandboxed, and a human is usually waiting for the response.
    2. 6:57 Hockin states the three design principles of Agent Substrate (security by default, near-zero cost for idle agents, fast wake-up) and what he calls aspirational goals: billions of agents per cluster, 10,000 activations per second and wake-up in about 100 milliseconds.
    3. 9:16 Berkovich defines the five terms: an actor runs one agent session, an actor template configures it, a worker is the pod that hosts actors, a node-level manager handles images and snapshots, and a network layer routes requests in and applies policy to traffic out.
    4. 13:06 He explains resume speed through layers: volumes always survive, while root filesystem changes and the memory snapshot are reused only if the OCI image is unchanged, otherwise the actor cold starts from its volumes.
    5. 15:26 Hockin describes a use case they see often: a managed agent service runs the agentic loop while the work it triggers runs in Agent Substrate inside the customer's own cluster, where it can be audited and shut off.

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.

He argues that without mesh authorization policies the prompt is the only guardrail, and that the mesh, not the model, should be the security boundary.

    5 min slot · Level not listed · Session

    Security, identity and policyAI agents and automationNetworking and connectivity

    Watch this if: You are building an agent platform and need tool calls to carry the real user's identity, not a shared service account.

    1. 0:18 The speaker names prompt injection, user impersonation and secret leakage as the three red flags of the agent identity problem.
    2. 0:57 He says that without workload identities in the mesh, a triage agent can reach every other agent and every tool.

    5. 4:52 He walks through the flow in which a token is minted at login, an Argo workflow sends the event and token to agentgateway, and the chosen agent calls the tool through an MCP server, REST API or CLI.

    Engin Diri

    Engin Diri of Pulumi recounts helping a European customer build a self-hosted inference platform, moving from whole GPUs and time slicing to NVIDIA MIG slices that pods request through Dynamic Resource Allocation. He shows a recorded demo of MIG profiles, resource slices and claims on an AWS node serving a model behind an inference gateway, and lists open questions such as quotas, models larger than a node and start-up ordering.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: you run inference on your own GPUs and want a practical walk through MIG slices requested with Dynamic Resource Allocation.

    1. 8:32 Diri says time slicing gives no memory or fault isolation between workloads, so the choice was between wasting GPUs and risking a noisy neighbor.
    2. 11:24 Diri says Dynamic Resource Allocation, which he dates to Kubernetes 1.34, lets a request describe device attributes instead of an integer count.
    3. 22:16 In the recorded demo, Diri lists the 1G, 2G and 4G MIG profiles on the node and the resource slices the DRA driver published.
    4. 24:28 Diri lists open day-two questions he is evaluating with the customer, including Kueue for MIG quota and which workload runs first.
    5. 28:06 Diri advises starting the DRA driver only after MIG is configured, because he ran into race conditions between the two.

    Will Your Gateway Leave You High and Dry?

    John Howard, Mitch Connors

    John Howard and Mitch Connors walk through version 3 of Howard's Gateway API Bench, which tests agentgateway, Envoy Gateway, Istio, kgateway, NGINX Gateway Fabric and Traefik on route updates, a 5,000 route scale test, route propagation time and rolling restarts. Framed around a fictional cardboard box startup, they report which implementations returned errors or used more CPU and memory in their runs, and Howard states up front that both speakers work on several of the gateways tested.

    30 min slot · Any Level · Session

    Networking and connectivityObservability and reliability

    Watch this if: you are choosing a Gateway API implementation, perhaps while moving off ingress-nginx, and want to see how six of them behaved under route churn and scale.

    1. 4:20 Howard says the two speakers are biased because they work on many of the gateways tested, and that the report is reproducible with shared data.
    2. 8:22 Howard reports that four implementations returned all 200s while a route was updated, while Envoy Gateway and NGINX had brief periods of downtime in his test.
    3. 13:59 In the 5,000 route test, Howard says the NGINX data plane used about three cores of CPU while serving no traffic.
    4. 16:40 Howard attributes the resource gap between Envoy based gateways to metrics defaults, saying Envoy Gateway and kgateway exposed 350,000 metrics out of the box.
    5. 21:11 Howard says no implementation failed during continuous backend pod restarts, while NGINX and Traefik had errors when the gateway itself was rolled out.
