    AI on Kubernetes Is Just a Pod With a GPU (and That's the Problem)

    Graziano Casto

    Graziano Casto compares deploying a web application with deploying a model on Kubernetes, starting from a plain Deployment that runs a vLLM container. He names three differences, which are whole-number GPU allocation, slow startup while model weights load, and requests that cost very different amounts of GPU work, and for each he points to projects he says address it.

    12 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You run web applications on Kubernetes and want a short orientation on what changes with model serving before choosing AI talks to watch.

    1. 0:36 The speaker shows what he calls the easiest way to deploy a model on Kubernetes: an ordinary Deployment running a vLLM container that serves a Llama 3.1 model.
    2. 3:01 He says a GPU is requested as a whole number, so a model that does not use a full GPU still leaves it overprovisioned.
    3. 3:43 He lists dynamic resource allocation in Kubernetes, HAMi for software-level enforcement and NVIDIA MIG for hardware partitioning as ways to share a GPU.
    4. 5:03 For slow startup he suggests relaxing liveness and readiness probes, caching downloaded weights on a persistent volume, and packaging weights as OCI artifacts mounted as image volumes.
    5. 6:57 He says round-robin load balancing does not fit chat workloads, and describes llm-d's KV-cache-aware routing, built on the Gateway API Inference Extension, as sending a conversation back to where its context lives.

    Breaking up Is Hard, but the Future Is with Helm 4

    Matt Farina, Joe Julian

    Helm maintainers Matt Farina and Joe Julian argue that users and tools built on the Helm SDK should move off Helm 3 before its security releases end, and explain that the SDK needed breaking changes that eight years of API compatibility guarantees had blocked. They walk through what changed in Helm 4, including WebAssembly plugins, server-side apply by default for new releases, kstatus-based status, chart digests, content-based caching and renamed flags, then give a step-by-step upgrade path and take questions.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you still run Helm 3 or maintain a tool that imports the Helm SDK and need to know what changes in Helm 4.

    1. 1:01 Matt Farina says his download statistics show about 16% of usage is still on Helm 3 and that about a quarter of the largest maintained tools importing the Helm SDK still use the Helm 3 SDK.
    2. 6:41 Joe Julian gives the Helm 3 timeline: limited, mostly security-only releases since September 9, with security updates ending February 10.
    3. 8:46 Farina describes WebAssembly plugins in Helm 4, which he says bring sandboxing, remove the need for install scripts that download per-platform binaries, and let plugins be written in any language that compiles to Wasm.
    4. 11:53 He explains that a release first installed with Helm 4 defaults to server-side apply, while a release installed with Helm 3 keeps client-side apply until the user opts in with a flag.
    5. 18:08 Julian lists upgrade steps: test representative charts and releases, run CI/CD commands, check plugins and post-renderers, verify registry logins and OCI installs, then roll out the Helm 4 binary.
