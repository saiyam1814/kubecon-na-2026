    Agent Substrate: Open Layers for Agentic Systems

    Jaana Dogan, Dmitry Berkovich, Tim Hockin, Eitan Yarmush, Luiz Scheidegger

    The speakers describe Agent Substrate as a way to run many stateful agents on Kubernetes by snapshotting idle sandboxes and resuming them when work arrives. They introduce a bridge for Claude Managed Agents and show attendees sending agents on missions in a virtual KubeCon.

    7 min slot · Level not listed · Keynote

    AI agents and automationKubernetes internals and runtimes

    Watch this if: you want a live example of running many stateful agents on Kubernetes and waking them only when they have work.

    1. 1:29 Dogan says the stateful, bursty nature of agent systems calls for workload resumption and security guardrails beyond what Google had in Borg and Kubernetes.
    2. 2:12 Berkovich describes Agent Substrate's design goals: isolated sandboxes with agent identity but no credentials, high density, and fast wake-ups that preserve state.
    3. 2:46 The speakers explain how Agent Substrate snapshots memory and disk before suspending idle workloads and resumes them on custom workers when needed.
    4. 4:04 Scheidegger announces the Agent Substrate Bridge for Claude Managed Agents, then shows a virtual KubeCon where attendees can send their agents on missions.
    5. 5:44 Dogan says the live demo was running on a single Google Kubernetes Engine cluster with about 24 nodes and about 65 agents per node.

    Kubernetes with Conviction: How Customization is Shaping the OSS AI Ecosystem's Future

    Jago Macleod, Shaun Hopper

    Jago Macleod describes treating Kubernetes as a shared core that Google Kubernetes Engine can adapt with targeted changes rather than a permanent fork. Shaun Hopper explains how Meta used that approach to customize node updates and coordinate the rollout of DaemonSets for its AI workloads.

    5 min slot · Level not listed · Keynote

    AI inference and servingKubernetes internals and runtimes

    Watch this if: you want to see how Google and Meta approach workload-specific Kubernetes changes without maintaining a permanent fork.

    1. 1:19 Macleod says large customers want to swap schedulers and autoscalers, tune the operating system, and adopt upstream changes faster.
    2. 1:57 Macleod describes treating Kubernetes as a kernel, then applying targeted changes on top of a base tested through the regular release channel.
    3. 3:31 Macleod calls GKE Frontier an operating model rather than a product, and Hopper explains why Meta wanted a custom operating system image.
    4. 4:12 Hopper describes working with Google to exclude nodes with active workloads from upgrades and give Meta control over DaemonSet rollouts.
    5. 6:13 Macleod says the same approach lets GKE preview builds bring upstream changes to users earlier in the release cycle.
