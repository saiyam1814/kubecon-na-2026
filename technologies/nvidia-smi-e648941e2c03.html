    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    Two Drivers, One Topology: GPU:NIC Rail Alignment for RDMA VMs with KubeVirt DRA

    Jian Li, Alay Patel, Kazuki Sato

    Kazuki Sato of NTT DOCOMO BUSINESS, Jian Li of SK Telecom and Alay Patel describe how a multi-site GPU platform on KubeVirt moved from a manual workaround to Dynamic Resource Allocation claims that pair each GPU with an RDMA NIC under the same PCIe root. They show a recorded benchmark comparing aligned and misaligned VMs, explain the Multus change they are proposing upstream, and outline what KubeVirt's DRA support covers today and what is planned.

    15 min slot · Level not listed · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you run GPU virtual machines with RDMA networking on KubeVirt and need each GPU paired with the right NIC without pinning devices by hand.

    1. 2:07 Sato describes the earlier workaround: filling a node with placeholder pods that each hold one GPU or NIC and deleting only the ones holding the wanted pair, which had to be redone VM by VM after every node or VM restart.
    2. 5:10 Li explains that the GPU driver and the SR-IOV NIC driver both publish the standard PCI root attribute, so one resource claim with a GPU request, a VF request and a match constraint lets the scheduler allocate them as a pair.
    3. 7:15 He says upstream KubeVirt network DRA could not consume a VF wired through a Multus network, so they added a feature gate that takes the VF from the resource claim and leaves the existing CNI chain unchanged.
    4. 10:21 In the recorded demo Sato compares two four-GPU VMs: he reports about 200 Gbps of RDMA bandwidth on the misaligned VM and 391 Gbps on the aligned one, with placement as the only difference.
    5. 12:33 Li says the next gap is that CPUs and huge pages are still placed by the kubelet without topology hints from DRA devices, so a VM can get its GPU and NIC on one socket and its memory on another.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
