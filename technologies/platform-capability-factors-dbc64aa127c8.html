    Platform Engineering after the AI Hype: Why IDPs Must Become Intent-Driven

    Daniel Bryant

    The speaker argues that AI agents calling internal platforms at machine speed expose three failure modes: too much API surface, confidently wrong requests, and nobody owning day two. He recommends intent-driven platform capabilities with guardrails, helpful refusal messages, and lifecycle ownership by the teams that produce them.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceAI agents and automation

    Watch this if: You build an internal developer platform and want to know what to change before AI agents become its main consumers.

    1. 3:39 The speaker describes an experiment in which several LLMs with kubectl access always produced a working Postgres, but he says each model and each run produced something subtly different.
    2. 10:40 The speaker names three failure modes he says he sees in the industry: too much surface, confidently wrong, and nobody owns day two.
    3. 15:42 The speaker contrasts resource-driven Terraform or OpenTofu with an intent-driven API where the consumer asks for a PCI DSS compliant database and the platform holds the guardrails.
    4. 18:53 The speaker borrows the idea of lane assist from Gregor Hohpe and says platform APIs should tell agents why a request is refused and what the options are, otherwise agents often work around the guardrail.
    5. 23:54 The speaker gives an example of a CVE fix rolled out once by the capability producer across a fleet, using Kratix promises, Crossplane composition revisions or KubeVela versioned definitions.

    The CNCF Platform Engineering User Group & Platform Factors

    Colin Griffin, Avinash Sabat

    Colin Griffin describes how the CNCF Platform Engineering User Group develops resources and recommends using its maturity model to decide where to invest rather than to maximize every dimension. Avinash Sabat presents draft Platform Capability Factors and uses a self-service database to explain what a capability should deliver and who should own it.

    30 min slot · Level not listed · Birds of a Feather

    Community and open source adoptionPlatform engineering and developer experience

    Watch this if: you are defining what a self-service platform capability should deliver and who will own it.

    1. 5:20 Griffin says the user group brings contributors together to write resources such as the platforms white paper, the maturity model, and its self-assessment.
    2. 8:30 Griffin says teams should use the maturity model to decide where investment makes sense rather than trying to reach its optimizing column in every area.
    3. 13:27 Sabat distinguishes platform operators who own shared infrastructure and governance, specialist teams that produce capabilities, and consumers who request them through self-service.
    4. 17:13 Sabat says a self-service database should deliver a complete outcome, including storage and backups, with clear responsibilities and no need to contact the database team for every request.
    5. 19:26 Sabat says a capability should reconcile repeated requests safely without drifting, and that both producers and consumers should be able to see how it is performing.

    The Prompt Layer: What Platform Engineering Has to Own Next

    Atulpriya Sharma

    The speaker argues that developers still decide alone which model to use, what to send to it and how much to spend, and that platform teams should own these decisions. He describes a prompt layer of five components built from existing tools and shows a recorded demo where an allow list keeps a secret file out of a prompt.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceAI agents and automation

    Watch this if: You run a platform team and developers in your organization each choose their own AI models, context and budgets.

    1. 11:51 The speaker says platforms already cover running and serving models, but developers still carry the load of choosing a model for each task and deciding what is safe to paste.
    2. 14:09 The speaker says an AI gateway enforces whatever you give it, including nothing, and quotes a line he attributes to the Platform Capability Factors paper that tooling can enforce a standard but cannot decide it.
    3. 16:35 The speaker lists the five components of the prompt layer: capability interface, context templates, token governance, agent permissions and observability.
    4. 20:24 The speaker says budgets should be assigned to a capability such as code review, not to a key or a person, and suggests falling back to a cheaper model at the limit.
    5. 27:32 In the recorded demo, the assistant with the prompt layer does the code review but cannot read the secret file, which the speaker says was dropped before the prompt reached the LLM.
