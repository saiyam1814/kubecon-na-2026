    AI Found a 0-Day in Metal3. What Happens Next?

    Tuomo Tanskanen

    Tuomo Tanskanen, who leads the Metal3 security committee, follows a vulnerability report from arrival through triage, fix, release and downstream upgrade, drawing on reports from his own AI discovery pipeline and showing how its findings broke down after triage. He also describes how fixes in OpenStack Ironic reach Metal3 and vendor distributions, and advises users to run supported releases, know their configuration and ask vendors how quickly they take in fixes.

    30 min slot · Level not listed · Session

    Security, identity and policyDelivery, GitOps and release safetyAI agents and automation

    Watch this if: you maintain a project that receives AI-generated vulnerability reports, or you run Metal3 and want to know how its security fixes reach you.

    1. 4:12 Tuomo Tanskanen says every vulnerability disclosure Metal3 received this year came from an AI discovery pipeline he built himself, which also scans OpenStack Ironic, and that its findings go through each project's normal security process.
    2. 8:27 He gives the pipeline's numbers: of about 220 findings, 80 were false or duplicates, 31 became hardening issues, 22 were plain bugs and 22 were confirmed, and he concludes that discovery is fast while triage, fixing and coordinated release are slow.
    3. 10:34 He says Metal3 fixes low and medium issues in the open, because GitHub private forks give almost no CI support and force manual testing, and reserves embargoed handling for high and critical ones.
    4. 14:41 He describes a lesson from combining four related cross-namespace issues into one advisory: no CVE could be issued for it, because a CVE covers a single issue.
    5. 20:20 Using two fixes as examples, he says each step down the dependency chain into vendor distributions took roughly a month, so fixes take a long time to reach production.

    Beyond Provisioning: Multi-Tenancy, Rack Awareness, and Declarative Networking in Metal3

    Kashif Khan, Sunnatillo Samadov

    Kashif Khan and Sunnatillo Samadov, both Metal3 maintainers, present three additions to the bare metal provisioning project: multi-tenancy through host claims, failure domains that spread control plane nodes across racks, and top-of-rack switch port configuration. They show a short recorded demo of each and close with which release and feature gate each one sits behind.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you run Kubernetes on bare metal and want several teams to share one hardware pool, rack-aware control planes, or switch ports configured from YAML.

    1. 5:40 Kashif Khan names three gaps he says Metal3 had: teams sharing hardware meant handing out BMC passwords, nothing kept control planes off a single rack, and switch port VLANs were typed by hand.
    2. 6:46 Kashif Khan explains the multi-tenancy design: tenants create a HostClaim in their own namespace, and an admin-owned HostDeployPolicy in the pool namespace decides which namespaces may consume which hosts.
    3. 12:24 Kashif Khan explains failure domains: label each BareMetalHost with its rack, list the failure domains on the Metal3 cluster, and Cluster API then spreads control plane nodes across them.
    4. 17:43 Sunnatillo Samadov introduces the BareMetalSwitch and HostNetworkAttachment resources, which he says let Ironic set switch port mode and VLAN tags during provisioning and clean them up afterwards.
    5. 23:19 The speakers give the status: multi-tenancy is alpha behind a feature gate, failure domains are available in the Cluster API provider release they name, and switch configuration is behind a feature gate in the Bare Metal Operator.

    Cloud Native Infrastructure in the AI Era: A TAG Infrastructure Panel

    Xing Yang, Dylan Page, Mesut Oezdil, Alexa Griffith, Kashif Khan, Thomas Schuetz

    The co-chairs and tech leads of the CNCF TAG Infrastructure describe the group's current work, including white papers on infrastructure lifecycle, AI for science, AI inference and data storage for AI, and a new telco AI-native initiative. They then each name what they see as the biggest challenge AI workloads pose for cloud native infrastructure and take audience questions on agent sandbox projects and moving HPC sites toward cloud native tools.

    30 min slot · Level not listed · Panel

    Community and open source adoptionAccelerators and workload schedulingAI inference and serving

    Watch this if: you run or plan AI infrastructure and want to know what the CNCF TAG Infrastructure is writing about it and where you can contribute.

    1. 2:04 Dylan Page describes the infrastructure lifecycle white paper, which he says is meant to advise on managing mixed public cloud, private cloud, edge and bare metal environments, and Thomas Schuetz adds that it covers when operator-based deployment fits better than Terraform or OpenTofu.
    2. 5:13 Kashif Khan introduces the telco AI-native initiative, saying the challenge for AI-native network functions is the infrastructure beneath the model, and that the group is collecting shared definitions and gaps from operators and vendors.
    3. 10:03 Xing Yang summarizes the TAG's white paper on data storage for cloud native AI, saying training, inference and agents each have different storage patterns, so no single AI storage fits all.
    4. 11:40 Asked for the biggest challenge, Dylan Page answers that it is people, describing a collision of cloud native, telecom and HPC cultures, while other panelists name GPU utilization, placement and the speed at which infrastructure is needed.
    5. 19:00 Mesut Oezdil argues that GPUs must be sliced to be economical and that MIG and time slicing fall short in mixed-vendor environments, and points to HAMi, which he maintains, as a vendor-agnostic option.

    Cluster API in 15 Minutes. A Primer on Declarative Kubernetes Cluster Management

    William Rizzo

    William Rizzo introduces Cluster API as the idea of representing a cluster as Kubernetes objects inside a management cluster, and walks through its core, infrastructure, bootstrap and control plane providers. He explains how machines map to nodes, in what order a cluster comes up, and how to try it locally with clusterctl and the Docker provider, then takes audience questions.

    12 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: You manage more than a few clusters by hand and want the Cluster API object model explained before you try the quick start.

    1. 0:30 The speaker states the idea behind Cluster API: a cluster becomes a set of Kubernetes objects inside a management cluster.
    2. 0:54 He describes the controllers: the core, an infrastructure provider for where machines run, a bootstrap provider for machine configuration, and a control plane provider for etcd and the API server.
    3. 3:27 He compares a MachineDeployment to a workload Deployment, with a MachineSet in the place of a ReplicaSet and a Machine in the place of a Pod.
    4. 4:43 He says cluster creation follows a sequence in which one control plane node must be built first, because otherwise etcd cannot form its Raft consensus.
    5. 9:39 Asked about self-hosted infrastructure, he says clusterctl uses kubeadm by default but that other control plane and bootstrap providers can be chosen at init.

    From Zero to GPU Cloud: 12 months building Mistral Compute on top of Open Source

    Léonard Suslian

    Léonard Suslian of Mistral AI describes how a team of about ten built Mistral Compute, a bare-metal Kubernetes service he says now manages 5,000 hosts, on Cluster API, Metal3, Kamaji and Sveltos plus its own operators. He then goes through what he says broke along the way, from Ironic and board management controllers to SNAT exhaustion, etcd storage and a DHCP storm.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: you are building or running bare-metal GPU clusters and want a candid list of what breaks between the racks arriving and tenants getting Kubernetes.

    1. 9:07 Suslian explains running each tenant's control plane as pods in the management cluster with Kamaji, which he says saves hardware and turns a control plane upgrade into a deployment rollout.
    2. 12:53 He describes using Sveltos from the management cluster to install add-ons chosen by the tenant, with drift detection that he says restores a deleted Cilium DaemonSet.
    3. 18:47 He says the team replaced Ironic with its own API-compatible rewrite in Go, scoped to their hardware, and went from first commit to production in 19 days.
    4. 21:03 He says hosts that cannot be fixed automatically get an AI agent in a pod with temporary credentials and scoped network access, and reports more than 20 such runs a day.
    5. 25:02 He recounts waking up to almost 900 nodes down because 10-minute DHCP leases caused a renewal storm the server could not keep up with, fixed by longer leases.

    Metal3 Project Update! Whats New and Exciting?

    Kashif Khan

    Kashif Khan, a Metal3 maintainer, explains how the project describes physical servers as Kubernetes resources and provisions them into clusters, and lists what recent releases shipped. He says the roadmap covers switch and network automation, multi-tenancy and a more stable Bare Metal Operator API, and that the project is aiming for CNCF graduation.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run Kubernetes on bare metal and want a five-minute update on what Metal3 shipped and what is planned.

    1. 0:26 Khan says Metal3 manages bare metal hosts through Kubernetes APIs: you describe a server as a resource, apply it, and it joins the cluster as a node with no SSH or manual steps.
    2. 1:51 Khan says the project moved from sandbox to incubating last year, has more than 100 contributors, and runs in production at Ericsson, Red Hat, SUSE and Mirantis.
    3. 2:25 Khan says Cluster API Provider Metal3 moved to the v1beta2 API and that Ironic 39 now comes bundled through the standalone operator, so OpenStack Ironic does not need a separate deployment.
    4. 2:48 Khan highlights security work on the provisioning path: TLS and authentication, stricter URL validation, image digest pinning and fuzz testing in CI.
    5. 3:16 Khan says top-of-rack switch management is in progress, and that multi-tenancy will let teams share one hardware pool while BMC credentials stay with the infrastructure admins.
