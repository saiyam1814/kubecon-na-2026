    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.

    Making Environments Repeatable: From Tools to Platform Capabilities

    Saiyam Pathak

    Saiyam explains the hidden setup, configuration, and readiness work behind requests for repeatable environments, and presents vCluster Stacks as a way to encode that work once. He argues that readiness should mean a validated user outcome, illustrated by GPU scheduling and a CUDA smoke test, rather than merely running components.

    5 min slot · Any Level · Keynote

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you are turning repeated environment provisioning steps into reusable platform capabilities.

    1. 0:13 Saiyam says the simple request for an environment hides installation, service trust, configuration handoff, and readiness work that platform teams must complete first.
    2. 0:53 Saiyam argues that repeatedly glue-fixing environments team by team eventually loses track of tools, versions, and ownership.
    3. 1:48 Saiyam says reusable environment automation has to encode ordered setup steps, pass one step's output into the next step, and prove readiness from the developer's perspective.
    4. 3:09 Saiyam uses a CUDA GPU stack to argue that readiness requires scheduler visibility of the GPU and a successful smoke-test job, not only healthy operator components.
    5. 4:21 Saiyam closes by asking platform teams what belongs in a reusable stack, what proves an environment ready, and which repeated requests the platform should handle for users.

    One Recipe, Five Clouds, One Query: Portable GPU Configuration with a Queryable Audit Layer

    Christopher Haar, Yuan Chen

    The speakers present AI Cluster Runtime (AICR), an open source project that turns layered recipes into validated GPU runtime bundles for different clouds, accelerators and workloads. They show commands for querying a configuration, diffing snapshots, checking upgrades and publishing signed evidence reports.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: You bring up GPU clusters on more than one cloud and want reproducible configuration that you can query and audit without touching a live cluster.

    1. 1:45 The speaker says a GB300 training cluster on EKS needs about 300 parameters set correctly across more than 16 components.
    2. 3:29 The speaker walks through the workflow: snapshot the cluster, generate a recipe, build bundles, deploy with a deployer of your choice, then validate.
    3. 9:08 In the recorded demo, the speaker reports throughput above 30,000 tokens per second and a time to first token of about 160 milliseconds.
    4. 12:44 The speaker explains the query command, which merges recipes and overlays into one values file and selects fields such as the GPU driver version across EKS, GKE and AKS.
    5. 18:15 The speaker runs query, snapshot, diff and upgrade check in a short demo, and says diff exits with code two so a CI pipeline fails on drift.

    When GPUs Become NUMA Nodes: Challenges Running Kubernetes with Memory-Coherent Hardware

    Kevin Klues

    Kevin Klues, presenting alone because his listed co-speaker could not attend, explains how NVIDIA systems with memory-coherent CPU and GPU links exposed GPU memory as NUMA nodes and why he says that broke the kubelet's memory accounting, pod memory limits and GPU isolation. He walks through two workarounds his team abandoned, the driver mode called CDMM that they adopted instead, and a kubelet fix that was still needed.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Kubernetes on NVIDIA GB200-class or other unified-memory hardware and want to know how GPU memory interacts with kubelet memory accounting.

    1. 7:29 Klues lists three problems with the driver's NUMA mode on Kubernetes: memory over-reporting to the kubelet, a broken pod memory limit contract, and any container being able to allocate GPU memory it was not assigned.
    2. 10:55 He describes the first attempt, hiding GPU NUMA nodes from the kubelet with reserved memory settings, and says it failed on ordering with the GPU driver and on dynamic MIG devices.
    3. 13:44 He describes a second attempt using an NRI plugin to restrict each container to the NUMA nodes of its own GPUs, which he says got complicated once GPUs were injected through CDI and DRA.
    4. 16:35 He introduces Coherent Driver-Based Memory Management (CDMM), a driver mode that he says keeps GPU memory NUMA nodes offline while retaining pointer coherency over NVLink.
    5. 18:39 He says enabling the topology manager stalled the kubelet because it iterated combinations of 34 NUMA nodes, and that a patch merged in Kubernetes 1.36 skips nodes with no memory.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
