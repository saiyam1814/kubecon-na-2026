    Engineering Kubernetes for the Next Era of Workloads

    Mike Stefaniak

    Mike Stefaniak describes bottlenecks AWS found when running large Kubernetes clusters and says the team contributed fixes upstream. He walks through watch-cache and scheduler changes, accelerator-aware provisioning with Karpenter, and parallel image unpacking in containerd.

    5 min slot · Level not listed · Keynote

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run large GPU clusters and want concrete examples of upstream fixes from image unpacking to accelerator placement.

    1. 0:47 Stefaniak says AWS replaced a long-held Kubernetes API server watch-cache lock with a lazy snapshot, cutting writer wait from over half a second to 2 ms in its million-pod benchmark.
    2. 1:03 Stefaniak says a new Horizontal Pod Autoscaler selector store removed a read/write bottleneck, letting AWS run four times as many HPA workers in its largest clusters.
    3. 1:21 Stefaniak says an incremental scheduler cache avoided rebuilding volume reference counts and that AWS saw scheduling stay above 300 pods per second in its largest clusters.
    4. 2:28 Stefaniak explains that Dynamic Resource Allocation can describe GPU and network topology, and says Karpenter can now model devices for instances it has not launched yet.
    5. 3:48 Stefaniak says parallel layer unpacking in containerd brought a 10 GB image pull from about two minutes to under 45 seconds in AWS's testing.

    Kubernetes Secrets Were a Bad Idea. Now What?

    Maxime Coquerel

    Maxime Coquerel argues, as his own opinion, that Kubernetes Secrets are risky because they are only base64 encoded in etcd, readable with broad RBAC permissions and have no lifecycle. He recommends encrypting etcd with a customer managed key, keeping secrets out of Git and mounting secrets from a real vault at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    5 min slot · Beginner · Lightning Talk

    Security, identity and policy

    Watch this if: you are deciding whether Kubernetes Secrets are good enough for your platform or which alternative to use.

    1. 0:43 Maxime Coquerel says a Kubernetes Secret is stored in etcd only base64 encoded, not encrypted, and that etcd is a key value store, not a vault.
    2. 1:46 He lists the weaknesses he sees, including that anyone with get, list or watch permissions can read secret contents.
    3. 2:05 He adds that Kubernetes Secrets have no lifecycle: no expiration date and no automatic renewal.
    4. 2:47 His first recommendation is to encrypt etcd with a customer managed key, which he says managed services such as Azure Kubernetes Service support.
    5. 3:49 He compares Sealed Secrets, SOPS and External Secrets Operator, and recommends mounting secrets as files at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    Open Source Has a Human Deficit. Here's How We Fix It.

    Catherine Paganini

    Catherine Paganini argues that open source is short on maintainers and that welcoming underrepresented groups is a way to make projects more sustainable. She introduces Merge Forward, a CNCF community group with groups such as Women in Cloud Native and Deaf and Hard of Hearing, and invites people to join as members, mentors or allies.

    5 min slot · Any Level · Lightning Talk

    Community and open source adoption

    Watch this if: you want to help more people from underrepresented groups become open source contributors and maintainers.

    1. 0:07 Catherine Paganini recalls a March 2022 warning to the Kubernetes steering committee that etcd had only one active and two occasional reviewing maintainers.
    2. 0:26 She points to ingress-nginx, which she says was wound down and stopped getting security patches, as another case of the same maintainer pattern.
    3. 1:25 She says more maintainers means more people, and that open source has overlooked many who do not see themselves represented and so see no path in.
    4. 2:41 She argues that people with similar backgrounds share unchallenged assumptions, which she links to missed edge cases and shipped defects.
    5. 3:23 She lists the Merge Forward groups, from Deep Roots and Women in Cloud Native to Neurodiversity and Deaf and Hard of Hearing, and points to the upcoming 2027 buddy program.

    SIG API Machinery in the Era of AI: Updates

    Joe Betz

    Joe Betz reviews a year of work in Kubernetes SIG API Machinery, from contributor trends to API server performance, resilience and controller improvements. He covers the storage version migrator, internal type and protobuf cleanups, declarative validation with its linter, manifest-based admission policies and client library updates, then outlines what comes next.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: you build Kubernetes APIs, CRDs or controllers and want to know what changed in the API machinery underneath them.

    1. 1:38 Betz says PRs to the SIG rose about 50% this year, which he links to AI-assisted development, while reviewer capacity stayed roughly flat.
    2. 7:21 Betz says the storage version migrator has finally landed, so CRD authors can migrate stored objects and eventually retire conversion webhooks.
    3. 12:14 Betz explains that making internal types match the preferred serving version lets the Go compiler skip needless copies during conversion.
    4. 14:45 Betz shows declarative validation, where tags on API types generate validation code, plus a linter that catches mistakes such as a field marked both required and optional.
    5. 17:10 Betz describes a tool to detect backward-incompatible CRD changes and manifest-based admission policies loaded at API server startup that users cannot bypass or modify.

    Zero-Ops Disaster Recovery: A Paved Path Through Multi-Cluster Orchestration

    Joe Nathan Abellard, Li Zhuyu

    Joe Nathan Abellard and Li Zhuyu describe how Bloomberg runs Karmada as a managed, highly available multi-cluster orchestration layer across data centers. They cover the operator, observability, scale testing with KWOK and ClusterLoader2, and the scheduler changes they made for large fan-out workloads.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster Kubernetes platform and want a detailed Karmada case study covering HA, observability and scheduler tuning.

    1. 2:11 The speakers say data center redundancy is a Bloomberg-wide mandate and that they chose Karmada, which has a standard kube API server, its own scheduler and placement driven by propagation policies.
    2. 8:06 They describe a managed Karmada operator they built that gives each tenant its own namespace and control planes, sets up ingress and registers member clusters automatically from a cluster inventory API.
    3. 10:14 They walk through an HA topology where every control plane runs on host clusters in several data centers, sharing a DNS endpoint and an etcd cluster spread over three data centers, and go through which failures it survives.
    4. 19:48 For scale tests they say they use KWOK so only one of each cluster's 1,000 nodes is real, drive load with ClusterLoader2 and measure end-to-end propagation latency with a sidecar controller.
    5. 29:43 They report that a separate fan-out scheduler for duplicated workloads cut P99 propagation latency from over three minutes at 20 objects per second to under one second at 50 objects per second in their tests.
