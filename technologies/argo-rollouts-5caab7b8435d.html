    Automated Resource Allocation Driven by Service Level Objectives

    Pedro Célestin, Julia Furst Morgado

    Pedro Célestin and Julia Furst Morgado present a case study in letting teams specify service objectives and using measured performance to test resource changes automatically. They describe using error budgets and production canaries to test proposed changes instead of letting an AI agent change allocation directly.

    25 min slot · Advanced · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: You want to turn service objectives into allocation decisions without handing an AI agent direct control of production.

    1. 2:55 The speakers translate an example latency goal into an error budget, then explain how budget burn could inform whether to add or reclaim resources.
    2. 7:20 They propose canarying a resource change, not just a new build. They explain that if more resources do not improve the service-level indicator, the cause may instead be a bad release.
    3. 9:45 They describe the division of work in their case study: developers set the service objective, while the platform tests its own allocation proposals and can keep or reverse a change based on measured results.
    4. 11:28 They say letting AI change production allocation directly did not work well for them, so they limited it to proposing changes that a production canary could verify.
    5. 13:25 They walk through their stack: Prometheus collects metrics, Argo CD deploys changes, Argo Rollouts runs canaries, and Knative is used in some cases rather than being required.

    Autoscaling at Scale with KEDA

    Ali Aqel

    Ali Aqel, a Stripe engineer and KEDA contributor, describes how Stripe's Kubernetes team runs workload autoscaling with KEDA across its clusters, organized around four principles: safe, stable, scalable and simple. He covers rollout protection, break-glass locks, canaries for every scaler, tuning and per-cluster Prometheus workspaces, and walks through two hypothetical incidents.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingObservability and reliabilityDelivery, GitOps and release safety

    Watch this if: you run KEDA or HPA on large clusters and want one company's guardrails, locks and canaries.

    1. 3:09 Ali gives Stripe's numbers: more than 90 self-managed clusters, about 84,000 deployments and 180,000 application pods for over 8,600 services, run by about a dozen Kubernetes engineers.
    2. 10:03 He says Stripe built a pod deletion cost controller that annotates pods so scale-downs keep the spread across availability zones.
    3. 11:02 He describes scale-down and scale-up locks, from one service up to global, built on KEDA's pause annotation and annotations he says Stripe upstreamed, including force activation.
    4. 13:17 He says a canary for every supported scaler pages the team when degraded, and that these canaries found Prometheus rate limiting and a DNS problem.
    5. 16:45 He says scaling on Prometheus broke Amazon Managed Prometheus rate limits, which led through caching and sync period changes to one autoscaling workspace per cluster.

    Next Generation DevOps: Reshaping the Cloud Native DevOps Infinity Loop with AI

    Rey Lejano

    The speaker reviews how DevOps and cloud native grew up together and then proposes a framework that places an example AI agent in each phase of the DevOps infinity loop. He says the agents take the drafting and repetitive work while people keep the judgment and approval steps.

    30 min slot · Beginner · Session

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You are new to cloud native delivery and want a phase-by-phase picture of where AI agents could fit in the DevOps loop.

    1. 3:28 The speaker introduces a framework for embedding AI in each phase of the DevOps infinity loop, with people remaining in the loop for accountability.
    2. 15:37 The speaker argues that AI is the next substrate, and says it does not change the stages of the loop but who or what executes each one.
    3. 17:31 For the plan phase, the speaker describes a spec agent that turns vague requests into user stories and draft architectural decision records, with the human deciding.
    4. 22:50 For the build phase, the speaker describes a pipeline agent that reviews container files, runs CVE scans, generates SBOMs and signs images, with policies enforced by the pipeline, in his case Tekton.
    5. 28:44 For deploy and operate, the speaker describes a rollout agent that runs canary steps with Argo Rollouts and watches metrics for rollback, and a runbook agent that does root cause analysis.

    Progressive Delivery for Trust: How Agents Earn the Right to Merge

    Darian DeFalco

    Darian DeFalco describes how Transfix applies progressive delivery to deciding when an automated pull request can merge. He explains how shadow evaluations, per-PR test environments, and narrow, reversible grants keep the decision separate from the permission to act.

    30 min slot · Any Level · Session

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You want to move from human review of every agent-written change to limited auto-merge based on observed outcomes.

    1. 8:27 DeFalco describes how Transfix turns each task into a Kubernetes Job with a limited GitHub token and runs it only in staging.
    2. 10:57 DeFalco explains that in shadow mode the agent opens a pull request and an evaluator logs what it would do without acting on the decision.
    3. 12:12 DeFalco shows how Argo CD creates a staging namespace for a labeled pull request and removes it when the label is removed.
    4. 13:35 DeFalco says a grant covers a narrow class of changes and each new pull request still needs a passing test for that exact commit.
    5. 16:22 DeFalco describes how a reverted merge suspends automation for that repository and triggers a pull request to remove the grant.

    Saturated by Design - Maximizing Cluster Allocation in On-Premises Kubernetes

    Dakota Sullivan, Isaac Wilson

    The speakers describe how The Trade Desk raised allocation in its fixed-size on-premises Kubernetes clusters from about 20% with default scheduler settings to what they say is a consistent 97%. They walk through four problems, node scoring, deployment overscaling, fragmentation and right-sizing, and the scoring change, two custom scheduler plugins and a simulation-driven controller they built for them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: You run fixed-capacity or on-premises Kubernetes clusters with large pods and topology constraints and want to see how one team pushed allocation toward full.

    1. 4:14 Isaac Wilson says switching node scoring from least allocated to most allocated was the easiest and most significant change, taking utilization from about 20% to 85%.
    2. 6:30 Dakota Sullivan describes Plimsoll, a custom scheduler plugin that holds back extra pods created during rollouts and deletions until terminating pods are gone, which he says also works with out-of-tree controllers such as Argo Rollouts.
    3. 11:24 Wilson describes ResourceShuffler, a second scheduler plugin that moves pods without topology spread constraints to make room for constrained pending pods while respecting PodDisruptionBudgets, bringing utilization to 97% by their account.
    4. 15:09 Sullivan explains modeling workloads elastically, which he compares to CSS flexbox: each has a basis scale plus a min and max, so all workloads shrink or grow fairly when capacity changes.
    5. 18:24 He introduces Bento, a controller that snapshots the cluster, runs simulations with the real Kubernetes scheduler to find ideal scales and moves workloads part way toward them on each loop.

    You Don’t Have to Choose: Argo and Flux Are Friends!

    Emily Chen, Leigh Capili

    Emily Chen of Akuity and Flux maintainer Leigh Capili compare the design priorities of Argo CD and Flux and describe ways teams run both, such as Flux for cluster add-ons across a fleet and Argo CD for developer applications. In live demos, Flux bootstraps Argo CD, a Flux signature failure shows up as a degraded Argo CD application, and Kargo promotes a Flux Helm release of cert-manager across three virtual clusters.

    30 min slot · Advanced · Session

    Delivery, GitOps and release safety

    Watch this if: your organization runs both Argo CD and Flux, or is arguing over which one to pick, and you want to see them working in one cluster.

    1. 8:43 Chen says Argo CD has shipped Flux health checks since version 2.13, so Flux Helm releases and kustomizations show their health in an Argo CD application.
    2. 10:12 The speakers describe a common split where Flux handles fleet management and cluster add-ons while Argo CD serves application developers.
    3. 16:34 In the demo, Capili pushes an unsigned chart and the signature verification failure from Flux appears in the Argo CD interface.
    4. 20:19 Chen's Kargo promotion of cert-manager commits directly to Git for Flux to pick up, without using Argo CD.
    5. 22:16 Capili says Kargo has only one health checker, for Argo CD applications, and proposes one that reads kstatus so Kargo could understand Flux and other tools.
