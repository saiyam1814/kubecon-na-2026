    Dockerfiles Made Software Reproducible. What Makes an Agent Reproducible?

    Per Krogslund

    Per Krogslund argues that a Dockerfile describes an agent's workload but says nothing about what the agent is allowed to reach, and presents Docker's open sandbox kit spec, which records those capabilities as annotations on an OCI image. He shows kits being run and built with Docker's microVM-based sandbox runtime and takes audience questions on Kubernetes support, other runtimes and updating a kit's metadata.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run coding agents and want to see one proposal for declaring an agent's network, credential and device access alongside its image so teams can share and check it.

    1. 4:54 Krogslund says a container is process isolation and not a security boundary, and that running a coding agent in a privileged container with access to the Docker socket gives it a route to the host machine.
    2. 6:57 He says Docker is building an agent runtime and supply chain on top of OCI and not a new format, that the sandbox kit spec is already open source, and that Docker has discussed handing it over to the CNCF.
    3. 11:03 He describes Docker's own runtime as a microVM with a private Docker engine whose only way out is a network proxy, which applies allow and deny rules and swaps a placeholder credential for the real one on outbound requests.
    4. 13:36 He walks through a kit's YAML file, which names the hosts the agent needs, the service credential it needs without storing it, and any agent context file, and later shows network rules that differ between install and run time.
    5. 21:31 Asked about Kubernetes, he says there is no Kubernetes runtime yet beyond an experimental version inside Docker, that the focus so far is the local experience, and that he wants input on the use cases.

    KitOps: The Whole Kit for AI Agents

    Gorkem Ercan

    Gorkem Ercan, the creator of KitOps, describes how the project now packages the parts of an AI agent, such as prompts, MCP servers, code and an agent definition, with the model as an optional piece. He explains the agent definition format and shows the init command generating a Kitfile for a support agent.

    5 min slot · Level not listed · Lightning Talk

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: you want one versioned package for an AI agent's prompts, skills, MCP servers and code.

    1. 2:06 Gorkem Ercan says KitOps added prompts as a distinct layer.
    2. 2:16 He says MCP servers are packaged as MCPB bundles and stored as OCI artifacts, alongside code and an agent definition, and that the model is now an optional piece.
    3. 3:00 He compares a Kitfile to a Dockerfile that tells the CLI what to package, and says the extended init command finds skills and MCP bundles and generates the Kitfile.
    4. 3:41 He walks through the agent definition: a framework naming the harness that runs the agent, an includes list of modules, and a needs section for things like secrets, OIDC and environment variables.
    5. 5:05 He demos a support agent that uses Claude Code with one local and one remote MCP server, runs the init command to get a Kitfile, and says it can then be packaged and pushed to an OCI registry.

    Kubernetes Anonymous: Confessions of Kubernetes Cargo Cultists

    Taylor Thomas, Brooks Townsend

    The speakers, who say they have worked both on Kubernetes-heavy platforms and on a wasmCloud platform that avoided Kubernetes, argue that both extremes are traps. They list red flags for using Kubernetes where it fits poorly, describe what each extreme cost them, and suggest that CNCF projects be compatible with Kubernetes without depending on it.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: You are deciding how much of your platform or project should be built on Kubernetes APIs and want the tradeoffs from people who tried both extremes.

    1. 1:43 The speakers poll the room on red and yellow flags, such as using Kubernetes as the database for config objects, making every service a CRD and mapping an API permission model onto Kubernetes RBAC.
    2. 10:58 Taylor Thomas says avoiding Kubernetes on principle for their wasmCloud platform was their own yellow flag, and that it cost them adoption and integrations with the rest of the ecosystem.
    3. 15:27 Describing Kargo, Thomas says Kubernetes became its database, API and auth model, and that most of its high and critical CVEs this year came from contorting the access model to fit Kubernetes RBAC.
    4. 17:29 He says Kargo 2.0 moves promotion and artifact tracking to a real database while Kubernetes stays as the execution substrate that runs pods.
    5. 20:21 Thomas asks people to stop putting everything in a CRD and offers test questions, including whether the work depends on a Kubernetes feature and whether it would be valuable outside Kubernetes.
