    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

    Gone in 60 Minutes: Effectively Close the Exploitable Window with Detection as Code

    Ben Hirschberg, Constanze Roedig

    Ben Hirschberg and Constanze Roedig show two ways to detect exploitation with Kubescape in the hours between a vulnerability becoming public and a patch being deployed, both shipped to the cluster as YAML through GitOps. Hirschberg writes rules from published indicators of compromise, and Roedig uses behavior profiles to flag deviations when the attacker's methods are not yet known.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyObservability and reliability

    Watch this if: you need a way to detect exploitation of a newly disclosed vulnerability in running workloads before a patch can be rolled out.

    1. 2:19 Hirschberg describes the setup: the Kubescape node agent with eBPF sensors and a rule engine whose detection rules are written in CEL, with alerts sent to Slack.
    2. 6:16 In a recorded demo he pastes the indicators of compromise from a published write-up of the poisoned Trivy GitHub Action into an AI agent, which opens a pull request with Kubescape detection rules that Argo CD syncs to the cluster.
    3. 9:32 Roedig introduces what she calls a software bill of behavior, a custom resource listing allowed capabilities, network traffic, executables and file opens as composable fragments that can be signed separately.
    4. 11:56 She says build runners are a poor fit for anomaly detection because their behavior is not bounded, then shows a profile-based setup still flagging the same indicators as the rules did.
    5. 16:54 For a PHP server that normally spawns shells, she says the profile caught the exploit because the id command ran outside the expected process tree, and argues a good profile has as few entries as possible.

    Goodbye Webhooks, Hello CEL: Using Native Validating and Mutating Admission Policies in Kubernetes

    Greg Bray

    Greg Bray of Google Cloud explains how ValidatingAdmissionPolicy and MutatingAdmissionPolicy let Kubernetes evaluate CEL expressions inside the API server, which he says avoids the latency and failure risk of admission webhooks. He also covers where he thinks the native policies fall short and a full policy engine such as Kyverno or Gatekeeper is still needed.

    30 min slot · Any Level · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you run admission webhooks for simple checks and want to know which of them can move to policies built into the API server.

    1. 4:49 Bray lists the pain points of webhooks: the API server has to call out of process, and he says a failing webhook set to fail closed can bring the whole control plane to a halt.
    2. 8:20 He shows CEL optional values, which he says arrived in Kubernetes 1.29 and replace long guarded expressions for fields such as annotations that may not exist.
    3. 12:16 He walks through MutatingAdmissionPolicy, which he says went GA in April, and compares declarative apply configurations with imperative JSON patches.
    4. 18:13 He describes manifest-based policies loaded from disk before the API server starts serving, which he says close the bootstrap gap and cannot be changed or deleted through the API.
    5. 20:46 He lists the limits of native policies: they see only the request and the old object, cannot read other resources or external data, and stop when a CEL cost budget is exceeded.

    OpenFGA: Fine-Grained Authorization for Apps, APIs, and Agents

    Will Vedder

    OpenFGA maintainer Will Vedder introduces OpenFGA as a centralized, Zanzibar-inspired authorization decision engine and explains its authorization models, tuples, check and list APIs, and CEL-based conditions through a running example of whether a user or the user's agent may deploy a service. He then presents dynamic conditions, which he describes as a new feature that attaches CEL expressions to tuples so per-task agent rules need no model change, with an MCP gateway as the enforcement point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing or building an authorization system and want an introduction to OpenFGA's model, plus its approach to scoping what an agent may do on a user's behalf.

    1. 4:54 Will Vedder compares RBAC, ABAC and ReBAC, saying relationship-based access control expresses inheritance and reverse lookups natively but requires writing or backfilling the relationships.
    2. 12:35 He says an OpenFGA check is a graph reachability problem: John may deploy the payments API because a chain of tuples links him through the SRE team and the checkout project to that service.
    3. 15:26 He describes conditions as OpenFGA's ABAC feature, written as CEL expressions and used for cases such as expiring grants, usage-based entitlements and IP allow lists.
    4. 17:40 He says the pattern they see most for authorizing AI agents is an MCP gateway that consults OpenFGA before forwarding a tool call.
    5. 20:57 He introduces dynamic conditions, where a CEL expression such as environment not equal to prod is stored on the tuple and evaluated at query time, so a new per-agent rule needs no model change.

They walk through the past year's changes, including structured z-pages, Resource State Metrics and native histograms, then list next year's plans and the subprojects where they say they need contributors.

    30 min slot · Level not listed · Session

    Watch this if: you run Kubernetes monitoring and want the maintainers' view of what changed in metrics, logs and traces and where the SIG wants help.

    1. 4:10 Catherine Fang presents the statusz and flagz z-pages, which she says expose a component's binary version and effective flags on its serving port and are gaining structured output formats this year.
    2. 8:02 Catherine introduces Resource State Metrics, a new component that she says uses CEL-style expressions to read any field of a custom resource without writing Go code in kube-state-metrics.

    Signed, Sealed, Denied: Attestation-Driven Admission with Kyverno + CEL at AT&T

    Chad Swenson, Sagar Kundral

    Chad Swenson of AT&T argues that a signature alone is not a deployment approval and describes a platform design where GitHub Actions emits Sigstore-backed attestations and Kyverno's ImageValidatingPolicy checks them against each environment's rules at admission. Sagar Kundral of Nirmata demos the policies on a live cluster and presents Kyverno 1.19 and 1.20 changes, benchmark numbers and advice on exceptions, failure behavior, evidence retention and rollout.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you sign images already and want to see how attestations can drive per-environment admission decisions that you can later explain to an auditor.

    1. 3:38 Chad says a valid signature and provenance are useful but neither is a deployment approval, so the platform must still ask whether trusted claims meet the destination's requirements.
    2. 5:15 Chad gives an example where the same image digest is admitted in development on provenance alone but denied in production because it lacks a signed SBOM attestation.
    3. 13:51 Chad says verifying only against GitHub's private Sigstore instance broke down for upstream and vendor images with other trust roots, and credits a fix released in Kyverno 1.19 after he raised it with the lead maintainer.
    4. 17:28 Sagar runs a scripted demo on a live cluster showing verification with a signer workflow identity, an unattested image blocked, a production denial for missing code reviews, a policy exception in dev, and an org ID pin.
    5. 24:38 Sagar presents benchmark numbers from a kind cluster where he says p50 admission latency fell from 990 ms to 96 ms and registry calls from 14 to 3 in Kyverno 1.20.

    Dr. Constanze Roedig

    Constanze Roedig walks through cloud native security in three parts, the software supply chain you consume, the software development lifecycle where you build and deploy, and the runtime, naming CNCF and OpenSSF projects for each. She closes with her view that AI agents put more weight on runtime detection and on protecting and rotating secrets.

    12 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: You find cloud native security overwhelming and want a 16-minute overview of which problem each group of projects addresses.

    1. 0:40 The speaker frames the talk around three areas: the supply chain of software you consume, the software development lifecycle where you produce and deploy it, and the runtime.
    2. 3:44 She says an SBOM declares what is in your software but cannot be assumed complete, and suggests following OpenSSF recommendations on tooling.
    3. 5:51 She distinguishes a signature from an attestation, which she describes as a piece of evidence put in an envelope together with a signature, and names in-toto.
    4. 10:36 For runtime detection she contrasts signatures, which encode known adversary behavior, with anomalies, which are deviations from your own baseline, and says to combine them.
    5. 14:18 She says that with AI agents there are vulnerabilities with no patches available, which in her view puts the spotlight on runtime detection and on short-lived, rotatable secrets.

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.

    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.

He shows a recorded demo of MIG profiles, resource slices and claims on an AWS node serving a model behind an inference gateway, and lists open questions such as quotas, models larger than a node and start-up ordering.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: you run inference on your own GPUs and want a practical walk through MIG slices requested with Dynamic Resource Allocation.

    1. 8:32 Diri says time slicing gives no memory or fault isolation between workloads, so the choice was between wasting GPUs and risking a noisy neighbor.
    2. 11:24 Diri says Dynamic Resource Allocation, which he dates to Kubernetes 1.34, lets a request describe device attributes instead of an integer count.
    3. 22:16 In the recorded demo, Diri lists the 1G, 2G and 4G MIG profiles on the node and the resource slices the DRA driver published.
