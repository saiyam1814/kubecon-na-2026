    Engineering Kubernetes for the Next Era of Workloads

    Mike Stefaniak

    Mike Stefaniak describes bottlenecks AWS found when running large Kubernetes clusters and says the team contributed fixes upstream. He walks through watch-cache and scheduler changes, accelerator-aware provisioning with Karpenter, and parallel image unpacking in containerd.

    5 min slot · Level not listed · Keynote

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run large GPU clusters and want concrete examples of upstream fixes from image unpacking to accelerator placement.

    1. 0:47 Stefaniak says AWS replaced a long-held Kubernetes API server watch-cache lock with a lazy snapshot, cutting writer wait from over half a second to 2 ms in its million-pod benchmark.
    2. 1:03 Stefaniak says a new Horizontal Pod Autoscaler selector store removed a read/write bottleneck, letting AWS run four times as many HPA workers in its largest clusters.
    3. 1:21 Stefaniak says an incremental scheduler cache avoided rebuilding volume reference counts and that AWS saw scheduling stay above 300 pods per second in its largest clusters.
    4. 2:28 Stefaniak explains that Dynamic Resource Allocation can describe GPU and network topology, and says Karpenter can now model devices for instances it has not launched yet.
    5. 3:48 Stefaniak says parallel layer unpacking in containerd brought a 10 GB image pull from about two minutes to under 45 seconds in AWS's testing.

    Frameworkless ML Serving: Scaling to Thousands of Models with KEDA, Pub/Sub, and Native K8s

    Robin Deaconu, Neb Jovanovic

    The presenters explain why multi-minute drug-discovery jobs led their team away from a general-purpose inference framework. They describe how stateless workers, durable queues, and native Kubernetes scheduling serve interactive and batch requests on the same fleet.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: interactive inference and long-running batch jobs need to share the same pool of accelerators.

    1. 6:01 The presenters explain why multi-minute accelerator jobs made durable requests and backlog-based scaling more useful to them than in-flight concurrency.
    2. 9:12 They describe how a stateless worker backed by an asynchronous queue became the core building block of the new platform.
    3. 16:29 They explain how KEDA wakes a deployment from zero replicas and passes queue signals to the Horizontal Pod Autoscaler for further scaling.
    4. 18:46 They walk through high-priority requests preempting batch workers and describe how queue leases let interrupted work become available again.
    5. 27:52 They describe dual-writing to Redis and Bigtable to verify parity before cutting over with a configuration flag they could flip back.

    Inside the Inference Load Balancer: Proxy/Controller Patterns for LLM Serving on Kubernetes

    Qianru Lao, Lu Zhang

    Qianru Lao and Lu Zhang explain how their inference load balancer steers requests across Kubernetes clusters when engine capacity, distance, and cache state differ. They describe a control plane that computes fleetwide weights, a data plane that applies them locally, and protections they use when load changes.

    30 min slot · Advanced · Session

    AI inference and servingNetworking and connectivity

    Watch this if: You are designing multi-cluster inference routing and want to see how one team separates request-path decisions from fleetwide optimization.

    1. 3:36 Zhang explains why an engine with cached conversation context can return the first token sooner than a less busy engine that must process that context again.
    2. 9:34 Zhang describes how moving traffic during weight updates can disturb cache reuse and feed oscillations back into the next update.
    3. 14:27 Lao describes how the control plane uses engine signals to calculate routing weights, while the data plane routes requests using local state.
    4. 16:58 Lao walks through a regional capacity example in which routing to a more distant engine can trade network latency for less waiting at the engine.
    5. 23:13 Zhang describes shedding a controlled share of requests early as a last line of defense when retries and penalties cannot compensate for insufficient capacity.
