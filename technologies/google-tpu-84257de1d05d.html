    Anthropic’s Kubernetes Scheduler for Frontier AI: What Worked, What Broke

    Decheng Dai

    Decheng Dai describes why Anthropic wrote its own Kubernetes scheduler for accelerator workloads, covering gang scheduling, the topologies of Google TPUs and AWS Trainium, and a tree model of data center networks. He walks through the design choices he says keep the scheduling loop fast on very large clusters, then discusses soft slicing, defragmentation and the lack of transactional binding in the API server.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimesNetworking and connectivity

    Watch this if: you schedule large training or inference jobs on Kubernetes and want to hear how one team handles gang and topology constraints at very large cluster sizes.

    1. 1:27 Dai frames the problem as gang scheduling plus topology-aware scheduling and describes two gang modes: a full gang where every pod must run, and replicas that are each a gang but fail independently.
    2. 6:47 He says the team models every cluster as a tree of network domains whose leaves are TPU slices, Trainium servers or GPU nodes, and built a drop-in replacement scheduler that jobs select by scheduler name.
    3. 8:15 He describes the control loop: take a snapshot of the cluster, plan all pending jobs from highest to lowest priority, and schedule jobs rather than pods, with the loop kept within 10 seconds on their largest cluster.
    4. 16:48 He says scoring nodes only once for jobs that are identical from a scheduling perspective is by far the largest scaling factor in their system.
    5. 23:55 As something that does not work well, Dai points to gang binding without transactions in the API server: some of the bind calls can fail, forcing eviction of the pods already bound.

    From Fine-Tuning to Production: Scaling Agentic AI at Shopify via Inference Perf

    Ashok Chandrasekar, Navjot Singh

    Navjot Singh of Shopify describes load testing the fine-tuned model behind Sidekick Pulse with Inference Perf's conversation replay, sweeping concurrency levels to find how many research conversations each GPU replica completes per hour and turning that into a GPU plan. Ashok Chandrasekar of Google then presents Inference Perf's goals of reliable load generation, realistic workloads and reproducible results, and walks through its workload catalog, agentic replay generators and metrics.

    30 min slot · Advanced · Session

    AI inference and servingAccelerators and workload schedulingAI agents and automation

    Watch this if: you need to size GPU capacity for multi-turn agent workloads and want to see how a load test is configured and read.

    1. 2:32 Singh says Pulse runs as an offline batch of multi-turn research conversations, so the metric they watch is throughput: how many research conversations each GPU replica completes per hour.
    2. 6:03 He walks through the Inference Perf config for Pulse: a seed so every run replays the same workload, 38 turns per conversation with an 8-second wait between calls, and a concurrent load type that holds a fixed number of conversations in flight.
    3. 9:12 Singh says they had a fixed budget of H100 GPUs for Pulse, ran the same seeded sweep on each GPU topology, and found the canary's production throughput matched the load test.
    4. 14:07 Chandrasekar shows a test in which a single-process Python benchmark asked for 5,000 QPS delivered about 150 to 400 and reported inflated latency against a simulated server, while Inference Perf's multiprocess design delivered the requested rate.
    5. 20:27 He lists four generators for agentic workloads in Inference Perf: conversation replay, OpenTelemetry trace replay, Weka trace replay aimed at KV cache hits, and synthetic agentic trace replay.

    The Latest in GPU, TPU, NIC and Other Device Support - WG Device Management

    John Belamaric, Morten Jæger Torkildsen

    Morten Torkildsen and John Belamaric of Google give the Device Management working group update, recapping why Dynamic Resource Allocation replaced the device plugin's opaque counters and what its four parts are. They cover the features that shipped in Kubernetes 1.37 and those planned for 1.38, go deeper on allocating CPU and memory through DRA and on its integration with workload-aware scheduling, and describe ecosystem adoption and next steps such as preemption and attaching GPUs to running pods.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you manage GPUs or other accelerators in Kubernetes and want to know which DRA features landed in 1.37 and what is planned next.

    1. 3:06 Morten Torkildsen outlines DRA's four parts: the resource slice API for describing devices, the resource claim API for requesting them, the scheduler matching the two, and the kubelet API that works with the DRA driver on the node.
    2. 6:11 He explains the extended resource request feature in 1.37, which lets cluster admins adopt DRA while workloads keep using device-plugin style requests that are matched to DRA devices underneath.
    3. 7:42 He describes device taints, which let a single failing GPU or TPU be tainted instead of the whole node, so workloads on the other devices are not disrupted.
    4. 11:52 John Belamaric explains node allocatable resources with DRA, which lets CPU and memory be selected through DRA so they can be aligned with the NIC and GPU, and tells the scheduler how to account for CPU requested in both the container spec and a resource claim.
    5. 16:30 He describes the DRA integration with workload-aware scheduling, where a resource claim attached to a pod group allocates a shared resource for a new replica and cleans it up when the replica scales down.

    When Training Dies at 3 AM: Correlating Kubernetes Events with AI-Framework Failures

    Wenjia Zhang, Yuchen Zhou

    Wenjia Zhang and Yuchen Zhou of Google, standing in for the work's main contributor Richa Banker, explain why a hardware fault under a distributed training job is hard to trace back from Kubernetes events hours later. They describe the pipeline they say is merged upstream in Ray and KubeRay, which joins events to pods and parent jobs while the pod still exists, shows them in a Platform Events tab in the Ray dashboard and exports them with Ray's own events.

    30 min slot · Any Level · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: ML engineers on your platform ask whether their code or the infrastructure killed a training job and you cannot answer from Kubernetes events the next morning.

    1. 3:39 Zhang walks through a 512-GPU training run where a GPU fault at 3:14 a.m. becomes, seven seconds later, a Python exception reported by Ray as an application failure, and by 9 a.m. kubectl get events shows nothing.
    2. 8:52 She names three obstacles: events expire after a one-hour TTL, or five minutes in a large cluster with heavy churn, they carry no labels or owner references, and the pod needed for the join may already be garbage collected.
    3. 15:43 Zhou describes two watches in the Ray head: one keeps an in-memory list of the cluster's live pods by label, the other checks namespace pod events against that list, with events kept in a fixed buffer of 1,000 keyed by event UID.
    4. 17:19 He says platform events are wrapped in the standard Ray event format and exported asynchronously to a log file or HTTP endpoint, so they stay searchable in a logging backend after the cluster and the Kubernetes events are gone.
    5. 20:59 He explains that node events land in the default or kube-system namespace where a Ray head cannot see them, so the KubeRay operator watches node warnings and re-emits one event per affected RayCluster into the team's namespace.
