    Autoscaling Reality Check: The Hands-On HTTP Optimization Challenge

    David Pech

    David Pech runs a hands-on tutorial in which attendees benchmark HTTP services in NGINX, Go, PHP and Java with k6 and watch how autoscaling reacts, first with the CPU-based Horizontal Pod Autoscaler and then with Knative scaling on concurrent requests. He walks through each round on a Grafana dashboard and describes the tuning he tried, including cases where he says his own improvement failed.

    80 min slot · Any Level · Tutorial

    Accelerators and workload schedulingObservability and reliability

    Watch this if: you run HTTP services behind HPA or Knative and want to see, round by round, where autoscaling lags behind real traffic.

    1. 10:11 The speaker lays out the lab: Argo CD, Istio, Knative and a Prometheus stack on a local k3d cluster or GitHub Codespaces, with k6 load tests run against services in several flavors.
    2. 29:15 In the NGINX round scaled on CPU, the speaker shows on the dashboard that pods stay at the maximum after the load falls and that latencies remain, and asks the room why.
    3. 36:23 The speaker explains Knative's panic window: when demand jumps well above the estimate the autoscaler enters panic mode and does not scale down during it.
    4. 1:03:46 For the Java round the speaker says slow startup limits how fast scaling can react, names GraalVM as one option, and shows a tuning attempt that he says failed completely.
    5. 1:06:13 In the scale-to-zero round the speaker points out that a workload at zero has no metrics, which he says makes alerting on it hard.

    Life After Strimzi 1.0.0

    Jakub Scholz

    Strimzi maintainer Jakub Scholz describes what the project has worked on since its 1.0 release, mainly security features and changes in the surrounding Kafka ecosystem. He also outlines planned work such as gatekeeper plugins, an MCP server, automatic rebalancing and a start on the path to CNCF graduation.

    30 min slot · Level not listed · Session

    Data, storage and stateDelivery, GitOps and release safety

    Watch this if: you run Kafka on Kubernetes with Strimzi and want to know what changed after 1.0 and what the maintainers plan next.

    1. 2:16 Scholz says cert-manager integration is in Strimzi 1.3 as early access, and notes it needs a private CA because certificates must carry internal Kubernetes DNS names.
    2. 6:49 He says internal cluster encryption can now be turned off, with service account tokens added as an alternative to mTLS so that authorization still works.
    3. 10:07 He says Strimzi 1.4 moves to Java 25 so that clients which support it use the ML-KEM post-quantum key exchange by default, and that a later release is meant to enable only TLS 1.3 by default.
    4. 16:31 He recounts how a long gap in Kafka Exporter releases led Strimzi to write its own replacement, and says both will be supported in parallel.
    5. 19:51 He introduces gatekeeper plugins, hooks called before and after reconciliation that he says can enforce or enrich custom resources, inspired by admission controllers, Kyverno and Open Policy Agent.

    OpenFeature as a Control Plane for OpenTelemetry

    Simon Schrottner, Juliano Costa

    Simon Schrottner and Juliano Costa present a proof of concept that uses OpenFeature flags to change at runtime which spans a service creates and how much it samples, without restarting the service or the collector. They say it is an experiment for Python and Java with no reliable performance numbers yet, and ask the community whether it should continue and where it should live.

    30 min slot · Advanced · Session

    Observability and reliabilityDelivery, GitOps and release safety

    Watch this if: you pay for more telemetry than you read and want to see feature flags switching span detail and sampling per service at runtime.

    1. 6:16 Costa reports that a flag limiting export to incoming requests and outgoing calls gave about 55% fewer spans stored and 31% fewer trace bytes received in their demo, traces only.
    2. 7:53 Schrottner uses the OpenFeature evaluation context with OpenTelemetry semantic convention attributes (service name, span kind, URL path) to write a rule that drops health-check spans at runtime.
    3. 10:33 They set sampling rates through flag rules, 50% for one production service, 10% for the rest of production and 100% for staging, and show the ingestion chart splitting per service and environment.
    4. 13:39 Costa argues that dropping telemetry in the collector still spends application CPU, memory and network egress on producing it, and both say they would keep the collector's sampling as a safety net.
    5. 18:20 Schrottner says they saw no big performance impact when switching flags but calls these not reliable benchmarks, and Costa adds they have not compared their instrumentation against stock OpenTelemetry instrumentation.

    Rego Without Borders: Breaking Down Language Barriers for Security Policy

    Philip Conrad

    Philip Conrad, an Open Policy Agent maintainer, describes how the project wants policy decisions to run inside applications instead of in a sidecar, which he says has so far been easy only in Go. He explains how the Rego intermediate representation lets other languages run policies natively, and names Swift OPA and the Java OPA SDK as two new projects that do it.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policy

    Watch this if: you want to run Rego policies inside a Swift or Java application without calling a separate Open Policy Agent over the network.

    1. 0:41 Philip Conrad describes Open Policy Agent as a general purpose policy engine, a CNCF graduated project since 2021, that takes structured input such as JSON or YAML and returns decisions.
    2. 1:36 He says the community increasingly wants the policy engine embedded in the application itself instead of running as a sidecar.
    3. 2:22 He says Go makes it hard to package a library for other languages, so those languages have been limited to REST API calls to an Open Policy Agent running elsewhere.
    4. 2:58 He explains the Rego intermediate representation from the project's Wasm pipeline: query plans that break rules into smaller imperative instructions, built with opa build and a plan target.
    5. 3:46 He names Swift OPA and the Java OPA SDK as two new projects this year that run these plans natively, and says the main gain is debugging, with data-heavy policies sometimes running faster than in OPA.

    The New Scaling Matrix: Balancing In-Place Resizing, VPA, HPA and Automation Solutions

    Dolis Sharma

    Dolis Sharma reviews resource optimization options on Kubernetes, from label-driven cleanup, HPA and VPA to in-place pod resizing, and describes a central right-sizing setup in which VPA recommendations feed Kyverno policy reports and an agent opens pull requests for teams to review. The speaker then argues that agents behave differently from applications and describes Agent Substrate as a runtime that snapshots idle agent sessions.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimesAI agents and automation

    Watch this if: you run right-sizing for many teams and want a GitOps-friendly way to act on VPA recommendations, or are starting to host agents.

    1. 3:02 The speaker recalls that HPA and VPA race against each other when set on the same resources, and that VPA changes on the cluster conflict with GitOps repositories.
    2. 4:36 The speaker says in-place pod resizing was introduced with JVM startup in mind, and that it helps for CPU but not for memory because the JVM sets its heap at startup.
    3. 11:50 The speaker describes VPA in recommendation mode on spoke clusters, with Kyverno policies comparing recommendations to what is deployed and writing the difference into a policy report.
    4. 14:26 The speaker says an agent on the Argo CD hub cluster reads the policy reports and creates a pull request, and that the setup does not suggest auto merge because a human should stay in the loop.
    5. 21:39 The speaker argues that one agent per pod wastes resources while the agent waits, then presents Agent Substrate as a runtime that snapshots idle sessions and frees capacity.
