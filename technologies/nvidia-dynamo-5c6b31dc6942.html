    Agentic AI: Let’s Build a Reference Architecture, Live? Or at Least Try!

    Ricardo Rocha

    Ricardo Rocha invites practitioners to sketch a cloud-native reference architecture for agentic AI from their own deployments. The group maps layers for gateway and inference, then discusses caller identity, privacy, and why an agent's lifetime affects how it should be run.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are planning an agent platform and want to compare architecture choices with other practitioners.

    1. 6:36 Rocha shows the draft architecture and places the gateway at the entry point, LangChain around orchestration, and Langfuse in the observability layer.
    2. 10:11 An attendee says caller identity can be lost on the way to the model and suggests preserving it across the chain for attribution and tracing, mentioning SPIFFE and SPIRE.
    3. 13:06 An attendee describes identifying and tokenizing sensitive fields before sending requests to a third-party inference engine, even if the requests are already signed.
    4. 22:16 An attendee contrasts one-shot agents that are seldom reused with long-running jobs, and Rocha adds that distinction to the architecture discussion about checkpointing and resuming work.
    5. 28:34 Rocha asks teams to contribute reference architectures and says submissions should include what worked, what did not, and the custom integration work they needed.

    Agentic Inference at Scale

    Maroon Ayoub, Sean Horgan

    Maroon Ayoub and Sean Horgan describe how llm-d serves agentic sessions, which they say read far more input than they generate, by routing to cached context, offloading KV cache and splitting prefill from decode. They show production examples of zero-downtime router rollouts and flow control, and outline the Agentic Inference SIG's plans for session-level orchestration.

    20 min slot · Level not listed · Session

    AI agents and automationAI inference and serving

    Watch this if: You serve coding agents or other long multi-turn LLM sessions on Kubernetes and care about cache hit rates.

    1. 0:36 Maroon Ayoub says agentic sessions send far more input than output, around a hundred to one, so avoiding recompute unlocks hardware capacity.
    2. 2:46 He describes a production case where prefill compute fell from 16% to 4% while traffic doubled, after fixing how vLLM handled a timestamp Claude Code injects into each turn's system prompt.
    3. 6:26 He explains how the llm-d router balances prefix cache affinity against load-aware routing to avoid hot spots.
    4. 10:44 He shows a production router rollout where the new router loads a state snapshot, takes over traffic and the old one drains with zero errors.
    5. 13:38 Sean Horgan outlines the Agentic Inference SIG's work on orchestrating whole sessions rather than single requests.

    Beyond Model Serving: Running Production LLMs on Kubernetes with KServe

    Johnu George, Jooho Lee

    The two KServe maintainers explain how the project added an LLMInferenceService API that builds on llm-d, vLLM and the Gateway API Inference Extension rather than a new inference engine. They then go through production patterns they say KServe addresses: cache-aware routing, streaming timeouts, split prefill and decode, multi-node serving, autoscaling signals, cold starts, model updates and LoRA adapters.

    30 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload schedulingNetworking and connectivity

    Watch this if: you serve LLMs on Kubernetes and want the KServe maintainers' checklist of routing, scaling and cold-start issues to plan for.

    1. 4:07 Jooho Lee describes the LLMInferenceService API, in which he says a workload controller manages single-node, multi-node and separate prefill deployments while a route controller manages the scheduler and Gateway API resources.
    2. 8:44 Jooho follows a request from the gateway to the endpoint picker, which he says can weigh prefix cache match, queue depth and KV cache usage instead of treating every healthy replica as equal.
    3. 12:47 Johnu George warns that with streaming, timeouts at each hop must exceed generation time, because he says client retries otherwise pile more load on the GPUs.
    4. 16:15 Johnu argues that GPU utilization is a misleading autoscaling signal for LLMs and says the number of requests waiting in the inference runtime's queue is a better one.
    5. 17:30 Johnu describes cold-start work with a local model cache and container snapshot and restore, and says they are seeing startup drop from minutes to a few seconds.

    Beyond One Model per GPU: Agent-Driven Placement for Maximum GPU Utilization on Kubernetes

    Weiqi Sun, Ratnopam Chakrabarti, Ajay Vohra, Vivek Kolasani, Felipe Garcia

    The speakers from AWS and NVIDIA present a pipeline in which an agent, a constraint solver and real GPU measurements search for ways to place several LLMs on shared GPUs with CUDA MPS while each model still meets its latency targets. They walk through the plan, profile, search and export stages, the hand-off to KAI Scheduler through Helm, and results they measured on L40S and H100 nodes.

    80 min slot · Advanced · Tutorial

    Accelerators and workload schedulingAI inference and servingAI agents and automation

    Watch this if: you serve many LLMs on Kubernetes and want a worked method for packing them onto fewer GPUs without breaking latency targets.

    1. 4:16 A speaker sets the running example: 15 models, two L40S machines with 16 GPUs, and the question of the fewest GPUs that still meet each model's service level objective.
    2. 20:19 A speaker says CUDA MPS gives no performance isolation, that the limits are caps and not guarantees, and that this is why every placement is benchmarked.
    3. 24:23 A speaker introduces the solution as a Claude skill split into plugins and commands that runs plan, profile and search stages, with a CP solver proposing placements for the agent to test.
    4. 43:24 A speaker explains that KAI Scheduler does not read the certified export directly, so a deployment adapter turns it into Helm values with one release per model.
    5. 1:02:25 A speaker gives five takeaways from the H100 experiments, including a measured co-location latency cost of about 1.3 to 2.3 times and a preference for MPS over time slicing.

    Follow the GPUs: How a Regulated Fortune 100 Serves Customers When No Single Cloud Has Enough

    Yuva Peavler, Michael Kinsley

    Yuva Peavler and Michael Kinsley of GEICO describe their hybrid cloud platform, a flat network across providers with a zero trust overlay built on SPIFFE/SPIRE, Istio and Cilium, and say it lets them move workloads to wherever GPUs are available. Michael then shares a tool they wrote to probe GPU availability across AWS and Azure regions, what four weeks of samples showed them, and their idea for a booking agent that reserves capacity ahead of demand.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you need GPUs without long reservations and want measured data on whether multi-region and multi-cloud help.

    1. 1:45 Michael gives the takeaways first: current single-GPU SKUs need multi-region support, flagship eight-GPU nodes have to be booked ahead, and he says the autoscaler will not do the booking.
    2. 3:43 Yuva explains the platform from the bottom up: one flat L3 network across every provider, identically built Kubernetes clusters, then SPIFFE/SPIRE identity, Istio mutual TLS and Cilium deny-by-default policy.
    3. 8:54 Yuva says they made SPIRE's data store pluggable in their fork and run Cassandra behind it for an active-active multi-region control plane, and that they have proposed this upstream.
    4. 16:54 Michael introduces their Follow the GPUs tool, which asks for GPUs, doubles the request after each yes until it gets a no, then waits about an hour and starts again.
    5. 22:02 Michael reports that in their data multi-region did not matter for small single-GPU SKUs but raised the chance of getting an RTX Pro 6000 from about 45% to 70 to 75%.

    One Recipe, Five Clouds, One Query: Portable GPU Configuration with a Queryable Audit Layer

    Christopher Haar, Yuan Chen

    The speakers present AI Cluster Runtime (AICR), an open source project that turns layered recipes into validated GPU runtime bundles for different clouds, accelerators and workloads. They show commands for querying a configuration, diffing snapshots, checking upgrades and publishing signed evidence reports.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: You bring up GPU clusters on more than one cloud and want reproducible configuration that you can query and audit without touching a live cluster.

    1. 1:45 The speaker says a GB300 training cluster on EKS needs about 300 parameters set correctly across more than 16 components.
    2. 3:29 The speaker walks through the workflow: snapshot the cluster, generate a recipe, build bundles, deploy with a deployer of your choice, then validate.
    3. 9:08 In the recorded demo, the speaker reports throughput above 30,000 tokens per second and a time to first token of about 160 milliseconds.
    4. 12:44 The speaker explains the query command, which merges recipes and overlays into one values file and selects fields such as the GPU driver version across EKS, GKE and AKS.
    5. 18:15 The speaker runs query, snapshot, diff and upgrade check in a short demo, and says diff exits with code two so a CI pipeline fails on drift.
