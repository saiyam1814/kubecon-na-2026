    Cloud Native without Limits: Powering the AI Era in the Open

    Chris Aniszczyk, Jonathan Bryce, Rita Zhang, Kevin Cochrane, Robert Nishihara, Justin Boitano, Bassam Tabbara

    The opening speakers say that agents are driving inference demand and describe how cloud providers are contributing fixes from production back to open source. The session includes announcements about KubeRay and OpenShell and a ModelPlane demo that moves an inference deployment between clouds.

    Length not listed · Level not listed · Type not listed

    AI inference and servingCommunity and open source adoption

    Watch this if: you want the opening announcements on AI infrastructure, with examples spanning Kubernetes inference, agent controls, and multi-cloud model serving.

    1. 5:00 Bryce cites OpenRouter and other providers as examples of an increase in inference traffic, saying he has seen it grow fourfold in eight months.
    2. 16:27 Zhang says CoreWeave feeds lessons from production back upstream, citing fair GPU scheduling in Kueue and hardening work in vLLM, NVIDIA Dynamo, and Grove.
    3. 31:53 Nishihara announces that KubeRay is joining CNCF and explains that Ray handles distributed coordination inside a Kubernetes workload, such as a reinforcement learning pipeline.
    4. 36:18 In a prerecorded segment, Boitano argues that infrastructure, not the agent itself, must enforce access boundaries, and says OpenShell has joined the CNCF Sandbox.
    5. 40:46 Tabbara demos ModelPlane, showing how it can serve the same model through one endpoint and move replicas between clouds when GPU capacity changes.

    Demystifying Upgrades for Stateful, Dormant AI Agents: Unleashing Seamless Updates in Dynamic Sand

    Zhang Zhen

    OpenKruise maintainer Zhang Zhen describes how OpenKruise Agents, which he presents as a Kubernetes-native sandbox operator that runs agent sandboxes as pods, upgrades sandboxes that hold state and are mostly hibernated. He walks through upgrade paths for warm pools, for sandboxes at claim time and for running or paused sandboxes, including recreate with backup hooks, in-place update, checkpoint and restore, an installer approach using ephemeral containers, and a sandbox service for fleet rollouts.

    30 min slot · Level not listed · Session

    AI agents and automationDelivery, GitOps and release safetyKubernetes internals and runtimes

    Watch this if: you run long-lived agent sandboxes on Kubernetes and need ways to patch them without losing the agent's files and session state.

    1. 3:32 Zhang Zhen says that in their production environment about 99% of sandboxes are hibernated at any time, so an upgrade has to reach paused sandboxes as well as running ones.
    2. 10:11 He describes probe-based idle detection, where a node daemon repeatedly runs a command inside the sandbox to check for an active session before an upgrade is allowed.
    3. 13:37 He says that on an overlay filesystem you cannot both swap the image and keep the writable layer for free, because mixing old and new files gives unpredictable results.
    4. 17:31 He presents a checkpoint and restore strategy that takes a filesystem-only snapshot, recreates the pod with non-image changes such as environment variables or mounts, and restores the writable layer.
    5. 21:14 He introduces a sandbox service that he compares to a Service plus Deployment for sandboxes, with a stable endpoint, a gateway mapping session IDs to sandboxes, and rollouts that drain old sandboxes.

    Just Keep Swimming: Benchmarking OSS Agent Memory on Kubernetes with OpenTelemetry

    Henrik Rexed

    Henrik Rexed describes benchmarking five open source agent memory servers (Mem0, MemOS, MemPalace, Zep and his own MemKeys) behind kagent agents on Kubernetes, with OpenTelemetry metrics he says he contributed to most of them. He reports results for an SRE troubleshooting scenario and a multi-agent coding scenario, and says which approach suited each in his tests.

    30 min slot · Advanced · Session

    AI agents and automationObservability and reliability

    Watch this if: you are choosing a memory backend for agents on Kubernetes and want to see how one benchmark compared token use, resource use and recall.

    1. 4:06 The speaker walks through the memory architectures he compares: plain embeddings, vector plus graph, knowledge graph, temporal knowledge graph, and a key-based store.
    2. 12:37 The speaker says he built one generic MCP server in front of all the memory backends so the kagent agent setup stays the same across runs.
    3. 13:36 The speaker explains the SRE scenario: a cold run with empty memory, then a warm run with memory populated, measuring the difference across injected Kubernetes and Gateway API failures.
    4. 19:56 The speaker reports that in the SRE scenario MemOS, Zep and MemPalace gained from memory on the warm run, while Mem0 and MemKeys did worse, which he puts down to retrieving wrong or too many facts.
    5. 22:36 The speaker concludes that embedding or text search suited the SRE case in his tests, while a key store helped the coding crew that already works with project metadata.

    Running Secure Agents at Scale

    Carlos Sanchez

    Carlos Sanchez describes how Adobe runs browser workloads for AI agents without running those browsers in the agent pods. He compares Kubernetes sandboxing options and walks through how Adobe uses Agent Sandbox to allocate, reuse, and retire remote Playwright environments.

    30 min slot · Advanced · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You run AI agents on Kubernetes and want to isolate remote browsers without changing how clients use Playwright.

    1. 3:50 Sanchez describes how single-writer persistent volumes can make rollouts interrupt an agent session while a replacement Kubernetes pod waits for the old one.
    2. 9:27 Sanchez names the sandboxing options he evaluated for Playwright, including Agent Sandbox, OpenShell, and Agent Substrate.
    3. 13:08 Sanchez shows the application design: the agent sends Playwright traffic to a proxy that decides whether to reuse or allocate a browser sandbox.
    4. 16:16 Sanchez explains how the controller uses a template, a warm pool, and a claim to give a caller a sandbox.
    5. 24:20 Sanchez describes keeping three Chromium and Playwright instances warm to reduce the wait when an agent requests a browser.
