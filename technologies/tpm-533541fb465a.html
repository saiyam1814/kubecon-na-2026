    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

    Legacy-Free, Zero-Maintenance Bare Metal Kubernetes Clusters With RISC-V and Immutable Linux

    Felicitas Pojtinger

    Felicitas Pojtinger of LiveKit argues that operators should be able to own every layer of their stack, and builds one on a SpacemiT K3 RISC-V board from open firmware up to a K3s cluster. Recorded demos show an AI agent flashing and debugging the board through a hardware harness, signed image updates with systemd-sysupdate, TPM-backed remote attestation and an attested process migration between nodes.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimes

    Watch this if: you want to see how far a fully open bare-metal stack on RISC-V can go, from firmware and signed images to attestation and a running cluster.

    1. 1:45 Pojtinger says x86 and Arm carry expensive licences and firmware blobs that cannot be inspected or replaced, which is her reason for building on RISC-V.
    2. 12:31 A recorded demo shows solenoids pressing the board's buttons to enter flash mode while an MCP server flashes the images, so an agent can then check the result over KVM, UART and JTAG.
    3. 18:48 She explains choosing systemd-sysupdate over bootc, with signed system and configuration extensions overlaid on an immutable /usr.
    4. 22:35 She describes measuring every boot stage into TPM platform configuration registers so the booted image can be compared with predicted values.
    5. 28:12 In a recorded demo she enables a signed K3s system extension on the board and runs Valkey, then shows the system refusing a tampered extension.
