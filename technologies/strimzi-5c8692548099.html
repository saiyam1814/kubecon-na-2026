    Life After Strimzi 1.0.0

    Jakub Scholz

    Strimzi maintainer Jakub Scholz describes what the project has worked on since its 1.0 release, mainly security features and changes in the surrounding Kafka ecosystem. He also outlines planned work such as gatekeeper plugins, an MCP server, automatic rebalancing and a start on the path to CNCF graduation.

    30 min slot · Level not listed · Session

    Data, storage and stateDelivery, GitOps and release safety

    Watch this if: you run Kafka on Kubernetes with Strimzi and want to know what changed after 1.0 and what the maintainers plan next.

    1. 2:16 Scholz says cert-manager integration is in Strimzi 1.3 as early access, and notes it needs a private CA because certificates must carry internal Kubernetes DNS names.
    2. 6:49 He says internal cluster encryption can now be turned off, with service account tokens added as an alternative to mTLS so that authorization still works.
    3. 10:07 He says Strimzi 1.4 moves to Java 25 so that clients which support it use the ML-KEM post-quantum key exchange by default, and that a later release is meant to enable only TLS 1.3 by default.
    4. 16:31 He recounts how a long gap in Kafka Exporter releases led Strimzi to write its own replacement, and says both will be supported in parallel.
    5. 19:51 He introduces gatekeeper plugins, hooks called before and after reconciliation that he says can enforce or enrich custom resources, inspired by admission controllers, Kyverno and Open Policy Agent.

    The Seams Are the Trap: Agent Fleets from CNCF Parts You Already Have

    Aleksander Slominski, Mariusz Sabath

    The presenters describe assembling an event-driven agent fleet from Kubernetes, KEDA, Kafka, and signed CloudEvents instead of buying an agent platform. They explain the limits of tying identity to a pod and show a recorded demo in which a worker rejects an unsigned event.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to reuse a Kafka and Kubernetes stack for agent workers and verify who sent their tasks.

    1. 3:09 The speaker describes using CloudEvents as a standard envelope so producers do not have to invent their own event types, identifiers, and payload structure.
    2. 4:29 The speaker says KEDA uses Kafka lag to decide when to bring up workers and can scale them back to zero when no events remain.
    3. 10:11 The speaker explains that the runner checks a signed event's origin and whether the agent may consume it, while Kafka preserves the event sequence for audit.
    4. 11:04 The speaker says SPIFFE and SPIRE can identify a workload, but asks how that identity should change when an agent loads new skills or plugins.
    5. 23:36 The speaker shows the recorded audit check and an agent rejecting an unsigned event that was sent directly to Kafka.
