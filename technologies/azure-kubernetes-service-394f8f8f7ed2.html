    Achieving Cross-Cloud Portability with the Kubernetes Resource Orchestrator

    Michael McCune, Daniel Bruno, Sitesh Pattanaik, Bridget Kromhout, Jesse Butler

    In this SIG Cloud Provider session, the chairs explain why the SIG took in kro as a subproject, and Jesse Butler lays out the problem of ordering, reconciling and exposing cloud resources as platform APIs. Daniel Bruno and Sitesh Pattanaik then walk through an example generative AI service API built as a ResourceGraphDefinition and show recorded demos of it deployed to GKE, AKS and EKS clusters.

    30 min slot · Level not listed · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you build a platform across more than one cloud and want to see what a single kro-defined API looks like from both the platform team's and the product team's side.

    1. 2:41 Bridget Kromhout says Amazon, Google, Microsoft and others wanted a consistent way to work with resources, and recalls Jesse Butler suggesting they skip 18 months of each doing it their own way.
    2. 10:01 Jesse Butler describes kro as a vendor-neutral composition layer over any resource in the cluster, naming Crossplane, ACK, KCC, ASO or controllers you built yourself.
    3. 15:19 Daniel Bruno shows what the product team writes: nine lines of YAML naming the instance, the model, the replica count and whether monitoring is on, deployed to clusters on several clouds.
    4. 17:01 Daniel Bruno shows the platform team's side: a ResourceGraphDefinition with CEL expressions for defaults and includeWhen conditions, written without Go controllers, with cloud-specific details read from ConfigMaps.
    5. 27:41 Sitesh Pattanaik explains custom status conditions written in CEL, such as a model cache bound condition, and later says kro emits a duration metric for how long a condition has held.

    Agentic AI, Assembled in the Open

    Jorge Palma

    Jorge Palma asks how teams can reproduce an agent's work after its compute goes away and define what runs inside it. He introduces a durable session journal and a portable agent definition, then walks through a scenario where an agent pauses for human approval and resumes later.

    5 min slot · Level not listed · Keynote

    AI agents and automationCommunity and open source adoption

    Watch this if: you want to understand what an agent platform needs for reproducible work, human approvals, and auditing.

    1. 0:37 Palma frames two problems: preserving an agent's work after compute is released and defining what runs inside the agent.
    2. 1:47 Palma explains how recording completions in a hash-linked, append-only journal lets a session be replayed or forked without making the same model calls again.
    3. 3:03 Palma introduces a portable, versioned JSON definition for an agent's instructions, tool providers, build information, and evaluation cases.
    4. 4:14 Palma describes a remediation workflow that waits for human approval and releases idle compute while the session waits.
    5. 4:49 Palma walks through how a suspended session resumes for a change-ticket request and how an auditor could replay or verify the record later.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.

    GPU Observability with eBPF: From Kernel Hooks to Kubernetes Metrics

    Qasim Sarfraz, Michael Friese

    Inspektor Gadget maintainers Qasim Sarfraz and Michael Friese of Microsoft show how eBPF probes on CUDA libraries can report GPU memory allocations per pod and trace them back to application code without changing the application. They demo allocation profiles and a Grafana dashboard for a vLLM workload, then explain how gadgets are packaged as OCI images and installed with one Helm chart.

    30 min slot · Advanced · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: you run GPU inference on Kubernetes and want per-pod GPU memory metrics and allocation profiles without changing application code.

    1. 2:13 Sarfraz explains attaching uprobes and uretprobes to CUDA allocation and free functions and recording each call in BPF maps, which the framework enriches with pod and namespace and exposes to Prometheus.
    2. 5:45 In a demo he reads an allocation profile for a vLLM workload and uses it to raise the GPU memory utilization setting, which he says yields about 3 GB more allocation.
    3. 9:51 He says device state such as memory held and utilization comes from NVIDIA's NVML library, not from eBPF probes, and is joined with the eBPF data per workload.
    4. 12:36 Friese describes a gadget as an OCI image holding eBPF programs, optional WebAssembly modules, metadata YAML and BTF information, with signatures verified by default.
    5. 16:36 He lists four official GPU gadgets covering allocation activity, allocation call stacks, per-GPU state and per-pod state, and says profiles can go to Pyroscope or any OpenTelemetry endpoint.

    Kubernetes Secrets Were a Bad Idea. Now What?

    Maxime Coquerel

    Maxime Coquerel argues, as his own opinion, that Kubernetes Secrets are risky because they are only base64 encoded in etcd, readable with broad RBAC permissions and have no lifecycle. He recommends encrypting etcd with a customer managed key, keeping secrets out of Git and mounting secrets from a real vault at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    5 min slot · Beginner · Lightning Talk

    Security, identity and policy

    Watch this if: you are deciding whether Kubernetes Secrets are good enough for your platform or which alternative to use.

    1. 0:43 Maxime Coquerel says a Kubernetes Secret is stored in etcd only base64 encoded, not encrypted, and that etcd is a key value store, not a vault.
    2. 1:46 He lists the weaknesses he sees, including that anyone with get, list or watch permissions can read secret contents.
    3. 2:05 He adds that Kubernetes Secrets have no lifecycle: no expiration date and no automatic renewal.
    4. 2:47 His first recommendation is to encrypt etcd with a customer managed key, which he says managed services such as Azure Kubernetes Service support.
    5. 3:49 He compares Sealed Secrets, SOPS and External Secrets Operator, and recommends mounting secrets as files at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    LTS, EOL, CVEs: Solutions for Stress-Inducing Scenarios

    Bridget Kromhout, Lachlan Evenson

    Bridget Kromhout and Lachlan Evenson of Microsoft discuss three pressures of running open source in production: long-term support for Kubernetes, projects reaching end of life, and the rising rate of vulnerabilities. They argue for upgrading regularly, looking for migration paths when a project ends, proposing changes upstream instead of carrying private forks, and judging patches by whether a flaw is exploitable in context.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyCommunity and open source adoption

    Watch this if: you run Kubernetes platforms and need arguments for regular upgrades, handling end-of-life projects and a sane approach to CVE patching.

    1. 7:51 The speakers say the long-term support discussion showed that users objected less to change than to breaking changes in every Kubernetes release, which led to work on better upgrades.
    2. 10:28 Evenson says their provider platform will start upgrades on behalf of customers, and Kromhout adds that this begins next summer.
    3. 13:12 Evenson says ingress-nginx had asked for maintainers for several years before its end of life, and points to Gateway API and other ingress controllers as paths forward.
    4. 17:08 Kromhout calls forking a trap, accepts a soft fork meant for upstreaming, and the speakers describe an etcd change whose authors became upstream maintainers.
    5. 20:54 Evenson calls chasing zero CVEs a trap as vulnerability rates rise, and points to VEX and OpenVEX for stating whether a flaw is exploitable in a given context.

    Managing Network Security in Multi-Tenant Environments with Istio and Cilium

    Michael Bolot, Zaira Shaikh

    Michael Bolot and Zaira Shaikh of GEICO describe replacing a mix of cloud firewalls, on-premises firewalls and in-cluster policies with one API that configures Istio and Cilium across clusters on a flat, routable pod IP space. They explain how SPIRE identities and Istio authorization policies decide which applications may talk, while a small set of Cilium policies blocks what bypasses the sidecar, and they close with tips for writing Cilium policies safely.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you run Cilium and Istio together and want to hear how one platform team splits network policy duties between them.

    1. 1:44 Bolot lists the problems with the legacy setup: no unified definition of the policy affecting a device, manual configuration, inconsistent enforcement and a complex network topology.
    2. 7:03 Shaikh describes the new system: pods are restricted by Istio resources and network policies written by a data plane agent on every workload cluster, configured from a central API server, with Cilium's BGP features advertising all pod IPs.
    3. 15:03 Bolot says SPIRE handles authentication by issuing workloads a certificate after attestation, and Istio authorization policies state what a given SPIFFE ID may reach, with service entries and workload entries connecting clusters.
    4. 19:55 Bolot gives three reasons they do not use Cilium for everything: they want authorization based on SPIFFE IDs, user-chosen labels would exhaust Cilium's identity map, and Cilium's layer 7 Envoy would duplicate the one Istio already runs.
    5. 25:29 Shaikh shares tips for Cilium policies, including using audit mode and Hubble, minding the default enforcement mode, and never cutting the operator or etcd off from the API server.

    One Recipe, Five Clouds, One Query: Portable GPU Configuration with a Queryable Audit Layer

    Christopher Haar, Yuan Chen

    The speakers present AI Cluster Runtime (AICR), an open source project that turns layered recipes into validated GPU runtime bundles for different clouds, accelerators and workloads. They show commands for querying a configuration, diffing snapshots, checking upgrades and publishing signed evidence reports.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: You bring up GPU clusters on more than one cloud and want reproducible configuration that you can query and audit without touching a live cluster.

    1. 1:45 The speaker says a GB300 training cluster on EKS needs about 300 parameters set correctly across more than 16 components.
    2. 3:29 The speaker walks through the workflow: snapshot the cluster, generate a recipe, build bundles, deploy with a deployer of your choice, then validate.
    3. 9:08 In the recorded demo, the speaker reports throughput above 30,000 tokens per second and a time to first token of about 160 milliseconds.
    4. 12:44 The speaker explains the query command, which merges recipes and overlays into one values file and selects fields such as the GPU driver version across EKS, GKE and AKS.
    5. 18:15 The speaker runs query, snapshot, diff and upgrade check in a short demo, and says diff exits with code two so a CI pipeline fails on drift.
