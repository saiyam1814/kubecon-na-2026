    Beyond Stateless vs Stateful: A Unified Workload API for Multi-Cluster Kubernetes

    Ronak Nathani

    Ronak Nathani describes how LinkedIn built a composable, multi-cluster workload API that treats the pod template, update strategy, persistence and placement as separate concerns instead of splitting workloads into stateless and stateful. He walks through the hub-and-spoke design, a demo of moving and coordinating workloads, and says the team plans to open source it.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesData, storage and state

    Watch this if: you design workload APIs for a platform that spans many clusters.

    1. 0:25 Ronak says LinkedIn's fleet has half a million machines, more than 3,000 applications and about 5 million containers, with over 100,000 deployments a week.
    2. 3:41 He introduces three objects: an immutable revision, a workload with replica count, revision distribution and update strategy, and a workload placement that admins control.
    3. 5:30 He says LinkedIn runs one generic controller for all stateful workloads and asks each team to write a coordinator that must approve every change before the workload acts.
    4. 11:15 He says pod disruption budgets stop working across clusters, so they use workload disruption budgets with an eviction webhook in each spoke that checks the hub.
    5. 17:43 Asked about existing projects, he says they looked at Open Cluster Management and Karmada but wanted rollouts, disruptions and availability respected globally rather than per cluster.

    Many Clusters, One GPU Pool: Locality-Aware Scheduling and Data Delivery With Kueue and Dragonfly

    Yiqing Wang, Adam Buran

    Yiqing Wang and Adam Buran describe how Roblox shares GPU capacity across clusters using Kueue while leaving each cluster to check its own capacity. They explain how a locality-aware dispatcher chooses clusters and how Dragonfly caches training data and checkpoints near the jobs that use them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingData, storage and state

    Watch this if: You operate GPU clusters in more than one location and want to share capacity without repeatedly pulling the same datasets across regions.

    1. 6:55 The speakers describe two levels of MultiKueue admission: the hub checks team quota, then the candidate clusters check node capacity and the first to admit the job runs it with KubeRay.
    2. 8:15 The speakers explain how the dispatcher first filters for requirements such as GPU type and full-job fit, then prefers the data region for a limited time before considering other regions.
    3. 9:19 The speakers explain how Roblox separates pool-wide guaranteed quota from cluster-level borrowing and uses preemption to reclaim borrowed GPUs when a guaranteed job arrives.
    4. 14:51 The speakers describe Dragonfly looking for file pieces in the local cache, other peers, and seed peers before falling back to Amazon S3.
    5. 15:55 The speakers report that half of the data served came from node-local cache and another 43 percent from peers in the same cluster, leaving 7 percent served from Amazon S3.

    Multi-Cluster Orchestration System: Karmada Updates and Use Cases

    Michas Szacillo

    Michas Szacillo, a Karmada maintainer at Bloomberg, introduces Karmada as a management system for many Kubernetes clusters across on-premises and cloud environments. He goes over its features and history, and announces that Karmada became a CNCF graduated project on September 3rd.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesPlatform engineering and developer experienceCommunity and open source adoption

    Watch this if: you run workloads across many Kubernetes clusters and want a short introduction to Karmada and where the project stands.

    1. 0:59 Michas Szacillo describes Karmada, short for Kubernetes Armada, as a CNCF project that manages Kubernetes clusters on premises and across different cloud providers.
    2. 1:48 He says users get one unified endpoint to deploy workloads to, and Karmada takes care of scheduling them across clusters.
    3. 2:07 He says the Karmada API server is modeled on the Kubernetes API server so existing kubectl workflows fit, and its scheduler places workloads on clusters the way the Kubernetes scheduler places pods on nodes.
    4. 2:53 He describes cross-cluster failover, where cluster health is tracked and applications are moved from one cluster to another, as a way to raise a platform's resiliency.
    5. 3:48 He announces that Karmada is officially a graduated project as of September 3rd, and thanks the people who helped with the adopter interviews.

    Multi-Cluster Orchestration System: Karmada Updates and Use Cases

    Joe Nathan Abellard, Hongcai Ren

    Joe Nathan Abellard of Bloomberg, a Karmada maintainer presenting alone because Hongcai Ren could not attend, explains how Karmada propagates workloads across clusters and which recent features target AI workloads. He then describes the managed multi-cluster platform Bloomberg built on Karmada, including its observability and scale-testing setup and a fan-out scheduler he says cut propagation latency, and closes with the 2026 roadmap.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster platform and want to see how one company operates Karmada as a managed service and tunes its scheduler under load.

    1. 3:39 Abellard walks through the propagation pipeline: a propagation policy matches a workload, the resource detector creates a resource binding, the scheduler assigns clusters, and work objects are applied to each member cluster.
    2. 6:44 He lists recent features aimed at AI workloads: multi-component scheduling for workloads such as Ray jobs, priority-based scheduling, federated resource quotas, and overflow cluster affinities that use on-prem GPUs before cloud ones.
    3. 11:22 He describes Bloomberg's high-availability topology, where each Karmada control plane is stretched across host clusters in several data centers so the managed service can survive the loss of a whole data center.
    4. 18:43 For scale tests he says they simulate 50 member clusters of 1,000 nodes each with KWOK, with one real node per cluster, and drive load with ClusterLoader2 while a sidecar measures end-to-end propagation latency.
    5. 26:12 He explains the fan-out scheduler built for duplicated placements, which only checks feasibility and so can run many workers; he reports P99 propagation latency under 1 second at 50 objects per second, against about 3 minutes 45 seconds at 20 with the default scheduler.

    N Clusters, One kubectl: Multi-Cluster That Just Works

    Anne Lau, Scott Brimhall

    The speakers describe how Salesforce spread workloads across clusters with Open Cluster Management and built a routing proxy so that developers keep using one kubeconfig and standard kubectl. They explain how the proxy fans out reads, sends writes to the hub's ManifestWorkReplicaSet, and routes logs and exec to the right cluster, followed by a recorded demo.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: You run workloads across several clusters and want developers to keep their single-cluster kubectl workflow.

    1. 2:25 The speaker says they chose Open Cluster Management and its ManifestWorkReplicaSet to run the same workloads in several clusters and load balance between them.
    2. 6:38 The speaker introduces what Salesforce calls Workload API, a routing proxy that passes Kubernetes API calls to the right cluster and stores no credentials on the server side.
    3. 8:02 The speaker explains reads: a list fans out to all managed clusters and aggregates the results with their origin, and a get treats the ManifestWorkReplicaSet spec as the source of truth.
    4. 10:56 The speaker explains how they guard against stale overwrites by using the parent ManifestWorkReplicaSet's resource version for concurrency control.
    5. 14:16 The recorded demo starts, showing get, scale, rollout restart, logs and exec through one gateway with standard kubectl.

    Welcome to Health Check Hell: CRDs, Statuses and Missing Standards

    Regina Voloshin, Dag Bjerre Andersen

    Regina Voloshin and Dag Bjerre Andersen describe how custom resources report status in different ways, so tools such as Argo CD, Flux, kro and Crossplane each have to be taught what healthy means. They show how Argo CD health checks are contributed as Lua scripts, present a prototype that reports health in three dimensions, and lay out options for moving health checks into a shared standard.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you write or rely on health checks for custom resources in GitOps tools and want to see where a common standard could come from.

    1. 6:03 The speaker explains that Argo CD has six health statuses and uses contributed Lua scripts to map each custom resource's status fields onto them.
    2. 11:37 The speaker says kro has no built-in health checks and Crossplane's cover only part of the ecosystem, so each tool has to be taught again what healthy means.
    3. 13:54 The speaker introduces kstatus, a Go library that reports a resource's reconciliation state, and says that among graduated and incubating CNCF projects only Flux and Helm seem to have adopted it.
    4. 18:05 The speaker argues that a single health value hides availability, and shows a prototype library he calls Kube Health that splits health into three dimensions.
    5. 23:17 The speaker walks through options for a shared approach: a common library, a Kubernetes aggregated API, health inside the custom resource status, or a Lua script in a CRD annotation.

    Zero-Ops Disaster Recovery: A Paved Path Through Multi-Cluster Orchestration

    Joe Nathan Abellard, Li Zhuyu

    Joe Nathan Abellard and Li Zhuyu describe how Bloomberg runs Karmada as a managed, highly available multi-cluster orchestration layer across data centers. They cover the operator, observability, scale testing with KWOK and ClusterLoader2, and the scheduler changes they made for large fan-out workloads.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster Kubernetes platform and want a detailed Karmada case study covering HA, observability and scheduler tuning.

    1. 2:11 The speakers say data center redundancy is a Bloomberg-wide mandate and that they chose Karmada, which has a standard kube API server, its own scheduler and placement driven by propagation policies.
    2. 8:06 They describe a managed Karmada operator they built that gives each tenant its own namespace and control planes, sets up ingress and registers member clusters automatically from a cluster inventory API.
    3. 10:14 They walk through an HA topology where every control plane runs on host clusters in several data centers, sharing a DNS endpoint and an etcd cluster spread over three data centers, and go through which failures it survives.
    4. 19:48 For scale tests they say they use KWOK so only one of each cluster's 1,000 nodes is real, drive load with ClusterLoader2 and measure end-to-end propagation latency with a sidecar controller.
    5. 29:43 They report that a separate fan-out scheduler for duplicated workloads cut P99 propagation latency from over three minutes at 20 objects per second to under one second at 50 objects per second in their tests.
