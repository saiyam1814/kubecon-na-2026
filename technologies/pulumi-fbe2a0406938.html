    I Built an AI Running Coach: A Personal kagent Agent in Production

    Adam Gordon Bell

    Adam Gordon Bell of Pulumi tells how he built a personal AI running coach that messages him in Slack, first as a Lambda function and then as a single long-running kagent session on a small Kubernetes cluster, to train for a trail race against a friend. He describes the design choices he says worked for him, shows his own training graphs from the year, and encourages the audience to build small agents for their own needs.

    30 min slot · Any Level · Session

    AI agents and automation

    Watch this if: you want a small, concrete example of a long-running personal agent on Kubernetes, told as a story with the design choices that kept it simple.

    1. 9:15 Bell describes his first version: an AWS Lambda called by a Strava webhook, a scraper for his Peloton treadmill data, a morning cron job, DynamoDB for storage and one LLM call that posted to Slack.
    2. 12:22 He shows the kagent version, an agent defined as one Kubernetes resource deployed with Pulumi, where the Strava hook, the Peloton sync and a morning cron all post messages into the running session over the agent-to-agent protocol.
    3. 13:54 His main lesson is to use deterministic code wherever possible: the MCP tool parses raw run data and hands the agent only the date, duration, incline and heart rate zones.
    4. 15:25 He keeps one session going indefinitely and handles memory with a custom compaction rule under fixed headings, plus tools that let the agent write to a plan file and an athlete file.
    5. 27:47 He reports finishing the 30K race in 4:30 against his friend's 4:41 from the previous year, after a year in which he says his weeks with three or more runs almost doubled.

    So You Want to Build a Platform? You Probably Already Have One

    Juho Syrjänen

    Juho Syrjänen argues that teams with infrastructure-as-code modules, Helm charts and CI/CD pipelines already have a platform, and that the next step is to wrap that code behind a platform API instead of rebuilding it. He describes how module version drift and agent-generated pull requests strain the module-per-repository model, and shows an approach using Kratix where a short custom resource triggers the existing code.

    30 min slot · Any Level · Session

    Platform engineering and developer experience

    Watch this if: you maintain Terraform or OpenTofu modules and Helm charts and want a way to turn them into a self-service platform without a rewrite.

    1. 3:11 The speaker describes the tempting plan of rebuilding everything with Crossplane, kro, Backstage and Kratix over a couple of years, and the pushback he says that proposal gets.
    2. 5:29 The speaker says the engineering behind existing infrastructure as code is solid and asks why it should not be reused.
    3. 11:54 The speaker proposes packaging the module and its wiring into one platform capability, which he describes as a single deterministic unit, with user configuration cut to about a dozen lines of YAML.
    4. 17:56 The speaker walks through delivery: the platform writes rendered output to a Git repository, Flux syncs it into destination clusters, and in-cluster operators apply it to the cloud provider.
    5. 19:19 The speaker says users and agents can then act on the platform without extra pull request approvals because a human already approved the platform code, then names Kratix and Crossplane as tools that help.

    Why Are You Still Wasting Whole GPUs? Hardware-Level Sharing, Scheduled with DRA

    Engin Diri

    Engin Diri of Pulumi recounts helping a European customer build a self-hosted inference platform, moving from whole GPUs and time slicing to NVIDIA MIG slices that pods request through Dynamic Resource Allocation. He shows a recorded demo of MIG profiles, resource slices and claims on an AWS node serving a model behind an inference gateway, and lists open questions such as quotas, models larger than a node and start-up ordering.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: you run inference on your own GPUs and want a practical walk through MIG slices requested with Dynamic Resource Allocation.

    1. 8:32 Diri says time slicing gives no memory or fault isolation between workloads, so the choice was between wasting GPUs and risking a noisy neighbor.
    2. 11:24 Diri says Dynamic Resource Allocation, which he dates to Kubernetes 1.34, lets a request describe device attributes instead of an integer count.
    3. 22:16 In the recorded demo, Diri lists the 1G, 2G and 4G MIG profiles on the node and the resource slices the DRA driver published.
    4. 24:28 Diri lists open day-two questions he is evaluating with the customer, including Kueue for MIG quota and which workload runs first.
    5. 28:06 Diri advises starting the DRA driver only after MIG is configured, because he ran into race conditions between the two.
