    Code, Containers, and Clusters: The Next Chapter of Apple's Container Framework

    Kathryn Baldauf, Vince Prignano

    Kathryn Baldauf and Vince Prignano of Apple walk through Apple container, which runs each Linux container in its own lightweight VM on a Mac, plus container machines for persistent Linux dev environments. They announce container cluster for local multi-node Kubernetes clusters and demo building a controller and deploying it to a three-node cluster with Cilium.

    10 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    Watch this if: you develop for Kubernetes on a Mac and want a local multi-node cluster that uses your locally built images without pushing them.

    1. 1:12 Vince Prignano says Apple bootstraps every cluster declaratively with Kubernetes Cluster API and ships a signed, continuously enforced bill of materials, and asks what it would take to bring that same bill of materials to the MacBook.
    2. 1:59 Kathryn Baldauf says Apple container, written in Swift for Apple silicon, runs each Linux container in its own lightweight VM, shares only the files you choose, and boots in under a second.
    3. 2:48 She introduces container machines: persistent Linux environments built from OCI images that share your Mac user and home folder, which she pitches as a good place for agent sessions.
    4. 4:06 She announces container cluster, which creates a real Kubernetes cluster bootstrapped by kubeadm, with each node as its own VM and a default CNI or one you bring.
    5. 6:53 Demo: Vince builds a controller image, creates a three-worker cluster with Cilium and the shared local image store, deploys with kubectl, then fixes a blocked app with a Cilium network policy.

    Green Dashboards, Broken Clusters: Taming Stale Watches in Kubernetes Operators

    Michael Aspinwall, Alvaro Aleman

    Michael Aspinwall and Alvaro Aleman explain how a controller that reads from a lagging informer cache can miss its own writes, using a DaemonSet controller case in which duplicate pods were created on every node. They describe the upstream Kubernetes work on comparable resource versions, informer staleness metrics and a consistency store in client-go, and the different approach controller-runtime takes with a client that waits for the cache to catch up.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you write or operate Kubernetes controllers and want to know how stale informer caches cause duplicate or wrong actions, and what client-go and controller-runtime now offer to avoid them.

    1. 3:47 Aspinwall walks through the case study: the DaemonSet controller's write expectations expire after about five minutes, so when the pod informer lags longer than that, the controller sees no pod in its stale cache and creates another one on the same node.
    2. 5:53 He says KEP-5504 extends to clients the guarantee that resource versions can be compared, so a controller can tell from the version returned by its write whether its cache has caught up.
    3. 6:21 He describes a new metric on every informer store in client-go that can be subtracted from the API server's watch cache resource version, and shows a scale-test graph in which one API server falls up to 350,000 resource versions behind.
    4. 7:17 He explains the consistency store, which records the resource version of each write and returns an error at the start of the next reconcile until the store has synced past it, and says it is already in the DaemonSet, Job, StatefulSet and ReplicaSet controllers.
    5. 18:27 Aleman describes controller-runtime's consistent client as two layers: reads that start after a write block until the write finishes, and then wait until the cache has reached the resource version that write returned.

    SIG API Machinery in the Era of AI: Updates

    Joe Betz

    Joe Betz reviews a year of work in Kubernetes SIG API Machinery, from contributor trends to API server performance, resilience and controller improvements. He covers the storage version migrator, internal type and protobuf cleanups, declarative validation with its linter, manifest-based admission policies and client library updates, then outlines what comes next.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: you build Kubernetes APIs, CRDs or controllers and want to know what changed in the API machinery underneath them.

    1. 1:38 Betz says PRs to the SIG rose about 50% this year, which he links to AI-assisted development, while reviewer capacity stayed roughly flat.
    2. 7:21 Betz says the storage version migrator has finally landed, so CRD authors can migrate stored objects and eventually retire conversion webhooks.
    3. 12:14 Betz explains that making internal types match the preferred serving version lets the Go compiler skip needless copies during conversion.
    4. 14:45 Betz shows declarative validation, where tags on API types generate validation code, plus a linter that catches mistakes such as a field marked both required and optional.
    5. 17:10 Betz describes a tool to detect backward-incompatible CRD changes and manifest-based admission policies loaded at API server startup that users cannot bypass or modify.

    SIG-Multicluster Intro and Deep Dive

    Laura Lorenz, Stephen Kitt

    Laura Lorenz and Stephen Kitt give an overview of SIG Multicluster and its APIs, from ClusterProfile and the About API to the Work API, placement decisions, the MCS API and multicluster-runtime. They cover recent cluster inventory and MCS API work, share findings from the SIG's multicluster user research, and explain how to get involved.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesNetworking and connectivity

    Watch this if: you manage many Kubernetes clusters and want to know which SIG Multicluster APIs exist and where they are heading.

    1. 0:52 Stephen Kitt lists reasons teams run several clusters, such as environment isolation, multi-tenancy, multicloud redundancy, data locality and capacity.
    2. 3:21 Kitt walks through the SIG's projects: ClusterProfile, the About API, the Work API, the placement decision API, the MCS API and multicluster-runtime.
    3. 5:53 Laura Lorenz explains cluster inventory credential plugins, a modular way for a hub cluster to look up credentials for spoke clusters.
    4. 10:11 Lorenz says the KEP was updated so the ClusterProfile kind must be namespace-scoped, driven by duplicate cluster names and clients that watch only a subset of clusters.
    5. 20:00 Lorenz shares insights from 12 user interviews, where deployment validation, recovery and troubleshooting across clusters were described as still largely manual.

    The Next Era of Kubernetes Operator Lifecycle Management

    Attila Mészáros, Rashmi Gottipati, Jordan Keister, Joe Lanford

    The Operator Framework maintainers open with this year's Java Operator SDK features and then describe how OLM v1 reduces installation to a single ClusterExtension resource. They outline work in flight on phased rollouts, deployment configuration, migration from OLM v0 and direct bundle installs, and plans for Helm chart support and a new catalog format.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: you ship or install operators with OLM and want to know what OLM v1 changes and how to move from v0.

    1. 1:28 Attila Mészáros introduces read-cache-after-write consistency in Java Operator SDK, an overlay cache on top of informers that he says became possible after Kubernetes guidance allowed comparing resource versions.
    2. 13:38 Rashmi Gottipati presents ClusterExtension as the single user-facing API with declarative version pinning, which she says matches the package manager behavior users asked for instead of v0 subscriptions.
    3. 15:54 She walks through dropping the dedicated install service account and RBAC, saying access is now controlled on the ClusterExtension itself with Kubernetes RBAC and validating admission policies.
    4. 18:52 Jordan Keister describes phase gates that expose where an installation stands, implemented with a new ClusterObjectDeployment API that he says is not tied to operators.
    5. 22:34 Joe Lanford outlines planned Helm chart support through direct bundle install, with templating that rejects non-deterministic actions and no hooks at first.
