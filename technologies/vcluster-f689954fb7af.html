    If It's Shared, It's Vulnerable: Is Kubernetes the Right Platform for Confidential Compute?

    Zvonko Kaiser

    The speaker argues that attestation proves a confidential workload's state but not who shares the node, silicon and Kubernetes control plane beneath it. He walks through published attacks on shared layers and concludes that confidential workloads need one node and one control plane per tenant.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: You run or plan confidential workloads on shared Kubernetes clusters and want to know what attestation does and does not cover.

    1. 3:35 The speaker says attestation proves a workload runs on a specific node in a specific cluster, but not who else shares that node.
    2. 5:32 The speaker describes two substrates shared by every tenant on a node, the Kubernetes control plane and the silicon, and says he counted 39 named attacks on these layers since 2023.
    3. 6:34 The speaker describes an attack he calls TDXRay, in which he says one VM reconstructed another VM's prompt from shared cache metadata without breaking encryption.
    4. 9:54 The speaker says one tenant per node still shares etcd, CNI and CSI, and that Kubernetes was never built to protect tenants from each other.
    5. 13:52 The speaker sums up his position as one node, one control plane, one tenant, with the workload owner owning the whole stack.

    Making Environments Repeatable: From Tools to Platform Capabilities

    Saiyam Pathak

    Saiyam explains the hidden setup, configuration, and readiness work behind requests for repeatable environments, and presents vCluster Stacks as a way to encode that work once. He argues that readiness should mean a validated user outcome, illustrated by GPU scheduling and a CUDA smoke test, rather than merely running components.

    5 min slot · Any Level · Keynote

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you are turning repeated environment provisioning steps into reusable platform capabilities.

    1. 0:13 Saiyam says the simple request for an environment hides installation, service trust, configuration handoff, and readiness work that platform teams must complete first.
    2. 0:53 Saiyam argues that repeatedly glue-fixing environments team by team eventually loses track of tools, versions, and ownership.
    3. 1:48 Saiyam says reusable environment automation has to encode ordered setup steps, pass one step's output into the next step, and prove readiness from the developer's perspective.
    4. 3:09 Saiyam uses a CUDA GPU stack to argue that readiness requires scheduler visibility of the GPU and a successful smoke-test job, not only healthy operator components.
    5. 4:21 Saiyam closes by asking platform teams what belongs in a reusable stack, what proves an environment ready, and which repeated requests the platform should handle for users.

    Managing Network Security in Multi-Tenant Environments with Istio and Cilium

    Michael Bolot, Zaira Shaikh

    Michael Bolot and Zaira Shaikh of GEICO describe replacing a mix of cloud firewalls, on-premises firewalls and in-cluster policies with one API that configures Istio and Cilium across clusters on a flat, routable pod IP space. They explain how SPIRE identities and Istio authorization policies decide which applications may talk, while a small set of Cilium policies blocks what bypasses the sidecar, and they close with tips for writing Cilium policies safely.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you run Cilium and Istio together and want to hear how one platform team splits network policy duties between them.

    1. 1:44 Bolot lists the problems with the legacy setup: no unified definition of the policy affecting a device, manual configuration, inconsistent enforcement and a complex network topology.
    2. 7:03 Shaikh describes the new system: pods are restricted by Istio resources and network policies written by a data plane agent on every workload cluster, configured from a central API server, with Cilium's BGP features advertising all pod IPs.
    3. 15:03 Bolot says SPIRE handles authentication by issuing workloads a certificate after attestation, and Istio authorization policies state what a given SPIFFE ID may reach, with service entries and workload entries connecting clusters.
    4. 19:55 Bolot gives three reasons they do not use Cilium for everything: they want authorization based on SPIFFE IDs, user-chosen labels would exhaust Cilium's identity map, and Cilium's layer 7 Envoy would duplicate the one Istio already runs.
    5. 25:29 Shaikh shares tips for Cilium policies, including using audit mode and Hubble, minding the default enforcement mode, and never cutting the operator or etcd off from the API server.
