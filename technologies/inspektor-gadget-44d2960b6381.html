    GPU Observability with eBPF: From Kernel Hooks to Kubernetes Metrics

    Qasim Sarfraz, Michael Friese

    Inspektor Gadget maintainers Qasim Sarfraz and Michael Friese of Microsoft show how eBPF probes on CUDA libraries can report GPU memory allocations per pod and trace them back to application code without changing the application. They demo allocation profiles and a Grafana dashboard for a vLLM workload, then explain how gadgets are packaged as OCI images and installed with one Helm chart.

    30 min slot · Advanced · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: you run GPU inference on Kubernetes and want per-pod GPU memory metrics and allocation profiles without changing application code.

    1. 2:13 Sarfraz explains attaching uprobes and uretprobes to CUDA allocation and free functions and recording each call in BPF maps, which the framework enriches with pod and namespace and exposes to Prometheus.
    2. 5:45 In a demo he reads an allocation profile for a vLLM workload and uses it to raise the GPU memory utilization setting, which he says yields about 3 GB more allocation.
    3. 9:51 He says device state such as memory held and utilization comes from NVIDIA's NVML library, not from eBPF probes, and is joined with the eBPF data per workload.
    4. 12:36 Friese describes a gadget as an OCI image holding eBPF programs, optional WebAssembly modules, metadata YAML and BTF information, with signatures verified by default.
    5. 16:36 He lists four official GPU gadgets covering allocation activity, allocation call stacks, per-GPU state and per-pod state, and says profiles can go to Pyroscope or any OpenTelemetry endpoint.
