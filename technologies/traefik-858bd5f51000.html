    Will Your Gateway Leave You High and Dry?

    John Howard, Mitch Connors

    John Howard and Mitch Connors walk through version 3 of Howard's Gateway API Bench, which tests agentgateway, Envoy Gateway, Istio, kgateway, NGINX Gateway Fabric and Traefik on route updates, a 5,000 route scale test, route propagation time and rolling restarts. Framed around a fictional cardboard box startup, they report which implementations returned errors or used more CPU and memory in their runs, and Howard states up front that both speakers work on several of the gateways tested.

    30 min slot · Any Level · Session

    Networking and connectivityObservability and reliability

    Watch this if: you are choosing a Gateway API implementation, perhaps while moving off ingress-nginx, and want to see how six of them behaved under route churn and scale.

    1. 4:20 Howard says the two speakers are biased because they work on many of the gateways tested, and that the report is reproducible with shared data.
    2. 8:22 Howard reports that four implementations returned all 200s while a route was updated, while Envoy Gateway and NGINX had brief periods of downtime in his test.
    3. 13:59 In the 5,000 route test, Howard says the NGINX data plane used about three cores of CPU while serving no traffic.
    4. 16:40 Howard attributes the resource gap between Envoy based gateways to metrics defaults, saying Envoy Gateway and kgateway exposed 350,000 metrics out of the box.
    5. 21:11 Howard says no implementation failed during continuous backend pod restarts, while NGINX and Traefik had errors when the gateway itself was rolled out.
