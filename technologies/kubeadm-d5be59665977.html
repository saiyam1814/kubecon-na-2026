    Cluster API in 15 Minutes. A Primer on Declarative Kubernetes Cluster Management

    William Rizzo

    William Rizzo introduces Cluster API as the idea of representing a cluster as Kubernetes objects inside a management cluster, and walks through its core, infrastructure, bootstrap and control plane providers. He explains how machines map to nodes, in what order a cluster comes up, and how to try it locally with clusterctl and the Docker provider, then takes audience questions.

    12 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: You manage more than a few clusters by hand and want the Cluster API object model explained before you try the quick start.

    1. 0:30 The speaker states the idea behind Cluster API: a cluster becomes a set of Kubernetes objects inside a management cluster.
    2. 0:54 He describes the controllers: the core, an infrastructure provider for where machines run, a bootstrap provider for machine configuration, and a control plane provider for etcd and the API server.
    3. 3:27 He compares a MachineDeployment to a workload Deployment, with a MachineSet in the place of a ReplicaSet and a Machine in the place of a Pod.
    4. 4:43 He says cluster creation follows a sequence in which one control plane node must be built first, because otherwise etcd cannot form its Raft consensus.
    5. 9:39 Asked about self-hosted infrastructure, he says clusterctl uses kubeadm by default but that other control plane and bootstrap providers can be chosen at init.

    Code, Containers, and Clusters: The Next Chapter of Apple's Container Framework

    Kathryn Baldauf, Vince Prignano

    Kathryn Baldauf and Vince Prignano of Apple walk through Apple container, which runs each Linux container in its own lightweight VM on a Mac, plus container machines for persistent Linux dev environments. They announce container cluster for local multi-node Kubernetes clusters and demo building a controller and deploying it to a three-node cluster with Cilium.

    10 min slot · Level not listed · Keynote

    Kubernetes internals and runtimes

    Watch this if: you develop for Kubernetes on a Mac and want a local multi-node cluster that uses your locally built images without pushing them.

    1. 1:12 Vince Prignano says Apple bootstraps every cluster declaratively with Kubernetes Cluster API and ships a signed, continuously enforced bill of materials, and asks what it would take to bring that same bill of materials to the MacBook.
    2. 1:59 Kathryn Baldauf says Apple container, written in Swift for Apple silicon, runs each Linux container in its own lightweight VM, shares only the files you choose, and boots in under a second.
    3. 2:48 She introduces container machines: persistent Linux environments built from OCI images that share your Mac user and home folder, which she pitches as a good place for agent sessions.
    4. 4:06 She announces container cluster, which creates a real Kubernetes cluster bootstrapped by kubeadm, with each node as its own VM and a default CNI or one you bring.
    5. 6:53 Demo: Vince builds a controller image, creates a three-worker cluster with Cilium and the shared local image store, deploys with kubectl, then fixes a blocked app with a Cilium network policy.

    Follow the GPUs: How a Regulated Fortune 100 Serves Customers When No Single Cloud Has Enough

    Yuva Peavler, Michael Kinsley

    Yuva Peavler and Michael Kinsley of GEICO describe their hybrid cloud platform, a flat network across providers with a zero trust overlay built on SPIFFE/SPIRE, Istio and Cilium, and say it lets them move workloads to wherever GPUs are available. Michael then shares a tool they wrote to probe GPU availability across AWS and Azure regions, what four weeks of samples showed them, and their idea for a booking agent that reserves capacity ahead of demand.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you need GPUs without long reservations and want measured data on whether multi-region and multi-cloud help.

    1. 1:45 Michael gives the takeaways first: current single-GPU SKUs need multi-region support, flagship eight-GPU nodes have to be booked ahead, and he says the autoscaler will not do the booking.
    2. 3:43 Yuva explains the platform from the bottom up: one flat L3 network across every provider, identically built Kubernetes clusters, then SPIFFE/SPIRE identity, Istio mutual TLS and Cilium deny-by-default policy.
    3. 8:54 Yuva says they made SPIRE's data store pluggable in their fork and run Cassandra behind it for an active-active multi-region control plane, and that they have proposed this upstream.
    4. 16:54 Michael introduces their Follow the GPUs tool, which asks for GPUs, doubles the request after each yes until it gets a no, then waits about an hour and starts again.
    5. 22:02 Michael reports that in their data multi-region did not matter for small single-GPU SKUs but raised the chance of getting an RTX Pro 6000 from about 45% to 70 to 75%.

    From Disk to Defense: Kubernetes Admission Policies the API Can't Touch

    Anish Ramasekar, Benjamin Elder

    The speakers present manifest-based admission control, which loads admission webhooks and policies from files on the API server's disk so that they cannot be deleted through the Kubernetes API. They replay a made-up outage in a recorded demo and describe the feature's limits, reload behavior and release status.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: You operate Kubernetes control planes for other teams or customers and want guardrails that a cluster admin cannot delete.

    1. 2:37 The speakers say a policy stored as an API object can be deleted like any other object, and that the API does not allow a policy that intercepts policies.
    2. 7:24 The speakers explain that policies are loaded from a directory on disk before the API server serves anything, the same idea as static pods.
    3. 8:55 The speakers say the feature gate was alpha in Kubernetes 1.36 and is beta and on by default in 1.37.
    4. 13:49 The speakers list the limits: no param refs, no service references, no service account tokens, and nothing that depends on the API.
    5. 16:46 The recorded demo starts on a kind cluster running Kubernetes 1.37, where the Helm upgrade, the webhook and the prune are denied.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.

    What’s New in Kairos, 2026 Edition

    William Rizzo

    William Rizzo, a Kairos maintainer, runs through the past year's releases: Kairos 4.4.0 in a monorepo, the Hadron Linux distribution, the Kairos operator, kubeadm support in the Kubernetes provider, and AuroraBoot. He also describes Cluster API providers for Kairos, which he says let Kamaji hosted control planes use Kairos-managed worker nodes.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run Kairos or immutable Linux at the edge and want a quick list of what changed over the past year.

    1. 0:52 William Rizzo says Kairos is now at version 4.4.0 and has moved to a monorepo with one version and one pipeline that builds everything.
    2. 1:29 He describes Hadron Linux as an immutable, minimal distribution built on musl and systemd, and says the work focused on hardening trusted boot, FIPS compliant images and gating releases on vulnerability scans.
    3. 2:40 He says the Kairos operator is a Kubernetes native way to handle day two operations such as draining, cordoning and upgrading nodes, and that it replaces their use of the system upgrade controller.
    4. 3:10 He says version 4.0 of the Kubernetes provider now supports kubeadm in addition to K3s and k0s.
    5. 4:26 He describes the Kairos Cluster API bootstrap and control plane provider, and says kubeadm worker node support means Kamaji hosted control planes can have Kairos-managed workers.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
