    Cloud Native without Limits: Powering the AI Era in the Open

    Chris Aniszczyk, Jonathan Bryce, Rita Zhang, Kevin Cochrane, Robert Nishihara, Justin Boitano, Bassam Tabbara

    The opening speakers say that agents are driving inference demand and describe how cloud providers are contributing fixes from production back to open source. The session includes announcements about KubeRay and OpenShell and a ModelPlane demo that moves an inference deployment between clouds.

    Length not listed · Level not listed · Type not listed

    AI inference and servingCommunity and open source adoption

    Watch this if: you want the opening announcements on AI infrastructure, with examples spanning Kubernetes inference, agent controls, and multi-cloud model serving.

    1. 5:00 Bryce cites OpenRouter and other providers as examples of an increase in inference traffic, saying he has seen it grow fourfold in eight months.
    2. 16:27 Zhang says CoreWeave feeds lessons from production back upstream, citing fair GPU scheduling in Kueue and hardening work in vLLM, NVIDIA Dynamo, and Grove.
    3. 31:53 Nishihara announces that KubeRay is joining CNCF and explains that Ray handles distributed coordination inside a Kubernetes workload, such as a reinforcement learning pipeline.
    4. 36:18 In a prerecorded segment, Boitano argues that infrastructure, not the agent itself, must enforce access boundaries, and says OpenShell has joined the CNCF Sandbox.
    5. 40:46 Tabbara demos ModelPlane, showing how it can serve the same model through one endpoint and move replicas between clouds when GPU capacity changes.

    Frameworkless ML Serving: Scaling to Thousands of Models with KEDA, Pub/Sub, and Native K8s

    Robin Deaconu, Neb Jovanovic

    The presenters explain why multi-minute drug-discovery jobs led their team away from a general-purpose inference framework. They describe how stateless workers, durable queues, and native Kubernetes scheduling serve interactive and batch requests on the same fleet.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: interactive inference and long-running batch jobs need to share the same pool of accelerators.

    1. 6:01 The presenters explain why multi-minute accelerator jobs made durable requests and backlog-based scaling more useful to them than in-flight concurrency.
    2. 9:12 They describe how a stateless worker backed by an asynchronous queue became the core building block of the new platform.
    3. 16:29 They explain how KEDA wakes a deployment from zero replicas and passes queue signals to the Horizontal Pod Autoscaler for further scaling.
    4. 18:46 They walk through high-priority requests preempting batch workers and describe how queue leases let interrupted work become available again.
    5. 27:52 They describe dual-writing to Redis and Bigtable to verify parity before cutting over with a configuration flag they could flip back.

    Many Clusters, One GPU Pool: Locality-Aware Scheduling and Data Delivery With Kueue and Dragonfly

    Yiqing Wang, Adam Buran

    Yiqing Wang and Adam Buran describe how Roblox shares GPU capacity across clusters using Kueue while leaving each cluster to check its own capacity. They explain how a locality-aware dispatcher chooses clusters and how Dragonfly caches training data and checkpoints near the jobs that use them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingData, storage and state

    Watch this if: You operate GPU clusters in more than one location and want to share capacity without repeatedly pulling the same datasets across regions.

    1. 6:55 The speakers describe two levels of MultiKueue admission: the hub checks team quota, then the candidate clusters check node capacity and the first to admit the job runs it with KubeRay.
    2. 8:15 The speakers explain how the dispatcher first filters for requirements such as GPU type and full-job fit, then prefers the data region for a limited time before considering other regions.
    3. 9:19 The speakers explain how Roblox separates pool-wide guaranteed quota from cluster-level borrowing and uses preemption to reclaim borrowed GPUs when a guaranteed job arrives.
    4. 14:51 The speakers describe Dragonfly looking for file pieces in the local cache, other peers, and seed peers before falling back to Amazon S3.
    5. 15:55 The speakers report that half of the data served came from node-local cache and another 43 percent from peers in the same cluster, leaving 7 percent served from Amazon S3.

    Ship Faster, Ship Safer: A K8s-Native Canary Pipeline for Critical Cluster Services

    Youmin Han, Zhuo Zhi

    Youmin Han and Zhuo Zhi describe why traffic splitting did not give LinkedIn the coverage it needed for cluster infrastructure releases. They show how the team combined namespace-scoped canaries, synthetic workloads, and Argo CD validation gates before promoting changes to production.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safety

    Watch this if: You need to validate critical Kubernetes components that cannot be canaried by shifting a percentage of user traffic.

    1. 9:39 The speakers say random traffic sampling missed GPU and job combinations and could not safely stage changes such as a shared database migration.
    2. 10:28 The speakers explain how dedicated canary instances run in the production cluster while a separate namespace directs only synthetic workloads to the new versions.
    3. 17:36 The speakers show how the Kubernetes API server matches a namespace label against webhook selectors so each pod goes through the canary or the stable admission webhook, not both.
    4. 21:30 The speakers describe using Argo CD PostSync hooks to run functional validation jobs once the canary resources are synced and healthy.
    5. 23:34 The speakers describe running the full GPU and CPU validation suites in canaries before the pipeline promotes changes to production clusters one at a time.

    The Scheduling Stack: Real-World Lessons from Anthropic, Anyscale, Google, and CERN

    Wojciech Tyczyński, Ricardo Rocha, Kaslin Fields, Decheng Dai, Jui-An Huang

    The panelists compare what upstream Kubernetes scheduling can handle with where their teams still specialize. They describe how placement, queueing, cluster boundaries, and resource fragmentation affect distributed workloads.

    30 min slot · Any Level · Panel

    Accelerators and workload scheduling

    Watch this if: you are deciding which scheduling concerns belong in Kubernetes and which belong in a higher-level workload scheduler.

    1. 5:42 Fields introduces KubeRay as the controller for running Ray on Kubernetes.
    2. 10:30 A panelist distinguishes workload placement from deciding what should run now or wait in a queue.
    3. 13:46 Rocha recalls splitting CERN clusters because the scheduler could not launch the volume of workloads CERN wanted, rather than because of node count.
    4. 20:01 A panelist explains why they try to keep a tightly coupled workload within one cluster instead of exposing it to failures across several clusters.
    5. 25:14 A panelist describes a background job that scans for fragmentation and moves workloads when it finds a better placement.
