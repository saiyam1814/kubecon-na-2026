    Beyond Model Serving: Running Production LLMs on Kubernetes with KServe

    Johnu George, Jooho Lee

    The two KServe maintainers explain how the project added an LLMInferenceService API that builds on llm-d, vLLM and the Gateway API Inference Extension rather than a new inference engine. They then go through production patterns they say KServe addresses: cache-aware routing, streaming timeouts, split prefill and decode, multi-node serving, autoscaling signals, cold starts, model updates and LoRA adapters.

    30 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload schedulingNetworking and connectivity

    Watch this if: you serve LLMs on Kubernetes and want the KServe maintainers' checklist of routing, scaling and cold-start issues to plan for.

    1. 4:07 Jooho Lee describes the LLMInferenceService API, in which he says a workload controller manages single-node, multi-node and separate prefill deployments while a route controller manages the scheduler and Gateway API resources.
    2. 8:44 Jooho follows a request from the gateway to the endpoint picker, which he says can weigh prefix cache match, queue depth and KV cache usage instead of treating every healthy replica as equal.
    3. 12:47 Johnu George warns that with streaming, timeouts at each hop must exceed generation time, because he says client retries otherwise pile more load on the GPUs.
    4. 16:15 Johnu argues that GPU utilization is a misleading autoscaling signal for LLMs and says the number of requests waiting in the inference runtime's queue is a better one.
    5. 17:30 Johnu describes cold-start work with a local model cache and container snapshot and restore, and says they are seeing startup drop from minutes to a few seconds.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.

    Multi-Cluster Orchestration System: Karmada Updates and Use Cases

    Joe Nathan Abellard, Hongcai Ren

    Joe Nathan Abellard of Bloomberg, a Karmada maintainer presenting alone because Hongcai Ren could not attend, explains how Karmada propagates workloads across clusters and which recent features target AI workloads. He then describes the managed multi-cluster platform Bloomberg built on Karmada, including its observability and scale-testing setup and a fan-out scheduler he says cut propagation latency, and closes with the 2026 roadmap.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster platform and want to see how one company operates Karmada as a managed service and tunes its scheduler under load.

    1. 3:39 Abellard walks through the propagation pipeline: a propagation policy matches a workload, the resource detector creates a resource binding, the scheduler assigns clusters, and work objects are applied to each member cluster.
    2. 6:44 He lists recent features aimed at AI workloads: multi-component scheduling for workloads such as Ray jobs, priority-based scheduling, federated resource quotas, and overflow cluster affinities that use on-prem GPUs before cloud ones.
    3. 11:22 He describes Bloomberg's high-availability topology, where each Karmada control plane is stretched across host clusters in several data centers so the managed service can survive the loss of a whole data center.
    4. 18:43 For scale tests he says they simulate 50 member clusters of 1,000 nodes each with KWOK, with one real node per cluster, and drive load with ClusterLoader2 while a sidecar measures end-to-end propagation latency.
    5. 26:12 He explains the fan-out scheduler built for duplicated placements, which only checks feasibility and so can run many workers; he reports P99 propagation latency under 1 second at 50 objects per second, against about 3 minutes 45 seconds at 20 with the default scheduler.

    Volcano for the Agentic AI Era: Unified Scheduling Across Training, Inference, and Agents

    Ricardo Aravena, Rainie Li

    Rainie Li explains how Volcano aims to schedule training, inference and agent workloads on one Kubernetes cluster, using a batch scheduler and an agent scheduler that share nodes through a sharding controller, plus multi-level gang scheduling, network topology hypernodes and gang-aware preemption. Ricardo Aravena then covers how workload controllers such as Kthena, KubeRay and Grove map onto Volcano primitives, the project's benchmarking work and the roadmap.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingAI agents and automationAI inference and serving

    Watch this if: you schedule AI training, inference or agent workloads on shared GPU clusters and want to know what Volcano offers for gang and topology-aware placement.

    1. 3:02 Rainie Li says Volcano uses two schedulers, a batch scheduler for coordinated workloads and an agent scheduler for latency-sensitive pods, with a sharding controller assigning candidate nodes to each and moving them as demand changes.
    2. 6:49 She introduces multi-level gang scheduling, in which a pod group contains subgroups with their own completeness requirements, such as a tensor-parallel group or a prefill or decode replica.
    3. 9:56 She explains gang-aware preemption, which treats victims as groups and simulates placement first, so no pod is evicted if the whole incoming gang cannot fit.
    4. 15:12 Ricardo Aravena says KubeRay support is merged upstream and listed for Volcano 1.16, and walks through how its head and worker groups translate into Volcano subgroups.
    5. 18:35 He describes the scheduling benchmark framework shipped with Volcano 1.15, which reports scheduling latency and binding throughput on kind, KWOK or an existing cluster, and notes it says nothing about GPU job speed.

    When Training Dies at 3 AM: Correlating Kubernetes Events with AI-Framework Failures

    Wenjia Zhang, Yuchen Zhou

    Wenjia Zhang and Yuchen Zhou of Google, standing in for the work's main contributor Richa Banker, explain why a hardware fault under a distributed training job is hard to trace back from Kubernetes events hours later. They describe the pipeline they say is merged upstream in Ray and KubeRay, which joins events to pods and parent jobs while the pod still exists, shows them in a Platform Events tab in the Ray dashboard and exports them with Ray's own events.

    30 min slot · Any Level · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: ML engineers on your platform ask whether their code or the infrastructure killed a training job and you cannot answer from Kubernetes events the next morning.

    1. 3:39 Zhang walks through a 512-GPU training run where a GPU fault at 3:14 a.m. becomes, seven seconds later, a Python exception reported by Ray as an application failure, and by 9 a.m. kubectl get events shows nothing.
    2. 8:52 She names three obstacles: events expire after a one-hour TTL, or five minutes in a large cluster with heavy churn, they carry no labels or owner references, and the pod needed for the join may already be garbage collected.
    3. 15:43 Zhou describes two watches in the Ray head: one keeps an in-memory list of the cluster's live pods by label, the other checks namespace pod events against that list, with events kept in a fixed buffer of 1,000 keyed by event UID.
    4. 17:19 He says platform events are wrapped in the standard Ray event format and exported asynchronously to a log file or HTTP endpoint, so they stay searchable in a logging backend after the cluster and the Kubernetes events are gone.
    5. 20:59 He explains that node events land in the default or kube-system namespace where a Ray head cannot see them, so the KubeRay operator watches node warnings and re-emits one event per affected RayCluster into the team's namespace.
