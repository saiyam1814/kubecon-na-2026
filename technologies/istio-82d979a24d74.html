    AI Gateways in Practice: Model Routing, Inference Scheduling, and MCP on Kubernetes

    Yuke Ning

    Yuke Ning walks through how Higress handles hosted model routing, traffic to self-hosted inference, and requests from agents to tools. He discusses where fallback stops working, how an endpoint picker participates in routing, and how the gateway bridges MCP transports.

    30 min slot · Level not listed · Session

    AI inference and servingNetworking and connectivity

    Watch this if: you run a gateway that must handle hosted models, your own inference workloads, and MCP tools.

    1. 5:11 Ning shows a Higress route configured to try a backup model provider after selected error responses.
    2. 7:47 He points out that status-based fallback cannot redirect a response once a successful stream has already started.
    3. 9:56 He walks through the Gateway API Inference Extension ownership model, in which application teams own routes and serving teams own the inference pools those routes target.
    4. 18:10 He contrasts rejecting the request if an external endpoint picker fails with allowing the gateway to choose an endpoint another way.
    5. 22:26 He describes three MCP roles for the gateway: exposing REST APIs as tools, proxying existing MCP servers, and bridging differences between clients and servers.

    Beyond End User: CAP and the Evolution of Open Source at CVS Health

    Michael Amundson, Jim Beyers

    Jim Beyers and Michael Amundson of CVS Health present CAP, the internal application platform they say lets a new hire ship to production on day one by hiding Kubernetes, Istio, DNS and certificates behind one app model. They demo creating and deploying an app, explain how CAP spreads services across clusters, and announce their first open source projects, Flag Controller and the CAP Registry API.

    5 min slot · Level not listed · Keynote

    Community and open source adoption

    Watch this if: you build an internal developer platform and want to see one that hides Kubernetes, Istio and DNS behind a single app model.

    1. 0:25 Jim Beyers says the CVS Health DevEx team built CAP, the CAP Application Platform, in about 10 months, and that it now serves hundreds of engineers and tens of thousands of deployments a month.
    2. 0:58 He says their feature flagging platform, built with OpenFeature, handles hundreds of millions of flag evaluations a day, and that CVS Health has joined CNCF as a platinum member.
    3. 1:45 Michael Amundson gives the question CAP is measured against, whether a new hire can ship to production on their first morning, and its tenets: no prerequisites, an abstract app model, and governance built into the platform.
    4. 3:08 Demo: a new app gets a Docusaurus quick start service, CAP creates the repo and CI pipeline, then deploys it to a cluster with a DNS name and TLS certificate in a couple of minutes.
    5. 5:30 CVS Health announces its first open source DevEx projects, the Flag Controller feature flagging product and the CAP Registry API, and says it plans to open source CAP fully next year.

    Every Kubernetes Object Deserves an Identity: The SPIFFE Broker API

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.

    “Allowed but Unsupported”: When Platform Support Boundaries Meet Enterprise Reality

    Niranjan Shankar

    Niranjan Shankar describes how the Azure Kubernetes Service team opened limited escape hatches for enterprise customers and what happened when support ownership was unclear. He uses packet loss at the boundary between a self-managed network plugin and a managed service mesh to show why teams need to name who owns the risk.

    25 min slot · Any Level · Session

    Platform engineering and developer experienceSecurity, identity and policy

    Watch this if: You need to give advanced platform users more control without leaving production support ownership ambiguous.

    1. 4:38 Shankar introduces the 'Allowed but Unsupported' tier and uses Istio to show how a team can allow a few EnvoyFilter uses, support routine MeshConfig fields, and block higher-risk settings.
    2. 11:39 He uses packet loss with a self-managed CNI and a provider-managed service mesh to explain why the boundary between supported and unsupported parts is hard to diagnose during an incident.
    3. 13:12 He recalls customers having trouble migrating from self-managed Prometheus to the managed offering because it did not support a rule resource they used.
    4. 20:35 He recommends giving unsupported features a signpost: a way to get best-effort help, an internal owner for production risk, and a path back to a supported option.
    5. 23:08 He closes with criteria for deciding what to expose, including whether teams can isolate the security risk, find an owner, or offer a narrower subset instead of the entire API.
