    Hannah Olukoye, Mofesola Babalola

    An engineering manager and an engineer describe how they would run AI inference traffic through Istio ambient mesh while keeping GPU spend and security under control. They say an endpoint picker that knows which backend holds a cached prompt beats plain load balancing from the second turn onward, and they report a bug they hit when combining it with ambient mTLS.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You plan to put LLM inference behind Istio ambient mesh and care about cache-aware routing and per-team token tracking.

    1. 0:52 Hannah Olukoye says load balancing that treats every request alike regardless of token count is a core problem for inference traffic.
    2. 1:25 She compares a per-pod Envoy sidecar at about 135 megabytes of memory with ztunnel in ambient mode, which she says stays at about seven megabytes for the whole node.
    3. 4:52 Mofesola Babalola says AI repeats the old layer 7 load-balancing problem, because routing should account for which pod holds the context, GPU capacity and KV cache state.

    5. 6:39 He says the endpoint picker expects a pod IP and port but received a mesh address under ambient mTLS and fell back to round robin, so he opened pull requests to Envoy and Istio.

    Breaking the O(n²) Wall: Pub/Sub Federation for Istio Multicluster Service Discovery

    Jack Ma, Zhewei Hu

    Two engineers from the Azure Kubernetes Service team describe replacing Istio's cross-cluster API server watches with a shared pub/sub broker for ambient multicluster service discovery. They present scale tests up to 100 clusters in which they say propagation latency stayed similar while istiod memory use dropped sharply.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You run or plan an Istio ambient mesh across many clusters and worry about remote secrets and istiod memory.

    1. 3:23 Jack Ma says 100 clusters need 10,000 remote watches under the current model, and that each istiod also carries memory overhead for the other clusters.
    2. 5:19 Zhewei Hu presents the alternative, in which each istiod talks only to its own API server, publishes global services and network gateways to a shared pub/sub broker, and subscribes to the others.
    3. 6:58 He describes scale tests at 10, 30, 60 and 100 clusters, each with 100 global services, and says median service creation and deletion latency showed no clear difference between the two approaches.
    4. 10:43 He says that at 100 clusters istiod used under 1 gigabyte of memory with pub/sub federation against almost 2.5 gigabytes with remote watches.
    5. 18:37 Answering a question about dropped messages, Jack Ma says the design sends incremental changes plus a full snapshot of global services every minute.

    Istio at Scale: Lessons, Pitfalls, and Observability

    Adarsh Kumar

    The speaker recounts debugging recurring CPU spikes in Istio sidecars that kept pushing autoscalers to their maximum without any rise in traffic. He says the cause was configuration pushes triggered by churn in an unrelated namespace, and that limiting what each sidecar can see removed the spikes and lowered sidecar memory use.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You run Istio sidecars at scale and see unexplained proxy CPU spikes or heavy configuration pushes.

    1. 2:45 The speaker says the problem began with alerts that Horizontal Pod Autoscalers had hit their maximum even though traffic had not grown.
    2. 3:14 He says the sidecar containers showed a repeating spiky CPU pattern, and telemetry showed a large number of xDS pushes with no obvious cause.
    3. 4:32 He inspects what a proxy knows with istioctl proxy-config on a recreated Bookinfo setup and finds a noisy worker from another namespace in the cluster list.
    4. 5:23 He explains that background workers on spot VMs were preempted often, so new pod IPs kept triggering endpoint pushes to every sidecar.
    5. 6:36 He applies a Sidecar resource that limits visibility to the same namespace and shows the unrelated clusters gone, which he says ended the CPU spikes and cut sidecar memory.

    ServiceEntry Visibility: Tomorrow's ServiceEntry, Today

    Ian Rudie

    An Istio networking and ztunnel maintainer introduces ServiceEntry visibility, a setting that lets mesh administrators decide which namespaces may publish a ServiceEntry mesh-wide. He says existing scoping tools are opt-in and do not suit the ambient data plane, and that the new feature makes self-service and multi-tenancy safer.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You let teams create their own ServiceEntry resources in a multi-tenant Istio mesh, especially with ambient.

    1. 0:22 The speaker says ServiceEntry is useful but has a global effect on service discovery, which makes self-service a problem.
    2. 0:39 He says exportTo and the Sidecar resource have been used to limit discoverability, but they are opt-in and need trust or an external validating webhook.
    3. 1:30 He says ztunnel is a node proxy with compact config, so supporting exportTo there would grow the config and slow service matching, which a prototype confirmed.
    4. 3:13 He explains that ServiceEntry visibility adds no new resource and gives a ServiceEntry either cluster-wide or namespace-only visibility, set by the mesh administrator at install or upgrade time.
    5. 4:19 He says the only matcher today is on namespace, and asks the audience which other matchers would be useful.

    Niranjan Shankar

    Niranjan Shankar describes how the Azure Kubernetes Service team opened limited escape hatches for enterprise customers and what happened when support ownership was unclear. He uses packet loss at the boundary between a self-managed network plugin and a managed service mesh to show why teams need to name who owns the risk.

    25 min slot · Any Level · Session

    Platform engineering and developer experienceSecurity, identity and policy

    Watch this if: You need to give advanced platform users more control without leaving production support ownership ambiguous.

    1. 4:38 Shankar introduces the 'Allowed but Unsupported' tier and uses Istio to show how a team can allow a few EnvoyFilter uses, support routine MeshConfig fields, and block higher-risk settings.
    2. 11:39 He uses packet loss with a self-managed CNI and a provider-managed service mesh to explain why the boundary between supported and unsupported parts is hard to diagnose during an incident.
