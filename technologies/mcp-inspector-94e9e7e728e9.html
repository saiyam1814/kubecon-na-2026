    Integrating Envoy AI Gateway and Kyverno Authz for Realtime Governance of LLM and MCP Traffic

    Jim Bugwadia, Deepak Goel

    Deepak Goel explains why enterprises put Agent Router, which he says was formerly called Envoy AI Gateway, between agents and their models and MCP tools, and Jim Bugwadia shows Kyverno Authz plugging into it through Envoy's external authorization protocol. In a live demo, Kyverno allows or blocks MCP tool calls by asking the Kubernetes API whether the calling user has the matching RBAC permission.

    25 min slot · Level not listed · Session

    Security, identity and policyNetworking and connectivityAI agents and automation

    Watch this if: You route LLM and MCP traffic through an Envoy-based gateway and want tool calls authorized against the Kubernetes RBAC you already have.

    1. 2:57 Deepak Goel says that once many agents, models, users and sessions are involved, enterprises need a layer between agent and model for routing, security, observability and token cost, which is what Agent Router provides.
    2. 8:51 Jim Bugwadia explains Envoy's two plugin protocols: external authz returns allow or deny on a request, while external processing also sees the response, which he says matters because an MCP server's reply can carry a prompt injection.
    3. 10:04 He says Agent Router already has JWT authentication, MCP session management, CEL checks and quotas, but not policy as code with reporting and exception management, which Kyverno adds.
    4. 15:56 In the demo, a tool call by user Alice against another team's namespace is blocked because Kyverno ran a Kubernetes SubjectAccessReview and RBAC denied it.
    5. 18:02 After he adds a role binding for Alice, the scale call that failed earlier goes through, and he then shows the policy report Kyverno generated for the blocked calls.

    One Platform for AuthN and AuthZ: Keycloak Meets AuthZEN

    Yoshiyuki Tabata

    Yoshiyuki Tabata splits authorization into delegation and access control, explains that the OpenID AuthZEN standard defines the interface between a policy enforcement point and a policy decision point, and describes Keycloak's experimental AuthZEN support. He then demonstrates an MCP setup in which Envoy enforces decisions it requests from Keycloak, which acts as both the OAuth authorization server and the decision point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Keycloak and want to see how it can also make fine-grained authorization decisions for MCP tools through the AuthZEN API.

    1. 2:20 Tabata separates authorization into two phases: delegation, where one party grants limited authority as in OAuth, and access control, where a gatekeeper decides on each request, and says good authorization needs both.
    2. 6:36 He explains that AuthZEN standardizes the interface between the policy enforcement point and the policy decision point, so the enforcement point does not depend on a product-specific API.
    3. 10:35 He says Keycloak has experimental support for the AuthZEN Authorization API 1.0 starting with version 26.7, exposing the evaluation and evaluations APIs so it can act as a decision point.
    4. 13:55 He introduces the demo architecture: MCP Inspector as the client, Envoy in front of the MCP server as the enforcement point, and Keycloak as both OAuth authorization server and AuthZEN decision point.
    5. 25:41 In the demo he assigns a role to the user in Keycloak and the previously denied delete tool call succeeds with the same access token, which he uses to show that no separate synchronization with a decision point is needed.
