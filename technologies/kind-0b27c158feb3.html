    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    From Pod Creation to First Packet

    Surya Seetharaman

    Surya Seetharaman traces pod networking from Kubernetes creating a sandbox to sending its first packet. She uses a kind cluster to show the network namespace, CNI setup, address assignment, and packet capture.

    30 min slot · Beginner · Session

    Kubernetes internals and runtimesNetworking and connectivity

    Watch this if: You want a practical way to trace a pod startup networking failure from its sandbox to its first outbound packet.

    1. 6:26 Seetharaman describes when the runtime creates the pause container and network namespace after the kubelet receives a pod.
    2. 8:06 Seetharaman uses crictl to identify a running pod's sandbox and explains why the pause container is not listed like an application container.
    3. 13:13 Seetharaman distinguishes the loopback setup from the primary CNI plugin and identifies kindnet as the plugin used in her demo.
    4. 20:11 Seetharaman explains how kindnet uses host-local IP address management to allocate a pod address from a configured range.
    5. 24:09 Seetharaman clears the ARP cache and captures traffic during a ping to show the address resolution and packets leaving the pod.

    One Workload to Rule Them All: Workload Aware Scheduling for Distributed AI Training on Kubernetes

    Andrey Velichkevich

    Andrey Velichkevich explains why scheduling distributed training one pod at a time can deadlock jobs and how the Kubernetes Workload and PodGroup APIs model them as a unit. He shows how Kubeflow Trainer exposes those capabilities through training runtimes and compares three scheduling policies on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: You run distributed training on Kubernetes and want to understand when pod groups and topology constraints matter.

    1. 0:48 Velichkevich illustrates how two training jobs can deadlock when the scheduler gives each job some GPUs but neither gets enough to start all its ranks.
    2. 4:44 Velichkevich distinguishes the Workload template from runtime PodGroups and shows how a PodGroup can express a minimum pod count and topology constraints.
    3. 7:10 Velichkevich introduces composite PodGroups for workloads with a hierarchy, where a parent can require a minimum number of child groups before scheduling proceeds.
    4. 10:12 Velichkevich explains the Kubeflow Trainer split: platform admins define runtime blueprints, and scientists use a Python SDK to submit jobs without managing Kubernetes deployment details.
    5. 15:17 In a local kind demo, Velichkevich sets up a comparison of default pod-by-pod placement, gang scheduling, and rack-constrained placement for a PyTorch job.

    Platform-First AI Agent Security: Zero-Trust Patterns for Kubernetes

    Carlos Santana

    Carlos Santana argues that a Kubernetes platform should treat agent-generated code as untrusted and provision isolation, credentials, and network policy separately. He describes using kro to compose those controls behind a platform API and shows captures of an Agent Sandbox warm pool assigning a ready pod.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to give teams a Kubernetes API for agents without giving those agents unrestricted access.

    1. 5:25 Santana describes SPIFFE and SPIRE as a way to identify an agent by URI and associate that identity with a credential across different environments.
    2. 12:14 Santana shows a kro ResourceGraphDefinition and explains how a declarative resource graph can give platform users a custom API without requiring the platform team to write a Go controller.
    3. 19:05 Santana compares gVisor, Kata Containers, and AWS Nitro Sandboxes as different isolation choices for running untrusted agent code.
    4. 21:27 Santana shows captures of a two-pod Agent Sandbox warm pool and says applying a claim assigned a ready pod instead of waiting for a fresh sandbox to start.
    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    Your CI's Mistaken Identity

    Andrew McNamara, Maia Iyer

    Andrew McNamara and Maia Iyer say a namespace and service account can tell you where a CI task runs without telling you what it should be allowed to do. They describe pairing per-task workload identities with admission-time policy and using those identities to authorize access and sign attestations.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetySecurity, identity and policy

    Watch this if: You want to avoid giving every task in a Kubernetes CI pipeline the same privileges.

    1. 4:30 The speakers explain that SPIRE can use more than namespace and service account when assigning workload identities, so CI pods in the same namespace can have different roles.
    2. 9:19 The speakers explain that a Tekton bundle's digest changes when its task definition changes, and show where Sigstore signatures and attestations can be stored.
    3. 14:14 The speakers describe using Kyverno admission policy to require extra verification before a task can get a production identity.
    4. 16:57 In the live demo, the speakers show that an unsigned task from an untrusted catalog was blocked before a pod was scheduled.
    5. 22:21 The speakers explain how task-scoped identities let a verification policy check not just for an attestation, but for the specific CI task expected to produce it.
