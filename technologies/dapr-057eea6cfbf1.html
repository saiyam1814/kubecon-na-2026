    Verifiable Execution: Durable Workflows That Cryptographically Prove What They Did

    Yaron Schneider

    Dapr co-creator Yaron Schneider reviews what is new in Dapr 1.19, including new building blocks, an MCP server and faster workflows, then introduces verifiable execution, in which each workflow step is signed and chained into an append-only history so tampering with stored state can be detected. He argues that logs and traces cannot prove what an agent or workflow did, and shows a local demo in which changing a payment amount directly in Postgres causes the workflow to be quarantined.

    30 min slot · Level not listed · Session

    Security, identity and policyObservability and reliability

    Watch this if: you run workflows or agents that take sensitive actions and need to prove afterwards that their recorded history was not altered.

    1. 0:31 Yaron Schneider lists the building blocks added in Dapr 1.19, a binary store, search and a vector database, and mentions that Dapr now has an MCP server.
    2. 2:02 He says workflow throughput is 40% better than in Dapr 1.18, and describes detached workflows that outlive their parent and access policies checked before a workflow starts.
    3. 8:44 He argues logs and traces are not enough for proof because they are plain text that can be changed, and that audit trails have to be custom built.
    4. 10:51 He explains verifiable execution: each step's inputs, outputs and caller are signed with a certificate and chained in an append-only log, and Dapr compares stored data against the chain when the workflow resumes.
    5. 17:34 Demo: he changes a pending $1,000 transfer to $9,999 with a SQL update in Postgres, resumes the workflow, and Dapr quarantines it with a history signature verification failure.

    Your Agent Needs a Platform: Cloud Native Infrastructure for Multi-Agent AI Systems

    Soham Ghadge

    Soham Ghadge describes problems he met running AI agents in production, such as crashes midway through a task, rate limits, repeated model calls and poor visibility, and maps each one to existing cloud native tools. He proposes defining agents as Kubernetes custom resources, saving each model call as a Dapr workflow step, queueing tasks through NATS JetStream and tracing with OpenTelemetry.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are building multi-agent systems and want a short overview of which cloud native tools cover crash recovery, queueing and tracing.

    1. 2:35 Ghadge lists his mapping of agent problems to tools, starting with describing each agent as a Kubernetes object through a CRD.
    2. 3:38 Ghadge shows a simplified agent definition as a Kubernetes object, with replicas, maximum tasks per copy and what the agent reads from and writes to.
    3. 7:00 Ghadge says to put every AI model call inside a saved step so that after a restart Dapr reuses the saved answer instead of paying for the call again.
    4. 7:39 Ghadge describes an agent queue, which he compares to a Redis queue, so agents do not handle every request directly.
    5. 9:48 Ghadge's conclusion is to treat an agentic system like a distributed system and agents like microservices.
