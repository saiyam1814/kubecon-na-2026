    All Things DRA in One Place: DRA Example Driver Deep Dive

    Jon Huhn

    Jon Huhn of Microsoft presents the DRA example driver, a Kubernetes-hosted driver with entirely synthetic devices that he says aims to show a runnable example of every Dynamic Resource Allocation feature. He walks through what a DRA driver does at each stage of a workload's life and runs four demos on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you want to try Dynamic Resource Allocation on a laptop or are writing a DRA driver and need a working reference.

    1. 4:38 Huhn explains binding conditions: the scheduler allocates a device, then waits for the driver to signal it is reachable from the node before binding the pod, with a stub controller in the example driver.
    2. 6:48 First demo: on a default Kubernetes 1.37 kind cluster he installs the driver's Helm chart and two pods are each allocated a different mock GPU, with no feature gates enabled.
    3. 8:57 Second demo: with the driver's webhook enabled, a ResourceClaim whose GPU config has an invalid time-slicing interval is rejected before any pod tries to start.
    4. 11:30 Last demo: he installs the driver twice, as mock GPUs and mock network devices, and a claim with a match attribute constraint gets a GPU and a NIC on the same PCIe root.
    5. 18:21 Huhn lists where the example driver is already used: the Kubernetes documentation, Cluster Autoscaler tests, the AI Conformance Program and SIG Scalability tests at up to 5,000 nodes.

    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

    When GPUs Become NUMA Nodes: Challenges Running Kubernetes with Memory-Coherent Hardware

    Kevin Klues

    Kevin Klues, presenting alone because his listed co-speaker could not attend, explains how NVIDIA systems with memory-coherent CPU and GPU links exposed GPU memory as NUMA nodes and why he says that broke the kubelet's memory accounting, pod memory limits and GPU isolation. He walks through two workarounds his team abandoned, the driver mode called CDMM that they adopted instead, and a kubelet fix that was still needed.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Kubernetes on NVIDIA GB200-class or other unified-memory hardware and want to know how GPU memory interacts with kubelet memory accounting.

    1. 7:29 Klues lists three problems with the driver's NUMA mode on Kubernetes: memory over-reporting to the kubelet, a broken pod memory limit contract, and any container being able to allocate GPU memory it was not assigned.
    2. 10:55 He describes the first attempt, hiding GPU NUMA nodes from the kubelet with reserved memory settings, and says it failed on ordering with the GPU driver and on dynamic MIG devices.
    3. 13:44 He describes a second attempt using an NRI plugin to restrict each container to the NUMA nodes of its own GPUs, which he says got complicated once GPUs were injected through CDI and DRA.
    4. 16:35 He introduces Coherent Driver-Based Memory Management (CDMM), a driver mode that he says keeps GPU memory NUMA nodes offline while retaining pointer coherency over NVLink.
    5. 18:39 He says enabling the topology manager stalled the kubelet because it iterated combinations of 34 NUMA nodes, and that a patch merged in Kubernetes 1.36 skips nodes with no memory.
