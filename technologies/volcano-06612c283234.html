    Cloud Native Infrastructure in the AI Era: A TAG Infrastructure Panel

    Xing Yang, Dylan Page, Mesut Oezdil, Alexa Griffith, Kashif Khan, Thomas Schuetz

    The co-chairs and tech leads of the CNCF TAG Infrastructure describe the group's current work, including white papers on infrastructure lifecycle, AI for science, AI inference and data storage for AI, and a new telco AI-native initiative. They then each name what they see as the biggest challenge AI workloads pose for cloud native infrastructure and take audience questions on agent sandbox projects and moving HPC sites toward cloud native tools.

    30 min slot · Level not listed · Panel

    Community and open source adoptionAccelerators and workload schedulingAI inference and serving

    Watch this if: you run or plan AI infrastructure and want to know what the CNCF TAG Infrastructure is writing about it and where you can contribute.

    1. 2:04 Dylan Page describes the infrastructure lifecycle white paper, which he says is meant to advise on managing mixed public cloud, private cloud, edge and bare metal environments, and Thomas Schuetz adds that it covers when operator-based deployment fits better than Terraform or OpenTofu.
    2. 5:13 Kashif Khan introduces the telco AI-native initiative, saying the challenge for AI-native network functions is the infrastructure beneath the model, and that the group is collecting shared definitions and gaps from operators and vendors.
    3. 10:03 Xing Yang summarizes the TAG's white paper on data storage for cloud native AI, saying training, inference and agents each have different storage patterns, so no single AI storage fits all.
    4. 11:40 Asked for the biggest challenge, Dylan Page answers that it is people, describing a collision of cloud native, telecom and HPC cultures, while other panelists name GPU utilization, placement and the speed at which infrastructure is needed.
    5. 19:00 Mesut Oezdil argues that GPUs must be sliced to be economical and that MIG and time slicing fall short in mixed-vendor environments, and points to HAMi, which he maintains, as a vendor-agnostic option.

    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    KubeRay 101

Kai-Hsun Chen then describes how his startup runs its audio model work on Ray, and the second half is audience questions on cluster sharing, reinforcement learning, MultiKueue and Grove.

    30 min slot · Level not listed · Birds of a Feather

    Accelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run Kubernetes and are new to Ray, and want to know what KubeRay's custom resources do and how one team pairs it with Kueue for training and serving.

    1. 5:42 Huang says Ray distributes actors across the resources it has but does not allocate those resources itself, and that on Kubernetes this is the job of KubeRay, an operator that manages the lifecycle of a Ray cluster.
    2. 6:12 He walks through the custom resources: RayCluster for a long-lived cluster suited to prototyping, RayJob and a cron variant that create a short-lived cluster and clean it up afterwards, and RayService for online serving.
    3. 9:32 Chen describes his company's audio model pipeline: Ray Data with CPU and GPU steps for data preparation, a Ray cluster with Kueue and MultiKueue for training and evaluation, and RayService for serving.
    4. 13:00 Huang lists recent contributions he attributes to other companies, including a history server for logs and events, a RocksDB backend for Ray's metadata store, Kubernetes RBAC for Ray token authentication, and integration with the Kubernetes workload API.
    5. 19:55 Asked about MultiKueue, Chen says he uses it with autoscaling and describes issues he ran into, such as one cluster holding hundreds of workload objects and a periodic reconnect that requeued everything, which he says were fixed upstream within days.

    Multi-Cluster Orchestration System: Karmada Updates and Use Cases

    Joe Nathan Abellard, Hongcai Ren

    Joe Nathan Abellard of Bloomberg, a Karmada maintainer presenting alone because Hongcai Ren could not attend, explains how Karmada propagates workloads across clusters and which recent features target AI workloads. He then describes the managed multi-cluster platform Bloomberg built on Karmada, including its observability and scale-testing setup and a fan-out scheduler he says cut propagation latency, and closes with the 2026 roadmap.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster platform and want to see how one company operates Karmada as a managed service and tunes its scheduler under load.

    1. 3:39 Abellard walks through the propagation pipeline: a propagation policy matches a workload, the resource detector creates a resource binding, the scheduler assigns clusters, and work objects are applied to each member cluster.
    2. 6:44 He lists recent features aimed at AI workloads: multi-component scheduling for workloads such as Ray jobs, priority-based scheduling, federated resource quotas, and overflow cluster affinities that use on-prem GPUs before cloud ones.
    3. 11:22 He describes Bloomberg's high-availability topology, where each Karmada control plane is stretched across host clusters in several data centers so the managed service can survive the loss of a whole data center.
    4. 18:43 For scale tests he says they simulate 50 member clusters of 1,000 nodes each with KWOK, with one real node per cluster, and drive load with ClusterLoader2 while a sidecar measures end-to-end propagation latency.
    5. 26:12 He explains the fan-out scheduler built for duplicated placements, which only checks feasibility and so can run many workers; he reports P99 propagation latency under 1 second at 50 objects per second, against about 3 minutes 45 seconds at 20 with the default scheduler.

    One Workload to Rule Them All: Workload Aware Scheduling for Distributed AI Training on Kubernetes

    Andrey Velichkevich

    Andrey Velichkevich explains why scheduling distributed training one pod at a time can deadlock jobs and how the Kubernetes Workload and PodGroup APIs model them as a unit. He shows how Kubeflow Trainer exposes those capabilities through training runtimes and compares three scheduling policies on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: You run distributed training on Kubernetes and want to understand when pod groups and topology constraints matter.

    1. 0:48 Velichkevich illustrates how two training jobs can deadlock when the scheduler gives each job some GPUs but neither gets enough to start all its ranks.
    2. 4:44 Velichkevich distinguishes the Workload template from runtime PodGroups and shows how a PodGroup can express a minimum pod count and topology constraints.
    3. 7:10 Velichkevich introduces composite PodGroups for workloads with a hierarchy, where a parent can require a minimum number of child groups before scheduling proceeds.
    4. 10:12 Velichkevich explains the Kubeflow Trainer split: platform admins define runtime blueprints, and scientists use a Python SDK to submit jobs without managing Kubernetes deployment details.
    5. 15:17 In a local kind demo, Velichkevich sets up a comparison of default pod-by-pod placement, gang scheduling, and rack-constrained placement for a PyTorch job.

    Optimize Your Heterogeneous AI Cluster

    Mengxuan Li

    HAMi maintainer Mengxuan Li of Dynamia.ai explains the two problems the project targets, GPUs that can only be allocated whole and multi-GPU placements that ignore how cards are connected, and how HAMi's device plugin and HAMi-core enforce per-container memory limits to share a GPU. He then covers newer features (dynamic MIG, remote GPU access from nodes without GPUs, AMD support), a HAMi variant built on Dynamic Resource Allocation that works with other schedulers, and the roadmap.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you operate GPU clusters on Kubernetes and want to share GPUs among workloads or see how HAMi fits with Dynamic Resource Allocation.

    1. 3:05 Li describes HAMi's two basic functions: GPU slicing, so a workload can be given part of a GPU, and scheduling that accounts for how GPUs on a node are connected when several are requested.
    2. 8:48 He explains dynamic MIG: the user states only the device memory needed, and HAMi finds a matching MIG template and a GPU with enough consecutive free slots, creates the instance, and recycles it when the workload ends.
    3. 11:22 He introduces remote GPU in version 2.11, where a pod on a CPU-only node reaches a GPU on another node over TCP and sees it when running nvidia-smi.
    4. 15:31 He says HAMi DRA, a webhook plus driver on top of Dynamic Resource Allocation, converts device-plugin style resource requests into resource claims automatically and adds allocation metrics, at the cost of the topology-aware scheduling of the original HAMi.
    5. 21:16 Roadmap: scheduling by rack and super pod network topology, kernel-level isolation through cgroups and MPS alongside HAMi-core, and multi-client remote GPU with per-client limits.

    Volcano for the Agentic AI Era: Unified Scheduling Across Training, Inference, and Agents

    Ricardo Aravena, Rainie Li

    Rainie Li explains how Volcano aims to schedule training, inference and agent workloads on one Kubernetes cluster, using a batch scheduler and an agent scheduler that share nodes through a sharding controller, plus multi-level gang scheduling, network topology hypernodes and gang-aware preemption. Ricardo Aravena then covers how workload controllers such as Kthena, KubeRay and Grove map onto Volcano primitives, the project's benchmarking work and the roadmap.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingAI agents and automationAI inference and serving

    Watch this if: you schedule AI training, inference or agent workloads on shared GPU clusters and want to know what Volcano offers for gang and topology-aware placement.

    1. 3:02 Rainie Li says Volcano uses two schedulers, a batch scheduler for coordinated workloads and an agent scheduler for latency-sensitive pods, with a sharding controller assigning candidate nodes to each and moving them as demand changes.
    2. 6:49 She introduces multi-level gang scheduling, in which a pod group contains subgroups with their own completeness requirements, such as a tensor-parallel group or a prefill or decode replica.
    3. 9:56 She explains gang-aware preemption, which treats victims as groups and simulates placement first, so no pod is evicted if the whole incoming gang cannot fit.
    4. 15:12 Ricardo Aravena says KubeRay support is merged upstream and listed for Volcano 1.16, and walks through how its head and worker groups translate into Volcano subgroups.
    5. 18:35 He describes the scheduling benchmark framework shipped with Volcano 1.15, which reports scheduling latency and binding throughput on kind, KWOK or an existing cluster, and notes it says nothing about GPU job speed.

    Why We Bet the Data Platform on Kubernetes - And How AI Is Changing How We Operate It

    Vara Bonthu, Damon Cortesi, Padma Aradhyula, Rainie Li, Ying Xiong

    Moderator Vara Bonthu asks panelists from Airbnb, Salesforce, Pinterest and Apple Maps why they moved Spark and other data workloads from Hadoop-style clusters to Kubernetes and what was hard about it. The panelists describe pod churn, scheduling choices among YuniKorn, Volcano and Kueue, and the AI agents and skills they say they now use for troubleshooting and upgrades.

    30 min slot · Beginner · Panel

    Data, storage and stateAI agents and automation

    Watch this if: you are weighing a move of Spark or other data workloads from Hadoop to Kubernetes and want to hear what four large operators ran into.

    1. 5:30 Damon Cortesi says Airbnb reached 100% Spark on Kubernetes a couple of weeks earlier, shut down its last Hadoop cluster, and runs about 4 million Spark jobs a week.
    2. 9:46 Padma Aradhyula says Salesforce Data Cloud runs thousands of small near-real-time Spark jobs lasting two to five minutes, and that the resulting pod churn puts heavy pressure on the API server.
    3. 11:38 Rainie Li describes Pinterest's Moka platform with Apache YuniKorn and a remote shuffle service, and reports a 10% job performance improvement and over 10% annual infrastructure savings.
    4. 14:45 Ying Xiong says the hardest start at Apple Maps was convincing people to try Kubernetes without data locality, followed by scalability issues from huge jobs and from users submitting thousands of jobs an hour.
    5. 21:46 Rainie describes a multi-agent setup where sub-agents reach platform components through MCP servers and search past incidents, and says it now helps fix over 50% of troubleshooting issues.

    Zero-Gap GPU Execution: Building Secure, Pre-Warmed Pod Runtimes for High-Velocity AI Agents

    Ankit Goyal, Cong Gu

    The LinkedIn speakers present Firepool, their control plane that hands GPU jobs from agents and reinforcement learning loops to pools of already running pods, so no pod is created on the job's critical path. They describe how pods are reset and reused per caller, how standby pods parked on busy GPUs with HAMi and Volcano take over when a job ends, and report that 19 of 20 pod requests in production are served from warm pods.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingAI agents and automationKubernetes internals and runtimes

    Watch this if: You run agent or reinforcement learning loops that need GPUs in short repeated bursts and want to cut pod cold starts without keeping GPUs idle.

    1. 5:07 Ankit Goyal says that with the image cached a new GPU pod takes 20 to 30 seconds to start, and that an agent running hundreds of GPU experiments pays that cost each time when it lives on CPU nodes.
    2. 8:48 He walks through a job submission and says there is no pod creation in the critical path: the dispatcher claims a warm pod and the Firepool agent inside it fetches the job's code and runs it.
    3. 14:24 Cong Gu describes the reuse rules: the Firepool agent kills the job's process tree and verifies the reset or deletes the pod, and an idle pod is held only for the caller that used it.
    4. 19:06 Ankit Goyal explains zero-gap: they use HAMi and Volcano only to schedule several pods onto one GPU, where one pod runs a job with the whole card and the rest are standby pods ready to take over.
    5. 22:09 He says Firepool pods run sandboxed with no egress by default, and outbound calls go through a sidecar proxy that injects credentials and checks policy, so agents never hold real credentials.
