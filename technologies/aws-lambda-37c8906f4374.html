    From Bearer Tokens to Mesh-Native mTLS: Modernizing Service Identity at Coinbase

    Zachary Schwartz, Yair Temkin

    Yair Temkin and Zachary Schwartz describe how Coinbase replaced a homegrown service-to-service auth system with SPIFFE identities issued by SPIRE and checked by an auth sidecar, and say every service is now off the legacy system. They share lessons from the migration and then outline plans to use Istio ambient mesh, with JWT validation at the ingress gateway and ztunnel mTLS, so the sidecars can eventually be removed.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you are planning a move from token-based service auth to SPIFFE identities or Istio ambient mesh and want a peer's account of the migration.

    1. 1:23 Temkin says the legacy service auth system was tightly coupled to AWS, tied to one region and JWT-only, and was retired in March 2025 when SPIRE became the paved road.
    2. 2:26 Schwartz lists why they chose SPIRE, including compatibility with services outside Kubernetes, JWT SVIDs and separate trust domains per region and environment, and reports 70% less CPU in the auth path and about 50 milliseconds less latency than the legacy system.
    3. 6:46 Schwartz says managing the migration centrally through the sidecar and a control plane, without pull requests in every service team's repository, let them move much faster, and that all services now use the SPIRE-based system.
    4. 10:42 Among the lessons, he says init containers could start before the auth sidecar and have no identity, which they solved with Kubernetes native sidecars, and that bursts of new pods overwhelmed the SPIRE agent until caching was tuned.
    5. 13:37 Temkin describes the ambient mesh plan for ingress: Envoy filters at the ingress gateway validate JWTs centrally and set a subject header, and authorization policies at the gateway and at ztunnel restrict who can call each service.

    I Built an AI Running Coach: A Personal kagent Agent in Production

    Adam Gordon Bell

    Adam Gordon Bell of Pulumi tells how he built a personal AI running coach that messages him in Slack, first as a Lambda function and then as a single long-running kagent session on a small Kubernetes cluster, to train for a trail race against a friend. He describes the design choices he says worked for him, shows his own training graphs from the year, and encourages the audience to build small agents for their own needs.

    30 min slot · Any Level · Session

    AI agents and automation

    Watch this if: you want a small, concrete example of a long-running personal agent on Kubernetes, told as a story with the design choices that kept it simple.

    1. 9:15 Bell describes his first version: an AWS Lambda called by a Strava webhook, a scraper for his Peloton treadmill data, a morning cron job, DynamoDB for storage and one LLM call that posted to Slack.
    2. 12:22 He shows the kagent version, an agent defined as one Kubernetes resource deployed with Pulumi, where the Strava hook, the Peloton sync and a morning cron all post messages into the running session over the agent-to-agent protocol.
    3. 13:54 His main lesson is to use deterministic code wherever possible: the MCP tool parses raw run data and hands the agent only the date, duration, incline and heart rate zones.
    4. 15:25 He keeps one session going indefinitely and handles memory with a custom compaction rule under fixed headings, plus tools that let the agent write to a plan file and an athlete file.
    5. 27:47 He reports finishing the 30K race in 4:30 against his friend's 4:41 from the previous year, after a year in which he says his weeks with three or more runs almost doubled.

    Untrusted Code on Secure Runtimes: Agent Sandboxes on Kubernetes

    Mofi Rahman

    Mofi Rahman leads a hands-on lab on GKE, with four Google colleagues helping attendees in the room, and explains that it uses the newly open-sourced Agent Substrate where the abstract promised Agent Sandbox. Attendees create workers, actor templates and actors, suspend and resume them with their state, allow a model call through an egress policy and run 20 actors on two workers, and he says internal benchmarks reached more than 100 million actors.

    80 min slot · Beginner · Tutorial

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you want to follow a full lab on suspending and resuming agent workloads on Kubernetes and see how actors differ from one pod per sandbox.

    1. 21:39 Rahman explains why the lab switched projects: Agent Sandbox maps a sandbox to a pod with warm pools, while Agent Substrate adds actors, many per pod, and he suggests Sandbox for agents that run for days and Substrate for short, bursty sessions.
    2. 25:22 He lists Substrate's parts: an API server, Postgres in place of etcd, which he says could not scale to the 100 million actor goal, egress control, and a router that proxies requests so actors do not each need an IP address.
    3. 36:15 He suspends an actor, sends it a request and gets an answer anyway, explaining that the router holds the request while the actor resumes from its snapshot mid-state, unlike Cloud Run, Lambda or Knative starting from zero.
    4. 49:14 A model call from the actor fails because egress is denied by default, and it succeeds after he creates an egress gateway and a policy that allows the one model URL.
    5. 57:09 A third actor times out on two full workers, and he stresses that Substrate does not decide when to suspend: the platform team defines idle, here three seconds without a request, after which 20 actors share two workers.

    Your Routes, My Rules: Making Gateway API Work at Enterprise Scale

    David Jumani

    David Jumani, a kgateway maintainer, argues that the hard part of running a gateway in a large organization is letting many teams ship routes without a platform team reviewing everything or teams breaking each other. He presents kgateway's route delegation, inherited policies and strict validation, and cites user scale numbers and resource reductions he attributes to the 2.5 release.

    5 min slot · Level not listed · Lightning Talk

    Networking and connectivitySecurity, identity and policy

    Watch this if: many teams share one gateway in your organization and you want them to own routes without breaking each other.

    1. 0:48 Jumani says Gateway API reference grants define where a route can connect but cannot require a prefix or stop one route from overriding another.
    2. 1:08 Jumani explains route delegation in kgateway: a platform team creates a parent route with a prefix and policy and delegates the sub-routes under it to specific teams.
    3. 2:16 Jumani says strict validation rejects a route with bad configuration instead of letting Envoy NACK it, which he says could otherwise bring down the whole gateway on a restart.
    4. 3:00 Jumani says one user runs kgateway with 700,000 concurrent gRPC streams, 90,000 JWT validations a second, over 200 proxies and about 300,000 pods that churn 11 times a day.
    5. 3:26 Jumani says the 2.5 release cut CPU use by 70% at 5,000 routes, memory by 95% at 40,000 routes and proxy memory by 48%.
