    Longhorn: Intro, Deep Dive and Q&A

    Shuo Wu, David Ko

    David Ko introduces Longhorn, a cloud native distributed block storage system for Kubernetes, and shares its release cadence, adoption numbers and contributor growth. He then compares the V1 and SPDK-based V2 data engines, explains snapshots, backups, disaster recovery and live upgrades, and outlines the 1.13 and 1.14 roadmap with early RDMA benchmarks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run Longhorn or need block storage on Kubernetes and want to compare the V1 and V2 data engines.

    1. 2:32 Ko says Longhorn runs on any compatible Kubernetes cluster and Linux distribution, including Talos, and ships minor releases every four months in line with Kubernetes.
    2. 4:58 Ko reports adoption up about 21% in six months to roughly 276,000 nodes and 60,000 clusters, from Longhorn's public usage metrics.
    3. 12:22 Ko explains that the V2 data engine uses SPDK in user space with NVMe over Fabrics, plus an interrupt mode so it can share CPU with applications.
    4. 19:21 Ko walks through V2 live upgrades, which move the volume target to another node so I/O continues while the upgrading node's instance manager restarts.
    5. 23:44 Ko lists the 1.14 plans, including RDMA support, I/O QoS, a new data engine for strict-local volumes and application-consistent snapshots and backups.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.

    SIG Storage Intro and Deep Dive

    Xing Yang, Hemant Kumar, Michelle Au

    Xing Yang, Hemant Kumar and Michelle Au explain what Kubernetes SIG Storage owns, from persistent volume APIs to CSI and COSI, and walk through recent storage features by category. They cover volume health, security changes, ephemeral volume updates, data protection, storage-aware scheduling and features still in design, then explain how to get involved.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run stateful workloads on Kubernetes and want a tour of the storage features landing in recent releases.

    1. 2:49 Kumar shows volume health reported on PVC and pod objects, plus a new alpha condition for the health of a whole storage subsystem on the CSINode object.
    2. 6:41 Au explains that the gitRepo volume plugin was removed because kubelet ran git clone on the host, and recommends an init container or sidecar instead.
    3. 10:02 Au introduces dynamic node-local ephemeral volumes, alpha in 1.38, which add and remove volumes from a running pod without recreating it.
    4. 14:55 Yang describes volume group snapshots, GA in 1.36, and changed block tracking, beta in 1.36, which lets backup vendors fetch only the blocks that changed.
    5. 19:58 Kumar explains an opt-in CSIDriver setting that stops pods from being scheduled to nodes without the driver, and how it interacts with Cluster Autoscaler.
