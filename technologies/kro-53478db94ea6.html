    Achieving Cross-Cloud Portability with the Kubernetes Resource Orchestrator

    Michael McCune, Daniel Bruno, Sitesh Pattanaik, Bridget Kromhout, Jesse Butler

    In this SIG Cloud Provider session, the chairs explain why the SIG took in kro as a subproject, and Jesse Butler lays out the problem of ordering, reconciling and exposing cloud resources as platform APIs. Daniel Bruno and Sitesh Pattanaik then walk through an example generative AI service API built as a ResourceGraphDefinition and show recorded demos of it deployed to GKE, AKS and EKS clusters.

    30 min slot · Level not listed · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you build a platform across more than one cloud and want to see what a single kro-defined API looks like from both the platform team's and the product team's side.

    1. 2:41 Bridget Kromhout says Amazon, Google, Microsoft and others wanted a consistent way to work with resources, and recalls Jesse Butler suggesting they skip 18 months of each doing it their own way.
    2. 10:01 Jesse Butler describes kro as a vendor-neutral composition layer over any resource in the cluster, naming Crossplane, ACK, KCC, ASO or controllers you built yourself.
    3. 15:19 Daniel Bruno shows what the product team writes: nine lines of YAML naming the instance, the model, the replica count and whether monitoring is on, deployed to clusters on several clouds.
    4. 17:01 Daniel Bruno shows the platform team's side: a ResourceGraphDefinition with CEL expressions for defaults and includeWhen conditions, written without Go controllers, with cloud-specific details read from ConfigMaps.
    5. 27:41 Sitesh Pattanaik explains custom status conditions written in CEL, such as a model cache bound condition, and later says kro emits a duration metric for how long a condition has held.

    Crossplane - The Cloud Native Framework for Platform Engineering

    Adam Wolfe Gordon, Jared Watts

    Crossplane maintainers Jared Watts and Adam Wolfe Gordon recap how composite resources, function pipelines and managed resources fit together, then demo two features they say are about to ship: simulations in the Crossplane CLI and function-controlled deletion in the 2.5 release. They also say v1.20 reaches end of life with that release, describe a proposed migration controller for moving v1 cluster-scoped resources to v2 namespaced ones, and credit the ModelPlane project with driving fixes upstream.

    30 min slot · Level not listed · Session

    Platform engineering and developer experience

    Watch this if: you run Crossplane and want to see a plan-style preview of changes and controlled deletion in action, or need to plan a move from v1 to v2.

    1. 11:09 Adam Wolfe Gordon introduces simulations, a set of Crossplane CLI commands built on render and crossplane-diff that also ask providers, through new plan servers, what they would do with a changed managed resource.
    2. 13:00 In a terminal demo he runs simulate commands on a managed resource, a composite resource and a whole project, and the output warns when an AWS VPC change would need a replacement and manual intervention.
    3. 18:04 Jared Watts says compositions get a deletion policy field in 2.5 with background, foreground and pipeline options, where pipeline calls the function pipeline during deletion so it can order and clean up.
    4. 22:14 In his demo, deleting a workspace with the pipeline deletion policy starts a backup job for its Postgres database before the resources are removed, while the background one is deleted immediately.
    5. 23:57 He says v2 is backwards compatible but recommends running the crossplane upgrade check command first, and that v1.20 reaches end of life with the 2.5 release.

    Four Resources, One Object: Surviving Gateway API After Ingress NGINX

    Sitesh Pattanaik

    Pattanaik demonstrates how replacing Ingress NGINX annotations with separate Gateway API and Envoy Gateway objects can leave route policies out of sync. He shows how his example uses a resource graph to manage those objects together and compares that approach with other ways to manage their lifecycle.

    30 min slot · Advanced · Session

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: you are migrating from Ingress NGINX and need a way to keep routes and their policies from drifting apart.

    1. 6:19 Pattanaik identifies the four resources in his example: an HTTPRoute plus security, backend traffic, and client traffic policies.
    2. 10:43 He explains that a policy's target reference does not tell the route about the policy or require it to share the route's lifetime.
    3. 20:47 He describes the platform team owning a ResourceGraphDefinition while an application team supplies inputs such as the hostname.
    4. 27:41 He shows that the graph manages the route and its authorization policy together when he switches to a replacement resource.
    5. 29:13 He compares Helm, kro, Crossplane, and a custom operator, asking which component will manage the full resource graph as a unit.

    Git, APIs, and Kubernetes: Where Should Platform Configuration Live

    Jesper Joergensen, Karunasri Garigipati, Joe Kutner, Rishabh Wason

    Karunasri Garigipati moderates a discussion between Jesper Joergensen of ConfigHub, Joe Kutner of Salesforce and Rishabh Wason of Heroku, with audience members joining in, on whether platform configuration belongs in Git, behind an API, or in the cluster. The speakers compare where their own configuration lives and cover rendered manifests, validation, short-lived environments, vulnerability rollouts and whether configuration should share a repository with application code.

    25 min slot · Level not listed · Birds of a Feather

    Platform engineering and developer experienceDelivery, GitOps and release safety

    Watch this if: your platform team is debating GitOps repositories versus an API or database for configuration and wants to hear how Heroku, Salesforce and others weigh the trade-offs.

    1. 3:27 Joergensen recalls that Heroku kept configuration in a database behind an API, says it has since moved into version control with long templating pipelines, and says his company is trying to give configuration its own path to production apart from code.
    2. 5:11 Kutner says Salesforce's internal platform moved from Git repositories owned by platform teams, which he calls a terrible experience for developers, to repositories owned by service owners, and argues teams should accept that there are several sources of truth.
    3. 13:35 Joergensen says the difficulty of managing configuration tempts people to abstract too much, and that higher-level constructs, with kro as his example, make it hard to customize something later.
    4. 19:12 On short-lived environments, Kutner says a commit for every dev sandbox once meant waiting about three weeks, and that his team now relaxes the Git requirement for dev environments and relies on APIs and a portal to show what is running.
    5. 24:49 In the closing poll on repositories, one audience member reports production incidents from developers assuming configuration and code merged together ship together, while another says separate repositories caused friction and their team moved configuration next to the code.

    Platform-First AI Agent Security: Zero-Trust Patterns for Kubernetes

    Carlos Santana

    Carlos Santana argues that a Kubernetes platform should treat agent-generated code as untrusted and provision isolation, credentials, and network policy separately. He describes using kro to compose those controls behind a platform API and shows captures of an Agent Sandbox warm pool assigning a ready pod.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to give teams a Kubernetes API for agents without giving those agents unrestricted access.

    1. 5:25 Santana describes SPIFFE and SPIRE as a way to identify an agent by URI and associate that identity with a credential across different environments.
    2. 12:14 Santana shows a kro ResourceGraphDefinition and explains how a declarative resource graph can give platform users a custom API without requiring the platform team to write a Go controller.
    3. 19:05 Santana compares gVisor, Kata Containers, and AWS Nitro Sandboxes as different isolation choices for running untrusted agent code.
    4. 21:27 Santana shows captures of a two-pod Agent Sandbox warm pool and says applying a claim assigned a ready pod instead of waiting for a fresh sandbox to start.
    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    So You Want to Build a Platform? You Probably Already Have One

    Juho Syrjänen

    Juho Syrjänen argues that teams with infrastructure-as-code modules, Helm charts and CI/CD pipelines already have a platform, and that the next step is to wrap that code behind a platform API instead of rebuilding it. He describes how module version drift and agent-generated pull requests strain the module-per-repository model, and shows an approach using Kratix where a short custom resource triggers the existing code.

    30 min slot · Any Level · Session

    Platform engineering and developer experience

    Watch this if: you maintain Terraform or OpenTofu modules and Helm charts and want a way to turn them into a self-service platform without a rewrite.

    1. 3:11 The speaker describes the tempting plan of rebuilding everything with Crossplane, kro, Backstage and Kratix over a couple of years, and the pushback he says that proposal gets.
    2. 5:29 The speaker says the engineering behind existing infrastructure as code is solid and asks why it should not be reused.
    3. 11:54 The speaker proposes packaging the module and its wiring into one platform capability, which he describes as a single deterministic unit, with user configuration cut to about a dozen lines of YAML.
    4. 17:56 The speaker walks through delivery: the platform writes rendered output to a Git repository, Flux syncs it into destination clusters, and in-cluster operators apply it to the cloud provider.
    5. 19:19 The speaker says users and agents can then act on the platform without extra pull request approvals because a human already approved the platform code, then names Kratix and Crossplane as tools that help.

    Steering the Ship: Ask the Kubernetes Steering Committee

    Kat Cosgrove, Maciej Szulik, Paco Xu, Michael McCune

    Members of the Kubernetes Steering Committee introduce three newly elected members and answer audience and anonymous questions in an open Q&A. Most questions concern AI: the load that AI-generated pull requests, issues and vulnerability reports put on maintainers, which AI tools the project is piloting, and whether agents could take over maintenance work. The panel also covers what Kubernetes does well, the new members' goals and their technical wish lists.

    30 min slot · Level not listed · Session

    Community and open source adoptionAI agents and automation

    Watch this if: you contribute to or maintain an open source project and want to hear how Kubernetes leadership is handling AI-generated contributions.

    1. 3:35 Asked for the biggest near-term challenge, the moderator says many on the committee think it is AI-generated contributions and their cost in maintainer time, and other members add AI-generated issues and vulnerability reports.
    2. 6:44 Michael McCune names workload-aware scheduling as the technical challenge and, on the social side, a growing knowledge gap between senior developers and juniors who arrive with AI tools.
    3. 7:47 The moderator says the committee asked GitHub for a way to stop Copilot being summoned in repositories that have it disabled, and that the setting is now generally available.
    4. 10:25 A committee member says CodeRabbit is approved by the CNCF and available to repositories on request, and the moderator clarifies that it is used in kubernetes-sigs but is not enabled in the main kubernetes repository or the website.
    5. 24:37 On agents taking over toil, the moderator says there is no scenario in which pull request review is fully handed to an agent, and Maciej Szulik says the project will limit how many pull requests one person can open in a given time frame.

    Welcome to Health Check Hell: CRDs, Statuses and Missing Standards

    Regina Voloshin, Dag Bjerre Andersen

    Regina Voloshin and Dag Bjerre Andersen describe how custom resources report status in different ways, so tools such as Argo CD, Flux, kro and Crossplane each have to be taught what healthy means. They show how Argo CD health checks are contributed as Lua scripts, present a prototype that reports health in three dimensions, and lay out options for moving health checks into a shared standard.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you write or rely on health checks for custom resources in GitOps tools and want to see where a common standard could come from.

    1. 6:03 The speaker explains that Argo CD has six health statuses and uses contributed Lua scripts to map each custom resource's status fields onto them.
    2. 11:37 The speaker says kro has no built-in health checks and Crossplane's cover only part of the ecosystem, so each tool has to be taught again what healthy means.
    3. 13:54 The speaker introduces kstatus, a Go library that reports a resource's reconciliation state, and says that among graduated and incubating CNCF projects only Flux and Helm seem to have adopted it.
    4. 18:05 The speaker argues that a single health value hides availability, and shows a prototype library he calls Kube Health that splits health into three dimensions.
    5. 23:17 The speaker walks through options for a shared approach: a common library, a Kubernetes aggregated API, health inside the custom resource status, or a Lua script in a CRD annotation.
