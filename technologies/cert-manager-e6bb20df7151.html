    All Things DRA in One Place: DRA Example Driver Deep Dive

    Jon Huhn

    Jon Huhn of Microsoft presents the DRA example driver, a Kubernetes-hosted driver with entirely synthetic devices that he says aims to show a runnable example of every Dynamic Resource Allocation feature. He walks through what a DRA driver does at each stage of a workload's life and runs four demos on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you want to try Dynamic Resource Allocation on a laptop or are writing a DRA driver and need a working reference.

    1. 4:38 Huhn explains binding conditions: the scheduler allocates a device, then waits for the driver to signal it is reachable from the node before binding the pod, with a stub controller in the example driver.
    2. 6:48 First demo: on a default Kubernetes 1.37 kind cluster he installs the driver's Helm chart and two pods are each allocated a different mock GPU, with no feature gates enabled.
    3. 8:57 Second demo: with the driver's webhook enabled, a ResourceClaim whose GPU config has an invalid time-slicing interval is rejected before any pod tries to start.
    4. 11:30 Last demo: he installs the driver twice, as mock GPUs and mock network devices, and a claim with a match attribute constraint gets a GPU and a NIC on the same PCIe root.
    5. 18:21 Huhn lists where the example driver is already used: the Kubernetes documentation, Cluster Autoscaler tests, the AI Conformance Program and SIG Scalability tests at up to 5,000 nodes.

    Authorized? It Depends.

    Rita Zhang, David Eads, Micah Hausler, Ben Petersen, Stanislav Láznička

    Kubernetes SIG Auth maintainers give a deep dive on conditional authorization, which lets an authorizer answer with conditions that are enforced later at admission, tracing the idea from a Cedar-based prototype to the interface now in the API server. They also cover a proposal to use the certificate APIs inside the platform, fixes to the Secrets Store CSI Driver and its sync controller, a proposal for authenticating requests to admission webhooks, and a proposal for signed requests to the API server.

    30 min slot · Level not listed · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you write Kubernetes authorizers, admission webhooks or platform extensions and want to know what SIG Auth is changing.

    1. 2:36 Rita Zhang gives the motivating case for conditional authorization: a controller that may update a pod but should only touch its own finalizer currently needs one access rule split across authorization and admission, which must be kept aligned.
    2. 9:25 David Eads describes the new conditional authorizer interface, in which an authorizer that answers maybe stores its conditions in the request context so admission can evaluate them once the object is available, and results are downgraded if the admission plugin is turned off.
    3. 16:09 He says the project does not yet know what the user-facing API on top of this mechanism should look like, and invites people to bring prototypes to the SIG Auth meeting.
    4. 18:45 Stanislav Láznička describes a proposal that adds a serving certificate signer for services and pods, so webhooks and aggregated API servers would no longer need to mint their own certificates.
    5. 31:50 Micah Hausler argues that most Kubernetes credentials can be replayed if logged or intercepted, and describes a proposal for clients to sign requests to the API server so that a captured request cannot be reused.

    Cloud Native Operators and You

    Corey McGalliard

    Corey McGalliard explains the Kubernetes control loop and the operator pattern of a custom resource definition plus a controller, then acts it out with three audience volunteers who keep a set number of balloons in a bucket. In the Q&A he says his team prefers operators over raw config maps because a custom resource can be validated, while noting this is an opinion and that implementations differ between projects.

    12 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: You want an intuitive picture of how Kubernetes controllers and operators reconcile state before reading any operator code.

    1. 1:09 The speaker describes the control loop from control theory: observe the current state, compare it with the desired state, and act to reconcile the two.
    2. 1:54 He explains the operator pattern as a custom resource definition that holds the desired state plus a controller that reconciles it, for things inside or outside the cluster.
    3. 4:35 He starts a live demonstration in which volunteers act as controllers: one inflates balloons to reach three in a bucket, one enforces a limit of two, and one reports when the bucket is empty.
    4. 7:59 He names cert-manager and KubeRay as CNCF projects that use the operator pattern, and says his team writes its own operators for an internal platform.
    5. 9:21 Asked whether to always use an operator when one exists, he says his team prefers it because a custom resource is a defined API contract that can be validated, unlike raw text in a config map.

    Data-Driven Platform Guardrails: What 16,500 Incidents Tell You to Automate First

    Henrique Santana, Henrique Dalssaso

    Henrique Santana and Henrique Dalssaso walk through the top root causes they found in more than 16,000 Kubernetes incidents, including IP exhaustion, auth failures and node provisioning problems. For each one they suggest platform guardrails to automate, and they explain how to run the same analysis on your own incident data.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you want a list of common Kubernetes incident root causes and the guardrails these speakers suggest automating for each.

    1. 1:35 The speakers describe their dataset as more than 16,000 incidents across many Kubernetes clusters from January to mid-May, grouped with AI and then reviewed by hand. They say DNS did not make their top 10 root causes.
    2. 3:57 They say about a third of one top pattern was pods with no IP address available, from small or shared subnets, and suggest Cilium multi-pool IPAM and broader Karpenter node pools.
    3. 6:59 For auth failures they separate missing permissions, RBAC that was never bound to the pod, and policies on the target endpoint, and suggest Kyverno policies, projected service account tokens and cert-manager.
    4. 16:20 For node provisioning failures, which they put at almost 15% of incidents, they suggest setting kube-reserved and system-reserved, Cluster API machine health checks and Karpenter node auto repair.
    5. 20:59 To repeat the analysis on your own data, they suggest classifying by what actually failed rather than the symptom, ranking by frequency, and asking whether the platform, the app team or both can fix it.

    30 min slot · Level not listed · Session

    5. 19:51 He introduces gatekeeper plugins, hooks called before and after reconciliation that he says can enforce or enrich custom resources, inspired by admission controllers, Kyverno and Open Policy Agent.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.

    Supply Chain, Runtime and SDLC: A Cloud Native Security Tour

    Dr. Constanze Roedig

    Constanze Roedig walks through cloud native security in three parts, the software supply chain you consume, the software development lifecycle where you build and deploy, and the runtime, naming CNCF and OpenSSF projects for each. She closes with her view that AI agents put more weight on runtime detection and on protecting and rotating secrets.

    12 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: You find cloud native security overwhelming and want a 16-minute overview of which problem each group of projects addresses.

    1. 0:40 The speaker frames the talk around three areas: the supply chain of software you consume, the software development lifecycle where you produce and deploy it, and the runtime.
    2. 3:44 She says an SBOM declares what is in your software but cannot be assumed complete, and suggests following OpenSSF recommendations on tooling.
    3. 5:51 She distinguishes a signature from an attestation, which she describes as a piece of evidence put in an envelope together with a signature, and names in-toto.
    4. 10:36 For runtime detection she contrasts signatures, which encode known adversary behavior, with anomalies, which are deviations from your own baseline, and says to combine them.
    5. 14:18 She says that with AI agents there are vulnerabilities with no patches available, which in her view puts the spotlight on runtime detection and on short-lived, rotatable secrets.

    The Operator Calls Are Coming from Inside the Namespace

    Justin O'Leary

    Justin O'Leary says he took over cloud environments from ordinary namespace access by asking cloud operators to act with their own credentials, and demos what he describes as the same confused-deputy flaw in Config Connector, Azure Service Operator, AWS Controllers for Kubernetes and Crossplane. He recounts how each vendor or project responded to his reports and closes with questions for people who run operators and changes for people who write them.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you run cloud-resource operators in multi-tenant clusters and want to see how namespace users might reach cloud IAM through them.

    1. 2:45 Justin's first demo applies an IAMPolicyMember resource aimed at a whole GCP organization, and he says Config Connector made a namespace developer organization owner in under a minute.
    2. 10:31 Justin names the pattern a confused deputy, citing Norm Hardy's 1988 description, and lists three ingredients: a field the user fills in, a powerful credential in the operator, and no check on who is asking.
    3. 15:02 Justin demos what he calls trust policy injection with AWS Controllers for Kubernetes, putting an outside AWS account on a role's trust policy, and says the cloud logs attribute the change to the operator.
    4. 23:17 Justin goes through common mitigations such as policy engines, narrower operator permissions, cloud guardrails, logs and OIDC, and argues none of them makes the operator check whether the requester is allowed.
    5. 26:15 Justin's closing advice for operator authors is to verify the caller with a SubjectAccessReview at admission, authorize references instead of trusting raw strings, and fail closed.

    Zero-Trust Telemetry: Stopping AI-Powered Poisoning Attacks on Observability Pipelines

    Chad M. Crowell, Diana Todea

    Chad M. Crowell and Diana Todea describe why telemetry should be treated as untrusted input when it feeds automated decisions. They propose independent controls for transport, query access, and network policy, then discuss how to verify those controls in Kubernetes.

    30 min slot · Advanced · Session

    Observability and reliabilitySecurity, identity and policy

    Watch this if: telemetry drives automated responses and you want to limit what each source and consumer can do.

    1. 13:37 The speakers describe using mutual TLS between OpenTelemetry Collectors and backends, and explain that verifying the sender does not verify that the data is true.
    2. 16:43 They propose checking the identity and scope of human and agent queries with fine-grained role-based access, then logging those decisions for audit.
    3. 20:02 They recommend default-deny network policies for the telemetry namespace, with explicit allowances for the application-to-collector and collector-to-backend flows.
    4. 22:42 They describe using Falco with Kubernetes audit events to detect suspicious activity, complementing the communication limits from network policy.
    5. 23:54 They recommend validating which sources feed Prometheus federation and restricting who can reach federation endpoints and exporters.
