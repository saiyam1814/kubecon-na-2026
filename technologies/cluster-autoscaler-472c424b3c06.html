    All Things DRA in One Place: DRA Example Driver Deep Dive

    Jon Huhn

    Jon Huhn of Microsoft presents the DRA example driver, a Kubernetes-hosted driver with entirely synthetic devices that he says aims to show a runnable example of every Dynamic Resource Allocation feature. He walks through what a DRA driver does at each stage of a workload's life and runs four demos on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you want to try Dynamic Resource Allocation on a laptop or are writing a DRA driver and need a working reference.

    1. 4:38 Huhn explains binding conditions: the scheduler allocates a device, then waits for the driver to signal it is reachable from the node before binding the pod, with a stub controller in the example driver.
    2. 6:48 First demo: on a default Kubernetes 1.37 kind cluster he installs the driver's Helm chart and two pods are each allocated a different mock GPU, with no feature gates enabled.
    3. 8:57 Second demo: with the driver's webhook enabled, a ResourceClaim whose GPU config has an invalid time-slicing interval is rejected before any pod tries to start.
    4. 11:30 Last demo: he installs the driver twice, as mock GPUs and mock network devices, and a claim with a match attribute constraint gets a GPU and a NIC on the same PCIe root.
    5. 18:21 Huhn lists where the example driver is already used: the Kubernetes documentation, Cluster Autoscaler tests, the AI Conformance Program and SIG Scalability tests at up to 5,000 nodes.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.

    Kubernetes under Fire: Igniting Performance and Burning Through Bottlenecks with Kube-Burner

    Andrew Collins

    Andrew Collins introduces kube-burner as a Go tool that creates, deletes and churns Kubernetes resources from YAML configs while collecting metrics, so teams can reproduce scale problems in a lab. He lists recent features and community testing work, and closes by urging people to burn down their lab rather than production.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you want a four-minute overview of what kube-burner does before trying it for cluster scale testing.

    1. 0:34 Andrew frames the problem with a simple pod-count reproducer and the questions it raises about scale rate, latency measurement, namespaces, metrics and churn.
    2. 1:16 Andrew describes kube-burner as a Go tool that takes YAML configs to create, delete and churn Kubernetes resources by count or percentage.
    3. 1:29 Andrew says it can collect metrics from the cluster's Prometheus and write them to JSON files, OpenSearch, local storage or Prometheus TSDB chunks.
    4. 1:54 Andrew lists newer features including scaffolded configs, pprof collection, grouping resources into waves, and incremental load that ramps up gradually.
    5. 2:35 Andrew names community testing done with kube-burner, including OVN-Kubernetes, node remediation operators, schedulers, Cluster Autoscaler and KubeVirt VM scale tests.

    Saturated by Design - Maximizing Cluster Allocation in On-Premises Kubernetes

    Dakota Sullivan, Isaac Wilson

    The speakers describe how The Trade Desk raised allocation in its fixed-size on-premises Kubernetes clusters from about 20% with default scheduler settings to what they say is a consistent 97%. They walk through four problems, node scoring, deployment overscaling, fragmentation and right-sizing, and the scoring change, two custom scheduler plugins and a simulation-driven controller they built for them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: You run fixed-capacity or on-premises Kubernetes clusters with large pods and topology constraints and want to see how one team pushed allocation toward full.

    1. 4:14 Isaac Wilson says switching node scoring from least allocated to most allocated was the easiest and most significant change, taking utilization from about 20% to 85%.
    2. 6:30 Dakota Sullivan describes Plimsoll, a custom scheduler plugin that holds back extra pods created during rollouts and deletions until terminating pods are gone, which he says also works with out-of-tree controllers such as Argo Rollouts.
    3. 11:24 Wilson describes ResourceShuffler, a second scheduler plugin that moves pods without topology spread constraints to make room for constrained pending pods while respecting PodDisruptionBudgets, bringing utilization to 97% by their account.
    4. 15:09 Sullivan explains modeling workloads elastically, which he compares to CSS flexbox: each has a basis scale plus a min and max, so all workloads shrink or grow fairly when capacity changes.
    5. 18:24 He introduces Bento, a controller that snapshots the cluster, runs simulations with the real Kubernetes scheduler to find ideal scales and moves workloads part way toward them on each loop.

    SIG Autoscaling Project Updates

    Jack Francis, Jason Deal, Heba Elayoty, Kuba Tużnik

    Jack Francis, Jason Deal, Heba Elayoty and Kuba Tużnik give updates on Kubernetes SIG Autoscaling projects, including Karpenter's DRA support, balanced consolidation and node repair, the capacity buffer and capacity quota APIs, and the split of Cluster Autoscaler into a core plus separate provider projects. Elayoty then explains what workload-aware scheduling needs from autoscalers, and Tużnik presents scheduler-driven autoscaling, a proposed redesign in which the scheduler requests nodes from the autoscaler.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Karpenter or Cluster Autoscaler and want the latest feature updates plus the proposed redesign of how autoscalers work with the scheduler.

    1. 3:28 Jason Deal says Karpenter added DRA support in its scheduling simulation in v1.14, covering structured parameters, consumable capacity, partitionable devices and prioritized alternatives, with provider implementations in the AWS provider and EKS Auto Mode.
    2. 6:11 He introduces balanced consolidation, which weighs the share of pods disrupted against the share of cost saved and only acts when the score passes a threshold.
    3. 10:08 Jack Francis says Cluster Autoscaler is being split into a core repository and separate provider projects, and that the SIG will keep supporting releases in the older all-in-one model for a transition period.
    4. 19:50 Kuba Tużnik describes the split brain problem: the autoscaler has to predict what the scheduler will decide, and when its predictions are off it makes wrong scaling decisions.
    5. 24:15 He outlines the proposed design in which the autoscaler publishes potential capacity and the scheduler issues node claims, and estimates it at more than ten KEPs over one to two years.

    The Future of Kubernetes Eviction and Node Lifecycle

    Lucy Sweet, Ryan Hallisey, Filip Křepinský

    Three members of the Node Lifecycle Working Group describe two efforts: Specialized Lifecycle Management, which adds shared lifecycle conditions to nodes, and a declarative EvictionRequest API meant to replace one-shot API-initiated eviction. Filip Křepinský explains the requester and responder model and runs a live demo, and Lucy Sweet says Anthropic already uses eviction requests in production.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: you drain or upgrade nodes under stateful or long-running workloads and want to see how eviction is meant to become declarative and observable.

    1. 3:52 Ryan Hallisey introduces node lifecycle conditions such as drain in progress and maintenance in progress, which he says merged as alpha in Kubernetes 1.37 to replace ad hoc node labels.
    2. 5:08 He names the open problem: anyone with permission can write these conditions, so two drains with different options can conflict, and the group is considering a new API to declare intent and serialize writers.
    3. 8:37 Lucy Sweet calls API-initiated eviction a point-and-shoot gun with a one-bit answer that cannot be observed until it happens, and says users build admission webhooks on top of it.
    4. 14:47 Filip Křepinský explains the responder contract: each responder reports a heartbeat within a deadline now set at 20 minutes, and one that stalls is skipped, ending with a fallback that calls the eviction API and respects PDBs.
    5. 25:38 Lucy Sweet says Anthropic uses the eviction request API in production and has issued millions of eviction requests, and that other companies have told the working group they use or plan to use it.

    The Latest in GPU, TPU, NIC and Other Device Support - WG Device Management

    John Belamaric, Morten Jæger Torkildsen

    Morten Torkildsen and John Belamaric of Google give the Device Management working group update, recapping why Dynamic Resource Allocation replaced the device plugin's opaque counters and what its four parts are. They cover the features that shipped in Kubernetes 1.37 and those planned for 1.38, go deeper on allocating CPU and memory through DRA and on its integration with workload-aware scheduling, and describe ecosystem adoption and next steps such as preemption and attaching GPUs to running pods.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you manage GPUs or other accelerators in Kubernetes and want to know which DRA features landed in 1.37 and what is planned next.

    1. 3:06 Morten Torkildsen outlines DRA's four parts: the resource slice API for describing devices, the resource claim API for requesting them, the scheduler matching the two, and the kubelet API that works with the DRA driver on the node.
    2. 6:11 He explains the extended resource request feature in 1.37, which lets cluster admins adopt DRA while workloads keep using device-plugin style requests that are matched to DRA devices underneath.
    3. 7:42 He describes device taints, which let a single failing GPU or TPU be tainted instead of the whole node, so workloads on the other devices are not disrupted.
    4. 11:52 John Belamaric explains node allocatable resources with DRA, which lets CPU and memory be selected through DRA so they can be aligned with the NIC and GPU, and tells the scheduler how to account for CPU requested in both the container spec and a resource claim.
    5. 16:30 He describes the DRA integration with workload-aware scheduling, where a resource claim attached to a pod group allocates a shared resource for a new replica and cleans it up when the replica scales down.

    WG-Batch Updates: What’s New and What Is Next?

    Amy Chen, Yuki Iwai, Marcin Wielgus

    Marcin Wielgus, Amy Chen and Yuki Iwai give an update on the Kubernetes Batch Working Group and its projects. They cover new Kueue features such as concurrent admission, configurable preemption, topology-aware spreading, the dynamic quota orchestrator and partial scale-up, then Job, JobSet and workload-aware scheduling updates.

    30 min slot · Level not listed · Session

    Accelerators and workload scheduling

    Watch this if: you run AI training or batch jobs on Kubernetes and want to know what changed in Kueue, Job and JobSet.

    1. 3:46 Wielgus says that since last November Kueue shipped 54 releases, while PRs, issues and contributors each more than doubled.
    2. 4:45 Wielgus explains concurrent admission, where virtual copies of a workload keep trying for cheaper reserved capacity and move the job there once it frees up.
    3. 12:36 Wielgus introduces topology-aware spreading for inference, which caps the share of serving capacity placed in one rack, for example at 45%.
    4. 14:27 Chen describes the dynamic quota orchestrator, which discovers real capacity from node pools or MultiKueue worker clusters and adjusts nominal quota automatically.
    5. 28:54 Iwai explains that Kueue is adopting a shared scheduler library from kube-scheduler so its node feasibility checks match what kube-scheduler will accept.
