    Achieving Cross-Cloud Portability with the Kubernetes Resource Orchestrator

    Michael McCune, Daniel Bruno, Sitesh Pattanaik, Bridget Kromhout, Jesse Butler

    In this SIG Cloud Provider session, the chairs explain why the SIG took in kro as a subproject, and Jesse Butler lays out the problem of ordering, reconciling and exposing cloud resources as platform APIs. Daniel Bruno and Sitesh Pattanaik then walk through an example generative AI service API built as a ResourceGraphDefinition and show recorded demos of it deployed to GKE, AKS and EKS clusters.

    30 min slot · Level not listed · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you build a platform across more than one cloud and want to see what a single kro-defined API looks like from both the platform team's and the product team's side.

    1. 2:41 Bridget Kromhout says Amazon, Google, Microsoft and others wanted a consistent way to work with resources, and recalls Jesse Butler suggesting they skip 18 months of each doing it their own way.
    2. 10:01 Jesse Butler describes kro as a vendor-neutral composition layer over any resource in the cluster, naming Crossplane, ACK, KCC, ASO or controllers you built yourself.
    3. 15:19 Daniel Bruno shows what the product team writes: nine lines of YAML naming the instance, the model, the replica count and whether monitoring is on, deployed to clusters on several clouds.
    4. 17:01 Daniel Bruno shows the platform team's side: a ResourceGraphDefinition with CEL expressions for defaults and includeWhen conditions, written without Go controllers, with cloud-specific details read from ConfigMaps.
    5. 27:41 Sitesh Pattanaik explains custom status conditions written in CEL, such as a model cache bound condition, and later says kro emits a duration metric for how long a condition has held.

    Autoscaling at Scale with KEDA

    Ali Aqel

    Ali Aqel, a Stripe engineer and KEDA contributor, describes how Stripe's Kubernetes team runs workload autoscaling with KEDA across its clusters, organized around four principles: safe, stable, scalable and simple. He covers rollout protection, break-glass locks, canaries for every scaler, tuning and per-cluster Prometheus workspaces, and walks through two hypothetical incidents.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingObservability and reliabilityDelivery, GitOps and release safety

    Watch this if: you run KEDA or HPA on large clusters and want one company's guardrails, locks and canaries.

    1. 3:09 Ali gives Stripe's numbers: more than 90 self-managed clusters, about 84,000 deployments and 180,000 application pods for over 8,600 services, run by about a dozen Kubernetes engineers.
    2. 10:03 He says Stripe built a pod deletion cost controller that annotates pods so scale-downs keep the spread across availability zones.
    3. 11:02 He describes scale-down and scale-up locks, from one service up to global, built on KEDA's pause annotation and annotations he says Stripe upstreamed, including force activation.
    4. 13:17 He says a canary for every supported scaler pages the team when degraded, and that these canaries found Prometheus rate limiting and a DNS problem.
    5. 16:45 He says scaling on Prometheus broke Amazon Managed Prometheus rate limits, which led through caching and sync period changes to one autoscaling workspace per cluster.

    Battle-tested Autoscaling Paradigms with KEDA

    Jan Wozniak, Christian Melendez

    Jan Wozniak and Christian Melendez run a live audience quiz backed by a small CPU-hosted model and use it to show KEDA scaling the pods while Karpenter scales the nodes. They walk through their recommendations on metric freshness, fallbacks between metric sources, spare node capacity through capacity buffers, and conservative scale-down.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingObservability and reliability

    Watch this if: you autoscale workloads on Kubernetes and want practical guidance on metric sources, fallbacks, node headroom and scale-down settings with KEDA and Karpenter.

    1. 3:45 Wozniak groups scaling metrics into reactive ones such as CPU and memory, proactive ones such as load balancer and queue metrics, and predictive ones, and says reactive scaling tends to run behind the load.
    2. 10:13 He says Prometheus can keep working for smaller environments, and suggests KEDA's OpenTelemetry scaler, which has metrics pushed to it, for teams that want to remove the scrape delay or that run a very large number of scaled objects.
    3. 12:58 He describes KEDA scaling modifiers and their dynamic fallback operator, then has the OpenTelemetry source killed live to show scaling continue on the Prometheus copy of the metric.
    4. 16:56 Melendez explains Karpenter's capacity buffers, where a pod template and a buffer object act as virtual pods that keep headroom ready, and compares this with the older pattern of low-priority balloon pods.
    5. 26:41 For scale-down, Melendez advises a stabilization window longer than the time an application needs to start on a fresh node, plus a delay on Karpenter consolidation, with GPU nodes removed only when empty.

    From Kernel to Kubectl in 30 Seconds: eBPF Observability with Inspektor Gadget

    Qasim Sarfraz

    Qasim Sarfraz, an Inspektor Gadget maintainer, shows how the trace DNS gadget collects kernel telemetry and enriches it with Kubernetes context, and explains that gadgets are eBPF programs stored as OCI images. He then demos extending the official DNS gadget with an extra field and running the rebuilt image from his own registry.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliabilityNetworking and connectivity

    Watch this if: You debug DNS or network issues in Kubernetes and want to see eBPF tracing from kubectl in under five minutes.

    1. 0:23 Qasim Sarfraz shows a command that traces all DNS requests in a cluster, with workload context, query and response details, response code and latency.
    2. 0:54 He says a gadget is an eBPF program plus metadata in an OCI registry; the Inspektor Gadget pod on each node pulls the image, loads the programs and adds Kubernetes context.
    3. 1:32 He groups the officially maintained gadgets into top gadgets, snapshot gadgets, trace or profile gadgets and special-purpose gadgets, and says the catalog is on Artifact Hub.
    4. 2:05 He says the telemetry can also be consumed through a desktop app, a Headlamp plugin, an MCP server and a Go API.
    5. 2:49 In the demo he adds an extended DNS errors field to a copy of the official DNS gadget, merges it so CI pushes the image, and runs it from his own repository.
