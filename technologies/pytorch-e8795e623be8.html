    Groundhog Pod: Scaling AI Inference with Kata Pod Snapshots

    David Justice, Roaa Sakr

    David Justice and Roaa Sakr describe a prototype that snapshots an initialized Kata pod VM along with its GPU state. They report a faster restore than cold start in their demo and discuss where hardware compatibility can limit reuse of a snapshot.

    30 min slot · Any Level · Session

    AI inference and servingKubernetes internals and runtimes

    Watch this if: You are comparing pre-warmed GPU pods with restoring initialized workloads when inference demand spikes.

    1. 6:52 The speakers say a VM snapshot may fail to restore on a different CPU microarchitecture and describe using virtual CPU profiles to define a compatible feature set.
    2. 8:47 The speakers explain that CUDA checkpointing moves GPU state into the running application inside the VM, so the subsequent VM snapshot can capture that state too.
    3. 13:00 In the inference demo, the speakers terminate the original pod and show another pod restoring from its snapshot and returning a response.
    4. 14:15 For the demo on an NVIDIA Tesla T4, the speakers report about 34 seconds for the cold start and 11 seconds from a snapshot, which skipped the software and model loading steps.
    5. 20:02 In a second demo, the speakers plot the training loss and show it continuing from a restored snapshot after the training pod is interrupted.

    One Workload to Rule Them All: Workload Aware Scheduling for Distributed AI Training on Kubernetes

    Andrey Velichkevich

    Andrey Velichkevich explains why scheduling distributed training one pod at a time can deadlock jobs and how the Kubernetes Workload and PodGroup APIs model them as a unit. He shows how Kubeflow Trainer exposes those capabilities through training runtimes and compares three scheduling policies on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: You run distributed training on Kubernetes and want to understand when pod groups and topology constraints matter.

    1. 0:48 Velichkevich illustrates how two training jobs can deadlock when the scheduler gives each job some GPUs but neither gets enough to start all its ranks.
    2. 4:44 Velichkevich distinguishes the Workload template from runtime PodGroups and shows how a PodGroup can express a minimum pod count and topology constraints.
    3. 7:10 Velichkevich introduces composite PodGroups for workloads with a hierarchy, where a parent can require a minimum number of child groups before scheduling proceeds.
    4. 10:12 Velichkevich explains the Kubeflow Trainer split: platform admins define runtime blueprints, and scientists use a Python SDK to submit jobs without managing Kubernetes deployment details.
    5. 15:17 In a local kind demo, Velichkevich sets up a comparison of default pod-by-pod placement, gang scheduling, and rack-constrained placement for a PyTorch job.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.

    Ship Faster, Ship Safer: A K8s-Native Canary Pipeline for Critical Cluster Services

    Youmin Han, Zhuo Zhi

    Youmin Han and Zhuo Zhi describe why traffic splitting did not give LinkedIn the coverage it needed for cluster infrastructure releases. They show how the team combined namespace-scoped canaries, synthetic workloads, and Argo CD validation gates before promoting changes to production.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safety

    Watch this if: You need to validate critical Kubernetes components that cannot be canaried by shifting a percentage of user traffic.

    1. 9:39 The speakers say random traffic sampling missed GPU and job combinations and could not safely stage changes such as a shared database migration.
    2. 10:28 The speakers explain how dedicated canary instances run in the production cluster while a separate namespace directs only synthetic workloads to the new versions.
    3. 17:36 The speakers show how the Kubernetes API server matches a namespace label against webhook selectors so each pod goes through the canary or the stable admission webhook, not both.
    4. 21:30 The speakers describe using Argo CD PostSync hooks to run functional validation jobs once the canary resources are synced and healthy.
    5. 23:34 The speakers describe running the full GPU and CPU validation suites in canaries before the pipeline promotes changes to production clusters one at a time.

    WG-Batch Updates: What’s New and What Is Next?

    Amy Chen, Yuki Iwai, Marcin Wielgus

    Marcin Wielgus, Amy Chen and Yuki Iwai give an update on the Kubernetes Batch Working Group and its projects. They cover new Kueue features such as concurrent admission, configurable preemption, topology-aware spreading, the dynamic quota orchestrator and partial scale-up, then Job, JobSet and workload-aware scheduling updates.

    30 min slot · Level not listed · Session

    Accelerators and workload scheduling

    Watch this if: you run AI training or batch jobs on Kubernetes and want to know what changed in Kueue, Job and JobSet.

    1. 3:46 Wielgus says that since last November Kueue shipped 54 releases, while PRs, issues and contributors each more than doubled.
    2. 4:45 Wielgus explains concurrent admission, where virtual copies of a workload keep trying for cheaper reserved capacity and move the job there once it frees up.
    3. 12:36 Wielgus introduces topology-aware spreading for inference, which caps the share of serving capacity placed in one rack, for example at 45%.
    4. 14:27 Chen describes the dynamic quota orchestrator, which discovers real capacity from node pools or MultiKueue worker clusters and adjusts nominal quota automatically.
    5. 28:54 Iwai explains that Kueue is adopting a shared scheduler library from kube-scheduler so its node feasibility checks match what kube-scheduler will accept.
