    Automated Resource Allocation Driven by Service Level Objectives

    Pedro Célestin, Julia Furst Morgado

    Pedro Célestin and Julia Furst Morgado present a case study in letting teams specify service objectives and using measured performance to test resource changes automatically. They describe using error budgets and production canaries to test proposed changes instead of letting an AI agent change allocation directly.

    25 min slot · Advanced · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: You want to turn service objectives into allocation decisions without handing an AI agent direct control of production.

    1. 2:55 The speakers translate an example latency goal into an error budget, then explain how budget burn could inform whether to add or reclaim resources.
    2. 7:20 They propose canarying a resource change, not just a new build. They explain that if more resources do not improve the service-level indicator, the cause may instead be a bad release.
    3. 9:45 They describe the division of work in their case study: developers set the service objective, while the platform tests its own allocation proposals and can keep or reverse a change based on measured results.
    4. 11:28 They say letting AI change production allocation directly did not work well for them, so they limited it to proposing changes that a production canary could verify.
    5. 13:25 They walk through their stack: Prometheus collects metrics, Argo CD deploys changes, Argo Rollouts runs canaries, and Knative is used in some cases rather than being required.

    Frameworkless ML Serving: Scaling to Thousands of Models with KEDA, Pub/Sub, and Native K8s

    Robin Deaconu, Neb Jovanovic

    The presenters explain why multi-minute drug-discovery jobs led their team away from a general-purpose inference framework. They describe how stateless workers, durable queues, and native Kubernetes scheduling serve interactive and batch requests on the same fleet.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: interactive inference and long-running batch jobs need to share the same pool of accelerators.

    1. 6:01 The presenters explain why multi-minute accelerator jobs made durable requests and backlog-based scaling more useful to them than in-flight concurrency.
    2. 9:12 They describe how a stateless worker backed by an asynchronous queue became the core building block of the new platform.
    3. 16:29 They explain how KEDA wakes a deployment from zero replicas and passes queue signals to the Horizontal Pod Autoscaler for further scaling.
    4. 18:46 They walk through high-priority requests preempting batch workers and describe how queue leases let interrupted work become available again.
    5. 27:52 They describe dual-writing to Redis and Bigtable to verify parity before cutting over with a configuration flag they could flip back.

    From Proxy to Platform: Building a Multi-Tenant AI Gateway

    Dibyo Mukherjee, Tushar More

    The speakers describe how Adobe turned an internal model proxy into a shared gateway with team-scoped access and self-service configuration. They explain how customer-facing agents changed the way they attributed spending and which safeguards they put around platform upgrades.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivity

    Watch this if: several teams need to share an AI gateway without sharing model access, logs, or spend limits.

    1. 6:46 The speakers explain how teams share a gateway while using separate model deployments, cloud accounts, and scoped keys.
    2. 8:23 They walk through a console that lets tenant admins add models and set fallback rules and budgets without a platform ticket.
    3. 11:08 They explain how internal applications provide a customer identity so budgets and rate limits can follow the customer rather than a shared agent key.
    4. 14:13 They describe adding a seven-day wait before promoting releases from development to production and running API contract tests on development upgrades.
    5. 15:54 They describe using KEDA to scale the proxy by in-flight requests and setting a grace period to let requests drain during rollouts.

    The Seams Are the Trap: Agent Fleets from CNCF Parts You Already Have

    Aleksander Slominski, Mariusz Sabath

    The presenters describe assembling an event-driven agent fleet from Kubernetes, KEDA, Kafka, and signed CloudEvents instead of buying an agent platform. They explain the limits of tying identity to a pod and show a recorded demo in which a worker rejects an unsigned event.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to reuse a Kafka and Kubernetes stack for agent workers and verify who sent their tasks.

    1. 3:09 The speaker describes using CloudEvents as a standard envelope so producers do not have to invent their own event types, identifiers, and payload structure.
    2. 4:29 The speaker says KEDA uses Kafka lag to decide when to bring up workers and can scale them back to zero when no events remain.
    3. 10:11 The speaker explains that the runner checks a signed event's origin and whether the agent may consume it, while Kafka preserves the event sequence for audit.
    4. 11:04 The speaker says SPIFFE and SPIRE can identify a workload, but asks how that identity should change when an agent loads new skills or plugins.
    5. 23:36 The speaker shows the recorded audit check and an agent rejecting an unsigned event that was sent directly to Kafka.
