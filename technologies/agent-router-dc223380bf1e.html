    Agents on the Platform: Four Perspectives on the Conversation We're Already Having in Private

    Kasper Borg Nissen, Juraci Paixão Kröhling, Joseph Sandoval, Jed Salazar, Alexa Griffith

    Kasper Borg Nissen moderates a panel on running agents on cloud native platforms, with panelists speaking from end user, security, inference and observability backgrounds. They discuss who owns agent infrastructure, treating agent workloads as untrusted, identity and brokered access, what to instrument, and where teams could start.

    30 min slot · Any Level · Panel

    AI agents and automationPlatform engineering and developer experienceSecurity, identity and policy

    Watch this if: your platform team is being asked to host agents and you want several views on security, identity and observability before you commit to a design.

    1. 7:01 A panelist speaking from the security side says recent kernel vulnerabilities suggest agent workloads should be considered adversarial, and expects sandboxing to stay a cat and mouse game.
    2. 13:04 The moderator says many projects now conform to OpenTelemetry and its GenAI semantics, and a panelist answers that new semantic conventions cannot be added on things that are still unstable.
    3. 17:29 A panelist says identity needs rethinking for agents, names SPIFFE and SPIRE as existing mechanisms, and says their complexity has kept them from being used everywhere.
    4. 20:39 A panelist describes brokering access: the agent gets an object capability for a specific action, such as reading a repository, instead of holding a token itself.
    5. 30:06 Asked where to start, a panelist recommends picking a pet project to learn how to work with agents hands-on.

    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    Evolution of Agentic Networking Stack in Envoy

    Boteng Yao, Yan Avlasov

    Two Envoy maintainers from Google describe what they are adding to Envoy for AI traffic: an AI protocol manager with its own filter chains, MCP support and a REST-to-MCP bridge. They also introduce Agent Router with a Python SDK and outline a roadmap that includes semantic routing and pluggable policy engines.

    10 min slot · Level not listed · Session

    Networking and connectivityAI agents and automation

    Watch this if: You run Envoy and want to hear from its maintainers what is being built into the proxy for LLM, MCP and agent traffic.

    1. 0:52 Yan Avlasov says Envoy has been integrated into continuous security scanning by frontier models.
    2. 3:40 Boteng Yao introduces an AI protocol manager with AI filter chains, which he describes as an "L8" layer for model extraction, schema validation, model routing, guardrail callouts and transcoding between providers.
    3. 6:26 He says Envoy is committed to tracking the latest MCP spec, including the move to stateless MCP, with routing by tool, spec validation, RBAC and ext_authz authorization, and a built-in bridge that exposes a REST API as an MCP server.
    4. 7:28 He introduces Agent Router and a new Python SDK that he says lets developers define model policies and failover without having to understand Envoy.
    5. 8:55 Yan Avlasov lists the roadmap for the next year: semantic routing, pluggable policy engines for agent governance, more model providers, advanced inference routing and hardening against frontier-model scans.

    Integrating Envoy AI Gateway and Kyverno Authz for Realtime Governance of LLM and MCP Traffic

    Jim Bugwadia, Deepak Goel

    Deepak Goel explains why enterprises put Agent Router, which he says was formerly called Envoy AI Gateway, between agents and their models and MCP tools, and Jim Bugwadia shows Kyverno Authz plugging into it through Envoy's external authorization protocol. In a live demo, Kyverno allows or blocks MCP tool calls by asking the Kubernetes API whether the calling user has the matching RBAC permission.

    25 min slot · Level not listed · Session

    Security, identity and policyNetworking and connectivityAI agents and automation

    Watch this if: You route LLM and MCP traffic through an Envoy-based gateway and want tool calls authorized against the Kubernetes RBAC you already have.

    1. 2:57 Deepak Goel says that once many agents, models, users and sessions are involved, enterprises need a layer between agent and model for routing, security, observability and token cost, which is what Agent Router provides.
    2. 8:51 Jim Bugwadia explains Envoy's two plugin protocols: external authz returns allow or deny on a request, while external processing also sees the response, which he says matters because an MCP server's reply can carry a prompt injection.
    3. 10:04 He says Agent Router already has JWT authentication, MCP session management, CEL checks and quotas, but not policy as code with reporting and exception management, which Kyverno adds.
    4. 15:56 In the demo, a tool call by user Alice against another team's namespace is blocked because Kyverno ran a Kubernetes SubjectAccessReview and RBAC denied it.
    5. 18:02 After he adds a role binding for Alice, the scale call that failed earlier goes through, and he then shows the policy report Kyverno generated for the blocked calls.

    The Emperor’s New Code: Your Developer Portal’s New Audience Is an Agent

    Erica Hughberg

    Erica Hughberg argues that coding agents need to be able to find and use a developer portal's platform capabilities without a human guide. She proposes comparing what services declare they intend to do with what they actually do at runtime when code ships without a full review.

    10 min slot · Any Level · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You maintain a developer portal and want agents to find the right platform capabilities without inventing their own.

    1. 1:58 Hughberg points out that teams wrote their golden paths, capability catalogs, and integration guides for humans, and asks them to treat coding agents as another audience.
    2. 3:48 She refers to the platform engineering community's work on platform capabilities and asks how teams can steer agent-assisted contributions back into shared tools instead of duplicating them.
    3. 6:47 She advises moving guidance out of chat-only channels and giving agents programmatic ways to find and invoke existing platform capabilities.
    4. 8:44 She proposes having production services declare what they intend to do, so runtime guardrails have something to compare with observed behavior when code was not fully reviewed.
    5. 9:14 She closes with questions teams can ask about their portals: can an agent read the guidance without a human guide, use the right capability, and make mistakes in a sandbox?

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.

    The Next Generation of Kyverno — Unified Policy as Code at Scale

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.
    3. 11:57 He describes a policy that intercepts Argo CD sync events and allows them only when a custom resource shows an approved change management window is open, with a precise denial reason otherwise.
    4. 13:34 He shares lessons learned: start in audit mode, treat the denial message as the user interface, make the paved path compliant by default and ship policy through the normal software lifecycle.
    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.
