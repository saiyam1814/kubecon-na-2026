    AI on Kubernetes Is Just a Pod With a GPU (and That's the Problem)

    Graziano Casto

    Graziano Casto compares deploying a web application with deploying a model on Kubernetes, starting from a plain Deployment that runs a vLLM container. He names three differences, which are whole-number GPU allocation, slow startup while model weights load, and requests that cost very different amounts of GPU work, and for each he points to projects he says address it.

    12 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You run web applications on Kubernetes and want a short orientation on what changes with model serving before choosing AI talks to watch.

    1. 0:36 The speaker shows what he calls the easiest way to deploy a model on Kubernetes: an ordinary Deployment running a vLLM container that serves a Llama 3.1 model.
    2. 3:01 He says a GPU is requested as a whole number, so a model that does not use a full GPU still leaves it overprovisioned.
    3. 3:43 He lists dynamic resource allocation in Kubernetes, HAMi for software-level enforcement and NVIDIA MIG for hardware partitioning as ways to share a GPU.
    4. 5:03 For slow startup he suggests relaxing liveness and readiness probes, caching downloaded weights on a persistent volume, and packaging weights as OCI artifacts mounted as image volumes.
    5. 6:57 He says round-robin load balancing does not fit chat workloads, and describes llm-d's KV-cache-aware routing, built on the Gateway API Inference Extension, as sending a conversation back to where its context lives.

    Cloud Native Infrastructure in the AI Era: A TAG Infrastructure Panel

    Xing Yang, Dylan Page, Mesut Oezdil, Alexa Griffith, Kashif Khan, Thomas Schuetz

    The co-chairs and tech leads of the CNCF TAG Infrastructure describe the group's current work, including white papers on infrastructure lifecycle, AI for science, AI inference and data storage for AI, and a new telco AI-native initiative. They then each name what they see as the biggest challenge AI workloads pose for cloud native infrastructure and take audience questions on agent sandbox projects and moving HPC sites toward cloud native tools.

    30 min slot · Level not listed · Panel

    Community and open source adoptionAccelerators and workload schedulingAI inference and serving

    Watch this if: you run or plan AI infrastructure and want to know what the CNCF TAG Infrastructure is writing about it and where you can contribute.

    1. 2:04 Dylan Page describes the infrastructure lifecycle white paper, which he says is meant to advise on managing mixed public cloud, private cloud, edge and bare metal environments, and Thomas Schuetz adds that it covers when operator-based deployment fits better than Terraform or OpenTofu.
    2. 5:13 Kashif Khan introduces the telco AI-native initiative, saying the challenge for AI-native network functions is the infrastructure beneath the model, and that the group is collecting shared definitions and gaps from operators and vendors.
    3. 10:03 Xing Yang summarizes the TAG's white paper on data storage for cloud native AI, saying training, inference and agents each have different storage patterns, so no single AI storage fits all.
    4. 11:40 Asked for the biggest challenge, Dylan Page answers that it is people, describing a collision of cloud native, telecom and HPC cultures, while other panelists name GPU utilization, placement and the speed at which infrastructure is needed.
    5. 19:00 Mesut Oezdil argues that GPUs must be sliced to be economical and that MIG and time slicing fall short in mixed-vendor environments, and points to HAMi, which he maintains, as a vendor-agnostic option.

    Deep Dive Into the DRA Driver for NVIDIA GPUs: What Works Today, What’s Coming and Why It Matters

    Shiva Krishna Merla, Varun Ramachandra Sekar US

    The two maintainers describe the current state of the NVIDIA DRA driver for GPUs, covering deployment, GPU sharing, health monitoring, KubeVirt passthrough, and compute domains. They show demos of GPUs switching between container and VM use and of a compute domain daemon set, and outline what they plan for the next release and how to migrate from the device plugin.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you allocate NVIDIA GPUs on Kubernetes and want the maintainers' view of what the DRA driver supports now and how to move off the device plugin.

    1. 6:51 The speaker describes system-mediated sharing planned for the next release, where pods in different namespaces each claim a share of a GPU using DRA consumable capacity.
    2. 8:01 The speaker says the driver watches GPU health events through NVML and publishes them as device taints, so the scheduler avoids those devices by default.
    3. 14:48 In a demo, the speaker starts four VMs and shows the node's GPUs moving from the NVIDIA driver to the VFIO driver for passthrough.
    4. 19:03 The speaker introduces a compute domain daemon set API that keeps IMEX daemons running before any workload is scheduled.
    5. 26:55 The speaker says existing device plugin requests for full GPUs and MIG devices can be translated to DRA resource claims, while time-sliced and MPS requests have no straightforward migration yet.

    Fixing GPU Time-Slicing on Kubernetes: Dynamic, Memory-Safe Sharing for AI Inference

    Julien Semaan

    The speaker shows a recorded demo in which a leaking workload on a time-sliced GPU causes an out-of-memory error in a neighboring LLM pod. He then combines KAI Scheduler fractions with HAMi-core memory enforcement and replays the scenario, where the misbehaving pod is the one that fails.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you share GPUs with time-slicing and want to see one way to stop a noisy neighbor from taking other pods' GPU memory.

    1. 1:40 The speaker explains that time-slicing with the NVIDIA device plugin makes the scheduler think there are more GPUs than physically exist.
    2. 5:43 In the first recorded demo, the speaker shows the CUDA out-of-memory error landing in an LLM pod rather than in the classifier that was leaking memory.
    3. 10:32 The speaker says a KAI Scheduler GPU fraction guides placement like a Kubernetes request and is not enforced at runtime.
    4. 12:57 The speaker describes HAMi-core as a library between the CUDA runtime and the driver that rejects allocations beyond the configured memory limit.
    5. 17:20 Replaying the scenario with KAI and HAMi-core, the speaker shows the misbehaving classifier pod hitting the error and restarting while both LLMs keep responding.

    Optimize Your Heterogeneous AI Cluster

    Mengxuan Li

    HAMi maintainer Mengxuan Li of Dynamia.ai explains the two problems the project targets, GPUs that can only be allocated whole and multi-GPU placements that ignore how cards are connected, and how HAMi's device plugin and HAMi-core enforce per-container memory limits to share a GPU. He then covers newer features (dynamic MIG, remote GPU access from nodes without GPUs, AMD support), a HAMi variant built on Dynamic Resource Allocation that works with other schedulers, and the roadmap.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you operate GPU clusters on Kubernetes and want to share GPUs among workloads or see how HAMi fits with Dynamic Resource Allocation.

    1. 3:05 Li describes HAMi's two basic functions: GPU slicing, so a workload can be given part of a GPU, and scheduling that accounts for how GPUs on a node are connected when several are requested.
    2. 8:48 He explains dynamic MIG: the user states only the device memory needed, and HAMi finds a matching MIG template and a GPU with enough consecutive free slots, creates the instance, and recycles it when the workload ends.
    3. 11:22 He introduces remote GPU in version 2.11, where a pod on a CPU-only node reaches a GPU on another node over TCP and sees it when running nvidia-smi.
    4. 15:31 He says HAMi DRA, a webhook plus driver on top of Dynamic Resource Allocation, converts device-plugin style resource requests into resource claims automatically and adds allocation metrics, at the cost of the topology-aware scheduling of the original HAMi.
    5. 21:16 Roadmap: scheduling by rack and super pod network topology, kernel-level isolation through cgroups and MPS alongside HAMi-core, and multi-client remote GPU with per-client limits.

    Scaling AI Model Distribution with Dragonfly: From HuggingFace to Production GPU Clusters

    Pavan Madduri

    Pavan Madduri, a Dragonfly contributor presenting alone because co-speaker Wenbo Qi could not travel, argues that pulling model weights of hundreds of gigabytes onto every GPU node at once is an infrastructure problem and explains how Dragonfly's peer-to-peer distribution and preheating address it. He then walks through the two pieces he says he contributed, the Hugging Face and ModelScope backends and the dragonfly-injector webhook, plus a cross-cloud pattern and the project roadmap.

    30 min slot · Level not listed · Session

    Data, storage and stateAI inference and serving

    Watch this if: large model downloads are slowing your GPU nodes or raising your egress bill and you want to see how Dragonfly handles it.

    1. 4:24 Pavan Madduri describes the thundering herd he sees with model weights: a scale-out sends 100 GPU nodes to the same registry at once, the origin saturates and downloads time out and retry.
    2. 10:04 He cites a test of a 130 GB model on 200 nodes where only the seed peer pulled from the origin, which he puts at about 99% less egress than 26 TB, and adds that the number depends on the setup.
    3. 13:01 He shows the Hugging Face and ModelScope backends: dfget with an hf scheme makes the seed peer fetch the model from the hub once and other nodes get the pieces from peers.
    4. 16:31 He explains the dragonfly-injector: a mutating admission webhook adds the Dragonfly client and daemon socket to pods carrying an inject annotation, so teams change Helm values instead of application code.
    5. 23:06 He lists the roadmap he took from version 2.6: a Python SDK after the Rust and Go ones, RDMA-based distribution between peers, and bandwidth negotiation across parent peers.

    The Latest in GPU, TPU, NIC and Other Device Support - WG Device Management

    John Belamaric, Morten Jæger Torkildsen

    Morten Torkildsen and John Belamaric of Google give the Device Management working group update, recapping why Dynamic Resource Allocation replaced the device plugin's opaque counters and what its four parts are. They cover the features that shipped in Kubernetes 1.37 and those planned for 1.38, go deeper on allocating CPU and memory through DRA and on its integration with workload-aware scheduling, and describe ecosystem adoption and next steps such as preemption and attaching GPUs to running pods.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you manage GPUs or other accelerators in Kubernetes and want to know which DRA features landed in 1.37 and what is planned next.

    1. 3:06 Morten Torkildsen outlines DRA's four parts: the resource slice API for describing devices, the resource claim API for requesting them, the scheduler matching the two, and the kubelet API that works with the DRA driver on the node.
    2. 6:11 He explains the extended resource request feature in 1.37, which lets cluster admins adopt DRA while workloads keep using device-plugin style requests that are matched to DRA devices underneath.
    3. 7:42 He describes device taints, which let a single failing GPU or TPU be tainted instead of the whole node, so workloads on the other devices are not disrupted.
    4. 11:52 John Belamaric explains node allocatable resources with DRA, which lets CPU and memory be selected through DRA so they can be aligned with the NIC and GPU, and tells the scheduler how to account for CPU requested in both the container spec and a resource claim.
    5. 16:30 He describes the DRA integration with workload-aware scheduling, where a resource claim attached to a pod group allocates a shared resource for a new replica and cleans it up when the replica scales down.

    Why Are You Still Wasting Whole GPUs? Hardware-Level Sharing, Scheduled with DRA

    Engin Diri

    Engin Diri of Pulumi recounts helping a European customer build a self-hosted inference platform, moving from whole GPUs and time slicing to NVIDIA MIG slices that pods request through Dynamic Resource Allocation. He shows a recorded demo of MIG profiles, resource slices and claims on an AWS node serving a model behind an inference gateway, and lists open questions such as quotas, models larger than a node and start-up ordering.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: you run inference on your own GPUs and want a practical walk through MIG slices requested with Dynamic Resource Allocation.

    1. 8:32 Diri says time slicing gives no memory or fault isolation between workloads, so the choice was between wasting GPUs and risking a noisy neighbor.
    2. 11:24 Diri says Dynamic Resource Allocation, which he dates to Kubernetes 1.34, lets a request describe device attributes instead of an integer count.
    3. 22:16 In the recorded demo, Diri lists the 1G, 2G and 4G MIG profiles on the node and the resource slices the DRA driver published.
    4. 24:28 Diri lists open day-two questions he is evaluating with the customer, including Kueue for MIG quota and which workload runs first.
    5. 28:06 Diri advises starting the DRA driver only after MIG is configured, because he ran into race conditions between the two.
