    Building Better Integration Test Images with Buildpacks

    Kathan Kashiparekh, Damini Satya

    Damini Satya and Kathan Kashiparekh of Salesforce describe how their integration testing platform team took over test image builds from service teams by adopting Cloud Native Buildpacks, replacing what they say were more than 6,000 Dockerfiles. They explain four buildpack concepts with examples from that work (buildpacks and builder images, layer caching, image extensions and rebase), show short demos, and close with when buildpacks fit and when Dockerfiles still do.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: your platform team maintains many similar Dockerfiles and you want to see how buildpacks centralize image builds and base image patching.

    1. 1:04 Damini Satya says service teams used to maintain a Dockerfile for every test repository, and that the platform team took over image builds with buildpacks and removed more than 6,000 Dockerfiles.
    2. 5:12 She walks through a minimal Python buildpack: a buildpack.toml manifest, a detect script that decides whether the buildpack applies, and a build script that creates a layer.
    3. 12:28 Kathan Kashiparekh contrasts Dockerfile caching, where changing one instruction invalidates everything after it, with buildpack layers that are isolated and marked for launch, build or cache.
    4. 16:06 He explains that buildpacks run as non-root and cannot install OS packages or pick a different run image, and that image extensions address this by generating a Dockerfile the lifecycle applies on top of the builder's images.
    5. 20:47 He describes rebase, which swaps a patched base image under unchanged layers with one pack rebase command instead of thousands of rebuilds, and says his team hopes to take it to production soon.

    Cloud Native: Built by Humans, Engineered to Evolve

    Jeffrey Sica

    Jeffrey Sica argues that cloud native can adapt to AI because the people who maintain its projects keep changing how they work without abandoning human review. He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    10 min slot · Level not listed · Keynote

    Community and open source adoptionKubernetes internals and runtimes

    Watch this if: you want to connect AI agent workloads to the reliability practices and contribution norms cloud native teams already use.

    1. 2:55 Sica asks the audience to see the people who keep showing up behind each logo in the cloud native landscape.
    2. 4:25 Sica says maintainers responded to AI-generated contributions by writing policies for what a good contribution looks like and what they expect the submitting human to review.
    3. 5:37 Sica uses the term agent speed for the number of machine actions between human decisions and argues that the change matters for software architecture.
    4. 6:30 Sica points to small blast radii, fast iteration and rollback, sandboxing, and APIs as reasons cloud native systems can adapt to agent workloads.
    5. 7:59 Sica argues that Kubernetes fits training and inference because they are distributed systems problems, not because Kubernetes was originally built for AI.

    Container Builds at Scale with Buildpacks

    Joe Kutner

    Joe Kutner of Salesforce presents Cloud Native Buildpacks as a way to turn source code into well-structured container images without a Dockerfile, and says the project graduated in the CNCF this past August. He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    1. 0:55 Joe Kutner says Cloud Native Buildpacks were created at Heroku about 12 years ago, joined the CNCF eight years ago and reached graduation this past August.
    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.
    3. 2:54 He says that with Dockerfiles a vulnerability in a shared base image means rebuilding every image, because of how linear layer caching works.
    4. 3:20 He explains rebase: because buildpacks know the boundary between OS and application layers, existing layers can be moved onto a new OS image without a build, which he says runs in milliseconds.
    5. 4:19 He says buildpacks can be run locally by installing the pack CLI and running pack build, choosing off-the-shelf buildpacks from Heroku, Google or Paketo, or writing your own.

    From Vibe to Live: Building for the Real World

    David Biel, Trey Caliva

    David Biel, who says he has no engineering background, and cloud security engineer Trey Caliva tell how David vibe-coded his family dental cabinet company's website and back-office tools and got them to production on managed services. Trey argues that the advice he gave in person should live in the AI's context as skills, hooks and MCP server permissions, so that platform teams can guide the many non-engineers he says are already building this way.

    30 min slot · Beginner · Session

    Platform engineering and developer experienceAI agents and automationDelivery, GitOps and release safety

    Watch this if: non-engineers in your company are shipping AI-built apps and you want ideas for guiding them.

    1. 2:22 David says he got the work done with a $200 Claude subscription, compared with the $5,000 to $10,000 his family was quoted for a website and brand about ten years earlier.
    2. 5:28 Trey says David's app runs on Firebase Hosting, Cloud Functions, Firestore and Firebase Auth, chosen so there are no servers to patch or clusters to run.
    3. 7:49 Trey lists what first-time builders may miss, such as open database rules, unauthenticated endpoints and pasting an API key into the chat.
    4. 10:16 Trey proposes putting guardrails in the AI's context through skills, hooks and MCP server access, with skills moving from ad hoc to a shared repo to a governed catalog.
    5. 13:47 Trey says skills advise and hooks enforce, showing a simplified hook that runs a script on each prompt to catch pasted secrets, plus deny rules that block deploying from a laptop.

Brandon Schoen explains how Heroku uses Kubernetes, Cloud Native Buildpacks, and OpenTelemetry to handle orchestration, base image updates, and observability for those builders.

    3 min slot · Level not listed · Keynote

    Platform engineering and developer experience

In an open discussion with the audience they talk about how to take part without being a chair or tech lead, how developers can find their way through the CNCF landscape, and where to find the meeting calendar and Slack channel.
