    10 Years, 10 Lessons

    Ram Iyengar

    Ram Iyengar of the Linux Foundation shares ten lessons from a decade around platform engineering, covering abstractions, definitions, metrics, costs, feedback and ownership. He argues that platform users are engineers who want to see inside the abstraction, and closes by saying developer experience is turning into agent experience.

    10 min slot · Any Level · Lightning Talk

    Platform engineering and developer experience

    Watch this if: you want an 11-minute list of one practitioner's platform lessons on abstractions, metrics, costs, feedback and ownership.

    1. 3:30 Iyengar says platform users are engineers who want to look inside an abstraction, and that handing one over to be used without examination creates friction with developer teams.
    2. 4:45 He says it is hard to agree on one definition of the platform, that it is more than a handful of tools put together, and that microservices got misread as letting every team pick any language.
    3. 7:01 On measurement, he asks whether time to first hello world or lead time for changes is the right metric, and whether 100% uptime counts as success if a database takes two days to get.
    4. 9:09 He calls feedback loops complaint boxes and suggests building a community instead: inner sourcing and growing platform advocates one team at a time.
    5. 10:15 He says developer experience has become agent experience, and closes with a bonus lesson 11: keep learning.

He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.

He shows kits being run and built with Docker's microVM-based sandbox runtime and takes audience questions on Kubernetes support, other runtimes and updating a kit's metadata.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    1. 4:54 Krogslund says a container is process isolation and not a security boundary, and that running a coding agent in a privileged container with access to the Docker socket gives it a route to the host machine.

    Extending the Immutable OS: Adding Tools to Flatcar with Systemd-Sysext

    Jan Bronicki

    Jan Bronicki, a Flatcar Container Linux maintainer, explains that an immutable OS has no package manager for adding software to the read-only /usr. He describes systemd-sysext as a signed, verifiable overlay on /usr for things like GPU drivers or Kubernetes binaries, and shows how it is declared in Butane.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: You run or are considering an immutable node OS and wonder how to add drivers or debugging tools to it.

    1. 0:46 Jan Bronicki says the core of an immutable OS, such as /usr, cannot be changed and is verifiable, meaning the kernel can check whether someone tampered with it.
    2. 1:19 He says package managers such as apt or dnf do not exist on such a system, which raises the question of how to get your software onto it.
    3. 1:48 He says systemd-sysext creates an overlay on top of /usr to add a particular runtime version, a GPU driver or anything else needed.
    4. 2:48 He says the key part is that a sysext is not a random blob of binaries: it plugs into the immutability and verification system, so tampering would not go unnoticed.
    5. 3:13 He shows a Butane config that declares which sysext version to fetch from where, says offline sources work, and says the binary is linked into /usr at boot.

    From Bytes to Traces: A Deep Dive into OpenTelemetry eBPF Instrumentation Internals

    Rafael Roquetto, Mike Dame

    Mike Dame walks through the user-space side of OpenTelemetry eBPF Instrumentation (OBI): how it discovers processes, enriches them with Kubernetes and container metadata, matches them against configured selectors and attaches eBPF programs. Rafael Roquetto then follows one HTTP request from bytes on the TCP receive path through eBPF maps and a ring buffer into a request span that is enriched and exported as OpenTelemetry traces and metrics.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you want to debug, extend or contribute to OpenTelemetry eBPF Instrumentation and need to know how it works internally.

    1. 1:50 Dame says a stated intent such as observing the checkout service has to be resolved to PIDs, and that everything in OBI works by PIDs.
    2. 7:39 Dame explains that OBI attaches a syscall probe to the bind function as a lazy signal that ports changed, instead of constantly scanning every process's ports.
    3. 14:52 Roquetto describes OBI hooking the TCP receive path and reading bytes into a small buffer along with the PID and connection information.
    4. 18:54 Roquetto says the completed HTTP info struct is shipped to user space through an eBPF ring buffer, where another enrichment pipeline starts.
    5. 22:41 Roquetto says the same request span structure feeds OpenTelemetry spans, span metrics, service graph metrics and RED metrics.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
