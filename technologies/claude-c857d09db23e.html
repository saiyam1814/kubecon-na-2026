    Yuke Ning

    Yuke Ning walks through how Higress handles hosted model routing, traffic to self-hosted inference, and requests from agents to tools. He discusses where fallback stops working, how an endpoint picker participates in routing, and how the gateway bridges MCP transports.

    30 min slot · Level not listed · Session

    AI inference and servingNetworking and connectivity

    Watch this if: you run a gateway that must handle hosted models, your own inference workloads, and MCP tools.

    1. 5:11 Ning shows a Higress route configured to try a backup model provider after selected error responses.
    2. 7:47 He points out that status-based fallback cannot redirect a response once a successful stream has already started.
    3. 9:56 He walks through the Gateway API Inference Extension ownership model, in which application teams own routes and serving teams own the inference pools those routes target.
    4. 18:10 He contrasts rejecting the request if an external endpoint picker fails with allowing the gateway to choose an endpoint another way.
    5. 22:26 He describes three MCP roles for the gateway: exposing REST APIs as tools, proxying existing MCP servers, and bridging differences between clients and servers.

    Dashboards-as-Code: Easy to Ship, Easy to Get Wrong

    Cecil Wöbker

    Cecil Wöbker describes how remberg moved from hand-written Grafana dashboards to scripts in CI that generate per-team dashboards, loaded into the cluster by the Grafana sidecar. He lists the mistakes his engineers ran into, including kube-state-metrics label allow lists, series that change across pod restarts and JSON that Grafana ignores.

    5 min slot · Beginner · Lightning Talk

    Delivery, GitOps and release safetyObservability and reliability

    Watch this if: you want engineers to ship their own dashboards as code and avoid common mistakes.

    1. 0:58 Cecil Wöbker says remberg's two hand-written Grafana dashboards were painful to keep current, so they were broken about half the time.
    2. 1:56 He describes scripts in CI/CD, often written with AI, that generate individual dashboards for each team based on the services it owns.
    3. 2:38 He explains the deployment: CI commits the script output, a labeled ConfigMap marks it as a dashboard, and the Grafana sidecar loads it automatically.
    4. 3:30 His first caveat: kube-state-metrics does not export all labels by default, so labels used for joins or filters must be on its allow list.
    5. 4:37 He warns that valid JSON is not always valid for Grafana and that AI tends to add fields from outdated docs, so dashboards still need checking.

    Free Tokens for Everyone

    William Morgan

    William Morgan says running open-weight models on Kubernetes shifts inference costs from buying tokens to operating GPU capacity. He presents Kinference as a layer for defining tenant policy, tracking usage, and routing requests to local or external backends.

    30 min slot · Beginner · Session

    AI inference and serving

    Watch this if: You run a Kubernetes platform and need to share inference capacity across teams without giving up visibility or control.

    1. 12:01 Morgan explains that choosing an open-weight model variant depends on available memory, context length, and expected concurrency, not just the model family.
    2. 14:39 Morgan frames shared GPU inference as a platform problem: teams want self-service and different levels of service while operators must keep finite capacity reliable.
    3. 18:12 Morgan describes putting a traffic enforcement gateway in front of model servers to handle multiple models and tenants with explicit policy.
    4. 21:01 Morgan says the gateway can export Prometheus-compatible metrics for existing dashboards and break out performance by model and tenant.
    5. 23:47 Morgan walks through policies that can choose a model, reject a request, or send it to an external provider using prompt, GPU, and tenant signals.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.

    The Seams Are the Trap: Agent Fleets from CNCF Parts You Already Have

    Aleksander Slominski, Mariusz Sabath

    The presenters describe assembling an event-driven agent fleet from Kubernetes, KEDA, Kafka, and signed CloudEvents instead of buying an agent platform. They explain the limits of tying identity to a pod and show a recorded demo in which a worker rejects an unsigned event.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to reuse a Kafka and Kubernetes stack for agent workers and verify who sent their tasks.

    1. 3:09 The speaker describes using CloudEvents as a standard envelope so producers do not have to invent their own event types, identifiers, and payload structure.
    2. 4:29 The speaker says KEDA uses Kafka lag to decide when to bring up workers and can scale them back to zero when no events remain.
    3. 10:11 The speaker explains that the runner checks a signed event's origin and whether the agent may consume it, while Kafka preserves the event sequence for audit.
    4. 11:04 The speaker says SPIFFE and SPIRE can identify a workload, but asks how that identity should change when an agent loads new skills or plugins.
    5. 23:36 The speaker shows the recorded audit check and an agent rejecting an unsigned event that was sent directly to Kafka.
