    Container Builds at Scale with Buildpacks

    Joe Kutner

    Joe Kutner of Salesforce presents Cloud Native Buildpacks as a way to turn source code into well-structured container images without a Dockerfile, and says the project graduated in the CNCF this past August. He explains how rebase swaps the operating system layers under existing images without running a build, then shows how to try buildpacks locally with the pack CLI.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: You maintain many Dockerfiles and want to know how buildpacks handle base image updates across a large fleet.

    1. 0:55 Joe Kutner says Cloud Native Buildpacks were created at Heroku about 12 years ago, joined the CNCF eight years ago and reached graduation this past August.
    2. 1:17 He describes buildpacks as a tool that turns application source code into a container image without a Dockerfile, with layers that map logically to application components.
    3. 2:54 He says that with Dockerfiles a vulnerability in a shared base image means rebuilding every image, because of how linear layer caching works.
    4. 3:20 He explains rebase: because buildpacks know the boundary between OS and application layers, existing layers can be moved onto a new OS image without a build, which he says runs in milliseconds.
    5. 4:19 He says buildpacks can be run locally by installing the pack CLI and running pack build, choosing off-the-shelf buildpacks from Heroku, Google or Paketo, or writing your own.

    Extending Envoy for Secure, Scalable Connectivity

    Basundhara Chakrabarty, Hong Sng

    Two Databricks engineers describe using Envoy with Rust dynamic modules to route to and isolate a large, churning fleet of per-tenant microVMs that run AI apps. They say one custom cluster replaced a cluster per workload at the regional ingress, and that a multi-tenant Envoy on each node mediates all ingress and egress for the sandboxes.

    10 min slot · Level not listed · Session

    Networking and connectivitySecurity, identity and policy

    Watch this if: You need Envoy to route to very large numbers of short-lived, per-tenant workloads and are considering Rust dynamic modules.

    1. 1:38 Basundhara Chakrabarty describes two Envoy layers: a regional ingress Envoy where scale is the concern, and a single multi-tenant Envoy per data plane node where tenant isolation and policy enforcement are the concern.
    2. 2:24 She says a route and cluster per microVM does not scale, because each churn event triggers CDS updates that are expensive on Envoy's single main thread.
    3. 3:07 She describes the alternative: one custom dynamic module cluster written in Rust that gets endpoint snapshots over EDS and runs a chain of pluggable load balancers.
    4. 4:38 She says moving service discovery work off Envoy's main thread into the Tokio runtime was probably the single biggest win for reaching millions of workloads per region.
    5. 7:01 Hong Sng says the same dynamic modules run in a separate filter chain per tenant, each with its own connection pool and cryptographic identity, which he says let a couple of engineers move from single-tenant to multi-tenant in months.

    AI agents and automationDelivery, GitOps and release safety

    Watch this if: You are designing an internal coding-agent platform and want examples of recoverable sessions, realistic testing, and human review.

    2. 5:34 Bowman explains how a separate disk-backed workspace for each session lets the team resume its work after a pod dies.
    3. 16:58 Bowman describes replacing separate staging stacks with shared team namespaces and using mirrord to route test traffic to a specific service preview.

    Linkerd, The Service Mesh for Everyone: gRPC Load Balancing & More

    Joe Fuller

    Joe Fuller of Buoyant explains why gRPC over a single HTTP/2 connection defeats connection-level load balancing on Kubernetes and presents a benchmark he says Buoyant ran comparing Linkerd with Istio and Cilium. He then covers what Linkerd 2.20 adds, mainly rate-limit-aware load balancing and a new circuit breaking mode, both alpha and opt-in, and what has shipped in edge releases for 2.21.

    30 min slot · Level not listed · Session

    Networking and connectivity

    Watch this if: you run gRPC services on Kubernetes and want to understand per-request load balancing, or you are deciding whether to turn on the new Linkerd 2.20 overload features.

    1. 4:21 Joe Fuller explains the gRPC problem: a client opens one HTTP/2 connection, every request lands on one pod, and scaling up does not help because new pods get none of the existing connections.
    2. 6:58 He describes a benchmark he says Buoyant's engineers ran on EKS against Istio in ambient and sidecar mode and Cilium in L7 mode, and reports Linkerd at about 92% of no-mesh throughput.
    3. 10:51 He describes the failure mode 2.20 targets: an overloaded pod that rejects requests quickly with 429 or RESOURCE_EXHAUSTED looks like the fastest endpoint to a latency-based balancer and gets more traffic.
    4. 12:11 He explains rate-limit-aware load balancing: the client proxy records a penalty of five seconds by default, or the server's back-off hint, instead of the fast rejection, so traffic shifts away and then returns as the penalty decays.
    5. 20:06 He says the destination controller no longer keeps a per-subscriber endpoint snapshot, which he says cut control plane memory by about 84% in load tests, and that native sidecars are GA and on by default.

    The Next Generation of Kyverno — Unified Policy as Code at Scale

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.
    3. 11:57 He describes a policy that intercepts Argo CD sync events and allows them only when a custom resource shows an approved change management window is open, with a precise denial reason otherwise.
    4. 13:34 He shares lessons learned: start in audit mode, treat the denial message as the user interface, make the paved path compliant by default and ship policy through the normal software lifecycle.
    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.
