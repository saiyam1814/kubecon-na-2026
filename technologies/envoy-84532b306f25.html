    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You plan to put LLM inference behind Istio ambient mesh and care about cache-aware routing and per-team token tracking.

    Adarsh Kumar

    The speaker recounts debugging recurring CPU spikes in Istio sidecars that kept pushing autoscalers to their maximum without any rise in traffic. He says the cause was configuration pushes triggered by churn in an unrelated namespace, and that limiting what each sidecar can see removed the spikes and lowered sidecar memory use.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You run Istio sidecars at scale and see unexplained proxy CPU spikes or heavy configuration pushes.

    1. 2:45 The speaker says the problem began with alerts that Horizontal Pod Autoscalers had hit their maximum even though traffic had not grown.
    2. 3:14 He says the sidecar containers showed a repeating spiky CPU pattern, and telemetry showed a large number of xDS pushes with no obvious cause.
    3. 4:32 He inspects what a proxy knows with istioctl proxy-config on a recreated Bookinfo setup and finds a noisy worker from another namespace in the cluster list.
    4. 5:23 He explains that background workers on spot VMs were preempted often, so new pod IPs kept triggering endpoint pushes to every sidecar.
    5. 6:36 He applies a Sidecar resource that limits visibility to the same namespace and shows the unrelated clusters gone, which he says ended the CPU spikes and cut sidecar memory.

    The Sidecar-to-Ambient Migration Nobody Warned Us About (AI Edition)

    Fabrizio Sgura

    The speaker argues that moving AI inference workloads from Istio sidecars to ambient mesh moves complexity to the node level instead of removing it. He recommends settling connection behavior and observability first, and testing with real inference traffic before migrating.

    Length not listed · Level not listed · Type not listed

    Unclassified

    Watch this if: You run AI inference on Istio sidecars and are weighing a move to ambient mesh.

    1. 0:54 The speaker explains that ambient moves layer 4 proxying to ztunnel at the node level and adds waypoint proxies for layer 7.
    2. 1:33 He says inference differs from ordinary web services because GPU nodes are expensive and requests are persistent HTTP/2 streaming connections.
    3. 3:06 He says long-lived inference connections must be tested against pod restarts, node drains and ztunnel restarts.
    4. 3:52 He says telemetry changes because ztunnel gives TCP metrics while HTTP metrics and tracing depend on waypoints, and reporter labels change, so dashboards may need adjusting.
    5. 4:49 He says that if he started again he would decide connection policy and observability first, and warns against upgrading the node-level proxy blindly while long-running workloads are active.

    Niranjan Shankar

    Niranjan Shankar describes how the Azure Kubernetes Service team opened limited escape hatches for enterprise customers and what happened when support ownership was unclear. He uses packet loss at the boundary between a self-managed network plugin and a managed service mesh to show why teams need to name who owns the risk.

    25 min slot · Any Level · Session

    Platform engineering and developer experienceSecurity, identity and policy

    Watch this if: You need to give advanced platform users more control without leaving production support ownership ambiguous.

    1. 4:38 Shankar introduces the 'Allowed but Unsupported' tier and uses Istio to show how a team can allow a few EnvoyFilter uses, support routine MeshConfig fields, and block higher-risk settings.
    2. 11:39 He uses packet loss with a self-managed CNI and a provider-managed service mesh to explain why the boundary between supported and unsupported parts is hard to diagnose during an incident.
    3. 13:12 He recalls customers having trouble migrating from self-managed Prometheus to the managed offering because it did not support a rule resource they used.
    4. 20:35 He recommends giving unsupported features a signpost: a way to get best-effort help, an internal owner for production risk, and a path back to a supported option.
    5. 23:08 He closes with criteria for deciding what to expose, including whether teams can isolate the security risk, find an owner, or offer a narrower subset instead of the entire API.
