    If It's Shared, It's Vulnerable: Is Kubernetes the Right Platform for Confidential Compute?

    Zvonko Kaiser

    The speaker argues that attestation proves a confidential workload's state but not who shares the node, silicon and Kubernetes control plane beneath it. He walks through published attacks on shared layers and concludes that confidential workloads need one node and one control plane per tenant.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: You run or plan confidential workloads on shared Kubernetes clusters and want to know what attestation does and does not cover.

    1. 3:35 The speaker says attestation proves a workload runs on a specific node in a specific cluster, but not who else shares that node.
    2. 5:32 The speaker describes two substrates shared by every tenant on a node, the Kubernetes control plane and the silicon, and says he counted 39 named attacks on these layers since 2023.
    3. 6:34 The speaker describes an attack he calls TDXRay, in which he says one VM reconstructed another VM's prompt from shared cache metadata without breaking encryption.
    4. 9:54 The speaker says one tenant per node still shares etcd, CNI and CSI, and that Kubernetes was never built to protect tenants from each other.
    5. 13:52 The speaker sums up his position as one node, one control plane, one tenant, with the workload owner owning the whole stack.

    KubeVirt's Architectural Leap: Pluggability, AI Hardware, and Maturing Governance

    Vladik Romanovsky, Itamar Holder

    KubeVirt maintainers Vladik Romanovsky and Itamar Holder mark the project's tenth year and its CNCF graduation by reviewing its pod-based architecture, its adoption of an enhancement proposal process, and this year's work on confidential VMs, NVIDIA hardware support and Dynamic Resource Allocation. Holder then explains the plugin framework from enhancement proposal 190, which is meant to let features be built out of tree, along with early work on supporting hypervisors beyond QEMU/KVM and the idea of using KubeVirt as an isolation backend for agent sandboxes.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run or extend KubeVirt and want to know how the plugin framework will replace sidecar hooks.

    1. 1:02 Vladik Romanovsky recalls early doubts about the project and explains the choice to tie a virtual machine's life cycle to a pod and run the virtualization stack inside it, which he says let KubeVirt reuse the Kubernetes security model, CNI, CSI and device plugins.
    2. 6:48 He says the last cycle had more than 100 open enhancement proposals, and that the project built a per-release tracker plus an AI agent that gathers related pull requests and estimates how likely each piece of work is to land by the freeze.
    3. 9:23 He describes building support for NVIDIA's newest hardware in a fork with Red Hat and NVIDIA engineers before bringing it back upstream, keeping the virt-launcher unprivileged by moving privileged operations into a device plugin.
    4. 14:39 Itamar Holder lists drawbacks of the existing sidecar hook: it edits the libvirt domain XML as a raw string, has no node access, and can only be enabled for everyone through one feature gate.
    5. 16:44 He walks through the new plugin model's three levels: a CEL expression that mutates the domain XML, a sidecar that works on a structured libvirt object with new pre-boot and pre-migration hooks, and node hooks answered by a plugin author's own DaemonSet.

    Legacy-Free, Zero-Maintenance Bare Metal Kubernetes Clusters With RISC-V and Immutable Linux

    Felicitas Pojtinger

    Felicitas Pojtinger of LiveKit argues that operators should be able to own every layer of their stack, and builds one on a SpacemiT K3 RISC-V board from open firmware up to a K3s cluster. Recorded demos show an AI agent flashing and debugging the board through a hardware harness, signed image updates with systemd-sysupdate, TPM-backed remote attestation and an attested process migration between nodes.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimes

    Watch this if: you want to see how far a fully open bare-metal stack on RISC-V can go, from firmware and signed images to attestation and a running cluster.

    1. 1:45 Pojtinger says x86 and Arm carry expensive licences and firmware blobs that cannot be inspected or replaced, which is her reason for building on RISC-V.
    2. 12:31 A recorded demo shows solenoids pressing the board's buttons to enter flash mode while an MCP server flashes the images, so an agent can then check the result over KVM, UART and JTAG.
    3. 18:48 She explains choosing systemd-sysupdate over bootc, with signed system and configuration extensions overlaid on an immutable /usr.
    4. 22:35 She describes measuring every boot stage into TPM platform configuration registers so the booted image can be compared with predicted values.
    5. 28:12 In a recorded demo she enables a signed K3s system extension on the board and runs Valkey, then shows the system refusing a tampered extension.

    Lima as the Universal AI Sandbox

    Akihiro Suda

    Akihiro Suda of NTT presents Lima as a virtual machine sandbox for AI coding agents, arguing that agents' built-in sandboxes are weaker than VMs and citing reports of agents deleting home directories, installing hallucinated packages and being prompt-injected. He covers the project's history and adopters, the two ways to pair agents with Lima (agent inside the VM, or outside it through Lima's MCP server), a demo of the sync mode that asks before writing changes back to the host, and the features added in versions 2.0 through 2.3.

    30 min slot · Level not listed · Session

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run AI coding agents on your laptop and want to confine them to a virtual machine.

    1. 2:08 Suda says the sandboxes built into AI agents, such as Landlock on Linux and sandbox-exec on macOS, are not as strong as virtual machines, and that with Lima any damage stays inside the VM or the files mounted into it.
    2. 12:36 He lays out two options: run the agent, and optionally GPU-accelerated inference, inside the VM, or keep the agent outside and connect it to Lima through its MCP server.
    3. 13:37 He describes sync mode as an alternative to mounting, in which synced directories are written back to the host only after the user confirms.
    4. 14:40 Demo: he runs OpenCode inside a Lima VM against a model running in the VM, has it edit a file, and on exit is asked whether to accept the changes, declining to sync them back.
    5. 20:21 He lists what version 2.3 adds, including a native Windows driver based on the Host Compute System, real IP networking on Linux hosts, hiding secrets from agents with an ignore file, and blocking guest access to the host's loopback.

    Plug and Play Volumes, hold the Pod

    Piotr Prokop PL, Sreeja Varnam

    The speakers explain why NVIDIA bypasses KubeVirt's attachment pod to hotplug storage for cloud gaming sessions. They present a proposal to make volume delivery pluggable while keeping the default attachment path intact.

    20 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: You need to hotplug storage into running KubeVirt VMs without the cost of an attachment pod.

    1. 0:30 The first speaker says GeForce NOW needs to expose storage to an application inside a running VM in under seven seconds and clean up automatically when something fails.
    2. 1:57 The first speaker walks through the default attachment pod and explains why scheduling and networking that pod adds work even when it only delivers a volume.
    3. 4:11 The first speaker reports that their direct path to the storage provider brought hotplug below four seconds in their tests, compared with eight to nine seconds and sometimes twenty before.
    4. 6:43 The second speaker introduces VEP-293, which proposes separating delivery, attach, and detach so an integration can replace one stage without changing the default behavior.
    5. 12:59 The second speaker describes node-local discovery: the provider publishes a file or block device, and KubeVirt handles the guest attachment instead of making the provider duplicate it.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
