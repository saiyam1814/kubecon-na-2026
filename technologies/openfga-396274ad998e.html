    One Platform for AuthN and AuthZ: Keycloak Meets AuthZEN

    Yoshiyuki Tabata

    Yoshiyuki Tabata splits authorization into delegation and access control, explains that the OpenID AuthZEN standard defines the interface between a policy enforcement point and a policy decision point, and describes Keycloak's experimental AuthZEN support. He then demonstrates an MCP setup in which Envoy enforces decisions it requests from Keycloak, which acts as both the OAuth authorization server and the decision point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Keycloak and want to see how it can also make fine-grained authorization decisions for MCP tools through the AuthZEN API.

    1. 2:20 Tabata separates authorization into two phases: delegation, where one party grants limited authority as in OAuth, and access control, where a gatekeeper decides on each request, and says good authorization needs both.
    2. 6:36 He explains that AuthZEN standardizes the interface between the policy enforcement point and the policy decision point, so the enforcement point does not depend on a product-specific API.
    3. 10:35 He says Keycloak has experimental support for the AuthZEN Authorization API 1.0 starting with version 26.7, exposing the evaluation and evaluations APIs so it can act as a decision point.
    4. 13:55 He introduces the demo architecture: MCP Inspector as the client, Envoy in front of the MCP server as the enforcement point, and Keycloak as both OAuth authorization server and AuthZEN decision point.
    5. 25:41 In the demo he assigns a role to the user in Keycloak and the previously denied delete tool call succeeds with the same access token, which he uses to show that no separate synchronization with a decision point is needed.

    OpenFGA: Fine-Grained Authorization for Apps, APIs, and Agents

    Will Vedder

    OpenFGA maintainer Will Vedder introduces OpenFGA as a centralized, Zanzibar-inspired authorization decision engine and explains its authorization models, tuples, check and list APIs, and CEL-based conditions through a running example of whether a user or the user's agent may deploy a service. He then presents dynamic conditions, which he describes as a new feature that attaches CEL expressions to tuples so per-task agent rules need no model change, with an MCP gateway as the enforcement point.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing or building an authorization system and want an introduction to OpenFGA's model, plus its approach to scoping what an agent may do on a user's behalf.

    1. 4:54 Will Vedder compares RBAC, ABAC and ReBAC, saying relationship-based access control expresses inheritance and reverse lookups natively but requires writing or backfilling the relationships.
    2. 12:35 He says an OpenFGA check is a graph reachability problem: John may deploy the payments API because a chain of tuples links him through the SRE team and the checkout project to that service.
    3. 15:26 He describes conditions as OpenFGA's ABAC feature, written as CEL expressions and used for cases such as expiring grants, usage-based entitlements and IP allow lists.
    4. 17:40 He says the pattern they see most for authorizing AI agents is an MCP gateway that consults OpenFGA before forwarding a tool call.
    5. 20:57 He introduces dynamic conditions, where a CEL expression such as environment not equal to prod is stored on the tuple and evaluated at query time, so a new per-agent rule needs no model change.

    What Can Your AI Agents Actually Do? Cedar Analysis for MCP Servers

    Lucas Käldström, Chris Burns

    Lucas Käldström and Chris Burns discuss putting authorization decisions for MCP servers in a policy engine so the rules can be analyzed separately from the application. They demonstrate how Cedar Woodpecker can flag combinations of permissions and help check a policy revision.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you operate MCP servers and want to reason about what permissions an agent can combine.

    1. 5:56 The speakers distinguish the component that enforces an authorization decision from the external policy engine that makes it.
    2. 15:04 They explain static analysis with a question about two policies: would they make the same decision for any user and request?
    3. 19:45 Käldström introduces Cedar Woodpecker, a tool for analyzing permissions expressed in Cedar.
    4. 22:26 Burns shows a local kind cluster running ToolHive and two MCP servers as the setting for the policy demo.
    5. 26:47 They rerun the policy analysis after tightening access and report that the unwanted permission combination is ruled out under the modeled assumptions.
