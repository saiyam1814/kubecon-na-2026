He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    David Justice, Roaa Sakr

    If It's Shared, It's Vulnerable: Is Kubernetes the Right Platform for Confidential Compute?

    Zvonko Kaiser

    The speaker argues that attestation proves a confidential workload's state but not who shares the node, silicon and Kubernetes control plane beneath it. He walks through published attacks on shared layers and concludes that confidential workloads need one node and one control plane per tenant.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: You run or plan confidential workloads on shared Kubernetes clusters and want to know what attestation does and does not cover.

    1. 3:35 The speaker says attestation proves a workload runs on a specific node in a specific cluster, but not who else shares that node.
    2. 5:32 The speaker describes two substrates shared by every tenant on a node, the Kubernetes control plane and the silicon, and says he counted 39 named attacks on these layers since 2023.
    3. 6:34 The speaker describes an attack he calls TDXRay, in which he says one VM reconstructed another VM's prompt from shared cache metadata without breaking encryption.
    4. 9:54 The speaker says one tenant per node still shares etcd, CNI and CSI, and that Kubernetes was never built to protect tenants from each other.
    5. 13:52 The speaker sums up his position as one node, one control plane, one tenant, with the workload owner owning the whole stack.

    Lessons Learned Sandboxing Agents with kagent

    Peter Jausovec, Nina Polshakova, Eitan Yarmush

    Peter Jausovec and Eitan Yarmush of Solo.io, the two speakers heard in the recording, walk through the sandboxing approaches they tried for kagent and say each one still kept an idle agent's pod running or tied identity to the pod. They explain why kagent 1.0 was rebuilt on Agent Substrate, list five lessons from that work, and demo Claude Managed Agents sessions running in sandboxes on their own cluster.

    30 min slot · Any Level · Session

    Security, identity and policyAI agents and automation

    Watch this if: you are choosing how to sandbox AI agents on Kubernetes and want to hear what one team found lacking in pod-per-agent setups.

    1. 3:40 Jausovec says they tried four things before Agent Substrate: their own pod-per-agent runtime, Anthropic's Sandbox Runtime, Agent Sandbox and NVIDIA's OpenShell, and that each solved only part of the problem.
    2. 9:08 Jausovec gives the reasons for Agent Substrate: idle agents are snapshotted to object storage and hold no compute, the Kubernetes API is off the hot path, restores take milliseconds, and actors are sandboxed with default-deny networking.
    3. 10:04 Yarmush tells how Solo started building an internal sandbox layer called Moat, then joined Google's Agent Substrate work instead, and says kagent 1.0 is now based entirely on Agent Substrate.
    4. 17:42 Yarmush starts the takeaways: isolation is table stakes and pause and resume is the hard part, every control must sit outside the agent, identity follows the actor, a suspended agent is stored data, and the sandbox runtime becomes a data format.
    5. 22:56 Demo: Jausovec creates two Claude Managed Agents sessions whose sandboxes run on his cluster, shows that one session cannot read the other's file, and shows a blocked request succeed after he applies an egress policy.

    Managing Network Security in Multi-Tenant Environments with Istio and Cilium

    Michael Bolot, Zaira Shaikh

    Michael Bolot and Zaira Shaikh of GEICO describe replacing a mix of cloud firewalls, on-premises firewalls and in-cluster policies with one API that configures Istio and Cilium across clusters on a flat, routable pod IP space. They explain how SPIRE identities and Istio authorization policies decide which applications may talk, while a small set of Cilium policies blocks what bypasses the sidecar, and they close with tips for writing Cilium policies safely.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you run Cilium and Istio together and want to hear how one platform team splits network policy duties between them.

    1. 1:44 Bolot lists the problems with the legacy setup: no unified definition of the policy affecting a device, manual configuration, inconsistent enforcement and a complex network topology.
    2. 7:03 Shaikh describes the new system: pods are restricted by Istio resources and network policies written by a data plane agent on every workload cluster, configured from a central API server, with Cilium's BGP features advertising all pod IPs.
    3. 15:03 Bolot says SPIRE handles authentication by issuing workloads a certificate after attestation, and Istio authorization policies state what a given SPIFFE ID may reach, with service entries and workload entries connecting clusters.
    4. 19:55 Bolot gives three reasons they do not use Cilium for everything: they want authorization based on SPIFFE IDs, user-chosen labels would exhaust Cilium's identity map, and Cilium's layer 7 Envoy would duplicate the one Istio already runs.
    5. 25:29 Shaikh shares tips for Cilium policies, including using audit mode and Hubble, minding the default enforcement mode, and never cutting the operator or etcd off from the API server.

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.
