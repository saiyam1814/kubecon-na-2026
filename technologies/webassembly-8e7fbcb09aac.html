    Breaking up Is Hard, but the Future Is with Helm 4

    Matt Farina, Joe Julian

    Helm maintainers Matt Farina and Joe Julian argue that users and tools built on the Helm SDK should move off Helm 3 before its security releases end, and explain that the SDK needed breaking changes that eight years of API compatibility guarantees had blocked. They walk through what changed in Helm 4, including WebAssembly plugins, server-side apply by default for new releases, kstatus-based status, chart digests, content-based caching and renamed flags, then give a step-by-step upgrade path and take questions.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you still run Helm 3 or maintain a tool that imports the Helm SDK and need to know what changes in Helm 4.

    1. 1:01 Matt Farina says his download statistics show about 16% of usage is still on Helm 3 and that about a quarter of the largest maintained tools importing the Helm SDK still use the Helm 3 SDK.
    2. 6:41 Joe Julian gives the Helm 3 timeline: limited, mostly security-only releases since September 9, with security updates ending February 10.
    3. 8:46 Farina describes WebAssembly plugins in Helm 4, which he says bring sandboxing, remove the need for install scripts that download per-platform binaries, and let plugins be written in any language that compiles to Wasm.
    4. 11:53 He explains that a release first installed with Helm 4 defaults to server-side apply, while a release installed with Helm 3 keeps client-side apply until the user opts in with a flag.
    5. 18:08 Julian lists upgrade steps: test representative charts and releases, run CI/CD commands, check plugins and post-renderers, verify registry logins and OCI installs, then roll out the Helm 4 binary.

    Engineering High-Performance Telemetry Pipelines: Lessons from Fluent Bit

    Eduardo Silva

    Eduardo Silva, creator and maintainer of Fluent Bit, walks through how a telemetry pipeline is built and what changed in the 5.2 release, including a new Lua scripting interface for logs, metrics and traces and a WebAssembly build that runs in the browser. He then describes the performance work behind the release, which he says came from profiling with perf, removing repeated encoding steps, pre-allocating memory and batching.

    30 min slot · Level not listed · Session

    Observability and reliability

    Watch this if: you run or build telemetry collectors and want to hear how the Fluent Bit maintainer profiles and removes CPU and memory overhead.

    1. 7:39 Silva introduces a new Lua scripting interface he calls FTS, which he says adds primitives for metrics and traces as well as logs, something scripts could not work with before.
    2. 11:13 He announces Fluent Bit Studio, an experimental web interface that he says runs Fluent Bit as WebAssembly in the browser so a configuration can be tried before it reaches production.
    3. 15:04 He describes letting an AI coding agent run perf against the code and collect results over repeated runs, and says Fluent Bit ships a benchmark skill others can copy.
    4. 18:13 He explains a fast path that decodes OTLP straight into the internal record format and encodes to MessagePack once, instead of encoding twice as before.
    5. 25:44 He compares Fluent Bit 5.2 with 5.1 and the OpenTelemetry Collector on OTLP processing and says the process of measuring mattered more than any single change.

    Evolution of Agentic Networking Stack in Envoy

    Boteng Yao, Yan Avlasov

    Two Envoy maintainers from Google describe what they are adding to Envoy for AI traffic: an AI protocol manager with its own filter chains, MCP support and a REST-to-MCP bridge. They also introduce Agent Router with a Python SDK and outline a roadmap that includes semantic routing and pluggable policy engines.

    10 min slot · Level not listed · Session

    Networking and connectivityAI agents and automation

    Watch this if: You run Envoy and want to hear from its maintainers what is being built into the proxy for LLM, MCP and agent traffic.

    1. 0:52 Yan Avlasov says Envoy has been integrated into continuous security scanning by frontier models.
    2. 3:40 Boteng Yao introduces an AI protocol manager with AI filter chains, which he describes as an "L8" layer for model extraction, schema validation, model routing, guardrail callouts and transcoding between providers.
    3. 6:26 He says Envoy is committed to tracking the latest MCP spec, including the move to stateless MCP, with routing by tool, spec validation, RBAC and ext_authz authorization, and a built-in bridge that exposes a REST API as an MCP server.
    4. 7:28 He introduces Agent Router and a new Python SDK that he says lets developers define model policies and failover without having to understand Envoy.
    5. 8:55 Yan Avlasov lists the roadmap for the next year: semantic routing, pluggable policy engines for agent governance, more model providers, advanced inference routing and hardening against frontier-model scans.

    GPU Observability with eBPF: From Kernel Hooks to Kubernetes Metrics

    Qasim Sarfraz, Michael Friese

    Inspektor Gadget maintainers Qasim Sarfraz and Michael Friese of Microsoft show how eBPF probes on CUDA libraries can report GPU memory allocations per pod and trace them back to application code without changing the application. They demo allocation profiles and a Grafana dashboard for a vLLM workload, then explain how gadgets are packaged as OCI images and installed with one Helm chart.

    30 min slot · Advanced · Session

    Observability and reliabilityAccelerators and workload scheduling

    Watch this if: you run GPU inference on Kubernetes and want per-pod GPU memory metrics and allocation profiles without changing application code.

    1. 2:13 Sarfraz explains attaching uprobes and uretprobes to CUDA allocation and free functions and recording each call in BPF maps, which the framework enriches with pod and namespace and exposes to Prometheus.
    2. 5:45 In a demo he reads an allocation profile for a vLLM workload and uses it to raise the GPU memory utilization setting, which he says yields about 3 GB more allocation.
    3. 9:51 He says device state such as memory held and utilization comes from NVIDIA's NVML library, not from eBPF probes, and is joined with the eBPF data per workload.
    4. 12:36 Friese describes a gadget as an OCI image holding eBPF programs, optional WebAssembly modules, metadata YAML and BTF information, with signatures verified by default.
    5. 16:36 He lists four official GPU gadgets covering allocation activity, allocation call stacks, per-GPU state and per-pod state, and says profiles can go to Pyroscope or any OpenTelemetry endpoint.

    Kubernetes Anonymous: Confessions of Kubernetes Cargo Cultists

    Taylor Thomas, Brooks Townsend

    The speakers, who say they have worked both on Kubernetes-heavy platforms and on a wasmCloud platform that avoided Kubernetes, argue that both extremes are traps. They list red flags for using Kubernetes where it fits poorly, describe what each extreme cost them, and suggest that CNCF projects be compatible with Kubernetes without depending on it.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: You are deciding how much of your platform or project should be built on Kubernetes APIs and want the tradeoffs from people who tried both extremes.

    1. 1:43 The speakers poll the room on red and yellow flags, such as using Kubernetes as the database for config objects, making every service a CRD and mapping an API permission model onto Kubernetes RBAC.
    2. 10:58 Taylor Thomas says avoiding Kubernetes on principle for their wasmCloud platform was their own yellow flag, and that it cost them adoption and integrations with the rest of the ecosystem.
    3. 15:27 Describing Kargo, Thomas says Kubernetes became its database, API and auth model, and that most of its high and critical CVEs this year came from contorting the access model to fit Kubernetes RBAC.
    4. 17:29 He says Kargo 2.0 moves promotion and artifact tracking to a real database while Kubernetes stays as the execution substrate that runs pods.
    5. 20:21 Thomas asks people to stop putting everything in a CRD and offers test questions, including whether the work depends on a Kubernetes feature and whether it would be valuable outside Kubernetes.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    Open Policy Agent. (OPA) Intro & Deep Dive

    Sebastian Spaink, Johan Fylling

    Sebastian Spaink and Johan Fylling introduce Open Policy Agent as a general-purpose policy engine and Rego as its declarative policy language. They then cover this year's Rego changes, new Java and Swift evaluators built on OPA's intermediate representation, runtime improvements, and updates from Gatekeeper, opa-java-wasm and Conftest.

    30 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: you write Rego policies and want to know about the new and, or and not semantics and the coming Rego v2.

    1. 0:53 Spaink describes the problem OPA targets: policy scattered across enforcement points owned by different teams, so nobody can easily answer what the policy is.
    2. 8:42 Fylling shows the new or keyword for inline disjunction, while still recommending helper rules to keep large logical expressions maintainable.
    3. 12:33 Fylling explains the pitfall where a not expression over an undefined input value stopped the whole rule, and how the compiler now wraps negations in closures.
    4. 17:14 Fylling says a Rego v2 import enables the new syntax per module, ahead of an OPA 2.0 release the team plans for next year.
    5. 20:06 Fylling presents Java and Swift evaluators that run OPA's intermediate representation inside applications as libraries, with bundle management and decision logging.

    Rego Without Borders: Breaking Down Language Barriers for Security Policy

    Philip Conrad

    Philip Conrad, an Open Policy Agent maintainer, describes how the project wants policy decisions to run inside applications instead of in a sidecar, which he says has so far been easy only in Go. He explains how the Rego intermediate representation lets other languages run policies natively, and names Swift OPA and the Java OPA SDK as two new projects that do it.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policy

    Watch this if: you want to run Rego policies inside a Swift or Java application without calling a separate Open Policy Agent over the network.

    1. 0:41 Philip Conrad describes Open Policy Agent as a general purpose policy engine, a CNCF graduated project since 2021, that takes structured input such as JSON or YAML and returns decisions.
    2. 1:36 He says the community increasingly wants the policy engine embedded in the application itself instead of running as a sidecar.
    3. 2:22 He says Go makes it hard to package a library for other languages, so those languages have been limited to REST API calls to an Open Policy Agent running elsewhere.
    4. 2:58 He explains the Rego intermediate representation from the project's Wasm pipeline: query plans that break rules into smaller imperative instructions, built with opa build and a plan target.
    5. 3:46 He names Swift OPA and the Java OPA SDK as two new projects this year that run these plans natively, and says the main gain is debugging, with data-heavy policies sometimes running faster than in OPA.

    The Easiest Path Wins: Earning Platform Adoption with DDD and Product Thinking

    Fabrizio Lazzaretti

    Fabrizio Lazzaretti of Wavestone argues that mandates make platforms serve everyone and no one, and lays out four steps for earning adoption instead. He combines a product canvas, domain-driven design techniques, Kotter's change steps and implementation advice such as offering a GUI and WebAssembly extensions.

    25 min slot · Any Level · Session

    Platform engineering and developer experience

    Watch this if: you are planning a new internal platform and want product canvas, DDD and change-management steps to earn adoption rather than mandate it.

    1. 1:41 Lazzaretti says mandates push a platform to serve everybody and turn the goal into registering more users instead of checking whether they are satisfied.
    2. 3:23 For the why, he suggests a product canvas over a long business plan: the label pitch, goals, key metrics, a specific target user group (never everybody) and how the platform is funded.
    3. 7:37 He brings in domain-driven design: domain storytelling with a business expert to agree a shared language, then event storming to find bounded contexts and where the software can be split.
    4. 14:29 On the human side he follows Kotter's eight steps for change, including a guiding coalition with a management sponsor and short-term wins from a lighthouse project.
    5. 17:03 For implementation, he says not to underestimate a GUI for getting new users started, and suggests server-side WebAssembly extensions as a sandbox where others can add features in their own language.
