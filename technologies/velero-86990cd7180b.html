    GitOps Meltdown: How a Commit Triggered a Cascading Delete of 39 Clusters in Production

    Deepak Goel

    Deepak Goel tells the story of an incident in which, he says, a Git commit that accidentally removed a top-level Flux Kustomization caused Flux to prune a management cluster's whole tree, including the Git server, Flux itself and 39 workload clusters. He walks through the two waves of deletion, the multi-day recovery in which application data was found in the storage system's recycle bin, and the lessons he draws about blast radius, guarded deletes and rehearsed recovery.

    30 min slot · Advanced · Session

    Observability and reliabilityDelivery, GitOps and release safety

    Watch this if: you run clusters with Flux and Cluster API and want to see how one bad commit can delete a fleet, and what the speaker changed afterward.

    1. 6:12 Goel explains that when a Flux Kustomization with pruning enabled is removed from the Git source, Flux deletes everything in that Kustomization's inventory and then the object itself.
    2. 11:00 He names three couplings behind the incident: the Git server ran on the management cluster Flux managed, Flux's own configuration came from Git, and one top-level Kustomization was parent to all the others.
    3. 15:07 He says that when support restarted Flux to fix the outage, the new Flux instance saw the objects marked for deletion and finished deleting them.
    4. 19:24 He says the daily Velero backups had never been tested and were of little use, and that the application data was finally recovered from the recycle bin of the underlying storage system.
    5. 22:00 His first lessons are to shrink the blast radius with one Kustomization per cluster and to make bulk deletion harder, for example by disabling prune or setting the deletion policy to orphan.

    Longhorn: Intro, Deep Dive and Q&A

    Shuo Wu, David Ko

    David Ko introduces Longhorn, a cloud native distributed block storage system for Kubernetes, and shares its release cadence, adoption numbers and contributor growth. He then compares the V1 and SPDK-based V2 data engines, explains snapshots, backups, disaster recovery and live upgrades, and outlines the 1.13 and 1.14 roadmap with early RDMA benchmarks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run Longhorn or need block storage on Kubernetes and want to compare the V1 and V2 data engines.

    1. 2:32 Ko says Longhorn runs on any compatible Kubernetes cluster and Linux distribution, including Talos, and ships minor releases every four months in line with Kubernetes.
    2. 4:58 Ko reports adoption up about 21% in six months to roughly 276,000 nodes and 60,000 clusters, from Longhorn's public usage metrics.
    3. 12:22 Ko explains that the V2 data engine uses SPDK in user space with NVMe over Fabrics, plus an interrupt mode so it can share CPU with applications.
    4. 19:21 Ko walks through V2 live upgrades, which move the volume target to another node so I/O continues while the upgrading node's instance manager restarts.
    5. 23:44 Ko lists the 1.14 plans, including RDMA support, I/O QoS, a new data engine for strict-local volumes and application-consistent snapshots and backups.

    N Clusters, One kubectl: Multi-Cluster That Just Works

    Anne Lau, Scott Brimhall

    The speakers describe how Salesforce spread workloads across clusters with Open Cluster Management and built a routing proxy so that developers keep using one kubeconfig and standard kubectl. They explain how the proxy fans out reads, sends writes to the hub's ManifestWorkReplicaSet, and routes logs and exec to the right cluster, followed by a recorded demo.

    30 min slot · Advanced · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: You run workloads across several clusters and want developers to keep their single-cluster kubectl workflow.

    1. 2:25 The speaker says they chose Open Cluster Management and its ManifestWorkReplicaSet to run the same workloads in several clusters and load balance between them.
    2. 6:38 The speaker introduces what Salesforce calls Workload API, a routing proxy that passes Kubernetes API calls to the right cluster and stores no credentials on the server side.
    3. 8:02 The speaker explains reads: a list fans out to all managed clusters and aggregates the results with their origin, and a get treats the ManifestWorkReplicaSet spec as the source of truth.
    4. 10:56 The speaker explains how they guard against stale overwrites by using the parent ManifestWorkReplicaSet's resource version for concurrency control.
    5. 14:16 The recorded demo starts, showing get, scale, rollout restart, logs and exec through one gateway with standard kubectl.
