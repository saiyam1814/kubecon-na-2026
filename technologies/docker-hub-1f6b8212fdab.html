    Dockerfiles Made Software Reproducible. What Makes an Agent Reproducible?

    Per Krogslund

    Per Krogslund argues that a Dockerfile describes an agent's workload but says nothing about what the agent is allowed to reach, and presents Docker's open sandbox kit spec, which records those capabilities as annotations on an OCI image. He shows kits being run and built with Docker's microVM-based sandbox runtime and takes audience questions on Kubernetes support, other runtimes and updating a kit's metadata.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run coding agents and want to see one proposal for declaring an agent's network, credential and device access alongside its image so teams can share and check it.

    1. 4:54 Krogslund says a container is process isolation and not a security boundary, and that running a coding agent in a privileged container with access to the Docker socket gives it a route to the host machine.
    2. 6:57 He says Docker is building an agent runtime and supply chain on top of OCI and not a new format, that the sandbox kit spec is already open source, and that Docker has discussed handing it over to the CNCF.
    3. 11:03 He describes Docker's own runtime as a microVM with a private Docker engine whose only way out is a network proxy, which applies allow and deny rules and swaps a placeholder credential for the real one on outbound requests.
    4. 13:36 He walks through a kit's YAML file, which names the hosts the agent needs, the service credential it needs without storing it, and any agent context file, and later shows network rules that differ between install and run time.
    5. 21:31 Asked about Kubernetes, he says there is no Kubernetes runtime yet beyond an experimental version inside Docker, that the focus so far is the local experience, and that he wants input on the use cases.

    K3s Lightning Update

    Orlin Vasilev

    Orlin Vasilev, who introduces himself as the K3s community manager, gives a short introduction to K3s and an update on its latest releases. He covers a fix for a systemd restart loop, Gateway API CRDs shipped out of the box, a move of the project's images to GitHub Container Registry, and community growth numbers.

    5 min slot · Level not listed · Lightning Talk

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: you use K3s and want the release changes that may need action, especially the image registry move.

    1. 0:25 Orlin Vasilev describes K3s as a Kubernetes distribution in a single binary under 100 MB that boots in seconds and can be installed with one curl command.
    2. 1:14 He highlights a fix in the release he names as 1.36.6 for a systemd restart loop that he says could occur on slow networks.
    3. 2:03 He says K3s now includes the Gateway API CRDs out of the box, so users can create gateways and HTTP routes without installing them manually.
    4. 2:17 He announces that K3s images are moving from the Rancher organization on Docker Hub to GitHub Container Registry, and says users with air-gapped setups, mirrors or private registries need to act and should read the blog post.
    5. 3:16 He reports that since the last KubeCon the project gained 1,600 GitHub stars, 238 forks and 44 contributors, for a total of 1,339 contributors.

    Lightning Harbor Update

    Orlin Vasilev

    Orlin Vasilev, the Harbor community manager, covers what shipped in Harbor 2.15 and 2.16, including ARM64 support, the move from Redis to Valkey and a PostgreSQL upgrade that he says needs extra steps. He shares contributor and pull request numbers, asks contributors for patience with reviews, and points to a proposal to run Harbor as a common registry for CNCF projects.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyCommunity and open source adoption

    Watch this if: you run Harbor and want to know what changes in 2.15 and 2.16 before you upgrade.

    1. 1:03 Orlin Vasilev says Harbor 2.15 added Cosign v3 bundles, replication adapters for JFrog and AWS ECR, and proxy cache connection limit updates.
    2. 1:25 He says Harbor 2.16 officially supports ARM64 and migrated from Redis to Valkey.
    3. 2:13 He says 2.16 moves the internal database from Postgres 15 to 18, so upgrades need a few steps and a database backup, and webhooks for private networks are disabled by default afterwards.
    4. 3:29 He says Harbor had 562 pull requests last year and 1,213 so far this year, and asks contributors to be patient and keep pull requests small because the reviewers are the same people.
    5. 4:42 He says the team opened a proposal for registry.cncf.io, with Harbor as a common registry for all CNCF projects, and invites people to read and vote on it.
