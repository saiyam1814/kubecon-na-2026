    Deep Dive Into the DRA Driver for NVIDIA GPUs: What Works Today, What’s Coming and Why It Matters

    Shiva Krishna Merla, Varun Ramachandra Sekar US

    The two maintainers describe the current state of the NVIDIA DRA driver for GPUs, covering deployment, GPU sharing, health monitoring, KubeVirt passthrough, and compute domains. They show demos of GPUs switching between container and VM use and of a compute domain daemon set, and outline what they plan for the next release and how to migrate from the device plugin.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you allocate NVIDIA GPUs on Kubernetes and want the maintainers' view of what the DRA driver supports now and how to move off the device plugin.

    1. 6:51 The speaker describes system-mediated sharing planned for the next release, where pods in different namespaces each claim a share of a GPU using DRA consumable capacity.
    2. 8:01 The speaker says the driver watches GPU health events through NVML and publishes them as device taints, so the scheduler avoids those devices by default.
    3. 14:48 In a demo, the speaker starts four VMs and shows the node's GPUs moving from the NVIDIA driver to the VFIO driver for passthrough.
    4. 19:03 The speaker introduces a compute domain daemon set API that keeps IMEX daemons running before any workload is scheduled.
    5. 26:55 The speaker says existing device plugin requests for full GPUs and MIG devices can be translated to DRA resource claims, while time-sliced and MPS requests have no straightforward migration yet.

    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    Free Tokens for Everyone

    William Morgan

    William Morgan says running open-weight models on Kubernetes shifts inference costs from buying tokens to operating GPU capacity. He presents Kinference as a layer for defining tenant policy, tracking usage, and routing requests to local or external backends.

    30 min slot · Beginner · Session

    AI inference and serving

    Watch this if: You run a Kubernetes platform and need to share inference capacity across teams without giving up visibility or control.

    1. 12:01 Morgan explains that choosing an open-weight model variant depends on available memory, context length, and expected concurrency, not just the model family.
    2. 14:39 Morgan frames shared GPU inference as a platform problem: teams want self-service and different levels of service while operators must keep finite capacity reliable.
    3. 18:12 Morgan describes putting a traffic enforcement gateway in front of model servers to handle multiple models and tenants with explicit policy.
    4. 21:01 Morgan says the gateway can export Prometheus-compatible metrics for existing dashboards and break out performance by model and tenant.
    5. 23:47 Morgan walks through policies that can choose a model, reject a request, or send it to an external provider using prompt, GPU, and tenant signals.

    From Pending Pod to Ready Node: Declarative Worker Images for Kubernetes Scale-Out

    Matt Boersma, Mark Rossetti

    The speakers break down what happens between a pending pod and a new worker doing useful work, and argue for moving repeatable setup into prepared, validated worker images. They describe a controller they built on Cluster API that declares worker images as custom resources, and share timings from a four-node GPU training job on Azure.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: You scale GPU or other specialized node pools and want to shorten the time from a pending pod to a worker doing useful work.

    1. 3:55 The speakers separate reusable preparation from the work every new machine must still do, and say it matters for node replacement and rolling updates as well as scale-out.
    2. 6:38 The speakers follow a Ray training job waiting for GPU nodes, and say useful work starts long after the containers report running.
    3. 13:34 The speakers propose two loops: a preparation loop that builds, validates and approves an image when inputs change, and a capacity loop that consumes the approved version on demand.
    4. 14:32 The speakers introduce Nodesmith, which they say declares a worker image as a custom resource, builds it with Packer and image-builder in the cluster, and hands the rollout to Cluster API.
    5. 16:49 The speakers report a median of about 13 minutes 10 seconds from capacity request to first training step with stock images, and about 9 minutes 23 seconds with prepared images.
