    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    From Vibe to Live: Building for the Real World

    David Biel, Trey Caliva

    David Biel, who says he has no engineering background, and cloud security engineer Trey Caliva tell how David vibe-coded his family dental cabinet company's website and back-office tools and got them to production on managed services. Trey argues that the advice he gave in person should live in the AI's context as skills, hooks and MCP server permissions, so that platform teams can guide the many non-engineers he says are already building this way.

    30 min slot · Beginner · Session

    Platform engineering and developer experienceAI agents and automationDelivery, GitOps and release safety

    Watch this if: non-engineers in your company are shipping AI-built apps and you want ideas for guiding them.

    1. 2:22 David says he got the work done with a $200 Claude subscription, compared with the $5,000 to $10,000 his family was quoted for a website and brand about ten years earlier.
    2. 5:28 Trey says David's app runs on Firebase Hosting, Cloud Functions, Firestore and Firebase Auth, chosen so there are no servers to patch or clusters to run.
    3. 7:49 Trey lists what first-time builders may miss, such as open database rules, unauthenticated endpoints and pasting an API key into the chat.
    4. 10:16 Trey proposes putting guardrails in the AI's context through skills, hooks and MCP server access, with skills moving from ad hoc to a shared repo to a governed catalog.
    5. 13:47 Trey says skills advise and hooks enforce, showing a simplified hook that runs a script on each prompt to catch pasted secrets, plus deny rules that block deploying from a laptop.

    Gone in 60 Minutes: Effectively Close the Exploitable Window with Detection as Code

    Ben Hirschberg, Constanze Roedig

    Ben Hirschberg and Constanze Roedig show two ways to detect exploitation with Kubescape in the hours between a vulnerability becoming public and a patch being deployed, both shipped to the cluster as YAML through GitOps. Hirschberg writes rules from published indicators of compromise, and Roedig uses behavior profiles to flag deviations when the attacker's methods are not yet known.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyObservability and reliability

    Watch this if: you need a way to detect exploitation of a newly disclosed vulnerability in running workloads before a patch can be rolled out.

    1. 2:19 Hirschberg describes the setup: the Kubescape node agent with eBPF sensors and a rule engine whose detection rules are written in CEL, with alerts sent to Slack.
    2. 6:16 In a recorded demo he pastes the indicators of compromise from a published write-up of the poisoned Trivy GitHub Action into an AI agent, which opens a pull request with Kubescape detection rules that Argo CD syncs to the cluster.
    3. 9:32 Roedig introduces what she calls a software bill of behavior, a custom resource listing allowed capabilities, network traffic, executables and file opens as composable fragments that can be signed separately.
    4. 11:56 She says build runners are a poor fit for anomaly detection because their behavior is not bounded, then shows a profile-based setup still flagging the same indicators as the rules did.
    5. 16:54 For a PHP server that normally spawns shells, she says the profile caught the exploit because the id command ran outside the expected process tree, and argues a good profile has as few entries as possible.

They then outline what they are working on for 2.17, such as syncing AI models from Hugging Face into Harbor as OCI artifacts, and ask for feedback on the open proposals.

    30 min slot · Level not listed · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you run Harbor and want to know what 2.16 changed and what the maintainers plan for 2.17, or if you need Harbor on Arm.

    1. 0:40 Vadim Bauer lists the highlights he picks from Harbor 2.16: custom project roles, a configurable proxy cache with bandwidth limits and regex filters, Valkey replacing Redis, multi-architecture images and PostgreSQL 18.
    2. 7:36 Rani Chowdary Mandepudi explains how Arm64 support landed upstream in four parts: native CI, build tooling, online and offline installers, and multi-platform OCI manifests.
    3. 14:23 Orlin Vasilev shows that pull requests nearly doubled year over year, which he attributes to AI, and asks contributors to link an issue, keep PRs small and be patient.
    4. 18:05 Vadim Bauer describes the model sync proposal for 2.17: replicate models from Hugging Face and convert them on the fly into OCI artifacts in the model spec format.
    5. 21:13 Vadim Bauer describes a proposed scanner spec upgrade that he says would let Harbor run several scanners at once, including linters, license and secret scanners, and aggregate the results.

    LTS, EOL, CVEs: Solutions for Stress-Inducing Scenarios

    Bridget Kromhout, Lachlan Evenson

    Bridget Kromhout and Lachlan Evenson of Microsoft discuss three pressures of running open source in production: long-term support for Kubernetes, projects reaching end of life, and the rising rate of vulnerabilities. They argue for upgrading regularly, looking for migration paths when a project ends, proposing changes upstream instead of carrying private forks, and judging patches by whether a flaw is exploitable in context.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safetyCommunity and open source adoption

    Watch this if: you run Kubernetes platforms and need arguments for regular upgrades, handling end-of-life projects and a sane approach to CVE patching.

    1. 7:51 The speakers say the long-term support discussion showed that users objected less to change than to breaking changes in every Kubernetes release, which led to work on better upgrades.
    2. 10:28 Evenson says their provider platform will start upgrades on behalf of customers, and Kromhout adds that this begins next summer.
    3. 13:12 Evenson says ingress-nginx had asked for maintainers for several years before its end of life, and points to Gateway API and other ingress controllers as paths forward.
    4. 17:08 Kromhout calls forking a trap, accepts a soft fork meant for upstreaming, and the speakers describe an etcd change whose authors became upstream maintainers.
    5. 20:54 Evenson calls chasing zero CVEs a trap as vulnerability rates rise, and points to VEX and OpenVEX for stating whether a flaw is exploitable in a given context.

    Mythos vs Maintainers: Drowning in the Vulnerability Tsunami

    Fabian Kammel, John Kjell

    Fabian Kammel, speaking as a security researcher, and John Kjell, speaking as a maintainer of in-toto's Witness, walk through finding, reporting, triaging, fixing and following up on a vulnerability at a time when they say AI models let anyone file reports that are hard to tell from real ones. They give recommendations for each side in three levels, from steps to adopt today to actions meant to help the wider ecosystem, and ask for empathy toward maintainers, whom they call the bottleneck.

    30 min slot · Any Level · Session

    Security, identity and policyCommunity and open source adoption

    Watch this if: you maintain an open source project or report vulnerabilities to one and want both sides' concrete steps for handling AI-assisted security reports.

    1. 3:45 Kjell says AI-generated reports were easy to spot and close a year ago, but that newer models let novices submit reports that look real and take a lot of effort to verify, and that curl and bug bounty programs have pulled back as a result.
    2. 8:25 Kammel says the first thing he does for AI-assisted research is build a sandbox, preferring micro VMs over sandboxes that share the host kernel, and that researchers should understand and reproduce a model's finding before reporting it.
    3. 10:40 Kjell advises maintainers to turn on GitHub's private vulnerability reporting and publish a security policy with a response time frame, report expectations, supported versions, scope and a threat model in the repository.
    4. 14:34 Kammel lists what a researcher's report should do: follow the project's security policy, check for duplicates, cut the model's text down, and propose a severity score, affected versions and a weakness type.
    5. 24:53 Kjell shows that a GitHub temporary private fork has no Actions tab, and says the Witness maintainers keep their own detached fork so that fixes can run through CI before release.

    Platform as Context: Evolving Our IDP for AI Agents

    Gang Luo

    Gang Luo of Electrolux Group explains how his team extended their internal developer platform so AI agents can use it as context through MCP tools. He shares the context categories they defined, a switch to GraphQL, and benchmarks where he reports lower token use and fewer tool calls.

    25 min slot · Intermediate · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    1. 1:56 Luo describes the starting point: about 400 developers, an average of six SREs, and an IDP where developers pick templates, get approval and have infrastructure provisioned for them on golden paths.
    2. 3:50 Because developers work in the IDE and terminal, his team added MCP read and write tools on top of the IDP so agents can read and provision the infrastructure it manages.
    3. 6:41 He lists the context agents need, starting with ownership, then infrastructure, deployment through GitHub Actions and telemetry, and says the IDP should hold only what is needed and point to the other sources.
    4. 9:29 He says moving the MCP tools from static APIs to GraphQL cut the tokens an agent used for discovery by about 80% from roughly 17K.
    5. 12:19 In benchmarks comparing an agent with GitHub alone against GitHub plus the IDP, he reports one task using 50% fewer tool calls and 65% fewer tokens, while noting some experiments got worse.

    Signed, Sealed, Denied: Attestation-Driven Admission with Kyverno + CEL at AT&T

    Chad Swenson, Sagar Kundral

    Chad Swenson of AT&T argues that a signature alone is not a deployment approval and describes a platform design where GitHub Actions emits Sigstore-backed attestations and Kyverno's ImageValidatingPolicy checks them against each environment's rules at admission. Sagar Kundral of Nirmata demos the policies on a live cluster and presents Kyverno 1.19 and 1.20 changes, benchmark numbers and advice on exceptions, failure behavior, evidence retention and rollout.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you sign images already and want to see how attestations can drive per-environment admission decisions that you can later explain to an auditor.

    1. 3:38 Chad says a valid signature and provenance are useful but neither is a deployment approval, so the platform must still ask whether trusted claims meet the destination's requirements.
    2. 5:15 Chad gives an example where the same image digest is admitted in development on provenance alone but denied in production because it lacks a signed SBOM attestation.
    3. 13:51 Chad says verifying only against GitHub's private Sigstore instance broke down for upstream and vendor images with other trust roots, and credits a fix released in Kyverno 1.19 after he raised it with the lead maintainer.
    4. 17:28 Sagar runs a scripted demo on a live cluster showing verification with a signer workflow identity, an unattested image blocked, a production denial for missing code reviews, a policy exception in dev, and an org ID pin.
    5. 24:38 Sagar presents benchmark numbers from a kind cluster where he says p50 admission latency fell from 990 ms to 96 ms and registry calls from 14 to 3 in Kyverno 1.20.

    Your Quickstart is Broken – AI Agents as Synthetic New Users

    Aman Singh

    Aman Singh describes how the Drasi maintainers use an AI agent as a synthetic new user that follows their tutorials exactly and reports where the docs and the real output differ. He walks through the setup with Dev Containers, GitHub Actions, GitHub Copilot CLI and Playwright, and shows bugs it found in Drasi, Dapr Agents and Radius tutorials.

    5 min slot · Any Level · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you maintain a project's tutorials and want them tested automatically the way a new user would follow them.

    1. 0:32 Aman Singh says a broken quickstart could be a user's first and last interaction with a young project like Drasi, which he helps maintain.
    2. 1:15 He describes giving the job to an AI agent acting as a beginner, with one key instruction: do not fix anything, report the gap instead of hiding it.
    3. 2:14 He explains the setup: the tutorial's Dev Container runs in a weekly GitHub Actions workflow with GitHub Copilot CLI and Playwright, and a failing run files a GitHub issue with the evidence.
    4. 3:20 He shows a tutorial where every command succeeded and CI was green, but the output was missing a name because the query read the wrong field.
    5. 4:09 He says the same prompt and workflow, with minimal changes, found gaps in the Dapr Agents and Radius getting started guides.
