    Cloud Native: Built by Humans, Engineered to Evolve

    Jeffrey Sica

    Jeffrey Sica argues that cloud native can adapt to AI because the people who maintain its projects keep changing how they work without abandoning human review. He connects agent workloads to familiar distributed systems practices such as limiting blast radius, rolling back quickly, and sandboxing untrusted code.

    10 min slot · Level not listed · Keynote

    Community and open source adoptionKubernetes internals and runtimes

    Watch this if: you want to connect AI agent workloads to the reliability practices and contribution norms cloud native teams already use.

    1. 2:55 Sica asks the audience to see the people who keep showing up behind each logo in the cloud native landscape.
    2. 4:25 Sica says maintainers responded to AI-generated contributions by writing policies for what a good contribution looks like and what they expect the submitting human to review.
    3. 5:37 Sica uses the term agent speed for the number of machine actions between human decisions and argues that the change matters for software architecture.
    4. 6:30 Sica points to small blast radii, fast iteration and rollback, sandboxing, and APIs as reasons cloud native systems can adapt to agent workloads.
    5. 7:59 Sica argues that Kubernetes fits training and inference because they are distributed systems problems, not because Kubernetes was originally built for AI.

    Kubeflow Graduation: Powering the Next Era of Cloud Native AI With an Open Community

    Ron Kahn, Andrey Velichkevich, Vara Bonthu, Ekin Karabulut, Manabu McCloskey

    Andrey Velichkevich announces Kubeflow's CNCF graduation and describes a project that has grown from making machine learning portable on Kubernetes into a platform for the AI lifecycle. The other speakers explain how their teams use it for distributed training and Spark workloads, and introduce a way to give agents shared definitions for business metrics.

    7 min slot · Level not listed · Keynote

    AI inference and servingCommunity and open source adoption

    Watch this if: you want examples of how teams use Kubeflow to connect distributed training, data processing, and agent workflows.

    1. 0:18 Velichkevich announces CNCF graduation and thanks the users, contributors, and maintainers who made it possible.
    2. 0:59 Velichkevich walks through Kubeflow components for processing data, running distributed training, developing in notebooks, and orchestrating pipelines.
    3. 3:29 Kahn explains how Run:ai translates an engineer's submission into a training job and uses topology-aware gang scheduling to start workers together.
    4. 5:03 Bonthu recounts how organizations came together to move the Spark Operator into Kubeflow and continue maintaining it.
    5. 6:37 McCloskey introduces the Semantic Operator as a way to give agents a shared definition for business metrics.

    One Workload to Rule Them All: Workload Aware Scheduling for Distributed AI Training on Kubernetes

    Andrey Velichkevich

    Andrey Velichkevich explains why scheduling distributed training one pod at a time can deadlock jobs and how the Kubernetes Workload and PodGroup APIs model them as a unit. He shows how Kubeflow Trainer exposes those capabilities through training runtimes and compares three scheduling policies on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload scheduling

    Watch this if: You run distributed training on Kubernetes and want to understand when pod groups and topology constraints matter.

    1. 0:48 Velichkevich illustrates how two training jobs can deadlock when the scheduler gives each job some GPUs but neither gets enough to start all its ranks.
    2. 4:44 Velichkevich distinguishes the Workload template from runtime PodGroups and shows how a PodGroup can express a minimum pod count and topology constraints.
    3. 7:10 Velichkevich introduces composite PodGroups for workloads with a hierarchy, where a parent can require a minimum number of child groups before scheduling proceeds.
    4. 10:12 Velichkevich explains the Kubeflow Trainer split: platform admins define runtime blueprints, and scientists use a Python SDK to submit jobs without managing Kubernetes deployment details.
    5. 15:17 In a local kind demo, Velichkevich sets up a comparison of default pod-by-pod placement, gang scheduling, and rack-constrained placement for a PyTorch job.

    SIG API Machinery in the Era of AI: Updates

    Joe Betz

    Joe Betz reviews a year of work in Kubernetes SIG API Machinery, from contributor trends to API server performance, resilience and controller improvements. He covers the storage version migrator, internal type and protobuf cleanups, declarative validation with its linter, manifest-based admission policies and client library updates, then outlines what comes next.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: you build Kubernetes APIs, CRDs or controllers and want to know what changed in the API machinery underneath them.

    1. 1:38 Betz says PRs to the SIG rose about 50% this year, which he links to AI-assisted development, while reviewer capacity stayed roughly flat.
    2. 7:21 Betz says the storage version migrator has finally landed, so CRD authors can migrate stored objects and eventually retire conversion webhooks.
    3. 12:14 Betz explains that making internal types match the preferred serving version lets the Go compiler skip needless copies during conversion.
    4. 14:45 Betz shows declarative validation, where tags on API types generate validation code, plus a linter that catches mistakes such as a field marked both required and optional.
    5. 17:10 Betz describes a tool to detect backward-incompatible CRD changes and manifest-based admission policies loaded at API server startup that users cannot bypass or modify.

    The Scheduling Stack: Real-World Lessons from Anthropic, Anyscale, Google, and CERN

    Wojciech Tyczyński, Ricardo Rocha, Kaslin Fields, Decheng Dai, Jui-An Huang

    The panelists compare what upstream Kubernetes scheduling can handle with where their teams still specialize. They describe how placement, queueing, cluster boundaries, and resource fragmentation affect distributed workloads.

    30 min slot · Any Level · Panel

    Accelerators and workload scheduling

    Watch this if: you are deciding which scheduling concerns belong in Kubernetes and which belong in a higher-level workload scheduler.

    1. 5:42 Fields introduces KubeRay as the controller for running Ray on Kubernetes.
    2. 10:30 A panelist distinguishes workload placement from deciding what should run now or wait in a queue.
    3. 13:46 Rocha recalls splitting CERN clusters because the scheduler could not launch the volume of workloads CERN wanted, rather than because of node count.
    4. 20:01 A panelist explains why they try to keep a tightly coupled workload within one cluster instead of exposing it to failures across several clusters.
    5. 25:14 A panelist describes a background job that scans for fragmentation and moves workloads when it finds a better placement.
