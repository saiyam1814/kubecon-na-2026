    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

    I Packaged My Application in a Container Image, and Now What?

    Aurélie Vache

    The speaker takes a small Go API packaged as a container image and walks through supply chain security steps for it, with a live demo for each one. She covers generating an SBOM, scanning for vulnerabilities, publishing a VEX file, signing the image, generating SLSA provenance and automating all of it in a GitHub Action.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: You can build and push a container image and want to see the next supply chain security steps done live, one command at a time.

    1. 2:18 The speaker starts with the SBOM, an inventory of the components in an image, and says it is no longer nice to have but becoming mandatory.
    2. 10:32 In the demo, a Trivy scan of the image reports 26 vulnerabilities, and the speaker points out that the first one applies to a Go version her application does not use.
    3. 13:22 The speaker introduces VEX as a way to tell users whether a vulnerability is exploitable in the application, and says OpenVEX is her favorite format.
    4. 17:11 After generating a VEX file with govulncheck and fixing its product ID, the speaker scans again with Trivy and she says the filtered result shows zero exploitable ones among the high and critical findings.
    5. 20:32 The speaker generates a key pair in a KMS, signs the image with Cosign and verifies the signature.

    ORAS Go v3: Batteries-Included Registry SDK

    Terry Howe

    Terry Howe, an ORAS and Helm maintainer, says oras-go v3 loads the same registry configuration files that Podman uses, so TLS, mirrors and policy no longer need to be wired by hand as in v2. He also describes a client builder, a changed token flow, namespace-scoped credentials, streaming without writing to disk and a new module path.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you build Go tools that push or pull OCI artifacts and are deciding whether to move from oras-go v2 to v3.

    1. 0:56 Howe says a single convenience function loads the Docker config, auth.json, registries.conf, policy.json, registries.d and certs.d files, following mostly the same priority as Podman.
    2. 3:09 Howe says v3 brings mirror support for air-gapped setups, policy support to allow or deny registries, and a token flow that tries OAuth2 first and falls back to the distribution token flow.
    3. 3:51 Howe says reading auth.json adds namespace-scoped credentials, which he says makes it possible to copy between Harbor projects that each have their own credentials.
    4. 4:29 Howe says v3 can stream data directly so large artifacts move without being written to disk.
    5. 4:47 Howe says the module path now points at GitHub after an outage made the earlier module path unavailable, and that 70 new contributors joined since v3 branched from v2.

    When Infrastructure Breaks in Production: How EarnIn Brought Testing to the Full CNCF Stack

    Priya Namasivayam

    Priya Namasivayam of EarnIn describes a cert-manager upgrade that looked healthy but broke Linkerd certificates and customer logins, and says the team responded by running infrastructure tests as Kubernetes resources with Testkube, triggered by Flux reconciliation. A co-presenter from Testkube runs a live demo on a kind cluster in which an operator upgrade passes health checks but fails a test workflow.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyObservability and reliability

    Watch this if: you upgrade cluster add-ons through GitOps and want to catch breakage that pod health checks do not show.

    1. 3:48 The speaker explains the incident: she says cert-manager 1.18 began rotating private keys on renewal instead of extending them, which broke certificates for Linkerd while everything looked green.
    2. 5:26 The speaker describes the fix as a Kubernetes-native testing setup built on Testkube, where tests and triggers are CRDs and a Git commit that starts Flux reconciliation also starts the tests.
    3. 10:35 The co-presenter starts the live demo by bringing up a kind cluster with Flux, CloudNativePG, cert-manager and a sample to-do application.
    4. 12:42 The co-presenter shows a Testkube test workflow for cert-manager that checks certificates are still valid after an upgrade.
    5. 20:49 After the simulated upgrade the test workflow fails, and the co-presenter explains that the operator is running but a breaking change stops the ServiceMonitor from working.
