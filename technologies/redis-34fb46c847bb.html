    Cloud Native Infrastructure in the AI Era: A TAG Infrastructure Panel

    Xing Yang, Dylan Page, Mesut Oezdil, Alexa Griffith, Kashif Khan, Thomas Schuetz

    The co-chairs and tech leads of the CNCF TAG Infrastructure describe the group's current work, including white papers on infrastructure lifecycle, AI for science, AI inference and data storage for AI, and a new telco AI-native initiative. They then each name what they see as the biggest challenge AI workloads pose for cloud native infrastructure and take audience questions on agent sandbox projects and moving HPC sites toward cloud native tools.

    30 min slot · Level not listed · Panel

    Community and open source adoptionAccelerators and workload schedulingAI inference and serving

    Watch this if: you run or plan AI infrastructure and want to know what the CNCF TAG Infrastructure is writing about it and where you can contribute.

    1. 2:04 Dylan Page describes the infrastructure lifecycle white paper, which he says is meant to advise on managing mixed public cloud, private cloud, edge and bare metal environments, and Thomas Schuetz adds that it covers when operator-based deployment fits better than Terraform or OpenTofu.
    2. 5:13 Kashif Khan introduces the telco AI-native initiative, saying the challenge for AI-native network functions is the infrastructure beneath the model, and that the group is collecting shared definitions and gaps from operators and vendors.
    3. 10:03 Xing Yang summarizes the TAG's white paper on data storage for cloud native AI, saying training, inference and agents each have different storage patterns, so no single AI storage fits all.
    4. 11:40 Asked for the biggest challenge, Dylan Page answers that it is people, describing a collision of cloud native, telecom and HPC cultures, while other panelists name GPU utilization, placement and the speed at which infrastructure is needed.
    5. 19:00 Mesut Oezdil argues that GPUs must be sliced to be economical and that MIG and time slicing fall short in mixed-vendor environments, and points to HAMi, which he maintains, as a vendor-agnostic option.

    DisaggregatedSet Meets Multi-EPP: Coordinating llm-d at Scale in production

    Mathis Felardos, Lucas Fernandes Martins

    Mathis Felardos presents DisaggregatedSet, which Mistral AI contributed to the LeaderWorkerSet project to deploy and roll out prefill and decode roles together. Lucas Fernandes Martins presents multi-EPP for llm-d, where several router replicas share in-flight load state through a pluggable cross-replica syncer, with Mistral's Redis implementation as the example.

    20 min slot · Level not listed · Session

    AI inference and serving

    Watch this if: You run disaggregated prefill and decode serving and want safer rollouts or a horizontally scaled llm-d router.

    1. 1:18 Mathis Felardos explains disaggregated serving, splitting compute-bound prefill from memory-bound decode, and why it is hard to operate during rollouts.
    2. 3:10 He describes DisaggregatedSet, contributed into LeaderWorkerSet, with declarative prefill and decode roles and coordinated rolling updates.
    3. 5:48 He describes cross-revision gating, where llm-d shifts requests gradually to a new revision so incompatible prefill and decode pods do not pair up.
    4. 9:07 Lucas Fernandes Martins shows why naive multiple EPP replicas diverge, and introduces a cross-replica syncer interface with set, get and aggregate.
    5. 14:38 He shows benchmarks where one EPP fails after around 700 requests per second while three EPPs syncing through Redis keep serving.

    Optimized Switchover Timing for Live Migration of Memory-Intensive Workloads

    Aseef Imran

    The speaker explains why live migrations of write-heavy virtual machines can stall and why timeouts and downtime ramps choose the switchover moment poorly. He presents a stall-detection approach that waits for a low point in the remaining data before switching over, which he says was merged as alpha in KubeVirt 1.9.

    20 min slot · Level not listed · Session

    Kubernetes internals and runtimesObservability and reliability

    Watch this if: You run memory-heavy virtual machines and want to understand how switchover timing affects live migration downtime.

    1. 3:37 The speaker says the standard approach waits for a target downtime, and that write-heavy workloads sometimes never reach it.
    2. 8:26 The speaker says downtime ramps work well only when tuned for the workload, with low-level parameters an end user should not have to set.
    3. 10:15 The speaker describes the key observation that stalled migrations fluctuate around a point, so switchover can be timed for a low point.
    4. 14:59 The speaker explains his definition of a stalled migration, which compares current remaining bytes with the smallest record outside a progress timeout window.
    5. 19:26 The speaker reports a Redis benchmark where average downtime went from about 5,000 to about 1,000 milliseconds, and another workload with no meaningful difference.

    Gang Luo

    25 min slot · Intermediate · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    1. 1:56 Luo describes the starting point: about 400 developers, an average of six SREs, and an IDP where developers pick templates, get approval and have infrastructure provisioned for them on golden paths.
    2. 3:50 Because developers work in the IDE and terminal, his team added MCP read and write tools on top of the IDP so agents can read and provision the infrastructure it manages.

    Your Agent Needs a Platform: Cloud Native Infrastructure for Multi-Agent AI Systems

    Soham Ghadge

    Soham Ghadge describes problems he met running AI agents in production, such as crashes midway through a task, rate limits, repeated model calls and poor visibility, and maps each one to existing cloud native tools. He proposes defining agents as Kubernetes custom resources, saving each model call as a Dapr workflow step, queueing tasks through NATS JetStream and tracing with OpenTelemetry.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are building multi-agent systems and want a short overview of which cloud native tools cover crash recovery, queueing and tracing.

    1. 2:35 Ghadge lists his mapping of agent problems to tools, starting with describing each agent as a Kubernetes object through a CRD.
    2. 3:38 Ghadge shows a simplified agent definition as a Kubernetes object, with replicas, maximum tasks per copy and what the agent reads from and writes to.
    3. 7:00 Ghadge says to put every AI model call inside a saved step so that after a restart Dapr reuses the saved answer instead of paying for the call again.
    4. 7:39 Ghadge describes an agent queue, which he compares to a Redis queue, so agents do not handle every request directly.
    5. 9:48 Ghadge's conclusion is to treat an agentic system like a distributed system and agents like microservices.
