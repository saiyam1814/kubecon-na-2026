    AI Gateways in Practice: Model Routing, Inference Scheduling, and MCP on Kubernetes

    Yuke Ning

    Yuke Ning walks through how Higress handles hosted model routing, traffic to self-hosted inference, and requests from agents to tools. He discusses where fallback stops working, how an endpoint picker participates in routing, and how the gateway bridges MCP transports.

    30 min slot · Level not listed · Session

    AI inference and servingNetworking and connectivity

    Watch this if: you run a gateway that must handle hosted models, your own inference workloads, and MCP tools.

    1. 5:11 Ning shows a Higress route configured to try a backup model provider after selected error responses.
    2. 7:47 He points out that status-based fallback cannot redirect a response once a successful stream has already started.
    3. 9:56 He walks through the Gateway API Inference Extension ownership model, in which application teams own routes and serving teams own the inference pools those routes target.
    4. 18:10 He contrasts rejecting the request if an external endpoint picker fails with allowing the gateway to choose an endpoint another way.
    5. 22:26 He describes three MCP roles for the gateway: exposing REST APIs as tools, proxying existing MCP servers, and bridging differences between clients and servers.

    Cache Me If You Can: LLM Inference with llm-d (with fun drawings)

    Alexa Griffith

    Alexa Griffith says adding inference replicas only helps if requests reach pods that have capacity or can reuse cached work. She walks through how llm-d picks endpoints, queues workloads, and tests those choices against latency and throughput goals.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: You run inference on Kubernetes and want to decide whether cache-aware routing, offload, or queue policy is worth tuning.

    1. 4:10 Griffith walks one request through llm-d's filter, score, and pick sequence, explaining how the router estimates which pods already hold a matching prefix.
    2. 8:43 Griffith says offloading the key-value cache to CPU memory can avoid recomputing it for long-lived requests, at the cost of slower access.
    3. 9:13 Griffith describes splitting prompt processing from token generation and notes that the two stages then have to transfer cached state.
    4. 14:07 Griffith explains how priority bands choose which class goes first and how separate fairness and ordering policies govern work within a band.
    5. 23:58 Griffith recommends choosing a tuning change based on a measured symptom, then benchmarking it against a small baseline before adding more configuration.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.

    Where Should Platform Complexity Live? Lessons from a Cross-Team PR Preview Platform

    Taiki Ono

    Taiki Ono describes a PR preview platform built on a Kubernetes controller that derives preview environments from existing manifests and routes traffic by a preview ID. He uses it to explain a model for deciding whether platform complexity should leak to teams, move into the platform or be absorbed by it.

    25 min slot · Intermediate · Session

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you build PR preview environments or any shared platform feature and want a way to decide which complexity the platform should own.

    1. 2:48 Ono compares generating preview manifests with a CLI or templating against creating preview resources directly in the cluster with a controller, and says his team chose the more complex controller route.
    2. 5:37 He gives a model for where platform complexity goes: leaked to product teams, moved into the platform unchanged, or absorbed, meaning the platform handles the same concerns simply.
    3. 10:19 In the architecture, a GitHub webhook creates a preview request, product teams write only a small custom resource, and the controller derives preview config from the base manifests without changing them.
    4. 16:58 For routing they build on the Gateway API for service mesh: a preview gateway puts a preview ID in a request header and sidecars route by it, which he says also lets previews span several products.
    5. 18:51 He says the platform first handled CORS but could not absorb credentialed requests simply, so the team handed CORS back to applications as a one-line change and redrew the boundary.
