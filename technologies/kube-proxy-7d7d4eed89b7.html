    Inside the Inference Load Balancer: Proxy/Controller Patterns for LLM Serving on Kubernetes

    Qianru Lao, Lu Zhang

    Qianru Lao and Lu Zhang explain how their inference load balancer steers requests across Kubernetes clusters when engine capacity, distance, and cache state differ. They describe a control plane that computes fleetwide weights, a data plane that applies them locally, and protections they use when load changes.

    30 min slot · Advanced · Session

    AI inference and servingNetworking and connectivity

    Watch this if: You are designing multi-cluster inference routing and want to see how one team separates request-path decisions from fleetwide optimization.

    1. 3:36 Zhang explains why an engine with cached conversation context can return the first token sooner than a less busy engine that must process that context again.
    2. 9:34 Zhang describes how moving traffic during weight updates can disturb cache reuse and feed oscillations back into the next update.
    3. 14:27 Lao describes how the control plane uses engine signals to calculate routing weights, while the data plane routes requests using local state.
    4. 16:58 Lao walks through a regional capacity example in which routing to a more distant engine can trade network latency for less waiting at the engine.
    5. 23:13 Zhang describes shedding a controlled share of requests early as a last line of defense when retries and penalties cannot compensate for insufficient capacity.

    Kubernetes The Hard Way - Live

    Lucy Sweet, Sandeep Kanabar

    Lucy Sweet and Sandeep Kanabar build a Kubernetes cluster live, starting each component on local virtual machines. They trace an application from a kubectl request through the API server, the scheduler, and the kubelet to a running container.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimes

    Watch this if: You want to see what changes when each Kubernetes component starts and how those changes turn a pod request into a running container.

    1. 6:54 Kanabar starts etcd and inspects its membership, explaining how the API server uses it to persist cluster state.
    2. 7:58 Kanabar verifies etcd by writing and reading a key, then explains why the API server is the entry point for other control-plane components.
    3. 12:41 Sweet explains reconciliation as observing actual state and taking steps toward the desired state, using a deployment with missing replicas as the example.
    4. 13:55 Sweet distinguishes the controller manager, which runs core controllers, from the scheduler, which chooses a node for a pod.
    5. 17:35 Sweet shows why a pod stays pending until a node joins, then uses crictl to inspect the NGINX container running under containerd.

    SIG Network Intro and Updates

    Surya Seetharaman, Guilherme Cassolato, Austin Abro, Bowei Du

    Four SIG Network contributors review what the SIG owns and what changed in 2026 across Kubernetes core and its subprojects, including kube-proxy's planned move to nftables as the default mode, Gateway API releases, Cluster Network Policy reaching v1beta1 and the status of smaller subprojects. They also report findings from the SIG's first structured survey of its 22 subprojects, and Austin Abro describes how he used AI to make his first contribution.

    30 min slot · Level not listed · Session

    Networking and connectivityKubernetes internals and runtimes

    Watch this if: you want a year's worth of Kubernetes networking changes in one session, or you run kube-proxy and need to plan for nftables.

    1. 3:40 Bowei Du mentions a new proposal for network-isolated pods with no networking by default, which he links to agent sandbox use cases, and lists deprecations of external IPs, kube-proxy IPVS mode and the Endpoints API.
    2. 4:45 Austin Abro explains the opt-in TCP userspace proxy that lets nftables mode serve NodePorts on localhost, and advises setting the kube-proxy backend explicitly before the default changes to nftables in 1.40.
    3. 9:57 Surya Seetharaman announces the v1beta1 release of Cluster Network Policy, which unifies the former admin and baseline CRDs, and notes the work began in March 2020.
    4. 16:11 Guilherme Cassolato says the SIG ran its first structured survey of its 22 subprojects and learned that AI is driving many agendas to the point of overlap, some projects have only one or two maintainers, and maintainers want faster API review.
    5. 20:47 Abro recounts using AI to learn kube-proxy internals for his localhost NodePort contribution, and says the maintainers' insistence on not breaking existing users kept the feature opt-in.

    When the Clock Lies: How an 8-Minute Time Skew Locked Kubernetes cluster for a day

    Akhil Mohan

    Akhil Mohan of VMware by Broadcom, a containerd maintainer, retraces how a CSI pod on an internal cluster sat in CreateContainerError for 19 hours after a hypervisor power failure while its containers were in fact running. He traces it to a VM that booted about eight minutes in the future, so tokens were issued in the future and kubelet's sorting of containers by creation time got stuck once chrony stepped the clock back, and he describes the fix of starting kubelet only after time sync.

    30 min slot · Any Level · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you operate Kubernetes nodes on virtual machines and want a worked example of debugging from a stuck pod down to the hardware clock.

    1. 0:26 Mohan lays out the symptom: a CSI pod in CreateContainerError with over 5,000 retries failing on a container name reservation, while crictl on the node shows the same containers already running.
    2. 8:51 He finds kube-proxy rejected by the API server because its service account token is not valid yet, issued by a control plane VM whose clock was ahead of the other two.
    3. 10:08 Journal logs show the time jumping backwards 45 seconds after boot: he says the VM inherited a clock about eight minutes ahead from the ESXi host and chrony stepped it back in one go, after kubelet had already started.
    4. 18:55 He explains the loop: kubelet sorts container statuses by created-at wall clock time, so the attempt created on the future clock always looks newest and kubelet keeps trying to recreate an attempt that is already running.
    5. 21:36 The fix he describes is ordering the kubelet systemd unit after a chrony wait service with a 180 second timeout, chosen so a node boots slower instead of never booting when NTP is unavailable.
