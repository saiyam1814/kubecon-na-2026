    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.
