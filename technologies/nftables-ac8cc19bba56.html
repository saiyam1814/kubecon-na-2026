    Debugging the Invisible: Standardizing Kubernetes Networking Expertise

    Faseela Kundattil, Marino Wijay, James Spurin, Chad M. Crowell, Christophe Sauthier

    Five panelists who created or teach around the Certified Kubernetes Network Engineer (CKNE) exam discuss why CNCF added a hands-on networking certification and what foundational networking knowledge they think Kubernetes engineers need. They argue that AI tools can speed up troubleshooting but that an engineer still has to judge the suggested fix, and they describe what the exam covers and how to prepare.

    30 min slot · Beginner · Panel

    Networking and connectivityCommunity and open source adoption

    Watch this if: you are deciding whether to study for the CKNE exam, or you come from traditional networking and want to know how that knowledge carries over to Kubernetes.

    1. 4:10 Sauthier says CKNE is a separate hands-on exam, not an extension of CKA, because practice builds instincts for a 3 a.m. incident and he wants common ground between the older NetOps world and the cloud native one.
    2. 10:20 Spurin says network policy lets you ignore iptables, nftables and eBPF until something breaks, and argues that without that low-level knowledge a person can only approve whatever an AI tool concludes.
    3. 15:34 Kundattil gives the example of an AI tool suggesting to disable mTLS to restore pod-to-pod connectivity in a service mesh, which she calls not the right fix.
    4. 20:11 Sauthier says some exam questions name the project to use while others leave the choice open, for example Cilium or Istio, and Wijay adds that candidates need subnetting, routing and BGP fundamentals and must read a tcpdump.
    5. 28:36 Asked whether CKNE will count toward Kubestronaut, Sauthier says it becomes a requirement for both Kubestronaut and Golden Kubestronaut from February 15.

    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    SIG Network Intro and Updates

    Surya Seetharaman, Guilherme Cassolato, Austin Abro, Bowei Du

    Four SIG Network contributors review what the SIG owns and what changed in 2026 across Kubernetes core and its subprojects, including kube-proxy's planned move to nftables as the default mode, Gateway API releases, Cluster Network Policy reaching v1beta1 and the status of smaller subprojects. They also report findings from the SIG's first structured survey of its 22 subprojects, and Austin Abro describes how he used AI to make his first contribution.

    30 min slot · Level not listed · Session

    Networking and connectivityKubernetes internals and runtimes

    Watch this if: you want a year's worth of Kubernetes networking changes in one session, or you run kube-proxy and need to plan for nftables.

    1. 3:40 Bowei Du mentions a new proposal for network-isolated pods with no networking by default, which he links to agent sandbox use cases, and lists deprecations of external IPs, kube-proxy IPVS mode and the Endpoints API.
    2. 4:45 Austin Abro explains the opt-in TCP userspace proxy that lets nftables mode serve NodePorts on localhost, and advises setting the kube-proxy backend explicitly before the default changes to nftables in 1.40.
    3. 9:57 Surya Seetharaman announces the v1beta1 release of Cluster Network Policy, which unifies the former admin and baseline CRDs, and notes the work began in March 2020.
    4. 16:11 Guilherme Cassolato says the SIG ran its first structured survey of its 22 subprojects and learned that AI is driving many agendas to the point of overlap, some projects have only one or two maintainers, and maintainers want faster API review.
    5. 20:47 Abro recounts using AI to learn kube-proxy internals for his localhost NodePort contribution, and says the maintainers' insistence on not breaking existing users kept the feature opt-in.

    The Missing Layer of Platform Maturity: Kubernetes Networking

    Faseela Kundattil, Christophe Sauthier, Chad M. Crowell, Marino Wijay, James Spurin

    The panel explains why Kubernetes networking remains a maturity gap despite higher-level abstractions, using incidents and observability workflows to show why engineers still need mental models of the underlying stack. The panelists describe the hands-on CKNE exam as a vendor-flexible way to validate networking skills while arguing that AI should assist rather than replace engineering judgment.

    35 min slot · Any Level · Panel

    Networking and connectivityPlatform engineering and developer experience

    Watch this if: your platform team owns Kubernetes networking troubleshooting or is evaluating the CKNE curriculum.

    1. 1:41 The panel argues that Kubernetes networking is a missing layer of platform maturity because usable abstractions still require underlying troubleshooting knowledge when failures occur.
    2. 10:08 Chad uses a 504 ingress incident to argue for peeling back the network path locally, from pod logs and events through service endpoints to ingress routing and host-header behavior.
    3. 15:21 James argues that engineers should learn enough iptables, nftables, conntrack, and eBPF to understand failures and judge AI-suggested fixes rather than treating AI as the authority.
    4. 17:35 Chad argues that knowing where in the networking stack a problem lives matters more than loyalty to a toolset, with observability used to narrow environment and namespace before deep packet inspection.
    5. 23:31 Christophe says SMEs from varied projects designed the hands-on CKNE exam so candidates can answer with different tools rather than being forced into one stack.
