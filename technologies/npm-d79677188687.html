    Built for What’s Next: Backstage’s Role in AI-Assisted Development

    Ben Lambert, Aramis Sennyey

    Aramis Sennyey and Ben Lambert share Backstage community numbers and the coming version 1 of the new frontend system, along with changes to internationalization, Backstage UI, TechDocs, the scaffolder and the catalog. They then show how Backstage can act as shared context for AI coding agents through catalog model introspection, a new AI resource kind, MCP server entities and a CLI module, with a live demo.

    30 min slot · Level not listed · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you run a Backstage portal and want to see what the new frontend system and its AI features mean for you.

    1. 2:36 Lambert says next week's mainline release includes version 1 of the new frontend system, with Backstage's own routing replacing the hard dependency on legacy React Router.
    2. 10:33 Lambert explains the scaffolder's move from Nunjucks in isolated-vm to a new sandboxed TypeScript templating interpreter, plus template dry runs callable as actions.
    3. 14:04 Sennyey reports that catalog database and query planner optimizations made simple queries 2 to 2.5 times faster and complex queries 10 to 20 times faster.
    4. 17:42 Lambert introduces a new AI resource kind in the catalog for rules, skills, plugins and marketplaces, alongside MCP servers stored as API entities.
    5. 23:00 Sennyey demos an agent that first hallucinates a payment gateway, then uses skills synced from the catalog and the Backstage MCP server to implement a batch refund.

    Dockerfiles Made Software Reproducible. What Makes an Agent Reproducible?

    Per Krogslund

    Per Krogslund argues that a Dockerfile describes an agent's workload but says nothing about what the agent is allowed to reach, and presents Docker's open sandbox kit spec, which records those capabilities as annotations on an OCI image. He shows kits being run and built with Docker's microVM-based sandbox runtime and takes audience questions on Kubernetes support, other runtimes and updating a kit's metadata.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run coding agents and want to see one proposal for declaring an agent's network, credential and device access alongside its image so teams can share and check it.

    1. 4:54 Krogslund says a container is process isolation and not a security boundary, and that running a coding agent in a privileged container with access to the Docker socket gives it a route to the host machine.
    2. 6:57 He says Docker is building an agent runtime and supply chain on top of OCI and not a new format, that the sandbox kit spec is already open source, and that Docker has discussed handing it over to the CNCF.
    3. 11:03 He describes Docker's own runtime as a microVM with a private Docker engine whose only way out is a network proxy, which applies allow and deny rules and swaps a placeholder credential for the real one on outbound requests.
    4. 13:36 He walks through a kit's YAML file, which names the hosts the agent needs, the service credential it needs without storing it, and any agent context file, and later shows network rules that differ between install and run time.
    5. 21:31 Asked about Kubernetes, he says there is no Kubernetes runtime yet beyond an experimental version inside Docker, that the focus so far is the local experience, and that he wants input on the use cases.

    In-Toto: Experiences a Few Million Attestations Later

    Santiago Torres-Arias, James Carnegie, Sivana Hamer, Aditya Sirish A Yelgundhalli

    Santiago Torres-Arias moderates a panel on how in-toto attestations are used in practice, with James Carnegie describing Datadog's internal deployment, Aditya Sirish A Yelgundhalli speaking as a maintainer and a Bloomberg engineer, and Sivana Hamer sharing her research on attestations found in the wild. The panelists discuss making attestations easy to create, a fragmented storage picture, the coming policy framework, how consumers can trust public attestations, and what agent-written code changes.

    30 min slot · Level not listed · Panel

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you produce or consume software supply chain attestations and want to hear how two companies and a researcher see in-toto adoption, storage and policy.

    1. 8:08 Carnegie says Datadog made attestations easy to create by binding ephemeral keys to OIDC, and that it now collects source attestations for every commit and over 2 million attestations a month.
    2. 9:21 He says Datadog began evaluating policy at deployment time, first in monitoring mode and then enforcing, and now also checks policy before pull requests merge, in CI and at runtime.
    3. 14:46 Hamer says her research found 42 million attestations in the wild as of June across almost 150,000 components, often produced by tooling such as npm provenance or PyPI trusted publishing without users knowing.
    4. 17:00 Yelgundhalli explains that the in-toto policy framework sets requirements such as artifact rules without mandating one policy engine or language, and that verification itself emits an attestation.
    5. 21:33 Carnegie says consumers lack a standard way to learn which attestations a producer should publish and with which keys; Datadog distributes keys and policies internally with TUF, which he rarely sees in open source.
