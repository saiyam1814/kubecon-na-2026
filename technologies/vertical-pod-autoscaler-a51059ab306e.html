    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

    Data-Driven Platform Guardrails: What 16,500 Incidents Tell You to Automate First

    Henrique Santana, Henrique Dalssaso

    Henrique Santana and Henrique Dalssaso walk through the top root causes they found in more than 16,000 Kubernetes incidents, including IP exhaustion, auth failures and node provisioning problems. For each one they suggest platform guardrails to automate, and they explain how to run the same analysis on your own incident data.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you want a list of common Kubernetes incident root causes and the guardrails these speakers suggest automating for each.

    1. 1:35 The speakers describe their dataset as more than 16,000 incidents across many Kubernetes clusters from January to mid-May, grouped with AI and then reviewed by hand. They say DNS did not make their top 10 root causes.
    2. 3:57 They say about a third of one top pattern was pods with no IP address available, from small or shared subnets, and suggest Cilium multi-pool IPAM and broader Karpenter node pools.
    3. 6:59 For auth failures they separate missing permissions, RBAC that was never bound to the pod, and policies on the target endpoint, and suggest Kyverno policies, projected service account tokens and cert-manager.
    4. 16:20 For node provisioning failures, which they put at almost 15% of incidents, they suggest setting kube-reserved and system-reserved, Cluster API machine health checks and Karpenter node auto repair.
    5. 20:59 To repeat the analysis on your own data, they suggest classifying by what actually failed rather than the symptom, ranking by frequency, and asking whether the platform, the app team or both can fix it.

    How Anthropic Almost Melted GKE (And the PRs That Saved It)

    Maciek Różacki, Jian Cheung

    Maciek Różacki and Jian Cheung walk through six incidents from about two years of running very large GKE clusters for Anthropic, covering API server overload, a stuck StatefulSet controller, and a restart storm. For each one they describe what they saw, the short-term mitigation, and the upstream Kubernetes change they say followed.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you run large or high-churn clusters and want concrete failure stories about list requests, watch caches, startup probes and staged recovery.

    1. 3:26 Różacki describes how API Priority and Fairness underestimated the cost of large pod lists, leading to API server replicas running out of memory in a loop, and names the watch cache and list pricing changes that followed.
    2. 7:20 Cheung describes a per-node add-on whose consistent reads fell through to a full storage scan when one replica's watch cache lagged, and says a one-line change to read from the cache resolved it that night.
    3. 13:28 Cheung explains how a 404 on a pod delete made the StatefulSet controller abort its whole sync during scale-down, and advises operator authors to treat not-found on delete as success.
    4. 16:52 Cheung walks through the restart loop in which the 210-second startup probe budget the kubelet allowed was shorter than the roughly 276 seconds the CNI agent needed to become ready at that cluster size.
    5. 19:01 The speakers describe recovering by blocking node traffic at the firewall so the control plane could warm up, then letting nodes back in one address range at a time.

    In-Place Pod Resizing Like I'm 5: Scaling Without Restarts

    Carlos Santana

    Carlos Santana explains how Kubernetes handles requests to resize an existing pod's CPU and memory. He walks through the API request, the kubelet's decisions, and how Vertical Pod Autoscaler can use the mechanism.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: You want to trace a pod resize through Kubernetes and distinguish a deferred resize from a rejected request.

    1. 3:30 Santana describes why teams with long-lived or stateful pods may want to change resources without recreating the pod and rebuilding its state.
    2. 9:30 Santana walks through the per-container resize policy and shows where CPU and memory restart behavior are configured.
    3. 13:22 Santana traces a kubectl patch to the resize subresource and explains where the API server validates it.
    4. 16:55 Santana shows how an accepted resize can remain deferred on a node that has not freed enough CPU, and points to pod status for evidence.
    5. 23:50 Santana introduces Vertical Pod Autoscaler as a controller that can recommend resource sizes and discusses its in-place-or-recreate mode.

    OpenCost: What's New, What's Next, and How We're Scaling Kubernetes Cost Intelligence

    Rajith Attapattu, Warwick Peatey

    The OpenCost maintainers review what they say the project shipped over the past year, focusing on its MCP server, signed releases with SBOMs, and KubeModel, which they describe as a usage model kept separate from pricing. They show a pre-recorded MCP query from Claude Code, say the MCP endpoint is still unauthenticated, and spend the second half answering audience questions about discounts, right-sizing and AI-assisted contributions.

    30 min slot · Level not listed · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you use OpenCost and want the maintainers' account of the MCP server, the supply chain changes and how KubeModel separates usage from pricing.

    1. 4:44 Warwick Peatey describes the OpenCost MCP server as an agentic proxy for the existing REST API that is designed for agents to consume, and lists its tools for allocation, asset, cloud and efficiency costs.
    2. 7:20 He shows a pre-recorded demo in Claude Code asking what each namespace cost over the last seven days, and notes some queries are slower than the OpenCost UI on large data.

    5. 27:34 Asked about agent-written pull requests, Peatey says the project accepts contributions regardless of author as long as a person is responsible for them.

    SIG Autoscaling Project Updates

    Jack Francis, Jason Deal, Heba Elayoty, Kuba Tużnik

    Jack Francis, Jason Deal, Heba Elayoty and Kuba Tużnik give updates on Kubernetes SIG Autoscaling projects, including Karpenter's DRA support, balanced consolidation and node repair, the capacity buffer and capacity quota APIs, and the split of Cluster Autoscaler into a core plus separate provider projects. Elayoty then explains what workload-aware scheduling needs from autoscalers, and Tużnik presents scheduler-driven autoscaling, a proposed redesign in which the scheduler requests nodes from the autoscaler.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Karpenter or Cluster Autoscaler and want the latest feature updates plus the proposed redesign of how autoscalers work with the scheduler.

    1. 3:28 Jason Deal says Karpenter added DRA support in its scheduling simulation in v1.14, covering structured parameters, consumable capacity, partitionable devices and prioritized alternatives, with provider implementations in the AWS provider and EKS Auto Mode.
    2. 6:11 He introduces balanced consolidation, which weighs the share of pods disrupted against the share of cost saved and only acts when the score passes a threshold.
    3. 10:08 Jack Francis says Cluster Autoscaler is being split into a core repository and separate provider projects, and that the SIG will keep supporting releases in the older all-in-one model for a transition period.
    4. 19:50 Kuba Tużnik describes the split brain problem: the autoscaler has to predict what the scheduler will decide, and when its predictions are off it makes wrong scaling decisions.
    5. 24:15 He outlines the proposed design in which the autoscaler publishes potential capacity and the scheduler issues node claims, and estimates it at more than ten KEPs over one to two years.

    The New Scaling Matrix: Balancing In-Place Resizing, VPA, HPA and Automation Solutions

    Dolis Sharma

    Dolis Sharma reviews resource optimization options on Kubernetes, from label-driven cleanup, HPA and VPA to in-place pod resizing, and describes a central right-sizing setup in which VPA recommendations feed Kyverno policy reports and an agent opens pull requests for teams to review. The speaker then argues that agents behave differently from applications and describes Agent Substrate as a runtime that snapshots idle agent sessions.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimesAI agents and automation

    Watch this if: you run right-sizing for many teams and want a GitOps-friendly way to act on VPA recommendations, or are starting to host agents.

    1. 3:02 The speaker recalls that HPA and VPA race against each other when set on the same resources, and that VPA changes on the cluster conflict with GitOps repositories.
    2. 4:36 The speaker says in-place pod resizing was introduced with JVM startup in mind, and that it helps for CPU but not for memory because the JVM sets its heap at startup.
    3. 11:50 The speaker describes VPA in recommendation mode on spoke clusters, with Kyverno policies comparing recommendations to what is deployed and writing the difference into a policy report.
    4. 14:26 The speaker says an agent on the Argo CD hub cluster reads the policy reports and creates a pull request, and that the setup does not suggest auto merge because a human should stay in the loop.
    5. 21:39 The speaker argues that one agent per pod wastes resources while the agent waits, then presents Agent Substrate as a runtime that snapshots idle sessions and frees capacity.
