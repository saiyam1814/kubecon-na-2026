    Beyond Provisioning: Multi-Tenancy, Rack Awareness, and Declarative Networking in Metal3

    Kashif Khan, Sunnatillo Samadov

    Kashif Khan and Sunnatillo Samadov, both Metal3 maintainers, present three additions to the bare metal provisioning project: multi-tenancy through host claims, failure domains that spread control plane nodes across racks, and top-of-rack switch port configuration. They show a short recorded demo of each and close with which release and feature gate each one sits behind.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you run Kubernetes on bare metal and want several teams to share one hardware pool, rack-aware control planes, or switch ports configured from YAML.

    1. 5:40 Kashif Khan names three gaps he says Metal3 had: teams sharing hardware meant handing out BMC passwords, nothing kept control planes off a single rack, and switch port VLANs were typed by hand.
    2. 6:46 Kashif Khan explains the multi-tenancy design: tenants create a HostClaim in their own namespace, and an admin-owned HostDeployPolicy in the pool namespace decides which namespaces may consume which hosts.
    3. 12:24 Kashif Khan explains failure domains: label each BareMetalHost with its rack, list the failure domains on the Metal3 cluster, and Cluster API then spreads control plane nodes across them.
    4. 17:43 Sunnatillo Samadov introduces the BareMetalSwitch and HostNetworkAttachment resources, which he says let Ironic set switch port mode and VLAN tags during provisioning and clean them up afterwards.
    5. 23:19 The speakers give the status: multi-tenancy is alpha behind a feature gate, failure domains are available in the Cluster API provider release they name, and switch configuration is behind a feature gate in the Bare Metal Operator.

    What's New in OVN-Kubernetes?

    Surya Seetharaman

    Surya Seetharaman tours OVN-Kubernetes features, from egress IPs and network policies to user-defined networks, BGP integration, EVPN and virtual machine networking. She stresses that OVN-Kubernetes and Kube-OVN are separate CNCF Sandbox projects and says hardware offload to DPUs is a reason NVIDIA runs the project in production.

    5 min slot · Level not listed · Lightning Talk

    Networking and connectivitySecurity, identity and policy

    Watch this if: you are choosing a Kubernetes network plugin and need tenant isolation, BGP or virtual machine networking.

    1. 0:19 Seetharaman says OVN-Kubernetes and Kube-OVN are two separate CNCF Sandbox network plugins that both use OVN and OVS but differ heavily in architecture and features.
    2. 2:10 Seetharaman says user-defined networks let users create isolated layer 2 or layer 3 networks per tenant, which she says sets the project apart from other network plugins.
    3. 3:05 Seetharaman says a no-overlay mode uses FRR and a BGP underlay for pod-to-pod traffic instead of Geneve encapsulation, which she says increases throughput.
    4. 3:50 Seetharaman describes EVPN as an emerging feature that stretches tenant networks across Kubernetes clusters and to on-site networks that do not run Kubernetes.
    5. 4:38 Seetharaman says hardware offload moves OpenFlow and Open vSwitch processing to a DPU, and that NVIDIA uses OVN-Kubernetes in production because of it.
