    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    Will Your Gateway Leave You High and Dry?

    John Howard, Mitch Connors

    John Howard and Mitch Connors walk through version 3 of Howard's Gateway API Bench, which tests agentgateway, Envoy Gateway, Istio, kgateway, NGINX Gateway Fabric and Traefik on route updates, a 5,000 route scale test, route propagation time and rolling restarts. Framed around a fictional cardboard box startup, they report which implementations returned errors or used more CPU and memory in their runs, and Howard states up front that both speakers work on several of the gateways tested.

    30 min slot · Any Level · Session

    Networking and connectivityObservability and reliability

    Watch this if: you are choosing a Gateway API implementation, perhaps while moving off ingress-nginx, and want to see how six of them behaved under route churn and scale.

    1. 4:20 Howard says the two speakers are biased because they work on many of the gateways tested, and that the report is reproducible with shared data.
    2. 8:22 Howard reports that four implementations returned all 200s while a route was updated, while Envoy Gateway and NGINX had brief periods of downtime in his test.
    3. 13:59 In the 5,000 route test, Howard says the NGINX data plane used about three cores of CPU while serving no traffic.
    4. 16:40 Howard attributes the resource gap between Envoy based gateways to metrics defaults, saying Envoy Gateway and kgateway exposed 350,000 metrics out of the box.
    5. 21:11 Howard says no implementation failed during continuous backend pod restarts, while NGINX and Traefik had errors when the gateway itself was rolled out.

    Your Routes, My Rules: Making Gateway API Work at Enterprise Scale

    David Jumani

    David Jumani, a kgateway maintainer, argues that the hard part of running a gateway in a large organization is letting many teams ship routes without a platform team reviewing everything or teams breaking each other. He presents kgateway's route delegation, inherited policies and strict validation, and cites user scale numbers and resource reductions he attributes to the 2.5 release.

    5 min slot · Level not listed · Lightning Talk

    Networking and connectivitySecurity, identity and policy

    Watch this if: many teams share one gateway in your organization and you want them to own routes without breaking each other.

    1. 0:48 Jumani says Gateway API reference grants define where a route can connect but cannot require a prefix or stop one route from overriding another.
    2. 1:08 Jumani explains route delegation in kgateway: a platform team creates a parent route with a prefix and policy and delegates the sub-routes under it to specific teams.
    3. 2:16 Jumani says strict validation rejects a route with bad configuration instead of letting Envoy NACK it, which he says could otherwise bring down the whole gateway on a restart.
    4. 3:00 Jumani says one user runs kgateway with 700,000 concurrent gRPC streams, 90,000 JWT validations a second, over 200 proxies and about 300,000 pods that churn 11 times a day.
    5. 3:26 Jumani says the 2.5 release cut CPU use by 70% at 5,000 routes, memory by 95% at 40,000 routes and proxy memory by 48%.
