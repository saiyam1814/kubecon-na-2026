    Cortex: Surviving High Cardinality Metrics

    Friedrich Gonzalez

    Friedrich Gonzalez, a Cortex maintainer, explains how unbounded labels multiply series counts and what Cortex offers to detect, reduce and survive high cardinality, including per-tenant limits, active series trackers, remote write v2 with native histograms, resource-based query rejection and eviction, and the Parquet block format. He also reports on the independent security audit done for the project's CNCF graduation.

    30 min slot · Level not listed · Session

    Observability and reliabilityData, storage and state

    Watch this if: you run Cortex or another Prometheus-compatible backend and need ways to find and contain high-cardinality metrics.

    1. 3:05 Friedrich Gonzalez separates bounded labels such as status codes and templated routes from unbounded ones such as user, request and trace IDs, and recommends putting unbounded data in logs, traces and exemplars.
    2. 8:16 He says Cortex limits protect a cluster but do not show which label is the problem, and introduces active series trackers in Cortex 1.22, which count active series matching a chosen label.
    3. 13:30 He explains that a classic histogram costs one series per bucket, 13 in his example, and recommends remote write v2 with native histograms or converted custom-bucket histograms to send each as a single series.
    4. 19:12 He describes resource-based protection in which a component checks its own CPU and heap every 100 milliseconds, rejects new work past a threshold and evicts the longest-running query, a feature he says now covers the querier.
    5. 24:58 He reports that the security audit required for CNCF graduation took place in April and found only medium and low issues, all of which he says are fixed, and asks Cortex users to upgrade.

    Feeding the GPU: Streaming Data into Training, Lakehouse, and Serving without the Serialization Tax

    Dheeraj Kapur, Deepak Choudhary

    The speakers describe a streaming design in which producers send Arrow IPC batches once to a gateway that writes them to GPU memory and to a lakehouse without converting rows to columns again. They share their own measurements for throughput, query engines and crash recovery, and say the work is not open source yet.

    30 min slot · Any Level · Session

    Data, storage and stateAccelerators and workload schedulingAI inference and serving

    Watch this if: You build streaming pipelines that feed both GPUs and lakehouse tables and want to see where serialization cost goes.

    1. 2:59 The speaker says separate pipelines for the GPU, the lakehouse and other destinations each convert row data into a columnar format again.
    2. 6:37 The speaker says the producer should send Arrow IPC so that preparation happens once, and that the format converts one to one into cuDF and Parquet.
    3. 10:51 The speaker explains that the gateway transfers batches into GPU memory, stores them in a durable log for the lakehouse, and sends the acknowledgment once the data is on disk.
    4. 17:00 The speaker reports a throughput of 3 million points per second with 20 pods, and says they want to scale the system to 17 million points per second.
    5. 21:33 The speaker says a fix took them from 25,000 duplicates to zero duplicates and no data loss over two weeks of chaos testing.

    Running Stateful Analytics on Kubernetes: Lessons from Building a Distributed DuckDB Platform

    Seth McCombs, Karim Alibhai

    Seth McCombs and Karim Alibhai explain the storage and operational decisions their teams had to make when running embedded DuckDB on Kubernetes. They describe treating data as versioned releases so teams could track its provenance, stage rollouts, and roll back.

    30 min slot · Any Level · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you already run DuckDB queries and need to manage data delivery, worker failures, and rollbacks on Kubernetes.

    1. 5:39 The speakers explain that an embedded database does not provide the data delivery path, so their design needs to account for storage, retrieval, and how quickly a query needs its data.
    2. 8:14 They sketch a query router that chooses between Snowflake and Greybeam and accounts for whether data lives in object storage or on a local drive.
    3. 10:44 They describe out-of-memory failures and ask how the service should report a lost query when a worker pod dies.
    4. 19:16 They argue that versioning data packages lets a team trace a discrepancy to the pipeline that produced the data.
    5. 21:20 They describe making data part of the application release cycle, with Argo CD rollbacks and an operator reconciling which source the pods read.
