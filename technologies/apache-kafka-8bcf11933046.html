    Falco Never Flies Alone: Runtime Security as an Ecosystem

    Leonardo Grasso, Alessandro Cannarella

    Leonardo Grasso and Alessandro Cannarella describe how Falco, now ten years old, spent the year consolidating its core and growing an ecosystem around it. They cover core and plugin updates, new experiments for AI coding agents, Falco Operator 0.5, and a from-scratch rewrite of Falcosidekick as version 3.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you run Falco for runtime security and want to see what changed in its core, the Falco Operator and Falcosidekick.

    1. 0:51 Grasso explains how Falco taps the Linux kernel with an eBPF probe or kernel module, enriches events with plugins, and matches them against YAML rules.
    2. 3:22 Grasso lists core cleanups such as removing the legacy BPF probe and gVisor support, new list operators in the rule language, and an experimental GPU hijacking rule.
    3. 6:38 Grasso introduces a new subproject that gives coding agents a version-pinned knowledge base and skills for contributing to the Falco code base.
    4. 16:35 Cannarella says Falco Operator 0.5 pulls artifacts from the registry once, serves them to every node, and checks rules against the Falco version before installing.
    5. 19:55 Cannarella announces Falcosidekick version 3, rewritten with per-output pipelines, live config reloads, API and UI configuration, and a single binary.

    Feeding the GPU: Streaming Data into Training, Lakehouse, and Serving without the Serialization Tax

    Dheeraj Kapur, Deepak Choudhary

    The speakers describe a streaming design in which producers send Arrow IPC batches once to a gateway that writes them to GPU memory and to a lakehouse without converting rows to columns again. They share their own measurements for throughput, query engines and crash recovery, and say the work is not open source yet.

    30 min slot · Any Level · Session

    Data, storage and stateAccelerators and workload schedulingAI inference and serving

    Watch this if: You build streaming pipelines that feed both GPUs and lakehouse tables and want to see where serialization cost goes.

    1. 2:59 The speaker says separate pipelines for the GPU, the lakehouse and other destinations each convert row data into a columnar format again.
    2. 6:37 The speaker says the producer should send Arrow IPC so that preparation happens once, and that the format converts one to one into cuDF and Parquet.
    3. 10:51 The speaker explains that the gateway transfers batches into GPU memory, stores them in a durable log for the lakehouse, and sends the acknowledgment once the data is on disk.
    4. 17:00 The speaker reports a throughput of 3 million points per second with 20 pods, and says they want to scale the system to 17 million points per second.
    5. 21:33 The speaker says a fix took them from 25,000 duplicates to zero duplicates and no data loss over two weeks of chaos testing.

    Follow the GPUs: How a Regulated Fortune 100 Serves Customers When No Single Cloud Has Enough

    Yuva Peavler, Michael Kinsley

    Yuva Peavler and Michael Kinsley of GEICO describe their hybrid cloud platform, a flat network across providers with a zero trust overlay built on SPIFFE/SPIRE, Istio and Cilium, and say it lets them move workloads to wherever GPUs are available. Michael then shares a tool they wrote to probe GPU availability across AWS and Azure regions, what four weeks of samples showed them, and their idea for a booking agent that reserves capacity ahead of demand.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you need GPUs without long reservations and want measured data on whether multi-region and multi-cloud help.

    1. 1:45 Michael gives the takeaways first: current single-GPU SKUs need multi-region support, flagship eight-GPU nodes have to be booked ahead, and he says the autoscaler will not do the booking.
    2. 3:43 Yuva explains the platform from the bottom up: one flat L3 network across every provider, identically built Kubernetes clusters, then SPIFFE/SPIRE identity, Istio mutual TLS and Cilium deny-by-default policy.
    3. 8:54 Yuva says they made SPIRE's data store pluggable in their fork and run Cassandra behind it for an active-active multi-region control plane, and that they have proposed this upstream.
    4. 16:54 Michael introduces their Follow the GPUs tool, which asks for GPUs, doubles the request after each yes until it gets a no, then waits about an hour and starts again.
    5. 22:02 Michael reports that in their data multi-region did not matter for small single-GPU SKUs but raised the chance of getting an RTX Pro 6000 from about 45% to 70 to 75%.

    Managing Network Security in Multi-Tenant Environments with Istio and Cilium

    Michael Bolot, Zaira Shaikh

    Michael Bolot and Zaira Shaikh of GEICO describe replacing a mix of cloud firewalls, on-premises firewalls and in-cluster policies with one API that configures Istio and Cilium across clusters on a flat, routable pod IP space. They explain how SPIRE identities and Istio authorization policies decide which applications may talk, while a small set of Cilium policies blocks what bypasses the sidecar, and they close with tips for writing Cilium policies safely.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you run Cilium and Istio together and want to hear how one platform team splits network policy duties between them.

    1. 1:44 Bolot lists the problems with the legacy setup: no unified definition of the policy affecting a device, manual configuration, inconsistent enforcement and a complex network topology.
    2. 7:03 Shaikh describes the new system: pods are restricted by Istio resources and network policies written by a data plane agent on every workload cluster, configured from a central API server, with Cilium's BGP features advertising all pod IPs.
    3. 15:03 Bolot says SPIRE handles authentication by issuing workloads a certificate after attestation, and Istio authorization policies state what a given SPIFFE ID may reach, with service entries and workload entries connecting clusters.
    4. 19:55 Bolot gives three reasons they do not use Cilium for everything: they want authorization based on SPIFFE IDs, user-chosen labels would exhaust Cilium's identity map, and Cilium's layer 7 Envoy would duplicate the one Istio already runs.
    5. 25:29 Shaikh shares tips for Cilium policies, including using audit mode and Hubble, minding the default enforcement mode, and never cutting the operator or etcd off from the API server.

    Gang Luo

    25 min slot · Intermediate · Session

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    Tracing at Scale: Running a 16 Billion Spans/Hour Pipeline at Nubank

    Felipe Araujo, Kaynan Coelho

    The speakers describe how Nubank built its distributed tracing pipeline, from instrumenting a handful of shared libraries to an ingestion platform built around the OpenTelemetry Collector, micro-batches on S3 and queues, KEDA scaling and tail sampling with Refinery before data goes to Honeycomb. They share the sampling rules they settled on, cases where traces helped them cut latency and storage, and advice for teams building something similar.

    30 min slot · Any Level · Session

    Observability and reliability

    Watch this if: You are scaling distributed tracing past what head sampling and a single vendor pipeline handle and want one bank's architecture and sampling choices.

    1. 1:34 Kaynan Coelho says the pipeline now receives more than 23 billion spans per hour, over 700 terabytes of data a day, and that five engineers work on it full time.
    2. 4:01 Coelho explains that because most Nubank services share the same Clojure template and libraries, they instrumented six core libraries instead of more than 4,000 services.
    3. 8:21 Felipe Araujo says streaming was too expensive and large batches too slow, so the collector writes roughly 10-second micro-batches to S3 and a queue notification tells the next application to pick them up, a pattern he identifies as claim check.
    4. 12:06 Araujo says percentage-based tail sampling hid rare critical paths, so they moved to dynamic rules that keep slow requests and all 500 errors and reduce fast, common successes.
    5. 14:23 Coelho describes using traces to find that some app requests waited on more than 30 content providers, and says the fixes brought latency in those transactions down to about 200 milliseconds.

    Validating Kubernetes Workloads: Checklists and Best Practices

    Nabarun Pal, Maciej Szulik, Liz Rice, Ricardo Aravena

    Organizers of the Kubernetes working group on workload conformance explain its charter: define how a well-behaved workload acts in a cluster, write objective tests for that, and eventually propose a CNCF conformance program. Most of the session is discussion with the audience about what should be in scope, including configuration variants, SBOMs, neutrality of the requirements and upgrade paths.

    30 min slot · Level not listed · Birds of a Feather

    Kubernetes internals and runtimesCommunity and open source adoption

    Watch this if: you ship or operate applications on Kubernetes and want a say in what a conformance check for well-behaved workloads should test.

    1. 1:53 Pal sets out the working group's charter: define generic behavior of workloads on Kubernetes, write verifiable tests for it, and build a conformance suite to hand to steering and architecture for vetting, while saying the group is far from that point.
    2. 6:25 Szulik says one goal is for an application vendor to be able to say its workload is a good citizen, for example respecting disruptions and graceful node shutdown, in the way a provider shows a cluster is conformant, with tooling anyone can run on their own apps.
    3. 14:16 An audience member asks for SBOMs with every delivered application; Szulik says the group had planned only must conditions and that he now leans toward adding optional ones, and Pal notes this would mean choosing between formats such as CycloneDX and SPDX.
    4. 18:35 An audience member warns that an earlier operator conformance effort turned into subjective rules such as requiring startup probes, and Szulik answers that he has no solution yet and that finding common ground is why the working group was started.
    5. 27:38 On upgrades, Pal says the group does want to check upgrade readiness, such as flagging use of deprecated Kubernetes APIs, and points to the API server's deprecated API usage metrics as one way to test it.
