    Falco Never Flies Alone: Runtime Security as an Ecosystem

    Leonardo Grasso, Alessandro Cannarella

    Leonardo Grasso and Alessandro Cannarella describe how Falco, now ten years old, spent the year consolidating its core and growing an ecosystem around it. They cover core and plugin updates, new experiments for AI coding agents, Falco Operator 0.5, and a from-scratch rewrite of Falcosidekick as version 3.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you run Falco for runtime security and want to see what changed in its core, the Falco Operator and Falcosidekick.

    1. 0:51 Grasso explains how Falco taps the Linux kernel with an eBPF probe or kernel module, enriches events with plugins, and matches them against YAML rules.
    2. 3:22 Grasso lists core cleanups such as removing the legacy BPF probe and gVisor support, new list operators in the rule language, and an experimental GPU hijacking rule.
    3. 6:38 Grasso introduces a new subproject that gives coding agents a version-pinned knowledge base and skills for contributing to the Falco code base.
    4. 16:35 Cannarella says Falco Operator 0.5 pulls artifacts from the registry once, serves them to every node, and checks rules against the Falco version before installing.
    5. 19:55 Cannarella announces Falcosidekick version 3, rewritten with per-output pipelines, live config reloads, API and UI configuration, and a single binary.

    Kevin Dubois

    Dubois uses a multiplayer racing game to demonstrate an agentic application with MCP tools and cooperating agents. He explains how he inspects and tests the application locally and what he would monitor and secure when deploying it to Kubernetes.

    30 min slot · Any Level · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are building an agentic application locally and want practical checks before deploying it to Kubernetes.

    3. 22:41 He opens the Quarkus developer UI to inspect Kafka game events, AI services, and the MCP tools the game exposes.
    4. 24:34 He shows how a model change led a game agent to choose a different speed multiplier and recommends adding evaluations to the test suite.
    5. 26:13 He recommends checking the health of sub-agents and MCP servers, not just the main application, and measuring latency and token usage.

    Millions of Events, One Right Order: Financial Data Processing at Intuit

    Yashash Lokesh, Sri Harsha Yayi

    The speakers describe using Numaflow to process streams of Intuit financial events on Kubernetes. They walk through a simple transaction pipeline, a multi-stage analytics pipeline, and an ordering example for customer account events.

    30 min slot · Any Level · Session

    Data, storage and state

    Watch this if: You are building a streaming pipeline where financial events for the same account must stay in order.

    1. 8:32 The speakers explain why Intuit wanted a common streaming platform: language lock-in, scaling through downstream bottlenecks, and preserving the order of financial events.
    2. 12:26 The speakers show a live transaction pipeline that consumes events from Kafka using a single Numaflow vertex.
    3. 15:13 The speakers walk through a financial analytics pipeline that filters at the source, pre-aggregates records, and routes results to different sinks.
    4. 16:36 The speakers use customer account changes to explain Numaflow's ordering option and why related events must stay in sequence throughout the pipeline.
    5. 18:23 The speakers explain how the same event pipeline can support model inference or agents by scaling its components independently.

    Platform as Context: Evolving Our IDP for AI Agents

    Gang Luo

    Gang Luo of Electrolux Group explains how his team extended their internal developer platform so AI agents can use it as context through MCP tools. He shares the context categories they defined, a switch to GraphQL, and benchmarks where he reports lower token use and fewer tool calls.

    25 min slot · Intermediate · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    1. 1:56 Luo describes the starting point: about 400 developers, an average of six SREs, and an IDP where developers pick templates, get approval and have infrastructure provisioned for them on golden paths.
    2. 3:50 Because developers work in the IDE and terminal, his team added MCP read and write tools on top of the IDP so agents can read and provision the infrastructure it manages.
    3. 6:41 He lists the context agents need, starting with ownership, then infrastructure, deployment through GitHub Actions and telemetry, and says the IDP should hold only what is needed and point to the other sources.
    4. 9:29 He says moving the MCP tools from static APIs to GraphQL cut the tokens an agent used for discovery by about 80% from roughly 17K.
    5. 12:19 In benchmarks comparing an agent with GitHub alone against GitHub plus the IDP, he reports one task using 50% fewer tool calls and 65% fewer tokens, while noting some experiments got worse.

    The Seams Are the Trap: Agent Fleets from CNCF Parts You Already Have

    Aleksander Slominski, Mariusz Sabath

    The presenters describe assembling an event-driven agent fleet from Kubernetes, KEDA, Kafka, and signed CloudEvents instead of buying an agent platform. They explain the limits of tying identity to a pod and show a recorded demo in which a worker rejects an unsigned event.

    30 min slot · Advanced · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to reuse a Kafka and Kubernetes stack for agent workers and verify who sent their tasks.

    1. 3:09 The speaker describes using CloudEvents as a standard envelope so producers do not have to invent their own event types, identifiers, and payload structure.
    2. 4:29 The speaker says KEDA uses Kafka lag to decide when to bring up workers and can scale them back to zero when no events remain.
    3. 10:11 The speaker explains that the runner checks a signed event's origin and whether the agent may consume it, while Kafka preserves the event sequence for audit.
    4. 11:04 The speaker says SPIFFE and SPIRE can identify a workload, but asks how that identity should change when an agent loads new skills or plugins.
    5. 23:36 The speaker shows the recorded audit check and an agent rejecting an unsigned event that was sent directly to Kafka.
