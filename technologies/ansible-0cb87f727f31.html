    Follow the GPUs: How a Regulated Fortune 100 Serves Customers When No Single Cloud Has Enough

    Yuva Peavler, Michael Kinsley

    Yuva Peavler and Michael Kinsley of GEICO describe their hybrid cloud platform, a flat network across providers with a zero trust overlay built on SPIFFE/SPIRE, Istio and Cilium, and say it lets them move workloads to wherever GPUs are available. Michael then shares a tool they wrote to probe GPU availability across AWS and Azure regions, what four weeks of samples showed them, and their idea for a booking agent that reserves capacity ahead of demand.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingNetworking and connectivityPlatform engineering and developer experience

    Watch this if: you need GPUs without long reservations and want measured data on whether multi-region and multi-cloud help.

    1. 1:45 Michael gives the takeaways first: current single-GPU SKUs need multi-region support, flagship eight-GPU nodes have to be booked ahead, and he says the autoscaler will not do the booking.
    2. 3:43 Yuva explains the platform from the bottom up: one flat L3 network across every provider, identically built Kubernetes clusters, then SPIFFE/SPIRE identity, Istio mutual TLS and Cilium deny-by-default policy.
    3. 8:54 Yuva says they made SPIRE's data store pluggable in their fork and run Cassandra behind it for an active-active multi-region control plane, and that they have proposed this upstream.
    4. 16:54 Michael introduces their Follow the GPUs tool, which asks for GPUs, doubles the request after each yes until it gets a no, then waits about an hour and starts again.
    5. 22:02 Michael reports that in their data multi-region did not matter for small single-GPU SKUs but raised the chance of getting an RTX Pro 6000 from about 45% to 70 to 75%.

    Sandboxing on Kubernetes with WebAssembly: A Hands-on Tutorial

    Eric Gregory, Bailey Hayes

    Eric Gregory and Bailey Hayes use wasmCloud and Kubernetes to show how WebAssembly components get explicit permissions for the resources they need. In the workshop, they start with an agent that has no tools and add capabilities one at a time, then show a separate scaling benchmark.

    80 min slot · Beginner · Tutorial

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: You want to see a WebAssembly sandbox on Kubernetes and how to grant an agent tool only the access it needs.

    1. 6:18 The speakers explain the deny-by-default model and show where the wasmCloud operator schedules a workload onto a host pod.
    2. 23:14 The speakers introduce the workshop's scripted model and explain why it makes the effect of sandbox permissions easier to distinguish from model behavior.
    3. 37:40 The speakers build an optional Rust component and inspect the WebAssembly interfaces it imports for HTTP and filesystem access.
    4. 56:36 The speakers demonstrate a narrow GitHub integration for triaging pull requests and explain how the host plugin keeps the sign-in token out of the workload.
    5. 1:03:56 The speakers switch from the single-instance workshop to a recorded density test and explain the resource constraints they encountered while scaling on Kubernetes.

    So You Want to Build a Platform? You Probably Already Have One

    Juho Syrjänen

    Juho Syrjänen argues that teams with infrastructure-as-code modules, Helm charts and CI/CD pipelines already have a platform, and that the next step is to wrap that code behind a platform API instead of rebuilding it. He describes how module version drift and agent-generated pull requests strain the module-per-repository model, and shows an approach using Kratix where a short custom resource triggers the existing code.

    30 min slot · Any Level · Session

    Platform engineering and developer experience

    Watch this if: you maintain Terraform or OpenTofu modules and Helm charts and want a way to turn them into a self-service platform without a rewrite.

    1. 3:11 The speaker describes the tempting plan of rebuilding everything with Crossplane, kro, Backstage and Kratix over a couple of years, and the pushback he says that proposal gets.
    2. 5:29 The speaker says the engineering behind existing infrastructure as code is solid and asks why it should not be reused.
    3. 11:54 The speaker proposes packaging the module and its wiring into one platform capability, which he describes as a single deterministic unit, with user configuration cut to about a dozen lines of YAML.
    4. 17:56 The speaker walks through delivery: the platform writes rendered output to a Git repository, Flux syncs it into destination clusters, and in-cluster operators apply it to the cloud provider.
    5. 19:19 The speaker says users and agents can then act on the platform without extra pull request approvals because a human already approved the platform code, then names Kratix and Crossplane as tools that help.

    What's New with Kubectl and Kustomize … and How You Can Help!

    Eddie Zaneski, Yugo Kobayashi, Maciej Szulik, Marly Salazar

    The SIG CLI maintainers walk through the past year of Kustomize and kubectl changes, including kuberc, KYAML and the move from SPDY to WebSockets. They then describe ideas they are still working on, ask for contributors, and take audience questions on drain flags and multi-cluster commands.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesDelivery, GitOps and release safety

    Watch this if: you use kubectl or Kustomize daily and want to know what changed, what is planned, and where a first contribution is easiest.

    1. 5:18 Yugo Kobayashi says AI contributions have raised the number of open Kustomize PRs and that he is preparing an AI contribution guide: state when AI was used, generated code is acceptable, but AI is not to be used for communication with maintainers.
    2. 7:25 Marly Salazar covers kuberc, which she says now includes command aliasing and a credential plugin allowlist, and the maintainers say it has fully graduated.
    3. 10:35 Maciej Szulik explains new node lifecycle conditions for maintenance, which he says were published in 1.37 and are being added to kubectl drain as an alpha behind a feature flag.
    4. 14:42 Eddie Zaneski describes the idea of a CRI-native copy API to replace the tar-based kubectl cp, which the maintainers say has a long history of path traversal CVEs.
    5. 20:37 The maintainers say Kustomize is kept alive by one maintainer and ask users to get their employers to let them contribute.

    Your GPU Nodes Deserve Better: Flatcar Container Linux for AI Workloads

    Jan Bronicki, Sayan Chowdhury

    Flatcar maintainers Jan Bronicki and Sayan Chowdhury introduce Flatcar Container Linux as an immutable, image-based operating system provisioned from a Butane configuration, and explain its read-only /usr partition, A/B updates and release channels. In recorded demos they provision a VM, add Kubernetes as a systemd system extension, bring up GPU nodes with NVIDIA drivers shipped as an extension, and switch driver versions with a config change and a reboot.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you run GPU nodes on Kubernetes and want to see how an immutable host OS handles NVIDIA driver updates and rollbacks.

    1. 5:12 Jan Bronicki presents the idea of the operating system as code: Flatcar is provisioned rather than installed, from one Butane YAML file applied at first boot, and the whole OS updates atomically so machines do not drift.
    2. 12:02 Sayan Chowdhury explains A/B partition updates, in which a new version is staged to the inactive /usr partition and becomes active after a successful boot, with automatic rollback to the previous version if the boot fails.
    3. 18:42 In a recorded demo, Jan Bronicki adds Kubernetes to a Flatcar VM as a systemd system extension declared in Butane, and shows kubeadm and kubectl available under the read-only /usr.
    4. 22:18 He explains that NVIDIA drivers are packaged as a system extension pinned to the kernel and Flatcar release, so they update and roll back with the OS, then shows nvidia-smi working on a Flatcar GPU node.
    5. 26:22 Sayan Chowdhury shows a recorded driver change on an AWS instance, editing the extension configuration from the 570 driver to 580 and rebooting to load the newer driver.
