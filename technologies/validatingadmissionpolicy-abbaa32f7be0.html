    From Disk to Defense: Kubernetes Admission Policies the API Can't Touch

    Anish Ramasekar, Benjamin Elder

    The speakers present manifest-based admission control, which loads admission webhooks and policies from files on the API server's disk so that they cannot be deleted through the Kubernetes API. They replay a made-up outage in a recorded demo and describe the feature's limits, reload behavior and release status.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: You operate Kubernetes control planes for other teams or customers and want guardrails that a cluster admin cannot delete.

    1. 2:37 The speakers say a policy stored as an API object can be deleted like any other object, and that the API does not allow a policy that intercepts policies.
    2. 7:24 The speakers explain that policies are loaded from a directory on disk before the API server serves anything, the same idea as static pods.
    3. 8:55 The speakers say the feature gate was alpha in Kubernetes 1.36 and is beta and on by default in 1.37.
    4. 13:49 The speakers list the limits: no param refs, no service references, no service account tokens, and nothing that depends on the API.
    5. 16:46 The recorded demo starts on a kind cluster running Kubernetes 1.37, where the Helm upgrade, the webhook and the prune are denied.

    Goodbye Webhooks, Hello CEL: Using Native Validating and Mutating Admission Policies in Kubernetes

    Greg Bray

    Greg Bray of Google Cloud explains how ValidatingAdmissionPolicy and MutatingAdmissionPolicy let Kubernetes evaluate CEL expressions inside the API server, which he says avoids the latency and failure risk of admission webhooks. He also covers where he thinks the native policies fall short and a full policy engine such as Kyverno or Gatekeeper is still needed.

    30 min slot · Any Level · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you run admission webhooks for simple checks and want to know which of them can move to policies built into the API server.

    1. 4:49 Bray lists the pain points of webhooks: the API server has to call out of process, and he says a failing webhook set to fail closed can bring the whole control plane to a halt.
    2. 8:20 He shows CEL optional values, which he says arrived in Kubernetes 1.29 and replace long guarded expressions for fields such as annotations that may not exist.
    3. 12:16 He walks through MutatingAdmissionPolicy, which he says went GA in April, and compares declarative apply configurations with imperative JSON patches.
    4. 18:13 He describes manifest-based policies loaded from disk before the API server starts serving, which he says close the bootstrap gap and cannot be changed or deleted through the API.
    5. 20:46 He lists the limits of native policies: they see only the request and the old object, cannot read other resources or external data, and stop when a CEL cost budget is exceeded.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    The Next Generation of Kyverno — Unified Policy as Code at Scale

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.
    3. 11:57 He describes a policy that intercepts Argo CD sync events and allows them only when a custom resource shows an approved change management window is open, with a precise denial reason otherwise.
    4. 13:34 He shares lessons learned: start in audit mode, treat the denial message as the user interface, make the paved path compliant by default and ship policy through the normal software lifecycle.
    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.
