    Beyond Dashboards: A Semantic Layer for AI-Driven Observability in Kubernetes

    Pronnoy Goswami

    Pronnoy Goswami argues that pasting raw logs and traces into an LLM gives unreliable answers, and presents a four-layer design that uses OpenTelemetry for consistent context and an MCP server that exposes typed, bounded, summarized tools instead of raw query access. He shows a recorded local demo with synthetic data and shares lessons on cardinality, latency and when he thinks the approach reduces MTTR.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automation

    Watch this if: you are wiring an AI agent to your metrics and traces and want a bounded design for it.

    1. 1:52 Pronnoy lists four ways he says raw telemetry in a prompt fails: volume, no schema, unbounded queries and no provenance.
    2. 4:20 He outlines the four layers: instrument with OpenTelemetry semantic conventions, collect and store, an MCP semantic query layer, and agents with human approval.
    3. 9:21 He says MCP tools should be designed for how an on-call engineer thinks rather than wrapping the Prometheus API, and should be typed, discoverable, summarized and cited.
    4. 13:00 In a recorded demo with a fault injected into a payments API, the tool reports spikes in the checkout API's error ratio and p99 latency and in the payments API's p99 latency as the top three signals.
    5. 17:32 He shares production lessons: never offer a free-form group by, back the catalog with recording rules, set per-tool timeouts and budgets, cache, and summarize inside the server.

    Lin Sun

    Lin Sun uses a live drone photo and a group of Kubernetes-hosted agents to make a short film with the audience. When the workflow hits a rate limit, she shows an agent proposing a pull request for human review and uses distributed traces to see what went wrong.

    AI agents and automation

    Watch this if: you want a live example of agents working across Kubernetes, pull requests, authentication, and distributed tracing.

    1. 1:14 Sun introduces the drone pilot and uses the live flight to capture an image of the audience for the demo.
    2. 2:49 Sun shows how she deploys agents with Argo CD and describes the services that let suspended agents resume when needed.
    3. 7:01 Sun calls on a platform agent to troubleshoot a rate-limit error, then reviews the pull request it opens before approving it.
    4. 12:39 Sun asks the audience for permission to publish the film and explains why the publishing tool requires authentication.
    5. 13:38 Sun uses distributed traces to identify the earlier rate-limit error and show where the successful run spent time generating video.

    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    80 min slot · Any Level · Tutorial

    Observability and reliability

    1. 4:14 The presenters explain why the Collector moved from component-specific conditions to a shared transformation language.
    2. 12:53 The presenters compare three ways to debug a statement: inspecting emitted telemetry, tracing individual evaluations, and testing in the OTTL playground.
    3. 30:16 The presenters use AI-related spans to show why processing order matters when some spans need a separate destination but the full trace also needs to be preserved.
    4. 37:01 The presenters use the OpenTelemetry Collector Builder to scaffold a custom Collector and explain where a custom transform function fits.
    5. 53:36 The presenters use ottl.run to demonstrate renaming legacy HTTP attributes to the current semantic-convention names.

    Sample Smarter, Not Harder (Or Not At All!)

    Reese Lee, Juliano Costa

    Reese Lee and Juliano Costa say sampling at the backend doesn't remove the overhead of generating telemetry in the application. Using the OpenTelemetry Demo, they compare disabling redundant instrumentation with probabilistic, policy-based tail, and adaptive sampling.

    30 min slot · Any Level · Session

    Observability and reliability

    Watch this if: You want to cut tracing overhead and keep visibility into slow, failing, or low-traffic requests.

    1. 8:58 The speakers show how they disabled overlapping HTTP instrumentation in the Node.js frontend so it did not generate spans they did not need.
    2. 11:49 The speakers set the collector to sample ten percent probabilistically and compare spans received by the collector with spans sent to Jaeger.
    3. 15:43 The speakers explain that tail sampling sends complete traces to the collector so it can apply policies before forwarding or dropping them.
    4. 16:49 The speakers show tail-sampling rules that keep errors and requests above a latency threshold rather than relying on a fixed fraction for all traces.
    5. 21:41 The speakers describe how adaptive sampling responds to changes in load so a rare checkout flow is more likely to remain visible during a traffic spike.

    Securing Rural Colorado with Open Source: Running a Student-Led SOC on Kubernetes

    Maciej Wal

    Maciej Wal describes how the Cybersecurity Center at Metropolitan State University of Denver replaced a vendor's security monitoring service, first with four virtual machines and then with a Kubernetes platform that he says he runs as the one full-time staff member. He covers the outages and adoption problems along the way, and how students learn log analysis and GitOps on the platform that monitors public sector partners.

    30 min slot · Any Level · Session

    Security, identity and policyObservability and reliability

    Watch this if: you are a very small team weighing Kubernetes for a security monitoring service, or want ideas for teaching students with real infrastructure.

    1. 3:19 The speaker says that after the vendor ended the service he built a replacement in about 66 days on four virtual machines, with WireGuard, single-node OpenSearch and a new ticketing tool.
    2. 6:45 The speaker explains picking the Kubernetes stack from the CNCF landscape, including Keycloak, Argo CD, OpenTofu and Fluent Bit, and says it cost around $1,000 a month.
    3. 8:33 The speaker recounts a flood of Suricata logs taking down the OpenSearch cluster, which he says had too little memory and no autoscaling, and learning of breakage days late.
    4. 12:01 The speaker says one of the hardest problems he found was the gap between offering self-service and people using it, after students did not adopt browser certificate access.
    5. 13:48 The speaker describes a student workshop on Argo CD, Envoy Gateway, cert-manager and GitHub Actions that ended with deploying a Minecraft server through GitOps.

Nili Guy then describes early work combining llm-d metrics with OpenCost to estimate the cost per token for self-hosted models by tenant and hardware.

    The Prompt Layer: What Platform Engineering Has to Own Next

    Atulpriya Sharma

    The speaker argues that developers still decide alone which model to use, what to send to it and how much to spend, and that platform teams should own these decisions. He describes a prompt layer of five components built from existing tools and shows a recorded demo where an allow list keeps a secret file out of a prompt.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceAI agents and automation

    Watch this if: You run a platform team and developers in your organization each choose their own AI models, context and budgets.

    1. 11:51 The speaker says platforms already cover running and serving models, but developers still carry the load of choosing a model for each task and deciding what is safe to paste.
    2. 14:09 The speaker says an AI gateway enforces whatever you give it, including nothing, and quotes a line he attributes to the Platform Capability Factors paper that tooling can enforce a standard but cannot decide it.
    3. 16:35 The speaker lists the five components of the prompt layer: capability interface, context templates, token governance, agent permissions and observability.
    4. 20:24 The speaker says budgets should be assigned to a capability such as code review, not to a key or a person, and suggests falling back to a cheaper model at the limit.
    5. 27:32 In the recorded demo, the assistant with the prompt layer does the code review but cannot read the secret file, which the speaker says was dropped before the prompt reached the LLM.

    Verticalizing Platform Intelligence for Regulated Domains

    William Rizzo, Kasper Borg Nissen

    William Rizzo of Mirantis and Kasper Borg Nissen of Dash0 argue that limits on AI agents in regulated industries should be enforced by the platform and not by the agent framework or its system prompt. They demo an insurance claims setup in which, as they describe it, agents get SPIFFE identities, reach tools only through a gateway with a hard payout ceiling, and leave an audit trail in OpenTelemetry traces.

    30 min slot · Advanced · Session

    Security, identity and policyAI agents and automationPlatform engineering and developer experience

    Watch this if: you have to put AI agents on a platform in a regulated business and need to show auditors what an agent did and who allowed it.

    1. 9:01 Rizzo describes the agent's identity as a passport: a SPIFFE-validated identity with no stored passwords, with Linkerd restricting which paths the agent can reach.
    2. 11:27 Nissen shows the two controls they set in agentgateway: a CEL rule with a hard 50,000 euro payout ceiling and an MCP guardrail that calls their own policy decision service.
    3. 13:00 Nissen explains using an OpenFeature flag to set how much autonomy the agent has, from every claim needing human approval to automatic payouts up to a set amount.
    4. 19:32 In the demo a customer message tries prompt injection to get 80,000 euros paid out, and Nissen shows the gateway refusing a payment above the ceiling.
    5. 23:41 Nissen shows the policy decision recorded as a custom span with attributes defined through OpenTelemetry Weaver, and the human approval linked to it as a second trace.
