    10 Years of Minikube and the Future of Millions of Users

    Medya Ghazizadeh

    The speaker, who says he led minikube for seven years, looks back on the project's ten years, including its testing infrastructure, benchmarking tools, and growth in downloads. He describes the project's reduced staffing since 2025, his own burnout and departure from Google, and what he hopes the next maintainers will do.

    30 min slot · Level not listed · Session

    Community and open source adoptionPlatform engineering and developer experience

    Watch this if: you use minikube or maintain an open source project and want a longtime maintainer's account of how it was built and what it needs next.

    1. 5:04 The speaker says minikube lets users choose the container runtime and whether to run in a container or a VM, and that its VM drivers allow AI workloads on a MacBook's GPU.
    2. 14:42 The speaker says the project ended up with 300 integration tests across 21 environment combinations, and credits that testing with catching Kubernetes regressions.
    3. 19:21 The speaker says a benchmark showed minikube's slow start came from lacking a preload mechanism, not from the driver, and that with preloads a VM-driver cluster starts in 13 seconds.
    4. 22:05 The speaker says that in 2025 he absorbed the work of four or five people, and that he rejected advice to let the project break in order to attract funding.
    5. 24:33 The speaker says he can no longer work on minikube full-time and hopes the next maintainers grow the bench, end reliance on any single company, and gain representation in Kubernetes decision-making.

    Five Stages of Kubernetes Security Grief

    Ann Wallace, Kavitha Daula

    Ann Wallace and Kavitha Daula walk through denial, anger, bargaining, depression and acceptance as stages of Kubernetes security, with Wallace voicing what teams say at each stage and Daula describing a CVE in the shared Linux kernel or container runtime that she says undercuts it. They conclude that namespaces and policies remain needed but do not give a workload its own kernel, and argue for hypervisor-based isolation with a guest kernel per workload.

    30 min slot · Any Level · Session

    Security, identity and policy

    Watch this if: you treat Kubernetes namespaces as a tenant boundary and want a quick tour of the kernel and runtime CVEs the speakers use to argue for hypervisor-based isolation.

    1. 3:09 For the denial stage, Daula says Kubernetes namespaces organize workloads but containers still share one Linux kernel, and walks through CVE-2022-0492, where a container could use the cgroups v1 release agent to run code as root on the host.
    2. 5:44 For anger, she describes a Netfilter use-after-free reachable from a container's own user and network namespaces, which she says researchers exploited to become root even though the application never touches firewall rules.
    3. 8:42 For bargaining, she recounts the 2019 runc escape in which the host runc binary could be overwritten, noting that running as non-root or enforcing SELinux could have prevented it but that policy does not patch a vulnerable runtime.
    4. 11:36 For depression, she explains Leaky Vessels, where a leaked file descriptor in runc gave a container access to the host file system, and says it covered four CVEs across runc and BuildKit.
    5. 13:46 For acceptance, Daula argues for changing the isolation boundary itself by giving each workload its own guest kernel behind a hypervisor, and says vulnerabilities do not disappear and the security policies are still needed.

    KubeVirt's Architectural Leap: Pluggability, AI Hardware, and Maturing Governance

    Vladik Romanovsky, Itamar Holder

    KubeVirt maintainers Vladik Romanovsky and Itamar Holder mark the project's tenth year and its CNCF graduation by reviewing its pod-based architecture, its adoption of an enhancement proposal process, and this year's work on confidential VMs, NVIDIA hardware support and Dynamic Resource Allocation. Holder then explains the plugin framework from enhancement proposal 190, which is meant to let features be built out of tree, along with early work on supporting hypervisors beyond QEMU/KVM and the idea of using KubeVirt as an isolation backend for agent sandboxes.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run or extend KubeVirt and want to know how the plugin framework will replace sidecar hooks.

    1. 1:02 Vladik Romanovsky recalls early doubts about the project and explains the choice to tie a virtual machine's life cycle to a pod and run the virtualization stack inside it, which he says let KubeVirt reuse the Kubernetes security model, CNI, CSI and device plugins.
    2. 6:48 He says the last cycle had more than 100 open enhancement proposals, and that the project built a per-release tracker plus an AI agent that gathers related pull requests and estimates how likely each piece of work is to land by the freeze.
    3. 9:23 He describes building support for NVIDIA's newest hardware in a fork with Red Hat and NVIDIA engineers before bringing it back upstream, keeping the virt-launcher unprivileged by moving privileged operations into a device plugin.
    4. 14:39 Itamar Holder lists drawbacks of the existing sidecar hook: it edits the libvirt domain XML as a raw string, has no node access, and can only be enabled for everyone through one feature gate.
    5. 16:44 He walks through the new plugin model's three levels: a CEL expression that mutates the domain XML, a sidecar that works on a structured libvirt object with new pre-boot and pre-migration hooks, and node hooks answered by a plugin author's own DaemonSet.
