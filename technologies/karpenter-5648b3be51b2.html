    Autoscaling at Scale with KEDA

    Ali Aqel

    Ali Aqel, a Stripe engineer and KEDA contributor, describes how Stripe's Kubernetes team runs workload autoscaling with KEDA across its clusters, organized around four principles: safe, stable, scalable and simple. He covers rollout protection, break-glass locks, canaries for every scaler, tuning and per-cluster Prometheus workspaces, and walks through two hypothetical incidents.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingObservability and reliabilityDelivery, GitOps and release safety

    Watch this if: you run KEDA or HPA on large clusters and want one company's guardrails, locks and canaries.

    1. 3:09 Ali gives Stripe's numbers: more than 90 self-managed clusters, about 84,000 deployments and 180,000 application pods for over 8,600 services, run by about a dozen Kubernetes engineers.
    2. 10:03 He says Stripe built a pod deletion cost controller that annotates pods so scale-downs keep the spread across availability zones.
    3. 11:02 He describes scale-down and scale-up locks, from one service up to global, built on KEDA's pause annotation and annotations he says Stripe upstreamed, including force activation.
    4. 13:17 He says a canary for every supported scaler pages the team when degraded, and that these canaries found Prometheus rate limiting and a DNS problem.
    5. 16:45 He says scaling on Prometheus broke Amazon Managed Prometheus rate limits, which led through caching and sync period changes to one autoscaling workspace per cluster.

    Battle-tested Autoscaling Paradigms with KEDA

    Jan Wozniak, Christian Melendez

    Jan Wozniak and Christian Melendez run a live audience quiz backed by a small CPU-hosted model and use it to show KEDA scaling the pods while Karpenter scales the nodes. They walk through their recommendations on metric freshness, fallbacks between metric sources, spare node capacity through capacity buffers, and conservative scale-down.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingObservability and reliability

    Watch this if: you autoscale workloads on Kubernetes and want practical guidance on metric sources, fallbacks, node headroom and scale-down settings with KEDA and Karpenter.

    1. 3:45 Wozniak groups scaling metrics into reactive ones such as CPU and memory, proactive ones such as load balancer and queue metrics, and predictive ones, and says reactive scaling tends to run behind the load.
    2. 10:13 He says Prometheus can keep working for smaller environments, and suggests KEDA's OpenTelemetry scaler, which has metrics pushed to it, for teams that want to remove the scrape delay or that run a very large number of scaled objects.
    3. 12:58 He describes KEDA scaling modifiers and their dynamic fallback operator, then has the OpenTelemetry source killed live to show scaling continue on the Prometheus copy of the metric.
    4. 16:56 Melendez explains Karpenter's capacity buffers, where a pod template and a buffer object act as virtual pods that keep headroom ready, and compares this with the older pattern of low-priority balloon pods.
    5. 26:41 For scale-down, Melendez advises a stabilization window longer than the time an application needs to start on a fresh node, plus a delay on Karpenter consolidation, with GPU nodes removed only when empty.

    Beyond One Model per GPU: Agent-Driven Placement for Maximum GPU Utilization on Kubernetes

    Weiqi Sun, Ratnopam Chakrabarti, Ajay Vohra, Vivek Kolasani, Felipe Garcia

    The speakers from AWS and NVIDIA present a pipeline in which an agent, a constraint solver and real GPU measurements search for ways to place several LLMs on shared GPUs with CUDA MPS while each model still meets its latency targets. They walk through the plan, profile, search and export stages, the hand-off to KAI Scheduler through Helm, and results they measured on L40S and H100 nodes.

    80 min slot · Advanced · Tutorial

    Accelerators and workload schedulingAI inference and servingAI agents and automation

    Watch this if: you serve many LLMs on Kubernetes and want a worked method for packing them onto fewer GPUs without breaking latency targets.

    1. 4:16 A speaker sets the running example: 15 models, two L40S machines with 16 GPUs, and the question of the fewest GPUs that still meet each model's service level objective.
    2. 20:19 A speaker says CUDA MPS gives no performance isolation, that the limits are caps and not guarantees, and that this is why every placement is benchmarked.
    3. 24:23 A speaker introduces the solution as a Claude skill split into plugins and commands that runs plan, profile and search stages, with a CP solver proposing placements for the agent to test.
    4. 43:24 A speaker explains that KAI Scheduler does not read the certified export directly, so a deployment adapter turns it into Helm values with one release per model.
    5. 1:02:25 A speaker gives five takeaways from the H100 experiments, including a measured co-location latency cost of about 1.3 to 2.3 times and a preference for MPS over time slicing.

    Data-Driven Platform Guardrails: What 16,500 Incidents Tell You to Automate First

    Henrique Santana, Henrique Dalssaso

    Henrique Santana and Henrique Dalssaso walk through the top root causes they found in more than 16,000 Kubernetes incidents, including IP exhaustion, auth failures and node provisioning problems. For each one they suggest platform guardrails to automate, and they explain how to run the same analysis on your own incident data.

    25 min slot · Intermediate · Session

    Observability and reliabilityPlatform engineering and developer experience

    Watch this if: you want a list of common Kubernetes incident root causes and the guardrails these speakers suggest automating for each.

    1. 1:35 The speakers describe their dataset as more than 16,000 incidents across many Kubernetes clusters from January to mid-May, grouped with AI and then reviewed by hand. They say DNS did not make their top 10 root causes.
    2. 3:57 They say about a third of one top pattern was pods with no IP address available, from small or shared subnets, and suggest Cilium multi-pool IPAM and broader Karpenter node pools.
    3. 6:59 For auth failures they separate missing permissions, RBAC that was never bound to the pod, and policies on the target endpoint, and suggest Kyverno policies, projected service account tokens and cert-manager.
    4. 16:20 For node provisioning failures, which they put at almost 15% of incidents, they suggest setting kube-reserved and system-reserved, Cluster API machine health checks and Karpenter node auto repair.
    5. 20:59 To repeat the analysis on your own data, they suggest classifying by what actually failed rather than the symptom, ranking by frequency, and asking whether the platform, the app team or both can fix it.

    Saturated by Design - Maximizing Cluster Allocation in On-Premises Kubernetes

    Dakota Sullivan, Isaac Wilson

    The speakers describe how The Trade Desk raised allocation in its fixed-size on-premises Kubernetes clusters from about 20% with default scheduler settings to what they say is a consistent 97%. They walk through four problems, node scoring, deployment overscaling, fragmentation and right-sizing, and the scoring change, two custom scheduler plugins and a simulation-driven controller they built for them.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: You run fixed-capacity or on-premises Kubernetes clusters with large pods and topology constraints and want to see how one team pushed allocation toward full.

    1. 4:14 Isaac Wilson says switching node scoring from least allocated to most allocated was the easiest and most significant change, taking utilization from about 20% to 85%.
    2. 6:30 Dakota Sullivan describes Plimsoll, a custom scheduler plugin that holds back extra pods created during rollouts and deletions until terminating pods are gone, which he says also works with out-of-tree controllers such as Argo Rollouts.
    3. 11:24 Wilson describes ResourceShuffler, a second scheduler plugin that moves pods without topology spread constraints to make room for constrained pending pods while respecting PodDisruptionBudgets, bringing utilization to 97% by their account.
    4. 15:09 Sullivan explains modeling workloads elastically, which he compares to CSS flexbox: each has a basis scale plus a min and max, so all workloads shrink or grow fairly when capacity changes.
    5. 18:24 He introduces Bento, a controller that snapshots the cluster, runs simulations with the real Kubernetes scheduler to find ideal scales and moves workloads part way toward them on each loop.

    SIG Autoscaling Project Updates

    Jack Francis, Jason Deal, Heba Elayoty, Kuba Tużnik

    Jack Francis, Jason Deal, Heba Elayoty and Kuba Tużnik give updates on Kubernetes SIG Autoscaling projects, including Karpenter's DRA support, balanced consolidation and node repair, the capacity buffer and capacity quota APIs, and the split of Cluster Autoscaler into a core plus separate provider projects. Elayoty then explains what workload-aware scheduling needs from autoscalers, and Tużnik presents scheduler-driven autoscaling, a proposed redesign in which the scheduler requests nodes from the autoscaler.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Karpenter or Cluster Autoscaler and want the latest feature updates plus the proposed redesign of how autoscalers work with the scheduler.

    1. 3:28 Jason Deal says Karpenter added DRA support in its scheduling simulation in v1.14, covering structured parameters, consumable capacity, partitionable devices and prioritized alternatives, with provider implementations in the AWS provider and EKS Auto Mode.
    2. 6:11 He introduces balanced consolidation, which weighs the share of pods disrupted against the share of cost saved and only acts when the score passes a threshold.

    4. 19:50 Kuba Tużnik describes the split brain problem: the autoscaler has to predict what the scheduler will decide, and when its predictions are off it makes wrong scaling decisions.
    5. 24:15 He outlines the proposed design in which the autoscaler publishes potential capacity and the scheduler issues node claims, and estimates it at more than ten KEPs over one to two years.

    Soma Koltai of Cloudera describes moving the Cloudera Data Warehouse control service from a single Go binary to Cadence workflows, using a small bridging layer shaped like the Cadence client API and a lease service on PostgreSQL so the refactoring could start before Cadence was integrated. Ender Demirkaya of the Cadence project explains how workflows and activities recover state, and says the Cadence team built distributed semaphores after hearing about Cloudera's use.

    30 min slot · Advanced · Session

    Observability and reliabilityData, storage and state

    Watch this if: you are breaking up a stateful monolith with long-running operations and want a staged way to adopt a workflow engine.

    1. 1:47 Koltai says provisioning a cluster and restoring workloads can take a whole hour, and under the previous architecture a failure meant the whole process was retried.
    2. 5:36 Demirkaya explains that developers annotate one function as a workflow and its external calls as activities, and if everything crashes another worker continues where it left off.

    The Future of Kubernetes Eviction and Node Lifecycle

    Lucy Sweet, Ryan Hallisey, Filip Křepinský

    Three members of the Node Lifecycle Working Group describe two efforts: Specialized Lifecycle Management, which adds shared lifecycle conditions to nodes, and a declarative EvictionRequest API meant to replace one-shot API-initiated eviction. Filip Křepinský explains the requester and responder model and runs a live demo, and Lucy Sweet says Anthropic already uses eviction requests in production.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimes

    Watch this if: you drain or upgrade nodes under stateful or long-running workloads and want to see how eviction is meant to become declarative and observable.

    1. 3:52 Ryan Hallisey introduces node lifecycle conditions such as drain in progress and maintenance in progress, which he says merged as alpha in Kubernetes 1.37 to replace ad hoc node labels.
    2. 5:08 He names the open problem: anyone with permission can write these conditions, so two drains with different options can conflict, and the group is considering a new API to declare intent and serialize writers.
    3. 8:37 Lucy Sweet calls API-initiated eviction a point-and-shoot gun with a one-bit answer that cannot be observed until it happens, and says users build admission webhooks on top of it.
    4. 14:47 Filip Křepinský explains the responder contract: each responder reports a heartbeat within a deadline now set at 20 minutes, and one that stalls is skipped, ending with a fallback that calls the eviction API and respects PDBs.
    5. 25:38 Lucy Sweet says Anthropic uses the eviction request API in production and has issued millions of eviction requests, and that other companies have told the working group they use or plan to use it.
