    Agentic AI: Let’s Build a Reference Architecture, Live? Or at Least Try!

    Ricardo Rocha

    Ricardo Rocha invites practitioners to sketch a cloud-native reference architecture for agentic AI from their own deployments. The group maps layers for gateway and inference, then discusses caller identity, privacy, and why an agent's lifetime affects how it should be run.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are planning an agent platform and want to compare architecture choices with other practitioners.

    1. 6:36 Rocha shows the draft architecture and places the gateway at the entry point, LangChain around orchestration, and Langfuse in the observability layer.
    2. 10:11 An attendee says caller identity can be lost on the way to the model and suggests preserving it across the chain for attribution and tracing, mentioning SPIFFE and SPIRE.
    3. 13:06 An attendee describes identifying and tokenizing sensitive fields before sending requests to a third-party inference engine, even if the requests are already signed.
    4. 22:16 An attendee contrasts one-shot agents that are seldom reused with long-running jobs, and Rocha adds that distinction to the architecture discussion about checkpointing and resuming work.
    5. 28:34 Rocha asks teams to contribute reference architectures and says submissions should include what worked, what did not, and the custom integration work they needed.

    Compliance Drift on Kubernetes: Building Proof Infrastructure for AI Agents in Regulated Industries

    Saideep Navakoti

    Saideep Navakoti presents ACRA, a Kubernetes proof workflow intended to detect changes in AI-agent behavior and make the resulting investigations auditable. He shows how the demo displays investigation tickets and describes how auditors could query evidence drawn from traces.

    25 min slot · Intermediate · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: You need to show auditors what an AI agent was approved to do and what it actually did.

    1. 7:55 Navakoti explains that Kyverno checks pod admission and OpenTelemetry records traces, but argues that neither alone tells an operator whether an agent's behavior has drifted.
    2. 9:32 He introduces ACRA's API server, controller, and gate, then explains how its contract evaluator checks agent behavior against a declared baseline.
    3. 12:21 He shows a demo UI that calls the API to display investigation tickets, after describing how a drift event produces evidence from collected traces.
    4. 20:04 He frames drift as a reason to re-approve an agent rather than silently fix it, and walks through how a custom Kubernetes controller reports the agent's state.
    5. 21:32 He describes evidence an auditor can query for a specific task or incident, including a telemetry graph rather than a manually maintained spreadsheet.

    Every Kubernetes Object Deserves an Identity: The SPIFFE Broker API

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    Platform-First AI Agent Security: Zero-Trust Patterns for Kubernetes

    Carlos Santana

    Carlos Santana argues that a Kubernetes platform should treat agent-generated code as untrusted and provision isolation, credentials, and network policy separately. He describes using kro to compose those controls behind a platform API and shows captures of an Agent Sandbox warm pool assigning a ready pod.

    30 min slot · Any Level · Session

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to give teams a Kubernetes API for agents without giving those agents unrestricted access.

    1. 5:25 Santana describes SPIFFE and SPIRE as a way to identify an agent by URI and associate that identity with a credential across different environments.
    2. 12:14 Santana shows a kro ResourceGraphDefinition and explains how a declarative resource graph can give platform users a custom API without requiring the platform team to write a Go controller.
    3. 19:05 Santana compares gVisor, Kata Containers, and AWS Nitro Sandboxes as different isolation choices for running untrusted agent code.
    4. 21:27 Santana shows captures of a two-pod Agent Sandbox warm pool and says applying a claim assigned a ready pod instead of waiting for a fresh sandbox to start.
    5. 25:48 Santana describes a credential proxy that attaches a credential to an outbound request without handing the underlying secret to the agent, and gives an Agent Substrate example.

    Stop Writing Secrets Into YAML: A Rotation-First Identity Pattern for Kubernetes

    Fabrizio Sgura

    Fabrizio Sgura proposes using workload identity first and issuing short-lived credentials only for dependencies that still require them. He walks through how Kubernetes, SPIRE, and OpenBao could support issuance, renewal, delivery, and revocation.

    30 min slot · Beginner · Session

    Security, identity and policy

    Watch this if: you want to replace static Kubernetes credentials a step at a time.

    1. 5:35 Sgura separates the roles of SPIFFE as a workload identity standard, SPIRE as its implementation, and OpenBao as a credential lifecycle manager.
    2. 10:26 He describes a layered design in which a workload first gets a short-lived identity document, and only uses a traditional credential if an external dependency needs one.
    3. 20:45 He explains that SPIRE issues a verifiable identity document after checking the workload, and gives X.509 and JWT as examples.
    4. 25:37 He describes using OpenBao for dynamic credentials, with External Secrets Operator or the Secrets Store CSI Driver handling delivery.
    5. 28:44 He recommends avoiding credentials when workload identity is enough, limiting the lifetime of any credentials issued, and designing for renewal and revocation.

    The Identity Crisis: Who is the AI Agent in Your Cluster?

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.

    Your CI's Mistaken Identity

    Andrew McNamara, Maia Iyer

    Andrew McNamara and Maia Iyer say a namespace and service account can tell you where a CI task runs without telling you what it should be allowed to do. They describe pairing per-task workload identities with admission-time policy and using those identities to authorize access and sign attestations.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetySecurity, identity and policy

    Watch this if: You want to avoid giving every task in a Kubernetes CI pipeline the same privileges.

    1. 4:30 The speakers explain that SPIRE can use more than namespace and service account when assigning workload identities, so CI pods in the same namespace can have different roles.
    2. 9:19 The speakers explain that a Tekton bundle's digest changes when its task definition changes, and show where Sigstore signatures and attestations can be stored.
    3. 14:14 The speakers describe using Kyverno admission policy to require extra verification before a task can get a production identity.
    4. 16:57 In the live demo, the speakers show that an unsigned task from an untrusted catalog was blocked before a pod was scheduled.
    5. 22:21 The speakers explain how task-scoped identities let a verification policy check not just for an attestation, but for the specific CI task expected to produce it.
