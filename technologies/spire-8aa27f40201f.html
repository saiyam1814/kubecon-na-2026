    From Bearer Tokens to Mesh-Native mTLS: Modernizing Service Identity at Coinbase

    Zachary Schwartz, Yair Temkin

    Yair Temkin and Zachary Schwartz describe how Coinbase replaced a homegrown service-to-service auth system with SPIFFE identities issued by SPIRE and checked by an auth sidecar, and say every service is now off the legacy system. They share lessons from the migration and then outline plans to use Istio ambient mesh, with JWT validation at the ingress gateway and ztunnel mTLS, so the sidecars can eventually be removed.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you are planning a move from token-based service auth to SPIFFE identities or Istio ambient mesh and want a peer's account of the migration.

    1. 1:23 Temkin says the legacy service auth system was tightly coupled to AWS, tied to one region and JWT-only, and was retired in March 2025 when SPIRE became the paved road.
    2. 2:26 Schwartz lists why they chose SPIRE, including compatibility with services outside Kubernetes, JWT SVIDs and separate trust domains per region and environment, and reports 70% less CPU in the auth path and about 50 milliseconds less latency than the legacy system.
    3. 6:46 Schwartz says managing the migration centrally through the sidecar and a control plane, without pull requests in every service team's repository, let them move much faster, and that all services now use the SPIRE-based system.
    4. 10:42 Among the lessons, he says init containers could start before the auth sidecar and have no identity, which they solved with Kubernetes native sidecars, and that bursts of new pods overwhelmed the SPIRE agent until caching was tuned.
    5. 13:37 Temkin describes the ambient mesh plan for ingress: Envoy filters at the ingress gateway validate JWTs centrally and set a subject header, and authorization policies at the gateway and at ztunnel restrict who can call each service.

    Managing Network Security in Multi-Tenant Environments with Istio and Cilium

    Michael Bolot, Zaira Shaikh

    Michael Bolot and Zaira Shaikh of GEICO describe replacing a mix of cloud firewalls, on-premises firewalls and in-cluster policies with one API that configures Istio and Cilium across clusters on a flat, routable pod IP space. They explain how SPIRE identities and Istio authorization policies decide which applications may talk, while a small set of Cilium policies blocks what bypasses the sidecar, and they close with tips for writing Cilium policies safely.

    30 min slot · Any Level · Session

    Security, identity and policyNetworking and connectivity

    Watch this if: you run Cilium and Istio together and want to hear how one platform team splits network policy duties between them.

    1. 1:44 Bolot lists the problems with the legacy setup: no unified definition of the policy affecting a device, manual configuration, inconsistent enforcement and a complex network topology.
    2. 7:03 Shaikh describes the new system: pods are restricted by Istio resources and network policies written by a data plane agent on every workload cluster, configured from a central API server, with Cilium's BGP features advertising all pod IPs.
    3. 15:03 Bolot says SPIRE handles authentication by issuing workloads a certificate after attestation, and Istio authorization policies state what a given SPIFFE ID may reach, with service entries and workload entries connecting clusters.
    4. 19:55 Bolot gives three reasons they do not use Cilium for everything: they want authorization based on SPIFFE IDs, user-chosen labels would exhaust Cilium's identity map, and Cilium's layer 7 Envoy would duplicate the one Istio already runs.
    5. 25:29 Shaikh shares tips for Cilium policies, including using audit mode and Hubble, minding the default enforcement mode, and never cutting the operator or etcd off from the API server.

    Fabrizio Sgura

    Fabrizio Sgura proposes using workload identity first and issuing short-lived credentials only for dependencies that still require them. He walks through how Kubernetes, SPIRE, and OpenBao could support issuance, renewal, delivery, and revocation.

    30 min slot · Beginner · Session

    Security, identity and policy

    Watch this if: you want to replace static Kubernetes credentials a step at a time.

    2. 10:26 He describes a layered design in which a workload first gets a short-lived identity document, and only uses a traditional credential if an external dependency needs one.

    Supply Chain, Runtime and SDLC: A Cloud Native Security Tour

    Dr. Constanze Roedig

    Constanze Roedig walks through cloud native security in three parts, the software supply chain you consume, the software development lifecycle where you build and deploy, and the runtime, naming CNCF and OpenSSF projects for each. She closes with her view that AI agents put more weight on runtime detection and on protecting and rotating secrets.

    12 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: You find cloud native security overwhelming and want a 16-minute overview of which problem each group of projects addresses.

    1. 0:40 The speaker frames the talk around three areas: the supply chain of software you consume, the software development lifecycle where you produce and deploy it, and the runtime.
    2. 3:44 She says an SBOM declares what is in your software but cannot be assumed complete, and suggests following OpenSSF recommendations on tooling.
    3. 5:51 She distinguishes a signature from an attestation, which she describes as a piece of evidence put in an envelope together with a signature, and names in-toto.
    4. 10:36 For runtime detection she contrasts signatures, which encode known adversary behavior, with anomalies, which are deviations from your own baseline, and says to combine them.
    5. 14:18 She says that with AI agents there are vulnerabilities with no patches available, which in her view puts the spotlight on runtime detection and on short-lived, rotatable secrets.

    Abdel Sghiouar

    Abdel Sghiouar argues that agents sharing a Kubernetes service account are hard to distinguish when something goes wrong. He proposes short-lived SPIFFE identities, gateways for authorization, and sandboxing, with humans setting policy instead of approving every action.

    10 min slot · Level not listed · Keynote

    AI agents and automationSecurity, identity and policy

    Watch this if: you need to separate agent identity, authorization, and runtime isolation when designing a Kubernetes platform.

    1. 1:23 Sghiouar says it is hard to predict which tools or endpoints an agent will call, and argues that a shared Kubernetes service account makes it hard to trace an incident to a particular replica.
    2. 2:40 Sghiouar distinguishes agents acting for a human from agents triggered autonomously, and argues the latter need a unique, short-lived identity tied to their task.
    3. 3:29 Sghiouar proposes SPIFFE and SPIRE for giving agents short-lived identities at runtime, potentially scoped to a replica or session.
    4. 4:15 Sghiouar says identity does not answer authorization and discusses using a gateway to evaluate what an agent wants to do before it accesses an external resource.
    5. 8:09 Sghiouar urges platform engineers to move from human approval of each action to human-defined governance that sets boundaries for what agents can do.

    Two GEICO engineers describe how they connect legacy Kubernetes clusters and VMs to a new Istio mesh without migrating those workloads first.     Networking and connectivity

    5. 6:55 They describe an xDS configuration server that gives each proxy least-access configuration based on its identity, fed by a simplified REST API so users do not write Envoy or Istio resources.
