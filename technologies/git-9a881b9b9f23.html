    Don’t Lose Your Agent’s Mind: Platform Patterns for Stateful Agents

    Evaline Ju, Maia Iyer

    The speakers explain why stateful agents lose sessions, files, and context when treated like ordinary pods, and they examine community work on sandboxing, snapshotting, and resuming agent state. They present their moca prototype and argue for server-held sessions, harness-neutral state, and an open harness-sandbox boundary.

    25 min slot · Any Level · Session

    AI agents and automationData, storage and state

    Watch this if: you are designing Kubernetes platform support for stateful or delegated AI agents.

    1. 4:00 The speakers say a plain pod is a poor fit for stateful agents because deleting the pod discards sessions, files, and learned context.
    2. 5:48 The speakers point to Agent Sandbox templates and Agent Substrate snapshot and resume work as community efforts aimed at configurable isolation and multiplexing idle agents.
    3. 9:19 The speakers present moca as their open-source managed-agents experiment, using Pi for the harness, Valkey for externalized sessions, and a relay boundary into pluggable sandboxes.
    4. 16:10 In the recorded demo, Evaline shows the user closing a session, starting another one, and still picking up the subagent's work without resending context.
    5. 18:41 The speakers argue that platforms should make sessions first-class and server-held, treat agent state as harness-neutral data, and make the harness-sandbox boundary an open protocol, while provenance, cost attribution, legibility, and delegated trust remain open.

    Arndt Schwenkschuster

    Arndt Schwenkschuster explains why a shared controller identity can be too broad when a Kubernetes operator acts for individual objects. He describes how the SPIFFE Broker API could give those objects separate identities and discusses uses in Flux, Istio, and secrets management.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you need a Kubernetes operator to access an external system without giving every object the same identity.

    1. 6:33 Schwenkschuster explains that assigning one service account to the controller makes onboarding easy but can give different teams' objects the same access to external Git repositories.
    2. 8:45 Schwenkschuster shows how a controller could act as a broker, requesting a SPIFFE ID for a specific GitRepository object so the external system can authorize that object rather than the whole controller.
    3. 11:16 Schwenkschuster says the Kubernetes object reference can include a UID, allowing a recreated object with the same name to receive a different identity.
    4. 12:51 Schwenkschuster says Flux can already use SPIFFE identifiers for its custom resources and explains how that can replace static secrets or a shared service account.
    5. 14:51 Schwenkschuster describes work on Istio ambient mode in which ztunnel would use a pod reference to request the pod's identity rather than authenticating as ztunnel itself.

    Xing Yang, Dave Smith-Uchida

Smith-Uchida then presents two white papers in progress, on data protection best practices and on recovering from ransomware attacks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you back up stateful workloads on Kubernetes or are planning how to recover from a ransomware attack.

    1. 0:53 Yang says GitOps can recreate manifests, but secrets and data in persistent volumes are not in Git, which is why the group builds Kubernetes-native data protection blocks.
    2. 5:47 Yang highlights COSI v1alpha2 support for one bucket access covering multiple buckets with read-write, write-only and read-only modes.

    Kubernetes Secrets Were a Bad Idea. Now What?

    Maxime Coquerel

    Maxime Coquerel argues, as his own opinion, that Kubernetes Secrets are risky because they are only base64 encoded in etcd, readable with broad RBAC permissions and have no lifecycle. He recommends encrypting etcd with a customer managed key, keeping secrets out of Git and mounting secrets from a real vault at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    5 min slot · Beginner · Lightning Talk

    Security, identity and policy

    Watch this if: you are deciding whether Kubernetes Secrets are good enough for your platform or which alternative to use.

    1. 0:43 Maxime Coquerel says a Kubernetes Secret is stored in etcd only base64 encoded, not encrypted, and that etcd is a key value store, not a vault.
    2. 1:46 He lists the weaknesses he sees, including that anyone with get, list or watch permissions can read secret contents.
    3. 2:05 He adds that Kubernetes Secrets have no lifecycle: no expiration date and no automatic renewal.
    4. 2:47 His first recommendation is to encrypt etcd with a customer managed key, which he says managed services such as Azure Kubernetes Service support.
    5. 3:49 He compares Sealed Secrets, SOPS and External Secrets Operator, and recommends mounting secrets as files at runtime with the Secrets Store CSI Driver or the OpenBao agent.

    Abby Bangser, Joel King

Joel describes how NatWest used product thinking, Kubernetes CRDs, GitOps reconciliation, and clear ownership boundaries to cut EKS cluster provisioning from eight to twelve weeks to 35 minutes.

    25 min slot · Intermediate · Session

    Platform engineering and developer experience

    Watch this if: you want a regulated-enterprise case study connecting platform-as-product theory to Kubernetes and GitOps implementation plus measured outcomes.

    1. 3:43 Joel says reuse failed when each application team copied and modified patterns, producing more than 135 variants, high cognitive load, configuration drift, and an eight-to-twelve-week path to a usable EKS cluster.
    2. 8:34 Joel says NatWest adopted platform as a product by exposing curated products through an abstracted API, using Git as the source of truth, reconciliation loops, and fleet management rather than team-by-team manual change.

    4. 19:55 Joel says the automated EKS product reduced provisioning from eight to twelve weeks to 35 minutes while including the AWS account, networking connectivity, guardrails, and self-service request path.
    5. 23:30 Abby closes by arguing that platform teams must optimize for outcomes over outputs, composing contributions into products that give users self-service access rather than merely automating infrastructure.
