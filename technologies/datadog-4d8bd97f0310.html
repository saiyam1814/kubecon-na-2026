    Achieving Cross-Cloud Portability with the Kubernetes Resource Orchestrator

    Michael McCune, Daniel Bruno, Sitesh Pattanaik, Bridget Kromhout, Jesse Butler

    In this SIG Cloud Provider session, the chairs explain why the SIG took in kro as a subproject, and Jesse Butler lays out the problem of ordering, reconciling and exposing cloud resources as platform APIs. Daniel Bruno and Sitesh Pattanaik then walk through an example generative AI service API built as a ResourceGraphDefinition and show recorded demos of it deployed to GKE, AKS and EKS clusters.

    30 min slot · Level not listed · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you build a platform across more than one cloud and want to see what a single kro-defined API looks like from both the platform team's and the product team's side.

    1. 2:41 Bridget Kromhout says Amazon, Google, Microsoft and others wanted a consistent way to work with resources, and recalls Jesse Butler suggesting they skip 18 months of each doing it their own way.
    2. 10:01 Jesse Butler describes kro as a vendor-neutral composition layer over any resource in the cluster, naming Crossplane, ACK, KCC, ASO or controllers you built yourself.
    3. 15:19 Daniel Bruno shows what the product team writes: nine lines of YAML naming the instance, the model, the replica count and whether monitoring is on, deployed to clusters on several clouds.
    4. 17:01 Daniel Bruno shows the platform team's side: a ResourceGraphDefinition with CEL expressions for defaults and includeWhen conditions, written without Go controllers, with cloud-specific details read from ConfigMaps.
    5. 27:41 Sitesh Pattanaik explains custom status conditions written in CEL, such as a model cache bound condition, and later says kro emits a duration metric for how long a condition has held.

    BurritoBot Said Let's Dance, the Platform Said No

    Whitney Lee, Michael Forrester

    Whitney Lee and Michael Forrester let the audience attack a deliberately unprotected burrito-ordering chatbot that is wired to MCP tools and runs on a Kubernetes-based internal developer platform. They then switch on Kubernetes guardrails and LLM-specific guardrails in stages and explain which control they say stopped each attack.

    30 min slot · Any Level · Session

    Security, identity and policyAI agents and automationPlatform engineering and developer experience

    Watch this if: you want to see prompt injection and tool poisoning against a chatbot on Kubernetes, and which guardrail the speakers use against each.

    1. 2:16 The speakers invite the audience to break a live BurritoBot that they say has no guardrails, warning that submitted prompts can be shown on screen.
    2. 7:29 Whitney talks the bot into revealing the fictional CEO's home address, which she says is stored in a Kubernetes secret the bot should not be able to read.
    3. 15:08 Whitney turns on the Kubernetes guardrails with one command and says it adds Kyverno, KubeArmor, RBAC and network policy, then maps each one to the attack it blocked.
    4. 19:29 Michael shows a support ticket with hidden instructions that makes the bot deploy an app, which he calls prompt injection in a trusted system, before turning on the AI guardrails.
    5. 28:21 Michael explains a poisoned get-weather MCP tool whose description makes the bot read an internal config, and says the MCP gateway's classifier removes the tool from the tool set.

    Choose Your Own Adventure: The Saga of Serving LLM Inference

    Whitney Lee, Viktor Farcic

    Whitney Lee and Viktor Farcic let the audience choose inference settings for a Qwen model on Kubernetes, then deploy that configuration alongside its opposite. They explain the tradeoffs behind each choice and compare signals from the running deployments.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: You want to see quantization, replication versus sharding, and speculative decoding compared in a live inference deployment.

    1. 3:16 Farcic starts deploying both the audience's configuration and the opposite choices so the two inference setups can be compared.
    2. 11:38 Lee explains how quantizing model weights can make a model fit on a GPU or leave more memory for the cache used by active conversations.
    3. 16:41 Lee compares replicating the whole model on multiple GPUs with sharding it across GPUs and explains why separate replica caches affect routing.
    4. 24:06 Lee explains how speculative decoding drafts several tokens ahead and how the model checks the guesses before accepting them.
    5. 29:13 The speakers use a Datadog dashboard fed by OpenTelemetry to inspect request rates for the two configurations under audience load.

    From Clever to Correct: Lessons from Rebuilding SeatGeek's Platform AI Agent

    Colin O'Dell

    Colin O'Dell describes why SeatGeek replaced its specialist-heavy platform agent, Rufus, with a generalist agent called Sandy that can carry a task from investigation through a code change. He explains how a per-session sandbox keeps full logs out of the agent's context and how the team uses reports from Slack or Jira to improve the agent itself.

    10 min slot · Intermediate · Lightning Talk

    AI agents and automationPlatform engineering and developer experience

    Watch this if: You are deciding what to build yourself when an internal platform agent needs to diagnose problems and make changes.

    1. 1:23 O'Dell explains how Rufus routed requests to four specialists that could not easily hand work off. An Argo CD specialist could diagnose a deployment failure but could not pass the fix to the coding agent.
    2. 4:10 He describes rebuilding around one OpenCode harness and a per-session sandbox, where Sandy can store full logs on disk and pull only the relevant lines into its context.
    3. 6:43 He explains why the team reused OpenCode and Daytona for the harness and sandboxes, leaving more time for platform-specific routines and skills.
    4. 7:05 He describes how the team uses Sandy to fix Sandy: a report from Slack or Jira can start a sandboxed fix and merge request. He also describes a tool that posts a short report when the agent gets stuck.
    5. 8:56 He argues for treating the internal agent as a product that keeps evolving, after putting Rufus into maintenance mode made later improvements harder to adopt.

    OpenFeature Update from the Maintainers

    Jonathan Norris, Todd Baert

    Jonathan Norris and Todd Baert report on OpenFeature's growth in providers and SDK downloads, including vendors that now use OpenFeature as their native SDK. They cover new Dart and C++ SDKs, spec 0.9.0, flagd and OFREP improvements, agent skills for OpenFeature, and governance changes.

    30 min slot · Level not listed · Session

    Delivery, GitOps and release safety

    Watch this if: you use feature flags and want to know what changed in OpenFeature, flagd and OFREP this year.

    1. 2:55 Norris says OpenFeature now has almost 300 providers across 51 vendors and, by his estimate, well over 100 million SDK downloads per quarter.
    2. 3:58 Baert describes vendors such as Datadog, Cloudflare, Google Cloud, Vercel and Dynatrace choosing OpenFeature as their native SDK.
    3. 6:41 Baert lists flagd changes, including fractional bucketing on any context type, disabled flags no longer counted as errors, and later a FIPS 140 mode.
    4. 10:08 Norris explains that OFREP can now send a server-sent events URL so clients refetch flags in real time when configuration changes.
    5. 12:12 Norris presents OpenFeature agent skills, saying evaluations improved Haiku from 59% to 89% and Sonnet from 79% to 94%.

    Triaging 4,700 Alerts/Month at $0.33 Each: Verkada's MCP Agent on Nine Production Clusters

    Adrian Ng, Rohan Sood

    Adrian Ng explains why alert fatigue grew at Verkada and shows the in-house SRE agent that replies to alerts in Slack with a root cause analysis and next steps. Rohan Sood details how it works across nine clusters, how they evaluate it, the incident mode they are building, and what they say keeps the cost near 33 cents per investigation.

    30 min slot · Any Level · Session

    AI agents and automationObservability and reliability

    Watch this if: you are thinking of building your own alert-triage agent and want one team's design, evaluation approach and cost levers.

    1. 6:29 Adrian says the agent handles about 4,700 alerts a month at roughly 30 cents each with a mean time to triage of about two minutes.
    2. 7:21 Rohan describes a serverless router that decides whether a Slack message is an alert and which of nine clusters owns it, then queues it for pods running an agent container, MCP sidecars and more than 80 tools.
    3. 13:37 Rohan says each team's Slack channel adds its own prompt to the base system prompt, so teams tune triage for their service by editing a markdown file.
    4. 15:00 Rohan says feedback buttons gave only about 100 clicks since April, so they run a sampled nightly replay eval that reruns alerts with a more powerful model plus live A/B tests of candidate builds.
    5. 25:45 Answering a cost question, Rohan says they keep a byte-stable prompt prefix of system prompt, channel prompt and tool schemas so most input tokens come from the cache.
