They show demos of GPUs switching between container and VM use and of a compute domain daemon set, and outline what they plan for the next release and how to migrate from the device plugin.

    KubeVirt's Architectural Leap: Pluggability, AI Hardware, and Maturing Governance

    Vladik Romanovsky, Itamar Holder

    KubeVirt maintainers Vladik Romanovsky and Itamar Holder mark the project's tenth year and its CNCF graduation by reviewing its pod-based architecture, its adoption of an enhancement proposal process, and this year's work on confidential VMs, NVIDIA hardware support and Dynamic Resource Allocation. Holder then explains the plugin framework from enhancement proposal 190, which is meant to let features be built out of tree, along with early work on supporting hypervisors beyond QEMU/KVM and the idea of using KubeVirt as an isolation backend for agent sandboxes.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload schedulingCommunity and open source adoption

    Watch this if: you run or extend KubeVirt and want to know how the plugin framework will replace sidecar hooks.

    1. 1:02 Vladik Romanovsky recalls early doubts about the project and explains the choice to tie a virtual machine's life cycle to a pod and run the virtualization stack inside it, which he says let KubeVirt reuse the Kubernetes security model, CNI, CSI and device plugins.
    2. 6:48 He says the last cycle had more than 100 open enhancement proposals, and that the project built a per-release tracker plus an AI agent that gathers related pull requests and estimates how likely each piece of work is to land by the freeze.
    3. 9:23 He describes building support for NVIDIA's newest hardware in a fork with Red Hat and NVIDIA engineers before bringing it back upstream, keeping the virt-launcher unprivileged by moving privileged operations into a device plugin.
    4. 14:39 Itamar Holder lists drawbacks of the existing sidecar hook: it edits the libvirt domain XML as a raw string, has no node access, and can only be enabled for everyone through one feature gate.
    5. 16:44 He walks through the new plugin model's three levels: a CEL expression that mutates the domain XML, a sidecar that works on a structured libvirt object with new pre-boot and pre-migration hooks, and node hooks answered by a plugin author's own DaemonSet.

    The Healthy Cluster, The Unhealthy VM:Why Infrastructure Metrics Are Only Half the Story in KubeVirt

    Smit Jain

    Smit Jain of the Portworx team at Everpure argues that infrastructure telemetry shows whether a KubeVirt cluster is healthy but not what the guest operating system inside a VM is experiencing. He walks through three incidents from his team's lab, a triage workflow that combines both views, and an open source operator his team wrote to collect guest metrics and logs.

    20 min slot · Level not listed · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you run production VMs on KubeVirt and have had users report slow or failing VMs while every cluster dashboard was green.

    1. 2:43 Jain lists what he says guest telemetry adds to infrastructure telemetry: detecting OS failures KubeVirt does not see, measuring which VMs are actually affected, narrowing the search, and validating that a fix worked.
    2. 7:33 First incident: a Linux VM's application filled a 50 GB filesystem and I/O failed while the VMI was running and the node looked healthy; his lesson is that filesystem usage in the guest is not volume usage.
    3. 9:41 Second incident: a Windows VM logged Event 129 I/O timeouts, and with guest telemetry enabled he says they could tie them to storage failures on the infrastructure side without logging into the VM.
    4. 10:43 Third incident: one VM saturated the disk on a shared node and two neighbours hit guest timeouts; they applied volume-level throttling and used guest metrics to confirm the recovery.
    5. 14:18 He introduces the KubeVirt observability operator, which reads an OS label in the VM spec, deploys node exporter or Windows exporter in the guest, and ships event logs and syslogs through Alloy to Loki.

    Time to Learn New Tricks to Improve Performance on DRA-Managed Devices

    Alexander Kanevskiy, Sara Qasmi

    Sara Qasmi of T-Systems shows measurements from LLM serving on two GPU server types, where she says the default Kubernetes device placement often lost bandwidth or added latency compared with hand-aligned devices. Alexander Kanevskiy of Intel explains why a NUMA number no longer describes modern CPU and PCI topology, and walks through newer Dynamic Resource Allocation features he says help express the alignment a workload needs.

    30 min slot · Advanced · Session

    Accelerators and workload schedulingAI inference and serving

    Watch this if: you place GPUs, NICs and CPUs for inference on Kubernetes and want measured examples of what device alignment changes.

    1. 5:23 Qasmi reports that GPU and NIC pairs aligned on the same PCI root reached full RDMA bandwidth on one platform while other pairings got 38%, yet on the second platform NUMA alignment was enough.
    2. 6:50 She says the default claim picked the wrong GPU pair in five of five runs on a busy node, and that NCCL's own peer-to-peer default also limited bandwidth until it was changed.
    3. 10:08 She measures CPU to GPU round-trip latency and says default pods were 33% slower, with eight of ten landing on the wrong socket, which an NRI topology plugin corrected.
    4. 14:56 Kanevskiy argues that a NUMA number only maps to the memory controller's mode of operation and is now a virtual value that does not describe physical topology.
    5. 20:38 He presents list attributes and derived attributes in DRA as ways to describe topology and compare values across drivers, and warns that a claim with no overlapping solution leaves the pod unscheduled.

    Two Drivers, One Topology: GPU:NIC Rail Alignment for RDMA VMs with KubeVirt DRA

    Jian Li, Alay Patel, Kazuki Sato

    Kazuki Sato of NTT DOCOMO BUSINESS, Jian Li of SK Telecom and Alay Patel describe how a multi-site GPU platform on KubeVirt moved from a manual workaround to Dynamic Resource Allocation claims that pair each GPU with an RDMA NIC under the same PCIe root. They show a recorded benchmark comparing aligned and misaligned VMs, explain the Multus change they are proposing upstream, and outline what KubeVirt's DRA support covers today and what is planned.

    15 min slot · Level not listed · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you run GPU virtual machines with RDMA networking on KubeVirt and need each GPU paired with the right NIC without pinning devices by hand.

    1. 2:07 Sato describes the earlier workaround: filling a node with placeholder pods that each hold one GPU or NIC and deleting only the ones holding the wanted pair, which had to be redone VM by VM after every node or VM restart.
    2. 5:10 Li explains that the GPU driver and the SR-IOV NIC driver both publish the standard PCI root attribute, so one resource claim with a GPU request, a VF request and a match constraint lets the scheduler allocate them as a pair.
    3. 7:15 He says upstream KubeVirt network DRA could not consume a VF wired through a Multus network, so they added a feature gate that takes the VF from the resource claim and leaves the existing CNI chain unchanged.
    4. 10:21 In the recorded demo Sato compares two four-GPU VMs: he reports about 200 Gbps of RDMA bandwidth on the misaligned VM and 391 Gbps on the aligned one, with placement as the only difference.
    5. 12:33 Li says the next gap is that CPUs and huge pages are still placed by the kubelet without topology hints from DRA devices, so a VM can get its GPU and NIC on one socket and its memory on another.
