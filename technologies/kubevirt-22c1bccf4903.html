    Longhorn: Intro, Deep Dive and Q&A

    Shuo Wu, David Ko

    David Ko introduces Longhorn, a cloud native distributed block storage system for Kubernetes, and shares its release cadence, adoption numbers and contributor growth. He then compares the V1 and SPDK-based V2 data engines, explains snapshots, backups, disaster recovery and live upgrades, and outlines the 1.13 and 1.14 roadmap with early RDMA benchmarks.

    30 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: you run Longhorn or need block storage on Kubernetes and want to compare the V1 and V2 data engines.

    1. 2:32 Ko says Longhorn runs on any compatible Kubernetes cluster and Linux distribution, including Talos, and ships minor releases every four months in line with Kubernetes.
    2. 4:58 Ko reports adoption up about 21% in six months to roughly 276,000 nodes and 60,000 clusters, from Longhorn's public usage metrics.
    3. 12:22 Ko explains that the V2 data engine uses SPDK in user space with NVMe over Fabrics, plus an interrupt mode so it can share CPU with applications.
    4. 19:21 Ko walks through V2 live upgrades, which move the volume target to another node so I/O continues while the upgrading node's instance manager restarts.
    5. 23:44 Ko lists the 1.14 plans, including RDMA support, I/O QoS, a new data engine for strict-local volumes and application-consistent snapshots and backups.

    Optimized Switchover Timing for Live Migration of Memory-Intensive Workloads

    Aseef Imran

    The speaker explains why live migrations of write-heavy virtual machines can stall and why timeouts and downtime ramps choose the switchover moment poorly. He presents a stall-detection approach that waits for a low point in the remaining data before switching over, which he says was merged as alpha in KubeVirt 1.9.

    20 min slot · Level not listed · Session

    Unclassified

    Watch this if: You run memory-heavy virtual machines and want to understand how switchover timing affects live migration downtime.

    1. 3:37 The speaker says the standard approach waits for a target downtime, and that write-heavy workloads sometimes never reach it.
    2. 8:26 The speaker says downtime ramps work well only when tuned for the workload, with low-level parameters an end user should not have to set.
    3. 10:15 The speaker describes the key observation that stalled migrations fluctuate around a point, so switchover can be timed for a low point.
    4. 14:59 The speaker explains his definition of a stalled migration, which compares current remaining bytes with the smallest record outside a progress timeout window.
    5. 19:26 The speaker reports a Redis benchmark where average downtime went from about 5,000 to about 1,000 milliseconds, and another workload with no meaningful difference.

    Plug and Play Volumes, hold the Pod

    Piotr Prokop PL, Sreeja Varnam

    The speakers explain why NVIDIA bypasses KubeVirt's attachment pod to hotplug storage for cloud gaming sessions. They present a proposal to make volume delivery pluggable while keeping the default attachment path intact.

    20 min slot · Level not listed · Session

    Data, storage and stateKubernetes internals and runtimes

    Watch this if: You need to hotplug storage into running KubeVirt VMs without the cost of an attachment pod.

    1. 0:30 The first speaker says GeForce NOW needs to expose storage to an application inside a running VM in under seven seconds and clean up automatically when something fails.
    2. 1:57 The first speaker walks through the default attachment pod and explains why scheduling and networking that pod adds work even when it only delivers a volume.
    3. 4:11 The first speaker reports that their direct path to the storage provider brought hotplug below four seconds in their tests, compared with eight to nine seconds and sometimes twenty before.
    4. 6:43 The second speaker introduces VEP-293, which proposes separating delivery, attach, and detach so an integration can replace one stage without changing the default behavior.
    5. 12:59 The second speaker describes node-local discovery: the provider publishes a file or block device, and KubeVirt handles the guest attachment instead of making the provider duplicate it.
