    Ricardo Rocha

    Ricardo Rocha invites practitioners to sketch a cloud-native reference architecture for agentic AI from their own deployments. The group maps layers for gateway and inference, then discusses caller identity, privacy, and why an agent's lifetime affects how it should be run.

    30 min slot · Level not listed · Birds of a Feather

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you are planning an agent platform and want to compare architecture choices with other practitioners.

    1. 6:36 Rocha shows the draft architecture and places the gateway at the entry point, LangChain around orchestration, and Langfuse in the observability layer.
    2. 10:11 An attendee says caller identity can be lost on the way to the model and suggests preserving it across the chain for attribution and tracing, mentioning SPIFFE and SPIRE.

    5. 28:34 Rocha asks teams to contribute reference architectures and says submissions should include what worked, what did not, and the custom integration work they needed.

    Agentic Inference at Scale

    Maroon Ayoub, Sean Horgan

    Maroon Ayoub and Sean Horgan describe how llm-d serves agentic sessions, which they say read far more input than they generate, by routing to cached context, offloading KV cache and splitting prefill from decode. They show production examples of zero-downtime router rollouts and flow control, and outline the Agentic Inference SIG's plans for session-level orchestration.

    20 min slot · Level not listed · Session

    AI agents and automationAI inference and serving

    Watch this if: You serve coding agents or other long multi-turn LLM sessions on Kubernetes and care about cache hit rates.

    1. 0:36 Maroon Ayoub says agentic sessions send far more input than output, around a hundred to one, so avoiding recompute unlocks hardware capacity.
    2. 2:46 He describes a production case where prefill compute fell from 16% to 4% while traffic doubled, after fixing how vLLM handled a timestamp Claude Code injects into each turn's system prompt.
    3. 6:26 He explains how the llm-d router balances prefix cache affinity against load-aware routing to avoid hot spots.
    4. 10:44 He shows a production router rollout where the new router loads a state snapshot, takes over traffic and the old one drains with zero errors.
    5. 13:38 Sean Horgan outlines the Agentic Inference SIG's work on orchestrating whole sessions rather than single requests.

    Clueless About The Cost of AI Model Usage? OpenCost+llm-d = first of a kind inference cost tracking

    Alexander Meijer

    Alexander Meijer, presenting alone because Sima Nadler could not attend, describes an integration where OpenCost reads llm-d and vLLM token metrics and combines them with GPU and provider pricing to report inference costs such as cost per token. He demos the APIs and dashboard live against an IBM Research cluster, comparing allocation and usage costs to find idle models, and outlines a roadmap for deeper GPU metrics.

    30 min slot · Any Level · Session

    AI inference and servingObservability and reliability

    Watch this if: you self-host LLMs on Kubernetes and want to know what each model and token actually costs.

    1. 1:46 Alexander Meijer says self-hosted models are generally cheaper than hosted ones, but that this only delays the cost problem.
    2. 6:40 He draws the line of responsibility: llm-d handles token counts, routing and scheduling, while OpenCost handles hardware metrics, pricing and cloud provider connections.
    3. 12:27 He explains the two cost bases: allocation, the max of request and usage, which he calls the production metric, and usage, which he calls the R&D metric.
    4. 16:41 His worked example divides a $15 deployment cost by 150 processed tokens to get $0.10 per token.
    5. 20:54 In the live demo, comparing $246 allocation cost with $22 usage cost shows one model was idle about 90 percent of the time, which he flags as a right-sizing target.

    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    From Fine-Tuning to Production: Scaling Agentic AI at Shopify via Inference Perf

    Ashok Chandrasekar, Navjot Singh

    Navjot Singh of Shopify describes load testing the fine-tuned model behind Sidekick Pulse with Inference Perf's conversation replay, sweeping concurrency levels to find how many research conversations each GPU replica completes per hour and turning that into a GPU plan. Ashok Chandrasekar of Google then presents Inference Perf's goals of reliable load generation, realistic workloads and reproducible results, and walks through its workload catalog, agentic replay generators and metrics.

    30 min slot · Advanced · Session

    AI inference and servingAccelerators and workload schedulingAI agents and automation

    Watch this if: you need to size GPU capacity for multi-turn agent workloads and want to see how a load test is configured and read.

    1. 2:32 Singh says Pulse runs as an offline batch of multi-turn research conversations, so the metric they watch is throughput: how many research conversations each GPU replica completes per hour.
    2. 6:03 He walks through the Inference Perf config for Pulse: a seed so every run replays the same workload, 38 turns per conversation with an 8-second wait between calls, and a concurrent load type that holds a fixed number of conversations in flight.
    3. 9:12 Singh says they had a fixed budget of H100 GPUs for Pulse, ran the same seeded sweep on each GPU topology, and found the canary's production throughput matched the load test.
    4. 14:07 Chandrasekar shows a test in which a single-process Python benchmark asked for 5,000 QPS delivered about 150 to 400 and reported inflated latency against a simulated server, while Inference Perf's multiprocess design delivered the requested rate.
    5. 20:27 He lists four generators for agentic workloads in Inference Perf: conversation replay, OpenTelemetry trace replay, Weka trace replay aimed at KV cache hits, and synthetic agentic trace replay.

    From GPU to Fleet. The llm-d KV Cache Hierarchy

    Vita Bortnikov, Nishtha Jain

    Vita Bortnikov and Nishtha Jain describe how llm-d and vLLM keep KV cache across GPU memory, CPU memory, local disks, network storage and peer-to-peer transfers between pods. They present benchmarks they say show storage offloading only holds up at scale when it is paired with storage-aware routing in the llm-d router.

    20 min slot · Level not listed · Session

    AI inference and servingData, storage and state

    Watch this if: You run LLM inference on Kubernetes and want to understand KV cache offloading tiers and cache-aware routing.

    1. 1:51 Vita Bortnikov says agentic workloads read far more than they write, with long inputs and short outputs, and cites up to 95% KV cache reuse.
    2. 4:44 She describes the offloading connector contributed upstream to vLLM, which tiers KV cache from GPU to CPU to storage, while llm-d handles orchestration and eviction.
    3. 7:15 She explains peer-to-peer KV cache transfer between nodes, used when the node holding a prefix is busy and for prefill/decode disaggregation.
    4. 12:15 Nishtha Jain introduces the third tier, shared network storage such as parallel file systems, which she says takes KV cache from gigabytes and terabytes to petabytes.
    5. 19:18 She calls storage offloading without storage-aware routing a failure at scale, citing throughput falling from about 2,500 to 700 tokens per second at 800 users when the router's storage index was off.

    Turning Apple Silicon into Production GPU Nodes for LLM Inference on Kubernetes

    Christopher Maher

    The speaker, who maintains LLMKube, shows live how a Mac joins a Kubernetes cluster as a MetalNode: an agent on the Mac starts the inference engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service. He says unified memory makes memory the thing to schedule on, recounts a kernel panic that led him to make the agent refuse models it cannot size, and shows traffic failing over to NVIDIA nodes when the Mac's lid closes.

    30 min slot · Advanced · Session

    AI inference and servingAccelerators and workload scheduling

    Watch this if: You want to serve LLMs on Macs or other unified-memory machines you already own, behind the same Kubernetes operator and service as your NVIDIA nodes.

    1. 5:16 The speaker lists why a Mac cannot simply join a cluster: Metal is not available inside a Linux container, no device plugin advertises the Mac's GPU, and the kubelet cannot see how much unified memory the GPU holds.
    2. 6:32 He describes the Mac path: an agent running under launchd watches for inference services, starts the engine natively and publishes an EndpointSlice, so clients see an ordinary OpenAI-compatible service.
    3. 9:16 In a live demo a second MacBook joins his home cluster with a token-based join command and appears as a MetalNode.
    4. 12:23 He says the agent now fails closed after an incident in which a memory check failed open, llama-server ran with mlock and the laptop hit a kernel panic; admission also counts memory already committed.
    5. 15:56 In a live demo he closes the lid of the Mac serving traffic, and the same endpoint is then answered by NVIDIA nodes in his home lab.
