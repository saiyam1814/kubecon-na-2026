    I Packaged My Application in a Container Image, and Now What?

    Aurélie Vache

    The speaker takes a small Go API packaged as a container image and walks through supply chain security steps for it, with a live demo for each one. She covers generating an SBOM, scanning for vulnerabilities, publishing a VEX file, signing the image, generating SLSA provenance and automating all of it in a GitHub Action.

    30 min slot · Any Level · Session

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: You can build and push a container image and want to see the next supply chain security steps done live, one command at a time.

    1. 2:18 The speaker starts with the SBOM, an inventory of the components in an image, and says it is no longer nice to have but becoming mandatory.
    2. 10:32 In the demo, a Trivy scan of the image reports 26 vulnerabilities, and the speaker points out that the first one applies to a Go version her application does not use.
    3. 13:22 The speaker introduces VEX as a way to tell users whether a vulnerability is exploitable in the application, and says OpenVEX is her favorite format.
    4. 17:11 After generating a VEX file with govulncheck and fixing its product ID, the speaker scans again with Trivy and she says the filtered result shows zero exploitable ones among the high and critical findings.
    5. 20:32 The speaker generates a key pair in a KMS, signs the image with Cosign and verifies the signature.

    k8gb Is Growing up: Incubating Global Load Balancing for Kubernetes

    Fabrizio Sgura

    Fabrizio Sgura gives an update on k8gb, the Kubernetes Global Balancer, which he says has moved from CNCF Sandbox to Incubating. He recaps its DNS-based design with no central management cluster, lists what changed on the way to incubation, and describes uses for multi-region AI inference endpoints and digital sovereignty.

    5 min slot · Level not listed · Lightning Talk

    Networking and connectivityObservability and reliability

    Watch this if: you run services in several clusters or regions and want a DNS-based way to fail over between them without a central control plane.

    1. 0:31 Fabrizio Sgura describes k8gb as global load balancing across Kubernetes clusters and regions using Kubernetes-native resources, with no central management cluster and each cluster making its own decisions.
    2. 1:09 He lists the traffic strategies: round robin, weighted round robin, failover and GeoIP routing, and notes that DNS changes only where new connections go.
    3. 1:48 He says three components work together: CoreDNS answers DNS queries, ExternalDNS automates DNS delegation, and the k8gb controller coordinates the strategy, with k8gb staying out of the data path.
    4. 3:28 He says that since Sandbox the project expanded Gateway API support, introduced a vendor-neutral API with a migration path, added zone delegation, moved to an OCI Helm registry and signs container images with Cosign.
    5. 4:11 He describes putting an OpenAI-compatible inference endpoint behind k8gb for regional failover, and a pairing with NVIDIA Dynamo where k8gb picks the healthy region and Dynamo picks the local worker.

    Lightning Harbor Update

    Orlin Vasilev

    Orlin Vasilev, the Harbor community manager, covers what shipped in Harbor 2.15 and 2.16, including ARM64 support, the move from Redis to Valkey and a PostgreSQL upgrade that he says needs extra steps. He shares contributor and pull request numbers, asks contributors for patience with reviews, and points to a proposal to run Harbor as a common registry for CNCF projects.

    5 min slot · Level not listed · Lightning Talk

    Delivery, GitOps and release safetyCommunity and open source adoption

    Watch this if: you run Harbor and want to know what changes in 2.15 and 2.16 before you upgrade.

    1. 1:03 Orlin Vasilev says Harbor 2.15 added Cosign v3 bundles, replication adapters for JFrog and AWS ECR, and proxy cache connection limit updates.
    2. 1:25 He says Harbor 2.16 officially supports ARM64 and migrated from Redis to Valkey.
    3. 2:13 He says 2.16 moves the internal database from Postgres 15 to 18, so upgrades need a few steps and a database backup, and webhooks for private networks are disabled by default afterwards.
    4. 3:29 He says Harbor had 562 pull requests last year and 1,213 so far this year, and asks contributors to be patient and keep pull requests small because the reviewers are the same people.
    5. 4:42 He says the team opened a proposal for registry.cncf.io, with Harbor as a common registry for all CNCF projects, and invites people to read and vote on it.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.

    Supply Chain Security at Home: From Source to Service Without the Hassle

    Andrew Thorp

    Andrew Thorp, a Tekton maintainer, walks through a self-hosted pipeline that takes a commit pushed to Forgejo and builds, pushes and signs a container image with Tekton on Kubernetes. He describes the roles of Tekton Pipelines, Pipelines as Code and Tekton Chains, shows a hermetic build step, and verifies the resulting attestation with Cosign.

    5 min slot · Level not listed · Lightning Talk

    Security, identity and policyDelivery, GitOps and release safety

    Watch this if: you build your own container images, at home or at work, and want to see what a signed, attested Tekton build pipeline involves.

    1. 0:54 Andrew Thorp lists what the setup needs: a Git host such as Forgejo, Tekton running on a Kubernetes cluster (he says a local kind cluster is enough for a small setup), and an image registry such as Harbor.
    2. 1:28 He describes three Tekton components: Tekton Pipelines as the engine that executes pipeline runs, Pipelines as Code as the bridge between the Git forge's webhook events and Tekton, and Tekton Chains for producing SLSA provenance attestations.
    3. 3:00 He shows a build step annotated with what he calls an alpha feature, hermetic execution mode, which he says runs the build in an isolated network space with no network access.
    4. 3:15 He explains that a hermetic build needs an earlier step that prefetches dependencies onto a persistent volume unless they are vendored, and a separate step afterwards to push the image.
    5. 4:21 He shows the attestation and signature from Tekton Chains and says cosign verify-attestation can be used to check them.

    Supply Chain, Runtime and SDLC: A Cloud Native Security Tour

    Dr. Constanze Roedig

    Constanze Roedig walks through cloud native security in three parts, the software supply chain you consume, the software development lifecycle where you build and deploy, and the runtime, naming CNCF and OpenSSF projects for each. She closes with her view that AI agents put more weight on runtime detection and on protecting and rotating secrets.

    12 min slot · Level not listed · Session

    Security, identity and policy

    Watch this if: You find cloud native security overwhelming and want a 16-minute overview of which problem each group of projects addresses.

    1. 0:40 The speaker frames the talk around three areas: the supply chain of software you consume, the software development lifecycle where you produce and deploy it, and the runtime.
    2. 3:44 She says an SBOM declares what is in your software but cannot be assumed complete, and suggests following OpenSSF recommendations on tooling.
    3. 5:51 She distinguishes a signature from an attestation, which she describes as a piece of evidence put in an envelope together with a signature, and names in-toto.
    4. 10:36 For runtime detection she contrasts signatures, which encode known adversary behavior, with anomalies, which are deviations from your own baseline, and says to combine them.
    5. 14:18 She says that with AI agents there are vulnerabilities with no patches available, which in her view puts the spotlight on runtime detection and on short-lived, rotatable secrets.

    The Next Generation of Kyverno — Unified Policy as Code at Scale

    Jim Bugwadia, Justin Munoz

    Jim Bugwadia explains why Kyverno moved from its own policy language to CEL-based policy types, how to migrate before the legacy types are removed in 1.20, and what the project plans next. Justin Munoz describes how his platform team at Kinexys by J.P. Morgan adopted Kyverno for namespace baselines, certificate rotation, permission tightening and change-window checks on Argo CD syncs, and shares the lessons the team took from it.

    30 min slot · Level not listed · Session

    Security, identity and policyAI agents and automation

    Watch this if: you run Kyverno and need to plan the move to CEL-based policies, or want to see how a regulated platform team uses it beyond admission control.

    1. 3:36 Jim Bugwadia says Kyverno chose CEL because it is the native policy language in Kubernetes, compiled and fast, and that Kyverno adds reporting, exceptions and policies for existing resources on top of the built-in admission policy types.
    2. 9:52 Justin Munoz describes using Kyverno to watch for newly issued certificates and trigger rolling restarts of deployments that cannot reload them on their own.
    3. 11:57 He describes a policy that intercepts Argo CD sync events and allows them only when a custom resource shows an approved change management window is open, with a precise denial reason otherwise.
    4. 13:34 He shares lessons learned: start in audit mode, treat the denial message as the user interface, make the paved path compliant by default and ship policy through the normal software lifecycle.
    5. 16:09 Bugwadia says release 1.20 removes the older policy types but leaves their CRDs in place so old policies show as not ready, and that 1.21 will remove the CRDs as well.

    Your CI's Mistaken Identity

    Andrew McNamara, Maia Iyer

    Andrew McNamara and Maia Iyer say a namespace and service account can tell you where a CI task runs without telling you what it should be allowed to do. They describe pairing per-task workload identities with admission-time policy and using those identities to authorize access and sign attestations.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetySecurity, identity and policy

    Watch this if: You want to avoid giving every task in a Kubernetes CI pipeline the same privileges.

    1. 4:30 The speakers explain that SPIRE can use more than namespace and service account when assigning workload identities, so CI pods in the same namespace can have different roles.
    2. 9:19 The speakers explain that a Tekton bundle's digest changes when its task definition changes, and show where Sigstore signatures and attestations can be stored.
    3. 14:14 The speakers describe using Kyverno admission policy to require extra verification before a task can get a production identity.
    4. 16:57 In the live demo, the speakers show that an unsigned task from an untrusted catalog was blocked before a pod was scheduled.
    5. 22:21 The speakers explain how task-scoped identities let a verification policy check not just for an attestation, but for the specific CI task expected to produce it.
