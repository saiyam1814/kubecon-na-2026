    Fake It Until You Make It: Mocking NVML to Test the Kubernetes GPU Stack on Zero GPUs

    Eduardo Arango Gutierrez, John Belamaric

    The presenters explain how Mokka mocks NVIDIA's management library to test Kubernetes GPU integration without physical GPUs. They demonstrate exposing a simulated GPU topology on CPU-only nodes and allocating it with an unmodified NVIDIA driver.

    30 min slot · Beginner · Session

    Accelerators and workload schedulingDelivery, GitOps and release safety

    Watch this if: you need to test GPU discovery, resource allocation, or failure handling in CI without reserving physical GPUs.

    1. 1:57 The presenters explain that supplying an ABI-compatible library lets software in a local kind cluster see simulated GPU hardware.
    2. 6:47 They describe using a C-to-Go bridge to implement NVML entry points and configurable GPU profiles.
    3. 8:22 They describe simulating temperature readings and GPU errors to exercise how infrastructure responds to failures.
    4. 14:59 They introduce the demo's 18-node GKE pool and explain that it will appear to Kubernetes as a rack of GB200 GPUs.
    5. 16:44 They deploy the standard NVIDIA DRA driver without modifying it, then show allocated resources on a pod's resource claim.

    Groundhog Pod: Scaling AI Inference with Kata Pod Snapshots

    David Justice, Roaa Sakr

    David Justice and Roaa Sakr describe a prototype that snapshots an initialized Kata pod VM along with its GPU state. They report a faster restore than cold start in their demo and discuss where hardware compatibility can limit reuse of a snapshot.

    30 min slot · Any Level · Session

    AI inference and servingKubernetes internals and runtimes

    Watch this if: You are comparing pre-warmed GPU pods with restoring initialized workloads when inference demand spikes.

    1. 6:52 The speakers say a VM snapshot may fail to restore on a different CPU microarchitecture and describe using virtual CPU profiles to define a compatible feature set.
    2. 8:47 The speakers explain that CUDA checkpointing moves GPU state into the running application inside the VM, so the subsequent VM snapshot can capture that state too.
    3. 13:00 In the inference demo, the speakers terminate the original pod and show another pod restoring from its snapshot and returning a response.
    4. 14:15 For the demo on an NVIDIA Tesla T4, the speakers report about 34 seconds for the cold start and 11 seconds from a snapshot, which skipped the software and model loading steps.
    5. 20:02 In a second demo, the speakers plot the training loss and show it continuing from a restored snapshot after the training pod is interrupted.

    Making Environments Repeatable: From Tools to Platform Capabilities

    Saiyam Pathak

    Saiyam explains the hidden setup, configuration, and readiness work behind requests for repeatable environments, and presents vCluster Stacks as a way to encode that work once. He argues that readiness should mean a validated user outcome, illustrated by GPU scheduling and a CUDA smoke test, rather than merely running components.

    5 min slot · Any Level · Keynote

    Delivery, GitOps and release safetyPlatform engineering and developer experience

    Watch this if: you are turning repeated environment provisioning steps into reusable platform capabilities.

    1. 0:13 Saiyam says the simple request for an environment hides installation, service trust, configuration handoff, and readiness work that platform teams must complete first.
    2. 0:53 Saiyam argues that repeatedly glue-fixing environments team by team eventually loses track of tools, versions, and ownership.
    3. 1:48 Saiyam says reusable environment automation has to encode ordered setup steps, pass one step's output into the next step, and prove readiness from the developer's perspective.
    4. 3:09 Saiyam uses a CUDA GPU stack to argue that readiness requires scheduler visibility of the GPU and a successful smoke-test job, not only healthy operator components.
    5. 4:21 Saiyam closes by asking platform teams what belongs in a reusable stack, what proves an environment ready, and which repeated requests the platform should handle for users.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.
