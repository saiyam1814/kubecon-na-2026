    Engineering High-Performance Telemetry Pipelines: Lessons from Fluent Bit

    Eduardo Silva

    Eduardo Silva, creator and maintainer of Fluent Bit, walks through how a telemetry pipeline is built and what changed in the 5.2 release, including a new Lua scripting interface for logs, metrics and traces and a WebAssembly build that runs in the browser. He then describes the performance work behind the release, which he says came from profiling with perf, removing repeated encoding steps, pre-allocating memory and batching.

    30 min slot · Level not listed · Session

    Observability and reliability

    Watch this if: you run or build telemetry collectors and want to hear how the Fluent Bit maintainer profiles and removes CPU and memory overhead.

    1. 7:39 Silva introduces a new Lua scripting interface he calls FTS, which he says adds primitives for metrics and traces as well as logs, something scripts could not work with before.
    2. 11:13 He announces Fluent Bit Studio, an experimental web interface that he says runs Fluent Bit as WebAssembly in the browser so a configuration can be tried before it reaches production.
    3. 15:04 He describes letting an AI coding agent run perf against the code and collect results over repeated runs, and says Fluent Bit ships a benchmark skill others can copy.
    4. 18:13 He explains a fast path that decodes OTLP straight into the internal record format and encodes to MessagePack once, instead of encoding twice as before.
    5. 25:44 He compares Fluent Bit 5.2 with 5.1 and the OpenTelemetry Collector on OTLP processing and says the process of measuring mattered more than any single change.

    Evolution of Agentic Networking Stack in Envoy

    Boteng Yao, Yan Avlasov

    Two Envoy maintainers from Google describe what they are adding to Envoy for AI traffic: an AI protocol manager with its own filter chains, MCP support and a REST-to-MCP bridge. They also introduce Agent Router with a Python SDK and outline a roadmap that includes semantic routing and pluggable policy engines.

    10 min slot · Level not listed · Session

    Networking and connectivityAI agents and automation

    Watch this if: You run Envoy and want to hear from its maintainers what is being built into the proxy for LLM, MCP and agent traffic.

    1. 0:52 Yan Avlasov says Envoy has been integrated into continuous security scanning by frontier models.
    2. 3:40 Boteng Yao introduces an AI protocol manager with AI filter chains, which he describes as an "L8" layer for model extraction, schema validation, model routing, guardrail callouts and transcoding between providers.
    3. 6:26 He says Envoy is committed to tracking the latest MCP spec, including the move to stateless MCP, with routing by tool, spec validation, RBAC and ext_authz authorization, and a built-in bridge that exposes a REST API as an MCP server.
    4. 7:28 He introduces Agent Router and a new Python SDK that he says lets developers define model policies and failover without having to understand Envoy.
    5. 8:55 Yan Avlasov lists the roadmap for the next year: semantic routing, pluggable policy engines for agent governance, more model providers, advanced inference routing and hardening against frontier-model scans.

    Fluent Bit: The Evolution of High-Performance Telemetry Pipelines

    Eduardo Silva

    Eduardo Silva introduces Fluent Bit as an agent or aggregator for moving logs, metrics and traces, and announces the Fluent Bit 5.2 release. He highlights a new typed Lua scripting interface, performance comparisons he presents against Fluent Bit 5.1 and the OpenTelemetry Collector, and a build of Fluent Bit that runs in the browser.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliability

    Watch this if: You run Fluent Bit and want the 5.2 release highlights in five minutes.

    1. 0:49 Eduardo Silva says Fluent Bit collects from sources such as journald, HTTP and OTLP with more than a hundred connectors, then filters data and routes it to multiple destinations.
    2. 1:46 He announces Fluent Bit 5.2 and lists a new journald collector that converts to OpenTelemetry logs, throttling for slow destinations, and improved filesystem buffering.
    3. 2:53 He says a new fully typed interface for Lua scripts, which he calls FTS, gives an API for logs, with the same available for metrics and traces.
    4. 4:11 He shows a comparison of the new version with Fluent Bit 5.1 and the OpenTelemetry Collector on throughput and CPU use when ingesting JSON logs and OTLP.
    5. 4:51 He says Fluent Bit can now be compiled to run in the browser, and that a first implementation called Fluent Bit Studio lets users test Lua scripts and processors before production.

    Multi-Cluster Orchestration System: Karmada Updates and Use Cases

    Joe Nathan Abellard, Hongcai Ren

    Joe Nathan Abellard of Bloomberg, a Karmada maintainer presenting alone because Hongcai Ren could not attend, explains how Karmada propagates workloads across clusters and which recent features target AI workloads. He then describes the managed multi-cluster platform Bloomberg built on Karmada, including its observability and scale-testing setup and a fan-out scheduler he says cut propagation latency, and closes with the 2026 roadmap.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesPlatform engineering and developer experience

    Watch this if: you run or plan a multi-cluster platform and want to see how one company operates Karmada as a managed service and tunes its scheduler under load.

    1. 3:39 Abellard walks through the propagation pipeline: a propagation policy matches a workload, the resource detector creates a resource binding, the scheduler assigns clusters, and work objects are applied to each member cluster.
    2. 6:44 He lists recent features aimed at AI workloads: multi-component scheduling for workloads such as Ray jobs, priority-based scheduling, federated resource quotas, and overflow cluster affinities that use on-prem GPUs before cloud ones.
    3. 11:22 He describes Bloomberg's high-availability topology, where each Karmada control plane is stretched across host clusters in several data centers so the managed service can survive the loss of a whole data center.
    4. 18:43 For scale tests he says they simulate 50 member clusters of 1,000 nodes each with KWOK, with one real node per cluster, and drive load with ClusterLoader2 while a sidecar measures end-to-end propagation latency.
    5. 26:12 He explains the fan-out scheduler built for duplicated placements, which only checks feasibility and so can run many workers; he reports P99 propagation latency under 1 second at 50 objects per second, against about 3 minutes 45 seconds at 20 with the default scheduler.

    New Traffic, New Rules: Standardizing AI-Aware Networking in Kubernetes

    Nir Rozenbaum, Keith Mattix

    Nir Rozenbaum and Keith Mattix present the proposals the Kubernetes AI Gateway Working Group has been developing for Gateway API: pre-routing filters for payload processing, a Backend resource, an endpoint selector, gateway routability and a multi-stage route. They explain the AI traffic cases behind each one, such as routing on the model name in the request body and calling external model providers, and say next steps include external processing, token-based rate limiting and consolidating AI networking efforts in SIG Network.

    30 min slot · Level not listed · Session

    Networking and connectivityAI inference and serving

    Watch this if: you build or operate gateways for inference or agent traffic and want to know which Gateway API additions the AI Gateway Working Group is proposing.

    1. 4:09 Nir Rozenbaum introduces pre-routing filters, an ordered list of filters that run before a route is selected, which he says is already experimental and lets a gateway promote the model name from the request body to a header for body-based routing.
    2. 7:46 Keith Mattix argues that the Kubernetes Service resource does two jobs, a producer-oriented front end with a DNS name and cluster IP and a consumer-oriented bag of endpoints, and that AI traffic to external model providers has made the limits more urgent.
    3. 12:56 He describes the Backend resource, now experimental in Gateway API, which holds an in-cluster endpoint selector or an external hostname plus TLS and protocol settings, and says it is not a full replacement for Service.
    4. 19:40 He presents the routability proposal for stating in a standard way whether a gateway is reachable only inside the cluster, and warns that a publicly reachable egress gateway becomes an open relay.
    5. 23:17 Nir Rozenbaum introduces the multi-stage route, which references existing routes and sequences stages such as tokenization, prefill and decode for one request, with payload processing handling what passes between stages.

    Welcome to Health Check Hell: CRDs, Statuses and Missing Standards

    Regina Voloshin, Dag Bjerre Andersen

    Regina Voloshin and Dag Bjerre Andersen describe how custom resources report status in different ways, so tools such as Argo CD, Flux, kro and Crossplane each have to be taught what healthy means. They show how Argo CD health checks are contributed as Lua scripts, present a prototype that reports health in three dimensions, and lay out options for moving health checks into a shared standard.

    30 min slot · Any Level · Session

    Platform engineering and developer experienceKubernetes internals and runtimes

    Watch this if: you write or rely on health checks for custom resources in GitOps tools and want to see where a common standard could come from.

    1. 6:03 The speaker explains that Argo CD has six health statuses and uses contributed Lua scripts to map each custom resource's status fields onto them.
    2. 11:37 The speaker says kro has no built-in health checks and Crossplane's cover only part of the ecosystem, so each tool has to be taught again what healthy means.
    3. 13:54 The speaker introduces kstatus, a Go library that reports a resource's reconciliation state, and says that among graduated and incubating CNCF projects only Flux and Helm seem to have adopted it.
    4. 18:05 The speaker argues that a single health value hides availability, and shows a prototype library he calls Kube Health that splits health into three dimensions.
    5. 23:17 The speaker walks through options for a shared approach: a common library, a Kubernetes aggregated API, health inside the custom resource status, or a Lua script in a CRD annotation.

    You Don’t Have to Choose: Argo and Flux Are Friends!

    Emily Chen, Leigh Capili

    Emily Chen of Akuity and Flux maintainer Leigh Capili compare the design priorities of Argo CD and Flux and describe ways teams run both, such as Flux for cluster add-ons across a fleet and Argo CD for developer applications. In live demos, Flux bootstraps Argo CD, a Flux signature failure shows up as a degraded Argo CD application, and Kargo promotes a Flux Helm release of cert-manager across three virtual clusters.

    30 min slot · Advanced · Session

    Delivery, GitOps and release safety

    Watch this if: your organization runs both Argo CD and Flux, or is arguing over which one to pick, and you want to see them working in one cluster.

    1. 8:43 Chen says Argo CD has shipped Flux health checks since version 2.13, so Flux Helm releases and kustomizations show their health in an Argo CD application.
    2. 10:12 The speakers describe a common split where Flux handles fleet management and cluster add-ons while Argo CD serves application developers.
    3. 16:34 In the demo, Capili pushes an unsigned chart and the signature verification failure from Flux appears in the Argo CD interface.
    4. 20:19 Chen's Kargo promotion of cert-manager commits directly to Git for Flux to pick up, without using Argo CD.
    5. 22:16 Capili says Kargo has only one health checker, for Argo CD applications, and proposes one that reads kstatus so Kargo could understand Flux and other tools.

    “Allowed but Unsupported”: When Platform Support Boundaries Meet Enterprise Reality

    Niranjan Shankar

    Niranjan Shankar describes how the Azure Kubernetes Service team opened limited escape hatches for enterprise customers and what happened when support ownership was unclear. He uses packet loss at the boundary between a self-managed network plugin and a managed service mesh to show why teams need to name who owns the risk.

    25 min slot · Any Level · Session

    Platform engineering and developer experienceSecurity, identity and policy

    Watch this if: You need to give advanced platform users more control without leaving production support ownership ambiguous.

    1. 4:38 Shankar introduces the 'Allowed but Unsupported' tier and uses Istio to show how a team can allow a few EnvoyFilter uses, support routine MeshConfig fields, and block higher-risk settings.
    2. 11:39 He uses packet loss with a self-managed CNI and a provider-managed service mesh to explain why the boundary between supported and unsupported parts is hard to diagnose during an incident.
    3. 13:12 He recalls customers having trouble migrating from self-managed Prometheus to the managed offering because it did not support a rule resource they used.
    4. 20:35 He recommends giving unsupported features a signpost: a way to get best-effort help, an internal owner for production risk, and a path back to a supported option.
    5. 23:08 He closes with criteria for deciding what to expose, including whether teams can isolate the security risk, find an owner, or offer a narrower subset instead of the entire API.
