    Composing Inference on Kubernetes: Gateway, Schedule, Serve, Observe

    Karena Angell, Alex Chircop

    Karena Angell and Alex Chircop argue that production inference on Kubernetes is too often built as a closed vertical stack, and present gateway, scheduling, serving and observability as separate layers joined by explicit interfaces. They go through six kinds of composability, show recorded lab runs of several traffic shapes and component swaps, and close with questions for teams to ask of their own clusters.

    30 min slot · Any Level · Session

    AI inference and servingNetworking and connectivityObservability and reliability

    Watch this if: you are building a shared inference platform on Kubernetes and want a way to decide which layer owns routing, admission, serving and tracing so that parts can be swapped later.

    1. 3:15 Angell says the biggest trap they see in production is building separate silos for chat, RAG and agents, which duplicates routing, scheduling and telemetry for what she describes as one nested workload.
    2. 14:16 Chircop separates admission from routing: he says a scheduler such as Kueue decides once whether pods can exist under quota and fairness rules, while the endpoint picker chooses which replica serves each prompt, using signals such as queue depth and a warm KV cache.
    3. 17:02 Chircop says the OpenTelemetry GenAI semantic conventions give components a shared vocabulary for spans and metrics, and W3C trace context propagation joins them into a single trace across the hops.
    4. 18:45 Angell cites Hugging Face moving Text Generation Inference into maintenance mode, and says teams that kept serving behind a gateway API contract could swap engines quickly while others had to rework their client apps.
    5. 27:13 Chircop narrates recorded lab runs in which gateways are swapped while routing live traffic, llm-d's endpoint picker is replaced by the reference picker for the Gateway API Inference Extension, and the scheduler is changed between Kueue, Volcano and KAI Scheduler.

    Kubernetes with Conviction: How Customization is Shaping the OSS AI Ecosystem's Future

    Jago Macleod, Shaun Hopper

    Jago Macleod describes treating Kubernetes as a shared core that Google Kubernetes Engine can adapt with targeted changes rather than a permanent fork. Shaun Hopper explains how Meta used that approach to customize node updates and coordinate the rollout of DaemonSets for its AI workloads.

    5 min slot · Level not listed · Keynote

    AI inference and servingKubernetes internals and runtimes

    Watch this if: you want to see how Google and Meta approach workload-specific Kubernetes changes without maintaining a permanent fork.

    1. 1:19 Macleod says large customers want to swap schedulers and autoscalers, tune the operating system, and adopt upstream changes faster.
    2. 1:57 Macleod describes treating Kubernetes as a kernel, then applying targeted changes on top of a base tested through the regular release channel.
    3. 3:31 Macleod calls GKE Frontier an operating model rather than a product, and Hopper explains why Meta wanted a custom operating system image.
    4. 4:12 Hopper describes working with Google to exclude nodes with active workloads from upgrades and give Meta control over DaemonSet rollouts.
    5. 6:13 Macleod says the same approach lets GKE preview builds bring upstream changes to users earlier in the release cycle.

    Pods in the Wild: Reinforcement Learning on Kubernetes with OpenRL

    Sunil Arora, Ravin Kumar

    Ravin Kumar uses DolphinGemma to illustrate what can happen when teams fine-tune an open model on a specialized dataset. Sunil Arora introduces OpenRL on Kubernetes and uses a demo recording to show how trainers and samplers can share a GPU pool.

    8 min slot · Level not listed · Keynote

    AI agents and automationAccelerators and workload scheduling

    Watch this if: you want an example of turning domain data into a fine-tuned model and scheduling reinforcement learning on Kubernetes.

    1. 1:38 A video shown by Kumar introduces DolphinGemma and says the team used decades of dolphin vocalization research to train a model that generates synthetic dolphin sounds.
    2. 2:26 Kumar walks through a fine-tuning workflow that starts with a base model and domain-specific data, then uses supervised fine-tuning or reinforcement learning.
    3. 4:02 Arora introduces OpenRL as a post-training service for Kubernetes and says its Tinker-compatible primitives let researchers design an RL loop separately from the infrastructure.
    4. 7:47 In the recorded demo, Arora shows OpenRL scheduling trainers and samplers onto GPUs and explains how Dynamic Resource Allocation partitions the accelerator pool.
    5. 8:39 Arora says the team is releasing post-training recipes and points to a legal-task example using Agent Substrate for RL environments and llm-d for sampling and judging.
