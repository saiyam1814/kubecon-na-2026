    Explore TAG Workloads Foundation: Core Runtime, Batch Scheduling, and Moar

    Stephen Rust, Yuan Tang, Marlow Warnicke, Rajas Kakodkar, Paco Xu

    Five leads of the CNCF TAG Workloads Foundation explain what a technical advisory group does, what this one covers, and how its batch subproject and white paper initiatives run. They then walk through graduated, incubating and sandbox projects they place in the TAG's scope and describe how newcomers can join meetings, reviews and initiatives.

    30 min slot · Level not listed · Session

    Community and open source adoptionKubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you maintain or use a workload, runtime or scheduling project and want to know what the TAG does and how to take part.

    1. 2:10 Stephen Rust describes a TAG as a technical advisory group that supports CNCF projects and says it is a way to scale advice across many projects with few people.
    2. 5:13 Rust says initiatives are time-bound efforts with a deliverable such as a white paper, while subprojects carry longer-term work, and that the TAG helps projects with their maturity reviews.
    3. 10:23 Marlow Warnicke describes the batch subproject's scheduling capabilities white paper, which she says aims to compare schedulers under different workload mixes, and asks for contributors.
    4. 14:15 Paco Xu lists graduated projects he places in the TAG's scope and says Karmada and Kubeflow graduated this year and KubeVirt graduated recently.
    5. 19:07 Rajas Kakodkar says no single role or expertise is needed to get involved, and suggests joining meetings, sharing pain points, demoing a project or reviewing white papers.

    Kubernetes The Hard Way - Live

    Lucy Sweet, Sandeep Kanabar

    Lucy Sweet and Sandeep Kanabar build a Kubernetes cluster live, starting each component on local virtual machines. They trace an application from a kubectl request through the API server, the scheduler, and the kubelet to a running container.

    30 min slot · Any Level · Session

    Kubernetes internals and runtimes

    Watch this if: You want to see what changes when each Kubernetes component starts and how those changes turn a pod request into a running container.

    1. 6:54 Kanabar starts etcd and inspects its membership, explaining how the API server uses it to persist cluster state.
    2. 7:58 Kanabar verifies etcd by writing and reading a key, then explains why the API server is the entry point for other control-plane components.
    3. 12:41 Sweet explains reconciliation as observing actual state and taking steps toward the desired state, using a deployment with missing replicas as the example.
    4. 13:55 Sweet distinguishes the controller manager, which runs core controllers, from the scheduler, which chooses a node for a pod.
    5. 17:35 Sweet shows why a pod stays pending until a node joins, then uses crictl to inspect the NGINX container running under containerd.

    Lima as the Universal AI Sandbox

    Akihiro Suda

    Akihiro Suda of NTT presents Lima as a virtual machine sandbox for AI coding agents, arguing that agents' built-in sandboxes are weaker than VMs and citing reports of agents deleting home directories, installing hallucinated packages and being prompt-injected. He covers the project's history and adopters, the two ways to pair agents with Lima (agent inside the VM, or outside it through Lima's MCP server), a demo of the sync mode that asks before writing changes back to the host, and the features added in versions 2.0 through 2.3.

    30 min slot · Level not listed · Session

    AI agents and automationSecurity, identity and policyKubernetes internals and runtimes

    Watch this if: you run AI coding agents on your laptop and want to confine them to a virtual machine.

    1. 2:08 Suda says the sandboxes built into AI agents, such as Landlock on Linux and sandbox-exec on macOS, are not as strong as virtual machines, and that with Lima any damage stays inside the VM or the files mounted into it.
    2. 12:36 He lays out two options: run the agent, and optionally GPU-accelerated inference, inside the VM, or keep the agent outside and connect it to Lima through its MCP server.
    3. 13:37 He describes sync mode as an alternative to mounting, in which synced directories are written back to the host only after the user confirms.
    4. 14:40 Demo: he runs OpenCode inside a Lima VM against a model running in the VM, has it edit a file, and on exit is asked whether to accept the changes, declining to sync them back.
    5. 20:21 He lists what version 2.3 adds, including a native Windows driver based on the Host Compute System, real IP networking on Linux hosts, hiding secrets from agents with an ignore file, and blocking guest access to the host's loopback.
