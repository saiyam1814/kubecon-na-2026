    All Things DRA in One Place: DRA Example Driver Deep Dive

    Jon Huhn

    Jon Huhn of Microsoft presents the DRA example driver, a Kubernetes-hosted driver with entirely synthetic devices that he says aims to show a runnable example of every Dynamic Resource Allocation feature. He walks through what a DRA driver does at each stage of a workload's life and runs four demos on a local cluster.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you want to try Dynamic Resource Allocation on a laptop or are writing a DRA driver and need a working reference.

    1. 4:38 Huhn explains binding conditions: the scheduler allocates a device, then waits for the driver to signal it is reachable from the node before binding the pod, with a stub controller in the example driver.
    2. 6:48 First demo: on a default Kubernetes 1.37 kind cluster he installs the driver's Helm chart and two pods are each allocated a different mock GPU, with no feature gates enabled.
    3. 8:57 Second demo: with the driver's webhook enabled, a ResourceClaim whose GPU config has an invalid time-slicing interval is rejected before any pod tries to start.
    4. 11:30 Last demo: he installs the driver twice, as mock GPUs and mock network devices, and a claim with a match attribute constraint gets a GPU and a NIC on the same PCIe root.
    5. 18:21 Huhn lists where the example driver is already used: the Kubernetes documentation, Cluster Autoscaler tests, the AI Conformance Program and SIG Scalability tests at up to 5,000 nodes.

    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

He lists recent features and community testing work, and closes by urging people to burn down their lab rather than production.

    5 min slot · Level not listed · Lightning Talk

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you want a four-minute overview of what kube-burner does before trying it for cluster scale testing.

    1. 0:34 Andrew frames the problem with a simple pod-count reproducer and the questions it raises about scale rate, latency measurement, namespaces, metrics and churn.
    2. 1:16 Andrew describes kube-burner as a Go tool that takes YAML configs to create, delete and churn Kubernetes resources by count or percentage.
    3. 1:29 Andrew says it can collect metrics from the cluster's Prometheus and write them to JSON files, OpenSearch, local storage or Prometheus TSDB chunks.
    4. 1:54 Andrew lists newer features including scaffolded configs, pprof collection, grouping resources into waves, and incremental load that ramps up gradually.
    5. 2:35 Andrew names community testing done with kube-burner, including OVN-Kubernetes, node remediation operators, schedulers, Cluster Autoscaler and KubeVirt VM scale tests.

    SIG Autoscaling Project Updates

    Jack Francis, Jason Deal, Heba Elayoty, Kuba Tużnik

    Jack Francis, Jason Deal, Heba Elayoty and Kuba Tużnik give updates on Kubernetes SIG Autoscaling projects, including Karpenter's DRA support, balanced consolidation and node repair, the capacity buffer and capacity quota APIs, and the split of Cluster Autoscaler into a core plus separate provider projects. Elayoty then explains what workload-aware scheduling needs from autoscalers, and Tużnik presents scheduler-driven autoscaling, a proposed redesign in which the scheduler requests nodes from the autoscaler.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you run Karpenter or Cluster Autoscaler and want the latest feature updates plus the proposed redesign of how autoscalers work with the scheduler.

    1. 3:28 Jason Deal says Karpenter added DRA support in its scheduling simulation in v1.14, covering structured parameters, consumable capacity, partitionable devices and prioritized alternatives, with provider implementations in the AWS provider and EKS Auto Mode.
    2. 6:11 He introduces balanced consolidation, which weighs the share of pods disrupted against the share of cost saved and only acts when the score passes a threshold.
    3. 10:08 Jack Francis says Cluster Autoscaler is being split into a core repository and separate provider projects, and that the SIG will keep supporting releases in the older all-in-one model for a transition period.
    4. 19:50 Kuba Tużnik describes the split brain problem: the autoscaler has to predict what the scheduler will decide, and when its predictions are off it makes wrong scaling decisions.
    5. 24:15 He outlines the proposed design in which the autoscaler publishes potential capacity and the scheduler issues node claims, and estimates it at more than ten KEPs over one to two years.

    SIG-Node: Intro and Deep Dive

    Peter Hunt, Tim Allclair, Dawn Chen, Mrunal Patel, Sergey Kanzhelev

    Host Peter Hunt introduces what SIG Node owns and then runs a panel of SIG Node leads on how the kubelet should serve agentic workloads alongside traditional ones. The panelists discuss dynamic containers, agent frameworks that bypass Kubernetes features, and how the SIG is trying to move enhancements from alpha to GA faster.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAI agents and automation

    Watch this if: you run agent or other short-lived workloads on Kubernetes and want to hear where SIG Node is taking the pod and the kubelet.

    1. 3:54 Peter Hunt lists what he says went GA in Kubernetes 1.36 and 1.37, including user namespaces, PSI and OCI volumes, and what moved to beta.
    2. 9:36 Dawn Chen says agent frameworks find the API server too slow for actors that want to resume in milliseconds, and that she told the Agent Substrate team to move fast and learn from users.
    3. 14:42 Tim Allclair says agent frameworks that do everything inside one container become opaque to Kubernetes and miss its observability, auditing, policy and identity.
    4. 16:46 Tim Allclair explains dynamic containers: injecting a container into a running pod with pre-allocated pod-level resources, which he says takes a few hundred milliseconds.
    5. 31:27 Asked when dynamic containers will be ready, Tim Allclair says the plan is alpha in 1.38, beta in 1.39 and GA in 1.40, and that he would not be surprised by a delay.

    Spark on Kubernetes: The Gap Between “It Works” and “It Works Well”

    Damon Cortesi

    Damon Cortesi says Airbnb finished moving its Spark fleet from Hadoop to Kubernetes two weeks before the talk and goes layer by layer through what failed on the way: the control plane, scheduling, nodes, disks, networking, Spark itself and observability. He says most of the 34 changes were small config edits or backported patches that were hard to find, and sums up the lesson as check your config, stress test, repeat.

    30 min slot · Advanced · Session

    Data, storage and stateKubernetes internals and runtimesObservability and reliability

    Watch this if: you run or plan to run Apache Spark on Kubernetes at scale and want a list of concrete failure points and the fixes one team applied.

    1. 1:23 Cortesi says Airbnb hit 100% two weeks earlier, shutting down its last legacy Hadoop cluster, with a fleet of about 588,000 daily Spark jobs.
    2. 4:55 On the control plane, he says dropping the events TTL from one hour to 10 minutes cut etcd P99 latency from half a second to under 25 milliseconds and the object count from 2 million to 400,000.
    3. 9:06 He describes two Apache YuniKorn problems, one asking for far more capacity than needed because of a Go bug and one asking for too little under FIFO sorting, and says KWOK let him test YuniKorn at scale without provisioning real capacity.
    4. 12:35 He says a Node Problem Detector log rotation bug marked healthy nodes as dead, so that about 74 nodes were removed in 24 hours, one of four node-health bugs they found.
    5. 16:28 He says unique pod labels pushed Cilium past its 65,000 identity limit at their pod creation rates, and the fix was basing identities on a short allow list of labels.
