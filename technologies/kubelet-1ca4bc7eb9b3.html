    Binary Version Is Not Behavior: Skip-Level Kubernetes Control Plane Upgrades With KEP-4330

    Sameer Marulkar

    Sameer Marulkar of LinkedIn's compute infrastructure team describes how his team moved the control planes of more than 250 on-prem clusters from Kubernetes 1.31 to 1.34 in one binary rollout by pinning the emulated version from KEP-4330 to 1.31 and promoting it later. He says this cut the upgrade from about 40 business days to under seven, and he lists the traps they hit and the metrics they used to verify what behavior was live.

    30 min slot · Advanced · Session

    Delivery, GitOps and release safetyKubernetes internals and runtimes

    Watch this if: you run your own Kubernetes control planes, are several minor versions behind, and want an upgrade path with a rollback step.

    1. 1:35 Marulkar states the result: instead of six fleet rollouts going one minor at a time, they shipped the 1.34 binary while it still behaved like 1.31, then did a single promotion, taking about seven business days instead of 40.
    2. 6:24 He explains the emulated version flag from KEP-4330: roll out the new binary with the flag pinned to the release you run today as the deploy step, then raise it later as the release step.
    3. 9:30 He lists the traps: the new code still needs a canary, a feature gate removed by 1.34 stops the binary from starting so gates must be pruned first, and kubelet skew is measured against the emulated version.
    4. 11:53 To verify emulation is on he says not to trust the build info, which only reports the binary, and to check the version info metric and the feature enabled metric instead.
    5. 15:51 At promotion he warns of two things that are easy to miss: removed APIs keep being served during the soak and break only when the emulated version is raised, and alpha features are not covered by emulation.

    CRI-O: Plug It, Tune It, Share It — Extending and Accelerating Your Runtime

    Sohan Kunkerkar, Ayato Tokubi

    Ayato Tokubi gives a CRI-O project update, explains how Node Resource Interface plugins adjust containers at creation with examples for ulimits, topology, devices and networking, and lists upstream enhancement proposals that touch container runtimes. Sohan Kunkerkar then walks through the Kubernetes memory QoS work, including why throttling and protection became opt-in, a proposal to have the Vertical Pod Autoscaler react to memory pressure, and progress on kubelet memory use and peer-to-peer image sharing.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesAccelerators and workload scheduling

    Watch this if: you operate Kubernetes nodes and want to know what NRI plugins can change, and where the memory QoS work in SIG Node is heading.

    1. 2:39 Ayato Tokubi introduces the Node Resource Interface as a pluggable way to add custom logic to container runtimes such as containerd and CRI-O, and walks through a ulimit adjuster plugin that changes the OCI spec before a container is created.
    2. 9:25 He advises starting with standard Kubernetes APIs and using NRI only for domain-specific needs, and says plugins are powerful enough to break a cluster, so operators should trust the plugins, restrict the NRI socket and plan for plugin failures.
    3. 14:41 Sohan Kunkerkar explains the memory QoS feature, in which the kubelet sets memory.min or memory.low to protect requests and memory.high to throttle a container before it reaches its limit.
    4. 17:52 He walks through an example where a container above memory.high on a node without swap is throttled so hard that throughput collapses, which he gives as the reason both memory QoS settings are now opt-in.
    5. 23:33 He says SIG Node concluded the kubelet is not the right place to react to memory.high throttling, and describes a proposal still in design for the Vertical Pod Autoscaler to treat a memory stall like an OOM kill and resize the pod in place.

    From Maintenance Chaos to Steady Uptime: GitOps-Driven Scheduling across GPU Fleets

    Natalie Bandel, Soumya Balakrishnan

    Natalie Bandel and Soumya Balakrishnan, who work on the Kubernetes infrastructure behind NVIDIA's GeForce NOW, describe how they coordinate node maintenance such as Kubernetes upgrades across many GPU clusters. They declare the target version in Git, let a controller in each cluster report drift, and have a fleet rollout planner and a lock service decide when each cluster may start.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyAccelerators and workload schedulingPlatform engineering and developer experience

    Watch this if: you run upgrades and node maintenance across many clusters and still coordinate them with spreadsheets and chat threads.

    1. 7:45 Balakrishnan describes a drift-detecting controller in every cluster that compares the version declared in Git with each node's kubelet version and raises a maintenance request to the fleet rollout planner without acting on it itself.
    2. 10:50 She says a ticket needs permission from a cluster lock service, a fleet-level gatekeeper that keeps an upgrade from colliding with incidents, change freezes or another maintenance, and the planner backs off and retries on a no.
    3. 12:54 She says done means three things for them: the node is upgraded, validated and returned to service, so a node at the right version that fails validation is not counted as done.
    4. 15:32 Bandel explains the split of decisions: the fleet planner decides when an upgrade starts in a cluster, and a controller inside the cluster picks which nodes drain first based on what is running, capacity and node health.
    5. 19:46 Bandel points to upstream work inside one cluster, a KEP for eviction requests that she says targets alpha in 1.38 and one for node lifecycle conditions, and says the fleet level is still the open part.

    Not All Memory Is Equal: How To Properly Observe Memory Usage

    Braydon Kains, Roger Coll

    The speakers explain why host, node, pod and process memory metrics differ, tracing each to the Linux file it is read from and to how the kernel treats anonymous and file-backed pages. Using the OpenTelemetry Collector contrib binary in live demos, they show that much of its resident memory is file-backed data that can be reclaimed, and they recommend collecting system usage, container usage and working set together.

    30 min slot · Advanced · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: You size memory limits or alert on memory in Kubernetes and want to know what RSS, usage and working set each count.

    1. 4:40 Roger Coll says the metrics differ because they are read from different files: system memory usage comes from /proc/meminfo, while the kubelet's node usage, RSS and working set come from the cgroup memory stats.
    2. 11:17 Braydon Kains says an OOM kill happens when there are no clean file-backed pages left to reclaim, not simply when a process is over its limit.
    3. 15:34 Roger Coll says the Collector contrib binary has 12,000 Go init functions, about 17 megabytes loaded into RAM, which run once at startup.
    4. 17:41 In a live demo, forcing a reclaim removes a large share of the contrib Collector's memory and much of it never pages back in; Braydon Kains adds that working set drops only after a reclaim classifies file pages as inactive.
    5. 23:14 Roger Coll says working set is the value Kubernetes treats as memory usage and the one the kubelet uses to pick pods to evict under node memory pressure.

    PKI Done Easy with Pod Certificates and Cluster Trust Bundles

    Taahir Ahmed, Stanislav Láznička

    Taahir Ahmed and Stanislav Láznička explain two Kubernetes features they say are stable in 1.37: Pod Certificates, where the kubelet generates a key and obtains and rotates a certificate for a pod, and Cluster Trust Bundles for distributing root certificates. They demo Ahmed's TinyCert signer issuing SPIFFE certificates to a client and a server, and outline built-in signers they hope to add upstream.

    30 min slot · Advanced · Session

    Security, identity and policyKubernetes internals and runtimes

    Watch this if: you still copy CA ConfigMaps into every namespace or hand-roll certificate requests for pods, and want the API-level view of the replacement.

    1. 5:44 Láznička describes the Pod Certificates flow: the kubelet generates the private key, publishes a PodCertificateRequest, a signer issues the certificate, and the kubelet writes both into the pod, so he says the key never leaves the node.
    2. 8:20 He says certificate lifetimes are capped at 24 hours for kubernetes.io signers and 91 days for all others, and that the kubelet also handles rotation.
    3. 10:26 Ahmed says Kubernetes has no built-in signer for these yet, so you bring your own, and introduces TinyCert, a small signer he wrote that he suggests for learning the feature set.
    4. 16:05 In the demo he applies a client and a server pod that each mount a SPIFFE certificate and trust bundle, shows the PodCertificateRequest objects, and reads logs of each side authenticating the other's SPIFFE ID.
    5. 22:48 Láznička outlines a planned built-in signer for service serving certificates, which he says would cover server TLS for webhooks and aggregated APIs inside a single cluster.

    The Latest in GPU, TPU, NIC and Other Device Support - WG Device Management

    John Belamaric, Morten Jæger Torkildsen

    Morten Torkildsen and John Belamaric of Google give the Device Management working group update, recapping why Dynamic Resource Allocation replaced the device plugin's opaque counters and what its four parts are. They cover the features that shipped in Kubernetes 1.37 and those planned for 1.38, go deeper on allocating CPU and memory through DRA and on its integration with workload-aware scheduling, and describe ecosystem adoption and next steps such as preemption and attaching GPUs to running pods.

    30 min slot · Level not listed · Session

    Accelerators and workload schedulingKubernetes internals and runtimes

    Watch this if: you manage GPUs or other accelerators in Kubernetes and want to know which DRA features landed in 1.37 and what is planned next.

    1. 3:06 Morten Torkildsen outlines DRA's four parts: the resource slice API for describing devices, the resource claim API for requesting them, the scheduler matching the two, and the kubelet API that works with the DRA driver on the node.
    2. 6:11 He explains the extended resource request feature in 1.37, which lets cluster admins adopt DRA while workloads keep using device-plugin style requests that are matched to DRA devices underneath.
    3. 7:42 He describes device taints, which let a single failing GPU or TPU be tainted instead of the whole node, so workloads on the other devices are not disrupted.
    4. 11:52 John Belamaric explains node allocatable resources with DRA, which lets CPU and memory be selected through DRA so they can be aligned with the NIC and GPU, and tells the scheduler how to account for CPU requested in both the container spec and a resource claim.
    5. 16:30 He describes the DRA integration with workload-aware scheduling, where a resource claim attached to a pod group allocates a shared resource for a new replica and cleans it up when the replica scales down.

    Two Drivers, One Topology: GPU:NIC Rail Alignment for RDMA VMs with KubeVirt DRA

    Jian Li, Alay Patel, Kazuki Sato

    Kazuki Sato of NTT DOCOMO BUSINESS, Jian Li of SK Telecom and Alay Patel describe how a multi-site GPU platform on KubeVirt moved from a manual workaround to Dynamic Resource Allocation claims that pair each GPU with an RDMA NIC under the same PCIe root. They show a recorded benchmark comparing aligned and misaligned VMs, explain the Multus change they are proposing upstream, and outline what KubeVirt's DRA support covers today and what is planned.

    15 min slot · Level not listed · Session

    Accelerators and workload schedulingNetworking and connectivity

    Watch this if: you run GPU virtual machines with RDMA networking on KubeVirt and need each GPU paired with the right NIC without pinning devices by hand.

    1. 2:07 Sato describes the earlier workaround: filling a node with placeholder pods that each hold one GPU or NIC and deleting only the ones holding the wanted pair, which had to be redone VM by VM after every node or VM restart.
    2. 5:10 Li explains that the GPU driver and the SR-IOV NIC driver both publish the standard PCI root attribute, so one resource claim with a GPU request, a VF request and a match constraint lets the scheduler allocate them as a pair.
    3. 7:15 He says upstream KubeVirt network DRA could not consume a VF wired through a Multus network, so they added a feature gate that takes the VF from the resource claim and leaves the existing CNI chain unchanged.
    4. 10:21 In the recorded demo Sato compares two four-GPU VMs: he reports about 200 Gbps of RDMA bandwidth on the misaligned VM and 391 Gbps on the aligned one, with placement as the only difference.
    5. 12:33 Li says the next gap is that CPUs and huge pages are still placed by the kubelet without topology hints from DRA devices, so a VM can get its GPU and NIC on one socket and its memory on another.

    When the Clock Lies: How an 8-Minute Time Skew Locked Kubernetes cluster for a day

    Akhil Mohan

    Akhil Mohan of VMware by Broadcom, a containerd maintainer, retraces how a CSI pod on an internal cluster sat in CreateContainerError for 19 hours after a hypervisor power failure while its containers were in fact running. He traces it to a VM that booted about eight minutes in the future, so tokens were issued in the future and kubelet's sorting of containers by creation time got stuck once chrony stepped the clock back, and he describes the fix of starting kubelet only after time sync.

    30 min slot · Any Level · Session

    Observability and reliabilityKubernetes internals and runtimes

    Watch this if: you operate Kubernetes nodes on virtual machines and want a worked example of debugging from a stuck pod down to the hardware clock.

    1. 0:26 Mohan lays out the symptom: a CSI pod in CreateContainerError with over 5,000 retries failing on a container name reservation, while crictl on the node shows the same containers already running.
    2. 8:51 He finds kube-proxy rejected by the API server because its service account token is not valid yet, issued by a control plane VM whose clock was ahead of the other two.
    3. 10:08 Journal logs show the time jumping backwards 45 seconds after boot: he says the VM inherited a clock about eight minutes ahead from the ESXi host and chrony stepped it back in one go, after kubelet had already started.
    4. 18:55 He explains the loop: kubelet sorts container statuses by created-at wall clock time, so the attempt created on the future clock always looks newest and kubelet keeps trying to recreate an attempt that is already running.
    5. 21:36 The fix he describes is ordering the kubelet systemd unit after a chrony wait service with a 180 second timeout, chosen so a node boots slower instead of never booting when NTP is unavailable.
