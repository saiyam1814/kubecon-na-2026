    Falco Never Flies Alone: Runtime Security as an Ecosystem

    Leonardo Grasso, Alessandro Cannarella

    Leonardo Grasso and Alessandro Cannarella describe how Falco, now ten years old, spent the year consolidating its core and growing an ecosystem around it. They cover core and plugin updates, new experiments for AI coding agents, Falco Operator 0.5, and a from-scratch rewrite of Falcosidekick as version 3.

    30 min slot · Level not listed · Session

    Kubernetes internals and runtimesSecurity, identity and policy

    Watch this if: you run Falco for runtime security and want to see what changed in its core, the Falco Operator and Falcosidekick.

    1. 0:51 Grasso explains how Falco taps the Linux kernel with an eBPF probe or kernel module, enriches events with plugins, and matches them against YAML rules.
    2. 3:22 Grasso lists core cleanups such as removing the legacy BPF probe and gVisor support, new list operators in the rule language, and an experimental GPU hijacking rule.
    3. 6:38 Grasso introduces a new subproject that gives coding agents a version-pinned knowledge base and skills for contributing to the Falco code base.
    4. 16:35 Cannarella says Falco Operator 0.5 pulls artifacts from the registry once, serves them to every node, and checks rules against the Falco version before installing.
    5. 19:55 Cannarella announces Falcosidekick version 3, rewritten with per-output pipelines, live config reloads, API and UI configuration, and a single binary.

    Following the Evidence with HolmesGPT: Troubleshooting Kubernetes Apps and Infrastructure

    Yash Sharma

    Yash Sharma, presenting alone after saying his co-speaker could not attend, describes his own experiment with HolmesGPT on a demo shop application running on a DigitalOcean Kubernetes cluster with three planted faults. He shows it investigating a full Postgres volume, a CPU-hungry CronJob and a cloud-side volume attachment limit, and then outlines how he would run it in production with read-only access and human approval for changes.

    30 min slot · Any Level · Session

    Observability and reliabilityAI agents and automation

    Watch this if: you are considering an AI troubleshooting assistant for Kubernetes and want to see it work through storage, CPU and cloud-provider faults before deciding how much access to give it.

    1. 4:41 Sharma describes HolmesGPT's loop: starting from an alert thread, it calls toolsets such as kubectl, PromQL, APIs and SQL, reruns the investigation if the results are not enough, and returns a root cause with evidence and a suggested fix.
    2. 12:21 In the live demo, after he fills the Postgres volume and checkout errors rise, the holmes ask command returns evidence of no space left on the device along with possible fixes.
    3. 17:26 He says HolmesGPT runs read-only in his cluster, so a kubectl exec it attempted was denied as needing approval, and it still traced the slow checkout API to the batch job he had added.
    4. 18:38 For the third case he explains a setup where a 16th pod cannot get a volume because of a per-node attachment limit on DigitalOcean Kubernetes, and shows holmes investigate alertmanager attributing the pending pod to the cloud provider side.
    5. 24:44 His security advice is to keep the tool read-only, require human approval for any write, issue least-privilege tokens per task, and check the logs rather than fully trusting the output, since logs can carry injected content.

    When Infrastructure Breaks in Production: How EarnIn Brought Testing to the Full CNCF Stack

    Priya Namasivayam

    Priya Namasivayam of EarnIn describes a cert-manager upgrade that looked healthy but broke Linkerd certificates and customer logins, and says the team responded by running infrastructure tests as Kubernetes resources with Testkube, triggered by Flux reconciliation. A co-presenter from Testkube runs a live demo on a kind cluster in which an operator upgrade passes health checks but fails a test workflow.

    30 min slot · Any Level · Session

    Delivery, GitOps and release safetyObservability and reliability

    Watch this if: you upgrade cluster add-ons through GitOps and want to catch breakage that pod health checks do not show.

    1. 3:48 The speaker explains the incident: she says cert-manager 1.18 began rotating private keys on renewal instead of extending them, which broke certificates for Linkerd while everything looked green.
    2. 5:26 The speaker describes the fix as a Kubernetes-native testing setup built on Testkube, where tests and triggers are CRDs and a Git commit that starts Flux reconciliation also starts the tests.
    3. 10:35 The co-presenter starts the live demo by bringing up a kind cluster with Flux, CloudNativePG, cert-manager and a sample to-do application.
    4. 12:42 The co-presenter shows a Testkube test workflow for cert-manager that checks certificates are still valid after an upgrade.
    5. 20:49 After the simulated upgrade the test workflow fails, and the co-presenter explains that the operator is running but a breaking change stops the ServiceMonitor from working.
