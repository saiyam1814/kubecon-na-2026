    A Decade of AI on Kubernetes: Kubeflow’s Journey to CNCF Graduation

    Valentina Rodriguez Sosa, Alexander Perlman, Christian Heusel, Shivay Lamba, David Aronchick

    Kubeflow co-founder David Aronchick recounts how the project started, and contributors describe its components, governance and what they say CNCF graduation required. The speakers then outline planned work, including Kubeflow Pipelines 3.0 changes such as removing the ML Metadata service, a unified Python SDK, trainer and notebook features, an MCP server and experimental Helm charts for the community distribution.

    30 min slot · Level not listed · Session

    Community and open source adoption

    Watch this if: you run or contribute to Kubeflow and want the origin story, what graduation involved, and the maintainers' stated plans for Pipelines 3.0, the SDK and agent support.

    1. 2:30 David Aronchick says the first Kubeflow release was deliberately small, with only a Jupyter notebook, a TensorFlow CRD and what later became KServe, and that pipelines came about six months later.
    2. 12:22 Christian Heusel says Kubeflow reached CNCF graduated status in July 2026, and that graduation required maintainers from at least two organizations per sub-project, independent adopters and a security and governance review.
    3. 20:56 Alexander Perlman says Kubeflow Pipelines 3.0 will consolidate the per-step driver pods into one pod per run, roughly halving the pod count, using Argo Workflows executor plugins.
    4. 22:13 He says 3.0 removes the ML Metadata microservice and database and moves execution tracking, artifacts, lineage and caching into the Pipelines API server.
    5. 29:24 Shivay Lamba describes an experimental Kubeflow MCP server that exposes trainer jobs to agents while applying the user's own Kubernetes permissions so the agent stays within bounds.

    WG-Batch Updates: What’s New and What Is Next?

    Amy Chen, Yuki Iwai, Marcin Wielgus

    Marcin Wielgus, Amy Chen and Yuki Iwai give an update on the Kubernetes Batch Working Group and its projects. They cover new Kueue features such as concurrent admission, configurable preemption, topology-aware spreading, the dynamic quota orchestrator and partial scale-up, then Job, JobSet and workload-aware scheduling updates.

    30 min slot · Level not listed · Session

    Accelerators and workload scheduling

    Watch this if: you run AI training or batch jobs on Kubernetes and want to know what changed in Kueue, Job and JobSet.

    1. 3:46 Wielgus says that since last November Kueue shipped 54 releases, while PRs, issues and contributors each more than doubled.
    2. 4:45 Wielgus explains concurrent admission, where virtual copies of a workload keep trying for cheaper reserved capacity and move the job there once it frees up.
    3. 12:36 Wielgus introduces topology-aware spreading for inference, which caps the share of serving capacity placed in one rack, for example at 45%.
    4. 14:27 Chen describes the dynamic quota orchestrator, which discovers real capacity from node pools or MultiKueue worker clusters and adjusts nominal quota automatically.
    5. 28:54 Iwai explains that Kueue is adopting a shared scheduler library from kube-scheduler so its node feasibility checks match what kube-scheduler will accept.

    Zero-Gap GPU Execution: Building Secure, Pre-Warmed Pod Runtimes for High-Velocity AI Agents

    Ankit Goyal, Cong Gu

    The LinkedIn speakers present Firepool, their control plane that hands GPU jobs from agents and reinforcement learning loops to pools of already running pods, so no pod is created on the job's critical path. They describe how pods are reset and reused per caller, how standby pods parked on busy GPUs with HAMi and Volcano take over when a job ends, and report that 19 of 20 pod requests in production are served from warm pods.

    30 min slot · Any Level · Session

    Accelerators and workload schedulingAI agents and automationKubernetes internals and runtimes

    Watch this if: You run agent or reinforcement learning loops that need GPUs in short repeated bursts and want to cut pod cold starts without keeping GPUs idle.

    1. 5:07 Ankit Goyal says that with the image cached a new GPU pod takes 20 to 30 seconds to start, and that an agent running hundreds of GPU experiments pays that cost each time when it lives on CPU nodes.
    2. 8:48 He walks through a job submission and says there is no pod creation in the critical path: the dispatcher claims a warm pod and the Firepool agent inside it fetches the job's code and runs it.
    3. 14:24 Cong Gu describes the reuse rules: the Firepool agent kills the job's process tree and verifies the reset or deletes the pod, and an idle pod is held only for the caller that used it.
    4. 19:06 Ankit Goyal explains zero-gap: they use HAMi and Volcano only to schedule several pods onto one GPU, where one pod runs a job with the whole card and the rest are standby pods ready to take over.
    5. 22:09 He says Firepool pods run sandboxed with no egress by default, and outbound calls go through a sidecar proxy that injects credentials and checks policy, so agents never hold real credentials.
