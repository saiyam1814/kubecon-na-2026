    Horizontally Scale MySQL on Kubernetes

    Matt Lord, Florent Poinsard

    Matt Lord introduces Vitess as a way to spread a MySQL workload across many servers while applications still see a single MySQL server, and walks through its components. Florent Poinsard then explains the MoveTables and Reshard workflows and runs a live demo that splits one shard into two under load on Kubernetes.

    30 min slot · Level not listed · Session

    Data, storage and state

    Watch this if: your MySQL database is outgrowing a single instance and you want to see what sharding it with Vitess on Kubernetes looks like.

    1. 2:46 Matt Lord says Vitess lets you distribute the workload of one MySQL instance across hundreds or thousands of MySQL servers while users still see a single server.
    2. 6:52 Matt Lord walks through the architecture: stateless VTGates that speak the MySQL protocol, VTTablets in front of each mysqld, the topology server, vtctld and VTOrc.
    3. 16:09 Florent Poinsard explains the MoveTables workflow: copy the data, keep streaming changes, switch reads and writes, and revert through reverse replication if needed.
    4. 21:02 Florent Poinsard starts the demo: a Vitess cluster on Kubernetes with the open source Vitess Operator on his laptop, with load pushing the single shard's CPU to 100%.
    5. 25:12 After completing the Reshard workflow, Florent Poinsard reports the demo going from about 7 to 8K QPS to 10 to 11K, with latency moving from about three milliseconds to two.

    Platform as a Product in a 300-Year-Old Bank

    Abby Bangser, Joel King

    Abby frames platform engineering as a shift toward self-service with guardrails and connects it to the CNCF white papers, maturity model, and an emerging marketplace model. Joel describes how NatWest used product thinking, Kubernetes CRDs, GitOps reconciliation, and clear ownership boundaries to cut EKS cluster provisioning from eight to twelve weeks to 35 minutes.

    25 min slot · Intermediate · Session

    Platform engineering and developer experience

    Watch this if: you want a regulated-enterprise case study connecting platform-as-product theory to Kubernetes and GitOps implementation plus measured outcomes.

    1. 3:43 Joel says reuse failed when each application team copied and modified patterns, producing more than 135 variants, high cognitive load, configuration drift, and an eight-to-twelve-week path to a usable EKS cluster.
    2. 8:34 Joel says NatWest adopted platform as a product by exposing curated products through an abstracted API, using Git as the source of truth, reconciliation loops, and fleet management rather than team-by-team manual change.
    3. 11:13 Joel explains that Kratix provides the product API through Kubernetes CRDs, after which pipelines write validated desired state to Git for downstream reconciliation.
    4. 19:55 Joel says the automated EKS product reduced provisioning from eight to twelve weeks to 35 minutes while including the AWS account, networking connectivity, guardrails, and self-service request path.
    5. 23:30 Abby closes by arguing that platform teams must optimize for outcomes over outputs, composing contributions into products that give users self-service access rather than merely automating infrastructure.

    Platform as Context: Evolving Our IDP for AI Agents

    Gang Luo

    Gang Luo of Electrolux Group explains how his team extended their internal developer platform so AI agents can use it as context through MCP tools. He shares the context categories they defined, a switch to GraphQL, and benchmarks where he reports lower token use and fewer tool calls.

    25 min slot · Intermediate · Session

    AI agents and automationPlatform engineering and developer experience

    Watch this if: you want to expose your internal developer platform to AI agents through MCP and see one team's measured token and tool-call results.

    1. 1:56 Luo describes the starting point: about 400 developers, an average of six SREs, and an IDP where developers pick templates, get approval and have infrastructure provisioned for them on golden paths.
    2. 3:50 Because developers work in the IDE and terminal, his team added MCP read and write tools on top of the IDP so agents can read and provision the infrastructure it manages.
    3. 6:41 He lists the context agents need, starting with ownership, then infrastructure, deployment through GitHub Actions and telemetry, and says the IDP should hold only what is needed and point to the other sources.
    4. 9:29 He says moving the MCP tools from static APIs to GraphQL cut the tokens an agent used for discovery by about 80% from roughly 17K.
    5. 12:19 In benchmarks comparing an agent with GitHub alone against GitHub plus the IDP, he reports one task using 50% fewer tool calls and 65% fewer tokens, while noting some experiments got worse.

    Why We Bet the Data Platform on Kubernetes - And How AI Is Changing How We Operate It

    Vara Bonthu, Damon Cortesi, Padma Aradhyula, Rainie Li, Ying Xiong

    Moderator Vara Bonthu asks panelists from Airbnb, Salesforce, Pinterest and Apple Maps why they moved Spark and other data workloads from Hadoop-style clusters to Kubernetes and what was hard about it. The panelists describe pod churn, scheduling choices among YuniKorn, Volcano and Kueue, and the AI agents and skills they say they now use for troubleshooting and upgrades.

    30 min slot · Beginner · Panel

    Data, storage and stateAI agents and automation

    Watch this if: you are weighing a move of Spark or other data workloads from Hadoop to Kubernetes and want to hear what four large operators ran into.

    1. 5:30 Damon Cortesi says Airbnb reached 100% Spark on Kubernetes a couple of weeks earlier, shut down its last Hadoop cluster, and runs about 4 million Spark jobs a week.
    2. 9:46 Padma Aradhyula says Salesforce Data Cloud runs thousands of small near-real-time Spark jobs lasting two to five minutes, and that the resulting pod churn puts heavy pressure on the API server.
    3. 11:38 Rainie Li describes Pinterest's Moka platform with Apache YuniKorn and a remote shuffle service, and reports a 10% job performance improvement and over 10% annual infrastructure savings.
    4. 14:45 Ying Xiong says the hardest start at Apple Maps was convincing people to try Kubernetes without data locality, followed by scalability issues from huge jobs and from users submitting thousands of jobs an hour.
    5. 21:46 Rainie describes a multi-agent setup where sub-agents reach platform components through MCP servers and search past incidents, and says it now helps fix over 50% of troubleshooting issues.
