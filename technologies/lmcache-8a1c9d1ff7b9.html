    Beyond Model Serving: Running Production LLMs on Kubernetes with KServe

    Johnu George, Jooho Lee

    The two KServe maintainers explain how the project added an LLMInferenceService API that builds on llm-d, vLLM and the Gateway API Inference Extension rather than a new inference engine. They then go through production patterns they say KServe addresses: cache-aware routing, streaming timeouts, split prefill and decode, multi-node serving, autoscaling signals, cold starts, model updates and LoRA adapters.

    30 min slot · Level not listed · Session

    AI inference and servingAccelerators and workload schedulingNetworking and connectivity

    Watch this if: you serve LLMs on Kubernetes and want the KServe maintainers' checklist of routing, scaling and cold-start issues to plan for.

    1. 4:07 Jooho Lee describes the LLMInferenceService API, in which he says a workload controller manages single-node, multi-node and separate prefill deployments while a route controller manages the scheduler and Gateway API resources.
    2. 8:44 Jooho follows a request from the gateway to the endpoint picker, which he says can weigh prefix cache match, queue depth and KV cache usage instead of treating every healthy replica as equal.
    3. 12:47 Johnu George warns that with streaming, timeouts at each hop must exceed generation time, because he says client retries otherwise pile more load on the GPUs.
    4. 16:15 Johnu argues that GPU utilization is a misleading autoscaling signal for LLMs and says the number of requests waiting in the inference runtime's queue is a better one.
    5. 17:30 Johnu describes cold-start work with a local model cache and container snapshot and restore, and says they are seeing startup drop from minutes to a few seconds.

    CoHDI: Bridging Kubernetes and Disaggregated Memory for Memory-Aware LLM Inference

    Naoki Oguchi, Hidetsugu Sugiyama

    Naoki Oguchi and Hidetsugu Sugiyama present CoHDI, a CNCF Sandbox project they describe as letting Kubernetes attach pooled CXL memory and GPUs to worker nodes on demand, with a focus on giving LLM inference more room for KV cache. They walk through the allocation sequence for an LMCache pod, share early measurements, and outline plans to split prefill and decode across sites connected by an optical network.

    30 min slot · Advanced · Session

    Data, storage and stateAI inference and servingAccelerators and workload scheduling

    Watch this if: you run LLM inference on Kubernetes and want to see how pooled CXL memory could be attached to nodes as an extra KV cache tier.

    1. 2:50 Oguchi says KV cache capacity needs to scale independently from GPU compute, after listing the drawbacks he sees in adding GPUs, adding local DRAM, or evicting the cache to storage.
    2. 6:47 Oguchi explains the CoHDI flow: a scheduled pod triggers composition, the Dynamic Device Scaler evaluates the GPU and CXL memory needed, and the Composable Resource Operator requests them from the pool and attaches them to the worker node.
    3. 11:52 Oguchi shows cache metrics where resubmitting the first prompt raises the blocks read from the second tier from 105 to 135, which he reads as KV cache kept in CXL memory being reused.
    4. 12:44 Oguchi reports first-stage results in which attached CXL memory was 10 times faster than SSD for random reads and 18 times faster for writes, and says LMCache still needs optimization for CXL access.
    5. 18:27 Sugiyama says GPU overprovisioning at the decode site remains a problem and describes decode nodes with few GPUs and large CXL memory pools composed by CoHDI as his answer.

    Reduce vLLM Pod Cold Starts with KServe Kernel Caching

    Jooho lee, Vishwa Hiren Gandhi

    The speakers explain how GPU kernel compilation can slow vLLM startup even when model weights are already cached. They describe KServe's approach for sharing signed kernel caches across pods and report what changed in their benchmark.

    30 min slot · Any Level · Session

    AI inference and serving

    Watch this if: Your vLLM replicas scale slowly even after you have cached the model weights.

    1. 4:33 The speakers break down a baseline vLLM startup of about 250 seconds and say the compilation step accounts for roughly 35 seconds, excluding image pulls and model downloads.
    2. 5:38 The speakers explain why a new replica can compile kernels again even after another pod has compiled them: the new pod does not inherit the previous pod's local cache.
    3. 10:31 The speakers propose packaging compiled kernels as a signed OCI artifact in a registry so another node can verify the signer before making the cache available.
    4. 13:52 The speakers distinguish a workload fingerprint that identifies where a cache came from from a compatibility fingerprint that checks whether compilation settings match.
    5. 18:24 In one benchmark, the speakers report that reusing the cache cut startup from 160 to 110 seconds and compilation from about 35 seconds to just over one second.
