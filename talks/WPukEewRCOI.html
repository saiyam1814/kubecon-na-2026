Talk summary

The two KServe maintainers explain how the project added an LLMInferenceService API that builds on llm-d, vLLM and the Gateway API Inference Extension rather than a new inference engine. They then go through production patterns they say KServe addresses: cache-aware routing, streaming timeouts, split prefill and decode, multi-node serving, autoscaling signals, cold starts, model updates and LoRA adapters.

Watch this if:

you serve LLMs on Kubernetes and want the KServe maintainers' checklist of routing, scaling and cold-start issues to plan for.

Key points from the speaker

  1. 4:07 Jooho Lee describes the LLMInferenceService API, in which he says a workload controller manages single-node, multi-node and separate prefill deployments while a route controller manages the scheduler and Gateway API resources.
  2. 8:44 Jooho follows a request from the gateway to the endpoint picker, which he says can weigh prefix cache match, queue depth and KV cache usage instead of treating every healthy replica as equal.
  3. 12:47 Johnu George warns that with streaming, timeouts at each hop must exceed generation time, because he says client retries otherwise pile more load on the GPUs.
  4. 16:15 Johnu argues that GPU utilization is a misleading autoscaling signal for LLMs and says the number of requests waiting in the inference runtime's queue is a better one.
  5. 17:30 Johnu describes cold-start work with a local model cache and container snapshot and restore, and says they are seeing startup drop from minutes to a few seconds.
