Talk summary

Navjot Singh of Shopify describes load testing the fine-tuned model behind Sidekick Pulse with Inference Perf's conversation replay, sweeping concurrency levels to find how many research conversations each GPU replica completes per hour and turning that into a GPU plan. Ashok Chandrasekar of Google then presents Inference Perf's goals of reliable load generation, realistic workloads and reproducible results, and walks through its workload catalog, agentic replay generators and metrics.

Watch this if:

you need to size GPU capacity for multi-turn agent workloads and want to see how a load test is configured and read.

Key points from the speaker

  1. 2:32 Singh says Pulse runs as an offline batch of multi-turn research conversations, so the metric they watch is throughput: how many research conversations each GPU replica completes per hour.
  2. 6:03 He walks through the Inference Perf config for Pulse: a seed so every run replays the same workload, 38 turns per conversation with an 8-second wait between calls, and a concurrent load type that holds a fixed number of conversations in flight.
  3. 9:12 Singh says they had a fixed budget of H100 GPUs for Pulse, ran the same seeded sweep on each GPU topology, and found the canary's production throughput matched the load test.
  4. 14:07 Chandrasekar shows a test in which a single-process Python benchmark asked for 5,000 QPS delivered about 150 to 400 and reported inflated latency against a simulated server, while Inference Perf's multiprocess design delivered the requested rate.
  5. 20:27 He lists four generators for agentic workloads in Inference Perf: conversation replay, OpenTelemetry trace replay, Weka trace replay aimed at KV cache hits, and synthetic agentic trace replay.
