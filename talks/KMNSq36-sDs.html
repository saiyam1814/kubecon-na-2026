Talk summary

The speaker explains how the Metal3 project is starting to use fuzz testing on small, fast targets such as parsers and validation functions, and stresses that each target needs a clear expected behavior. He runs three Bare Metal Operator fuzz targets in a GitHub Actions workflow and says the project is at an early stage with many targets still to add.

Watch this if:

you maintain Kubernetes controllers and want a practical starting point for adding fuzz tests without flooding maintainers with noise.

Key points from the speaker

  1. 5:49 The speaker names the components in scope, the IP address manager, the Cluster API provider, Bare Metal Operator, and Ironic Standalone Operator, and says he is not claiming they all have the same fuzzing coverage.
  2. 7:28 The speaker says a fuzzer does not know which unusual results are wrong, so each target needs an oracle such as no panic, a required invariant, or an expected error.
  3. 13:03 The speaker lists good first targets: parsers, decoders, validation paths, input normalization, and small deterministic functions with a clear expected behavior.
  4. 18:46 In a live run, the speaker starts a one-minute workflow with three Bare Metal Operator fuzz targets and explains that the reported new interesting inputs mean new code paths, not faults.
  5. 25:38 The speaker gives current target counts per component and his estimate of how many more each needs, and invites new contributors to start with the least covered ones.
