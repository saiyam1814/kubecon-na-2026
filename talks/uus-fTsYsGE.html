Talk summary

The speakers describe how Salesforce spread workloads across clusters with Open Cluster Management and built a routing proxy so that developers keep using one kubeconfig and standard kubectl. They explain how the proxy fans out reads, sends writes to the hub's ManifestWorkReplicaSet, and routes logs and exec to the right cluster, followed by a recorded demo.

Watch this if:

You run workloads across several clusters and want developers to keep their single-cluster kubectl workflow.

Key points from the speaker

  1. 2:25 The speaker says they chose Open Cluster Management and its ManifestWorkReplicaSet to run the same workloads in several clusters and load balance between them.
  2. 6:38 The speaker introduces what Salesforce calls Workload API, a routing proxy that passes Kubernetes API calls to the right cluster and stores no credentials on the server side.
  3. 8:02 The speaker explains reads: a list fans out to all managed clusters and aggregates the results with their origin, and a get treats the ManifestWorkReplicaSet spec as the source of truth.
  4. 10:56 The speaker explains how they guard against stale overwrites by using the parent ManifestWorkReplicaSet's resource version for concurrency control.
  5. 14:16 The recorded demo starts, showing get, scale, rollout restart, logs and exec through one gateway with standard kubectl.
