Talk summary

Dmitry Shmulevich explains that topology-aware schedulers need an accurate, current map of where nodes sit in the network, and that topology data comes in many formats. He presents Topograph, which uses provider plugins to read topology from clouds and fabrics and engine plugins to publish it in the format each scheduler expects.

Watch this if:

you run GPU clusters and want topology-aware scheduling to get accurate network topology data.

Key points from the speaker

  1. 0:25 Dmitry Shmulevich says distributed AI jobs run better on nodes that are close in the network, and that schedulers need an accurate topology map to place them.
  2. 0:55 He describes the topology sources: cloud providers expose node labels and custom APIs, while on-prem clusters rely on fabric management tools and protocols.
  3. 1:31 He lists what consumers expect: topology node labels for schedulers, ResourceClaims and ResourceSlices for DRA, a proposed node feature group in NFD, and annotations plus a ConfigMap for Slinky.
  4. 2:02 He explains the Topograph design: providers query a cloud or fabric and build a common topology graph, engines translate it for a scheduler, and it watches cluster events to stay current.
  5. 3:39 He outlines plans for device-level topology, such as GPU-to-NIC rail mapping and accelerator cliques whose membership can change when a link degrades.
