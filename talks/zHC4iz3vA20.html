Talk summary

John Belamaric explains what SIG Architecture owns in the Kubernetes project, including the enhancement proposal template, production readiness review, API review and conformance criteria. Jordan Liggitt then describes three areas he says changed this year: keeping existing behavior stable through opt-in changes and feature gates, a design principle of degrading gracefully at scale, and making API review faster with linters, declarative validation and more reviewers.

Watch this if:

you contribute to Kubernetes or write controllers and want to know how SIG Architecture handles compatibility, feature gates, stale caches and API review.

Key points from the speaker

  1. 5:50 Jordan Liggitt says a couple of Kubernetes releases shipped with zero action-required release notes, and that the goal is to keep that number at zero by making big changes transparent or opt-in.
  2. 6:58 He says feature gates are now handed out freely, even for bug fixes that might not be compatible for everyone, so affected users have a fast mitigation and can emulate an older version's gate state.
  3. 11:02 He summarizes a case study on controllers acting on stale caches, saying one DaemonSet controller bug created an extra pod per node every five minutes and most controllers wasted work on writes the server rejected.
  4. 14:10 He says resource versions were officially declared comparable, and controller guidance now says to track the last written version as a high watermark and back off until the cache catches up.
  5. 16:01 He describes declarative validation, where simple rules are annotated on the Go types and require a failing test case, as one of the changes that shrinks what an API reviewer has to check.
