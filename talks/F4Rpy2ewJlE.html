Talk summary

Two platform engineers at a Fortune 100 company describe adding AI agents to the places people already ask questions: the developer portal, kubectl, node debugging with netshoot, and a ClickHouse history of cluster objects. They say they keep the agents safe with a read-only kubectl wrapper, permission rules shared in a Git repository and RBAC that excludes secrets, and that deterministic tools worked better for them than prompts.

Watch this if:

You run a platform team and want concrete, read-only ways to let AI agents answer developers' and on-call engineers' questions about clusters.

Key points from the speaker

  1. 4:15 Anton Alexander says their approach was to start with a question, not an AI product, and to put AI where that question is already asked.
  2. 5:24 He says the agent in the developer portal passes the developer's identity to the cluster so it cannot see more than that person can, and it traces a 503 to a wrong service selector.
  3. 9:19 He says instructions are guidance, not enforcement, so their coding agent may only call a wrapper CLI that exposes read-only kubectl operations, with other commands denied by permission rules.
  4. 12:26 The wrapper also lets the agent schedule a netshoot pod on a target node and run an allowed set of commands, for node-level questions the Kubernetes API cannot answer.
  5. 15:43 Scott Adams describes watching every object in their clusters and storing spec and status history in ClickHouse, so an agent can answer with SQL what changed or whether an image ever ran.
