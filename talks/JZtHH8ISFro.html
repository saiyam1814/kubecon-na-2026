Talk summary

The speaker describes a layered design for running MCP tool execution for many users on Kubernetes, with a separate sandbox per workspace and warm pools from OpenKruise. He walks through isolation boundaries, egress control, pool sizing, pause and restore, and upgrades, and says allocation latency should be measured separately from the first successful tool call.

Watch this if:

you are planning per-user sandboxes for agent tool calls on Kubernetes and want to know what to measure before scaling.

Key points from the speaker

  1. 4:05 The speaker separates three responsibilities: MCP describes how tools are discovered and called, a workspace service decides which environment a caller may use, and the execution runtime supplies the isolation boundary.
  2. 6:37 The speaker says a namespace is a place for team policy, quotas, and access control but does not give each sandbox its own kernel.
  3. 10:44 The speaker introduces the OpenKruise resources: SandboxSet for the warm inventory, SandboxClaim to take an unused instance, and Sandbox for the allocated environment.
  4. 15:35 The speaker says a sub-100-millisecond allocation figure needs a measured configuration behind it, and asks for warm hits and misses to be reported separately from first tool call latency.
  5. 20:50 The speaker describes upgrading claimed sandboxes: the default recreate mode replaces the pod, while the checkpoint restore mode he attributes to version 0.6 keeps the root filesystem but loses memory and IP.
