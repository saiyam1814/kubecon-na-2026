Talk summary

Taiki Ono describes a PR preview platform built on a Kubernetes controller that derives preview environments from existing manifests and routes traffic by a preview ID. He uses it to explain a model for deciding whether platform complexity should leak to teams, move into the platform or be absorbed by it.

Watch this if:

Watch this if you build PR preview environments or any shared platform feature and want a way to decide which complexity the platform should own.

Key points from the speaker

  1. 2:48 Ono compares generating preview manifests with a CLI or templating against creating preview resources directly in the cluster with a controller, and says his team chose the more complex controller route.
  2. 5:37 He gives a model for where platform complexity goes: leaked to product teams, moved into the platform unchanged, or absorbed, meaning the platform handles the same concerns simply.
  3. 10:19 In the architecture, a GitHub webhook creates a preview request, product teams write only a small custom resource, and the controller derives preview config from the base manifests without changing them.
  4. 16:58 For routing they build on the Gateway API for service mesh: a preview gateway puts a preview ID in a request header and sidecars route by it, which he says also lets previews span several products.
  5. 18:51 He says the platform first handled CORS but could not absorb credentialed requests simply, so the team handed CORS back to applications as a one-line change and redrew the boundary.
