Talk summary

The speakers, an SRE and an application engineer at Best Buy, argue that AI in incident response falls short when it sees telemetry but not the context a team relies on, such as recent deployments, dependencies and current service owners. Using three example incidents they say are illustrative, they describe the context sources to connect, a read-only tool gateway for the agent and what to measure, and conclude that AI should work with SREs.

Watch this if:

You are adding AI to incident response and want a grounded view of what context it needs before its summaries can be trusted.

Key points from the speaker

  1. 8:03 In the first example a 'CPU is high' page arrives 20 minutes after a deployment without mentioning it; the speakers say timing makes the deploy a place to start looking, not a proven root cause.
  2. 10:58 In the second example latency starts upstream but the alert fires on a downstream service, and the speakers say the AI found the loudest service, not the guilty one, because it lacked dependency context.
  3. 12:39 In the third example the alert and summary are correct but ownership data is stale, so the page goes to a former owner and time is lost finding the right team.
  4. 15:28 The speakers call these data and operational problems, not model problems, giving the example of a service named checkout-v2 in deployment logs and checkout-api in metrics.
  5. 19:36 They describe a tool gateway through which the agent reads telemetry, deployment records, ownership and SLO data with read-only scope, audit logging of queries and source and timestamp on each result.
